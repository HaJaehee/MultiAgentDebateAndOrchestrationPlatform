## 레이어 구조

```text
┌──────────────────────────────────────────────────────────────────┐
│  UI 레이어  (app/ui/)                            NiceGUI         │
│  app.py · personas_page.py · theme.py                            │
│  components/  sidebar · roster · chat_feed · artifact_viewer     │
└───────────────────────────┬──────────────────────────────────────┘
                            │ 이벤트 구독 (WebSocket)
┌───────────────────────────▼──────────────────────────────────────┐
│  오케스트레이션 레이어  (app/orchestration/)                      │
│  runner.py    토론을 브라우저에서 떼어 낸 백그라운드 태스크        │
│  engine.py    계획 → 라운드 루프 → 합성 상태 머신                 │
│  strategies.py  누가 언제 어떤 지침으로 말하는가                  │
│  state.py · control.py   토론 상태 / 정지·개입 신호               │
└──────┬──────────────────────────────────────┬────────────────────┘
       │                                      │
┌──────▼───────────────────────┐  ┌───────────▼────────────────────┐
│  에이전트 레이어 (app/agents/)│  │  MCP 레이어 (app/mcp/)          │
│  pool.py    풀 등록/갱신      │  │  manager.py  서버 수명·도구 조회│
│  base.py    Agent 모델        │  │  client.py   stdio 세션 하나    │
│  llm.py     LiteLLM 호출 루프 │  │                                 │
│  personas.py 세션별 인격·스냅샷│  │  ─ stdio ─▶ 외부 MCP 서버 프로세스│
└──────┬───────────────────────┘  └────────────────────────────────┘
       │
┌──────▼───────────────────────────────────────────────────────────┐
│  설정 · 영속화 레이어                                             │
│  config.py    conf.json 로더 / 기록기 / 환경변수 치환             │
│  database/    models.py (ORM) · session.py (비동기 세션 팩토리)    │
└──────────────────────────────────────────────────────────────────┘
```

계층 간 의존 방향은 **상위 계층에서 하위 계층으로만 단방향으로** 흐릅니다. 특히 오케스트레이션 실행기인 `runner.py`는 UI 계층의 구체적인 구현을 전혀 알지 못합니다. 백엔드 엔진 태스크가 NiceGUI의 화면 위젯 요소를 직접 조작하지 않으므로, 유저가 브라우저를 새로고침하여 웹소켓 클라이언트 객체가 소멸하더라도 백그라운드 토론 태스크는 중단 없이 정상 진행됩니다.

## 기동 순서

`app/main.py`의 `lifespan` 비동기 컨텍스트 매니저가 다음과 같은 엄밀한 순서로 시스템을 초기화 및 정리합니다.

```text
1. get_config()          conf.json 파싱 → 환경변수 치환 → Pydantic 검증
2. init_db(db_url)       SQLite 테이블 생성 (없으면)
3. mcp_mgr.initialize()  MCP 서버 프로세스 기동 + 도구 목록 수집
4. get_agent_pool()      설정에서 에이전트 등록
   ── yield ── (서비스 중)
5. runner.shutdown()     백그라운드 토론 태스크 취소
6. mcp_mgr.shutdown()    MCP 세션 종료 + 자식 프로세스 정리
```

3단계의 MCP 초기화가 일부 실패하더라도 메인 웹 서버는 안전하게 기동합니다. 연결에 실패한 도구 서버는 상단 상태 칩에 비활성(회색/빨간색)으로 표시되며, 해당 도구를 활용하려던 에이전트는 도구 호출 없이 일반 텍스트 추론으로 발언을 대체합니다.
→ [MCP 호스트](../03-core/04-mcp-host.md)

## 한 턴의 데이터 흐름

유저가 메시지를 전송하고 최종 산출물이 생성되기까지의 전체 흐름입니다.

```text
브라우저 입력
   │
   ▼
DebateRunner.start(session_id, prompt)      ← app/orchestration/runner.py
   │  세션 단위 asyncio.Task 생성
   │  ┌────────────────────────────────────────────────┐
   │  │ TurnRun : 정본 스냅샷 + 구독 큐 팬아웃          │
   │  └────────────────────────────────────────────────┘
   ▼
OrchestratorEngine.run_turn()               ← app/orchestration/engine.py
   │
   ├─ 1. 세션 로드 (전략, 라운드 수, 활성 에이전트, 커스텀 지침)
   ├─ 2. 작업 공간 적용 → 필요하면 MCP 서버 재기동
   ├─ 3. prepare_agents_for_turn()  ← 첫 턴이면 여기서 스냅샷 잠금
   ├─ 4. 이전 대화 기록을 DB 에서 로드 (맥락 보존)
   │
   ├─ status="planning"    오케스트레이터가 목표 분해
   │
   ├─ status="debating"    for round in 1..max_rounds:
   │      │                    전략이 발언자와 순서를 결정
   │      │                    각 발언자마다:
   │      │                      LLMCaller.call_agent()
   │      │                        └─ 도구 루프 (최대 max_tool_iterations)
   │      │                             └─ MCPManager.execute_tool()
   │      │                    발언·도구기록을 DB 에 저장하고 이벤트 발행
   │      └─ 매 발언 사이에 정지 요청 / 유저 개입 확인
   │
   ├─ status="synthesizing" 오케스트레이터가 전체를 종합
   │                        → 코드 블록을 파싱해 아티팩트로 추출
   │
   └─ status="completed"    is_consensus_reached 판정
        │
        ▼
   이벤트 팬아웃 → 붙어 있는 모든 브라우저 화면 갱신
```

자세한 단계별 설명은 [토론 한 턴의 생애주기](../04-workflows/01-debate-turn.md) 문서를 참고하시기 바랍니다.

## 두 가지 상태, 두 가지 수명

이 시스템에는 서로 다른 수명 주기와 관리 책임을 지닌 두 가지 상태가 존재하며, 이를 혼합할 경우 심각한 정합성 결함이 발생합니다.

| 구분 | 시스템 배포 설정 | 대화 세션 상태 |
| :--- | :--- | :--- |
| **단일 정본 (Source of Truth)** | `conf.json` 로컬 파일 | SQLite 로컬 데이터베이스 |
| **적용 범위** | 프로세스 전역 (모든 세션이 기본 공유) | 특정 대화 세션 1개 |
| **관리 대상 데이터 예시** | 에이전트 마스터 풀, 모델명, 도구 권한, MCP 서버 목록 | 세션별 페르소나 초안, 작업 공간 디렉터리, 발언 이력, 최종 산출물 |
| **변경 시 영향도** | 향후 새롭게 시작될 신규 세션에만 적용 | 해당 대화 세션에만 국소적으로 적용 |
| **수정 잠금(Lock) 조건** | 시스템 내에 실행 중인 토론 세션이 존재하면 편집 잠금 | 첫 유저 메시지 기록 시 페르소나 및 에이전트 구성 스냅샷 영구 잠금 |

로스터 패널의 UI 컨트롤이 "현재 대화 전용 설정"과 "전역 시스템 설정"으로 시각적으로 명확히 분리되어 있는 이유가 바로 여기에 있습니다. → [로스터 편집](../04-workflows/03-roster-editing.md)

## 동시성 모델

- **백그라운드 토론 태스크**: 세션당 정확히 1개씩 배정되며, `DebateRunner`가 `dict[session_id, TurnRun]` 레지스트리로 안전하게 통합 관리합니다.
- **클라이언트 구독 큐**: 연결된 브라우저 탭당 1개씩 할당됩니다. 브라우저가 종료되면 해당 큐만 안전하게 회수하고 백엔드 토론은 중단 없이 지속됩니다.
- **MCP 도구 서버**: **작업 공간 디렉터리마다 1개의 서버 프로세스 묶음**이 배정됩니다. 도구 서버가 감시할 루트 디렉터리가 프로세스 기동 시점에 고정되므로, 작업 폴더별로 독립된 서버 풀(`MCPRuntimePool`)을 동적 할당합니다. 따라서 서로 다른 작업 공간을 사용하는 대화 세션들은 물리적으로 완벽히 격리되어 동시 병렬 실행됩니다. 반면 동일한 작업 공간을 공유하는 대화 세션들은 단일 런타임 묶음을 안전하게 공유합니다.
- **런타임 동시성 상한**: `MCP_MAX_RUNTIMES` 환경변수로 제어되며 기본값은 4개입니다. 이는 동시 토론 세션 수의 인위적 제한이 아니라, 호스트 서버 머신의 메모리 예산을 보호하기 위한 **서로 다른 작업 공간 디렉터리의 최대 허용치**입니다. 사용 가능한 런타임 슬롯이 고갈될 경우 `RuntimeCapacityError`와 함께 실행을 명시적으로 거절합니다. 타 세션의 작업 폴더를 은밀히 침범하느니 명시적으로 실행을 차단한다는 데이터 정직성 대원칙을 철저히 준수합니다.
- **파이썬 샌드박스 커널**: "대화 세션 × 발언자" 단위로 엄격히 격리됩니다. 호스트 머신의 전체 커널 허용 예산(기본 16개)을 현재 활성화된 런타임 수로 균등 분할하여 관리합니다.
