# 기술 스택

> 상위: [시스템 개요](README.md) · 다음: [아키텍처](02-architecture.md)

전체 파이프라인이 **순수 파이썬 환경**으로 단일화되어 있습니다. 복잡한 프런트엔드 빌드 단계(Node.js 툴체인, 웹팩/Vite 번들러, 별도 dev 개발 서버)가 없으며, 단 하나의 `uvicorn` 프로세스가 REST API와 웹 UI 화면을 함께 서빙합니다. 이것이 외부 인터넷이 단절된 폐쇄망 배포를 매우 현실적이고 가볍게 만드는 핵심 요인입니다. 반입할 대상이 오직 파이썬 런타임과 wheel 패키지뿐이기 때문입니다.

## 왜 이것을 골랐는가

### FastAPI + NiceGUI — 파이썬 단일 프로세스 아키텍처

NiceGUI는 브라우저 내부적으로 Vue.js 및 Quasar 컴포넌트를 렌더링하지만, 개발자는 오직 파이썬 코드만으로 화면을 작성합니다. `ui.run_with(server, ...)` 설정을 통해 기존 FastAPI 애플리케이션에 자연스럽게 마운트되므로, **REST API와 웹 UI 화면이 동일한 네트워크 포트와 비동기 이벤트 루프**에서 함께 동작합니다.

```python
# app/main.py
server = FastAPI(lifespan=lifespan)   # /api/* 엔드포인트
create_ui()                            # NiceGUI 페이지 등록
ui.run_with(server, dark=True)         # 같은 앱에 마운트
```

이를 통해 다음과 같은 이점을 얻을 수 있습니다.

- 별도의 프런트엔드 빌드 산출물이 존재하지 않으므로, 파이썬 소스 코드만 반입하면 패치가 즉시 완료됩니다.
- 에이전트의 실시간 토론 진행 상황을 WebSocket을 통해 브라우저로 스트리밍하는 코드를 직관적인 순수 파이썬 비동기 함수로 작성할 수 있습니다.
- 백엔드 도메인 객체(에이전트 풀, MCP 매니저 등)를 UI 컴포넌트에서 메모리 상에서 직접 참조할 수 있으므로, 번거로운 별도 직렬화 계층을 관리할 필요가 없습니다.

### LiteLLM — 공급자 설정을 선언적 문자열로 관리

에이전트마다 서로 다른 모델을 조합하여 운용하는 것이 MADO 시스템의 핵심 전제입니다. LiteLLM은 OpenAI, Anthropic, Google, Azure, AWS Bedrock, 로컬 Ollama, vLLM, LM Studio, 그리고 사내 보안 게이트웨이까지 방대한 공급자들을 `acompletion()` 비동기 호출 하나로 완벽히 통합합니다. 모델 교체가 **복잡한 코드 수정이 아니라 설정 파일의 단순 문자열 변경**으로 완결됩니다.

```json
"model": "openai/gpt-4o"
"model": "anthropic/claude-3-5-sonnet-20241022"
"model": "ollama_chat/qwen2.5-coder:14b"
```

`drop_params: true` 설정은 로컬 및 다양한 오픈소스 모델과의 하위 호환성을 보장하기 위한 안전장치입니다. 특정 엔드포인트가 인식하지 못하는 부가 파라미터(`top_p` 등)를 클라이언트 단에서 사전에 제거하여, 불필요한 400 Bad Request 오류로 전체 요청이 중단되는 현상을 방지합니다.

### MCP — 도구 런타임을 프로세스 경계 외부로 격리

에이전트에게 파일 시스템을 조작하고 임의 코드를 실행하는 권한을 메인 애플리케이션 프로세스 내부에 직접 구현할 경우, 도구의 위험한 연산이 웹 서버와 동일한 권한 수준에서 실행됩니다. MCP 도구 서버들은 **독립된 외부 프로세스**로 기동되며 표준 입출력(stdio)을 통해 통신하므로 다음과 같은 강력한 격리를 제공합니다.

- 파일 시스템 서버가 사전에 인가된 작업 디렉터리 외부의 경로 접근을 자체적으로 엄격히 차단합니다.
- 파이썬 샌드박스 서버의 코드 실행 커널이 비정상 종료되더라도 메인 웹 서버 프로세스는 아무런 영향 없이 안정적으로 동작을 유지합니다.
- 새로운 외부 도구를 시스템에 추가하는 작업이 설정 파일에 실행 명령어 한 줄을 등록하는 것으로 단순화됩니다.

MCP SDK 버전을 `mcp>=1.29.0,<2`로 고정한 데에는 명확한 기술적 이유가 있습니다. MCP 2.x 버전에서 `mcp.server.fastmcp` 모듈이 제거되고 인터페이스가 대폭 개편되었으며, 시스템에 동봉된 샌드박스 서버와 `mcp-server-git` 서버가 여전히 1.x 계열의 API 사양을 요구하기 때문입니다.

### SQLite + SQLAlchemy 2.0 — 파일 하나로 완결되는 영속화

다자간 토론 기록은 특정 대화 세션당 기록을 수행하는 주체가 단일 태스크뿐이므로 동시성 쓰기 경합이 매우 적으며, 시스템 이전 시 단일 SQLite DB 파일 하나만 복사하면 백업 및 복구가 끝납니다. `aiosqlite` 드라이버를 결합하여 완전한 비동기 I/O를 수행하므로 데이터베이스 작업 대기 중에도 메인 이벤트 루프가 차단되지 않습니다. 데이터베이스 접속 주소(`db_url`)가 설정 파일로 분리되어 있으므로, 향후 엔터프라이즈 환경에서 PostgreSQL과 같은 외부 DBMS로 이전할 때 드라이버 연결 문자열만 교체하여 손쉽게 대응할 수 있습니다.

### Pydantic v2 + 표준 `json` — 선언적 설정 읽기와 프로그램적 쓰기

시스템 설정 파일 포맷으로 표준 JSON을 채택한 것은 의도적인 아키텍처 선택입니다. MADO는 설정을 **읽기만 하는 것이 아니라 화면에서 수정한 내용을 프로그램적으로 지속 덮어쓰기(Write-back)하기 때문입니다.** 웹 UI 화면에서 에이전트를 추가하거나 발언 순서를 변경하면 그 결과가 로컬 설정 파일에 즉시 영속화되어야 합니다. 파이썬 표준 라이브러리에 완성도 높은 JSON 직렬화기가 내장되어 있으므로, 설정 갱신 로직을 딕셔너리 조작 몇 줄로 안전하게 구현할 수 있습니다.

> 과거 버전에서는 TOML 포맷을 사용했습니다. 그러나 파이썬 표준 라이브러리에 TOML 파서(`tomllib`)만 내장되어 있고 직렬화 라이브러리가 제공되지 않아, 덮어쓰기 코드가 취약한 줄 단위 문자열 편집으로 구현되어 있었습니다. 여러 줄 문자열 내부 여부 추적, 섹션 헤더 판별, 데이터 타입별 수작업 직렬화 등 복잡한 문제가 지속되었으며, 이에 대한 상세 배경은 [설정 레이어](../03-core/01-config-layer.md) 문서에서 확인하실 수 있습니다.

## 의존성 목록

`requirements.txt` 전문:

```text
fastapi>=0.115.0
uvicorn>=0.30.0
nicegui>=2.0.0
pydantic>=2.8.0
pydantic-settings>=2.4.0
sqlalchemy>=2.0.30
aiosqlite>=0.20.0
litellm>=1.40.0
mcp>=1.29.0,<2

mcp-server-git>=2025.1.14   # git MCP 서버
jupyter_client>=8.0          # sandbox MCP 서버가 커널 구동에 사용
ipykernel>=6.0
# mcp-server-fetch           # 선택: 외부 네트워크가 열린 환경에서만

python-dotenv>=1.0.0
pytest>=8.0.0
pytest-asyncio>=0.23.0
```

**Node.js는 런타임 의존성이 아닙니다.** 기본 탑재된 공식 MCP 도구 서버 3종(filesystem, memory, sequential-thinking)은 순수 JavaScript로 패키징되어 있어 단일 `node.exe` 실행 파일 하나만 있으면 외부 설치 없이 즉시 구동됩니다. npm/npx 패키지 매니저는 초기 빌드 시점에만 필요하며, 최종 폐쇄망 번들 패키지에는 포함되지 않습니다.
