## 시스템을 관통하는 세 가지 핵심 원칙

### 1. 실패를 절대 숨기지 않습니다

MADO 시스템은 어떤 상황에서도 임의로 "그럴듯한 모의(Mock) 대체 답변"을 만들어내지 않습니다.

| 발생 상황 | 시스템의 실제 동작 | 엄격히 배제되는 동작 |
| :--- | :--- | :--- |
| LLM 엔드포인트 응답 불가 | 해당 발언을 명시적 실패로 기록하고 최종 합성 프롬프트에 알립니다. | 임의로 대체 문장을 생성하지 않습니다. |
| MCP 서버 연결 실패 | 상태 칩에 즉시 오류를 표시하고 해당 도구를 제외한 채 진행합니다. | 도구 실행 결과를 흉내 내지 않습니다. |
| 도구 루프 호출 한도 소진 | `LLMUnavailableError` 예외를 발생시킵니다. | 임의의 임시 자리표시자(placeholder) 답변을 반환하지 않습니다. |
| 설정 파일 문법 오류 | 오류가 발생한 줄 번호와 함께 저장을 거부하며 실행 설정을 유지합니다. | 결함이 있는 불완전한 설정을 부분 적용하지 않습니다. |

이 원칙이 준수되지 않으면 **토론 기록 전체의 신뢰성이 무너집니다.** 네 명의 에이전트가 치열하게 합의한 것처럼 보이는 최종 산출물이, 실제로는 세 에이전트의 침묵이나 오류로 인해 왜곡된 결과일 수 있기 때문입니다.

### 2. 배포 설정과 대화 상태를 엄격히 분리합니다

```text
conf.json (배포 설정)              SQLite (대화 상태)
├── 에이전트 목록                  ├── 발언 기록
├── 모델 · 엔드포인트 · 키          ├── 도구 실행 기록
├── 도구 권한                      ├── 산출물
├── 발언 순서 · 진영                ├── 페르소나 초안
└── MCP 서버                       └── config_snapshot ← 세션 시작 시점의 배포 설정 복사본
     │                                    ▲
     └──── 첫 메시지 전송 시 스냅샷으로 고정 ────┘
```

세션이 시작되면 해당 대화는 더 이상 외부의 `conf.json` 파일을 참조하지 않습니다. 세션 진행 도중 서버 관리자가 배포 설정을 변경하더라도, 기존 토론은 생성 시점의 스냅샷을 기반으로 일관성 있게 완결됩니다.
자세한 내용은 [데이터베이스와 세션 스냅샷](07-persistence.md) 문서를 참고하십시오.

### 3. 하드코딩된 에이전트 키를 배제합니다

초기 설계에서는 전략 코드 내에 `{"architect": 0, "coder": 1, "critic": 2}`와 같은 고정 매핑 테이블이 존재했습니다. 그러나 사용자가 화면에서 에이전트를 자유롭게 동적으로 생성하고 편집할 수 있게 되면서 이러한 방식은 즉시 한계에 부딪혔습니다. 테이블에 명시되지 않은 에이전트는 발언 순서가 맨 뒤로 밀리거나, 디베이트 모드에서 어느 진영에도 배정되지 못하는 문제가 발생했습니다.

현재 MADO에서는 **발언 순서와 진영 정보를 에이전트 객체 자체가 직접 관리합니다** (`debate_priority`, `debate_stance`). 소스 코드 내에서 특정 에이전트 키가 직접 참조되는 곳은 오케스트레이터 자신을 토론 라운드에서 제외하는 단 한 줄뿐이며, 이 역시 에이전트 역할명이 아닌 시스템 아키텍처 상의 필터링입니다.
자세한 내용은 [토론 전략](06-debate-strategies.md) 문서를 참고하십시오.
