## 핵심 구성 객체

| 객체명 | 주요 역할 | 알고 있는 영역 | 모르는 영역 (관심사 분리) |
| :--- | :--- | :--- | :--- |
| `OrchestratorEngine` | 토론 한 턴을 계획 수립부터 최종 합성까지 전체 실행 | 에이전트 풀, LLM 호출기, MCP 매니저, DB 세션 | 브라우저 UI 컴포넌트, 실시간 웹소켓 구독자 |

## 백그라운드 태스크 분리의 필요성

과거에는 채팅 입력 이벤트 핸들러 내부에서 `engine.run_turn()` 코루틴을 직접 `await`하여 동기적으로 실행했습니다. 그러나 사용자가 브라우저 페이지를 새로고침하거나 페르소나 관리 화면으로 이동하면 다음과 같은 치명적인 문제가 발생했습니다:

- NiceGUI 프레임워크가 해당 웹소켓 클라이언트 연결을 정리하면서, 백그라운드에서 UI를 갱신하려던 코루틴이 참조하던 부모 엘리먼트 슬롯이 즉시 소멸했습니다. 이로 인해 `The parent element this slot belongs to has been deleted.` 예외가 터지며 **진행 중이던 토론 전체가 비정상 중단**되었습니다.
- 프로세스가 살아남더라도 브라우저를 새로고침한 사용자는 진행 중인 토론 상태를 다시 조회할 방법이 없었습니다.

```text
DebateRunner
  │
  ├── asyncio.Task (세션당 1개의 백그라운드 태스크)
  │      └── engine.run_turn(on_event=...)
  │
  └── TurnRun  ← 이벤트 스트림을 두 갈래로 분기
        │
        ├── 정본 스냅샷    현재까지의 모든 발언 및 진행 상태를 메모리에 유지
        │                 새로 접속하거나 새로고침한 화면은 이를 기반으로 즉시 복원
        │
        └── 화면별 구독 큐 브라우저 연결(화면)당 독립 큐 할당. 화면 종료 시 큐만 안전하게 폐기
```

엔진 태스크는 NiceGUI UI 엘리먼트를 직접 조작하지 않고 이벤트만 발행하므로, 브라우저 클라이언트 연결이 끊기거나 새로고침되어도 토론 코루틴은 전혀 영향을 받지 않습니다. 구독 큐의 크기는 최대 2,000개로 제한되어 있어, 특정 브라우저의 렌더링이 지연되더라도 토론 엔진의 진행을 방해하지 않으며 메모리 누수를 방지합니다. 큐가 넘칠 경우 해당 화면은 최신 정본 스냅샷을 기반으로 피드를 안전하게 재동기화합니다.

## 토론 턴 상태 머신 (State Machine)

```text
    idle
      │  run_turn() 호출
      ▼
  ┌─────────┐
  │planning │  오케스트레이터의 목표 분석 및 이번 턴 세부 계획 수립
  └────┬────┘
       ▼
  ┌─────────┐◀────────────────┐
  │debating │                 │  round < max_rounds
  └────┬────┘─────────────────┘  and not stop_requested
       │
       │  라운드 상한 도달 · 사용자 조기 정지 · 사전 합의 도달
       ▼
  ┌────────────┐
  │synthesizing│  전체 토론 맥락을 종합 분석 → 최종 아티팩트 추출
  └────┬───────┘
       ▼
  ┌─────────┐        ┌───────┐
  │completed│        │ error │
  └─────────┘        └───────┘
```

`DebateState`(Pydantic 모델)가 상태 머신 전반의 상태 데이터를 캡슐화하여 관리합니다.

| 필드명 | 설명 및 역할 |
| :--- | :--- |
| `messages` | 현재 턴의 발언 및 누적된 이전 턴 발언 기록 목록 |
| `tool_records` | 도구 호출 실행 이력 상세 |
| `artifacts` | 최종 합성 단계에서 추출된 산출물 목록 |
| `current_round` / `max_rounds` | 현재 진행 중인 라운드 번호 및 최대 허용 라운드 수 |
| `failed_agent_keys` | **네트워크나 엔드포인트 장애로 발언하지 못한 에이전트 키 목록** |
| `stopped_early` | 사용자가 정지 버튼을 통해 남은 라운드를 건너뛰었는지 여부 |
| `interjection_count` | 토론 도중 사용자가 메모를 통해 개입한 총 횟수 |
| `is_consensus_reached` | 실패한 에이전트가 없고 조기 중단 없이 합의에 도달했을 때만 `True` |

`failed_agent_keys`와 `stopped_early` 필드는 **최종 합성 단계의 프롬프트에서 직접 참조**합니다. 토론이 충분히 이루어지지 못한 불완전한 상태를 오케스트레이터 모델이 명확히 인지하고 있어야, 존재하지 않는 허구의 의견을 마치 정상적으로 논의된 것처럼 왜곡하여 합성하는 오류를 방지할 수 있습니다.

## 토론 라운드 실행 루프

```text
for round_num in 1..max_rounds:
    speakers = _select_speakers(...)        ← 전략 규칙 또는 오케스트레이터 지명에 따름

    for index, agent in enumerate(speakers):
        ├─ control 상태 확인 ── 정지 요청 있음? ──▶ 라운드 루프 즉시 탈출
        │                    └─ 개입 메모 있음? ──▶ 사용자 발언 형태로 프롬프트에 주입
        │
        ├─ context = _context_for_speech(agent, ...)
        │      컨텍스트 한도 초과 위험 시 이전 기록을 요약본으로 압축
        │      시스템 프롬프트: 에이전트 페르소나 + 세션 커스텀 지침 (세션 동안 불변)
        │      초기 목표 메시지: 초기 사용자 요청 + 사용자 발언 이력 + 이번 턴 계획 (+ 이전 요약)
        │      토론 전사 본문: 내가 마지막으로 발언한 이후의 발언은 원문 그대로,
        │                     그보다 오래된 타인의 발언은 요지만 제공, 긴 코드는 참조 링크로 대체
        │      최종 지시 메시지: 결정 장부 + 라운드 번호 + 전략 지침 + 요지 작성 의무화 지시
        │
        ├─ _speak(agent, context)
        │      └─ LLMCaller.call_agent()  ← 스트리밍 출력 및 도구 루프 실행
        │             호출 성공 시 → 발언을 DB에 영구 저장하고 실시간 이벤트 발행
        │             호출 실패 시 → 연결 실패 알림을 기록하고 failed_agent_keys에 추가
        │
        └─ 도구 실행 이력을 DB에 저장
```

**병렬 지시 전략(`parallel_dispatch`)은 라운드 단위로 실행 경로가 분기됩니다.** 발언자를 한 명씩 순차적으로 세우는 일반 루프와 병렬 호출을 함께 처리할 수 없으므로, `_run_parallel_round()` 전용 메서드가 해당 라운드 전체를 책임집니다.

```text
for round_num in 1..max_rounds:                     ← parallel_dispatch 전용 라운드 루프
    ├─ 사용자 개입 메모 반영 및 정지 요청 확인       (이번 라운드 작업 분배의 근거)
    ├─ _dispatch_parallel_tasks()                    오케스트레이터에게 에이전트별 세부 과업 분배 요청
    │      분배 실패 시 → 세부 과업 없이 전원 동시 실행 + 안전 폴백 알림 기록
    ├─ 모든 에이전트의 프롬프트를 **사전에 일괄 생성** (동료의 중간 답변이 맥락에 섞이지 않도록 격리)
    ├─ asyncio.gather( ... ) under Semaphore(parallel_limit)
    │      각 _speak()는 db_lock을 사용하여 DB 쓰기 구간만 안전하게 직렬화
    │      created_at 타임스탬프는 의도된 지시 순서대로 사전에 고정 부여
    └─ _merge_parallel_round()                       병렬 라운드 결과 취합 (정지 요청 시 생략)
```

| 발생하는 기술적 제약 | 시스템의 해결 방식 |
| :--- | :--- |
| SQLAlchemy `AsyncSession`은 동일 세션의 동시 비동기 쿼리를 허용하지 않음 (`IllegalStateChangeError` 발생) | `_speak(db_lock=...)`를 통해 **데이터베이스 기록 구간만 세마포어로 직렬화**합니다. 대기 시간이 긴 LLM API 호출은 락 외부에서 완전 병렬로 처리됩니다. |
| 대화 기록은 `created_at` 시간순으로 정렬되어 다시 읽힘 | `_speak(created_at=...)`에 의도된 지시 순서 타임스탬프를 명시적으로 부여하고, `state.messages` 리스트 역시 동일한 순서로 정렬합니다. |
| 뒤늦게 시작된 에이전트의 발언이 앞서 완료된 동료의 답변을 컨텍스트로 참조하는 현상 발생 | 해당 라운드에 참여하는 모든 에이전트의 프롬프트를 `asyncio.gather` 실행 **이전에 모두 사전 생성**하여 완전한 독립성을 보장합니다. |
| 병렬 실행 도중에는 개별 발언 사이의 틈(Gap)이 존재하지 않음 | 사용자 개입 메모 및 정지 요청 확인을 라운드 시작 경계에서 원자적으로 처리합니다. |

사용자의 정지 요청과 개입 메모는 항상 **발언과 발언 사이의 안전한 유휴 지점**에서만 확인하여 처리합니다. LLM이 발언을 생성하는 도중에 강제로 중단하면 불완전하게 잘린 반쪽짜리 발언이 DB에 남아 데이터 일관성을 훼손하기 때문입니다.

## 대화 기억 보존 체계 (Conversation Memory, v0.8.3)

과거에는 컨텍스트 창이 가득 차면 오래된 발언부터 전체를 삭제했습니다. 이로 인해 1턴에서 사용자가 제시했던 핵심 제약 조건이 가장 먼저 소실되어, 후속 턴에서 사용자의 초기 지시를 위반하는 문제가 발생했습니다. 현재 시스템은 4중 계층으로 대화 맥락을 철저히 보존합니다:

| 보존 계층 | 주입 위치 | 주입 및 갱신 시점 |
| :--- | :--- | :--- |
| **사용자 발언 기록** (사용자의 모든 입력 원문) | 초기 목표 메시지 (컨텍스트 축소 시에도 보존되는 고정 영역). 전사 본문에서는 참조로 대체 | 매 LLM 호출 시. 컨텍스트 예산의 최대 25%까지 할당하며 초과 시 최근 발언부터 유지 |
| **이번 턴 계획** | 초기 목표 메시지 | 오케스트레이터의 계획 발언 완료 이후 매 발언마다 주입 |
| **결정 장부** (요구사항, 확정 결정, 기각안, 미해결 쟁점, 역할 분담) | 최종 지시 메시지, **이번 차례 발언 지침 바로 앞** | 마지막 라운드를 제외한 매 라운드 종료 시 + 최종 합성 완료 후 갱신 |
| **앞선 논의 요약본** | 초기 목표 메시지 | 해당 발언자의 컨텍스트 창 크기에 이전 발언 원문 전체가 들어가지 못할 때만 선별 주입 |

- 세션 커스텀 지침은 시스템 프롬프트에 고정 주입됩니다. 반면 결정 장부는 시스템 프롬프트에 넣지 않고 마지막 메시지에 배치합니다. 라운드마다 동적으로 변경되는 장부 텍스트가 프롬프트 앞단에 위치하면 외부 LLM 제공자의 프롬프트 캐싱(Prompt Caching)이 무효화되기 때문입니다. 동일한 이유로 라운드 표시자 역시 메시지 말미로 이동되었습니다.
- **이전 발언은 필요한 수준으로 정밀하게 압축하여 전달합니다.** 각 에이전트는 발언 말미에 `## 요지` 섹션을 작성합니다(별도의 추가 LLM 호출 없음). 에이전트는 자신이 마지막으로 발언한 이후의 동료 발언은 원문 그대로 전달받고, 그보다 오래된 타인의 긴 발언은 요지만 전달받습니다. 본인의 이전 발언, 짧은 발언, `@` 멘션으로 자신을 지목한 발언은 원문이 유지되되, 15줄 및 800자를 초과하는 긴 코드 블록은 1줄짜리 메타데이터 참조(줄 수, 첫 줄, 관련 파일 경로)로 자동 변환됩니다. 단, Mermaid 다이어그램은 시각적 연속성을 위해 원문이 보존되며, 최종 합성 단계에서는 전체 기록을 원문으로 참조합니다.
- 결정 장부 갱신 호출이 실패하면 이전 장부 내용을 안전하게 유지하고, 요약 생성에 실패하면 기존 방식대로 오래된 발언부터 순차 생략합니다. 어느 쪽의 실패도 전체 토론을 중단시키지 않습니다.
- 이로 인해 한 턴당 오케스트레이터의 보조 호출이 라운드 수(`max_rounds`)만큼 추가로 발생합니다 (라운드가 1회인 경우 1회 추가).
- UI 로스터 패널의 커스텀 지침 하단 **결정 장부** 영역에서 현재 합의된 장부 내용을 실시간 읽기 전용으로 확인할 수 있습니다. 만약 잘못 요약된 항목이 있다면 채팅 피드에서 정정 발언을 입력하여 다음 라운드 갱신에 즉시 반영할 수 있습니다.

## 실시간 사용자 제어 통로 (TurnControl)

`TurnControl`은 웹 브라우저 UI와 백그라운드 엔진 사이에서 비동기 제어 명령을 주고받는 가벼운 우편함 역할을 수행합니다.

```python
class TurnControl:
    def request_stop(self): ...          # 토론 조기 정지 요청
    def add_note(self, text): ...        # 사용자 개입 메모 추가
    def drain_notes(self): ...           # 엔진이 누적된 개입 메모 수거
    async def ask_tool_budget(...): ...  # 도구 상한 확장을 사용자에게 질의
    def resolve_tool_budget(...): ...    # UI에서 사용자의 결정을 응답
```

| 구분 | 사용자 정지 요청 (`request_stop`) | 백그라운드 태스크 강제 취소 (`cancel()`) |
| :--- | :--- | :--- |
| 진행 중인 현재 발언 | 끝까지 완료될 때까지 안전하게 기다림 | 즉시 강제 중단되어 데이터 잘림 |
| 남아 있는 후속 라운드 | 안전하게 건너뜀 | 즉시 건너뜀 |
| 최종 합성 단계 | **정상적으로 실행됨** | 실행되지 않음 |
| 최종 산출물(Artifacts) | **완전하게 생성됨** | 생성되지 않음 |

정지 요청이 태스크 강제 취소보다 훨씬 우수한 이유가 여기에 있습니다. 사용자가 도중에 멈추더라도 그때까지 나눈 심도 있는 토론 내용을 바탕으로 유의미한 최종 결론과 산출물을 정상 도출해 내기 때문입니다.

**개입 메모(Interjection Note)**는 다음 발언자의 입력 컨텍스트에 사용자 발언 형태로 자연스럽게 삽입됩니다. 토론 도중 방향을 급히 수정하고 싶을 때 처음부터 세션을 다시 시작할 필요 없이 언제든 궤도를 수정할 수 있습니다.

### 결정 요청 (DecisionRequest): 엔진에서 사용자로의 질의 통로

정지와 개입은 사용자가 엔진 방향으로 전달하는 명령인 반면, 결정 요청은 그 반대 방향입니다: **한도에 도달한 에이전트가 사용자에게 직접 확인을 요청하고**, 사용자의 응답이 도착할 때까지 해당 발언 작업이 일시 대기합니다. 도구 예산과 컨텍스트 창 질의 모두 동일한 요청 메커니즘(`DecisionRequest`)을 사용하며, `kind` 필드를 통해 요청 유형을 식별합니다.

| `kind` 식별자 | 발생 시점 | 승인 시 확장의 의미 | 3분 무응답(Timeout) 시 처리 |
| :--- | :--- | :--- | :--- |
| `tool_budget` | 도구 호출 상한 도달 시 | `+N회` 추가 허용 (하드 상한 130회) | 도구를 배제하고 즉시 최종 결론 작성 |
| `context_window` | 컨텍스트 창 상한 초과 시 | `+N 토큰` 확장 (**모델의 물리적 실제 상한까지만**) | 오래된 내용을 생략하고 토론 계속 진행 |

컨텍스트 창 확장은 **해당 턴에서 단 1회만 질의**합니다 (`DebateState.context_grant`). 토론이 심화되면 거의 모든 에이전트가 동일한 컨텍스트 한계에 직면하므로, 매 발언마다 사용자에게 질의하면 토론 흐름이 끊기기 때문입니다. 자세한 내용은 [LLM 통합](03-llm-integration.md#도구-루프-내-컨텍스트-포화-제어-및-메모리-오프로딩) 문서를 참고하십시오.

```text
LLM 도구 루프 (호출 상한 도달)
   │  budget_arbiter(info) 호출
   ▼
_make_budget_arbiter()  ──▶ on_event: tool_budget_exhausted ──▶ UI 화면 (결정 안내 줄 표시)
   │                                                                │
   │  control.ask_tool_budget(timeout=180s)                         │
   ▼                                                                ▼
 비동기 대기 ◀──────── control.resolve_tool_budget(extra, id) ◀── 사용자 선택: 확장 / 마무리
   │
   ├─ extra > 0 → 상한을 늘려 해당 발언 턴을 계속 이어 진행
   └─ extra = 0 또는 3분 무응답 → 도구 없이 지금까지의 결과로 결론 작성 후 종료
```

| 사용자 응답 | 확장 승인 | 지금 마무리 선택 | 3분 무응답 (타임아웃) |
| :--- | :--- | :--- | :--- |
| 진행 중인 에이전트 발언 | 발언을 계속 이어 진행함 | 도구 없이 즉시 결론 작성 | 도구 없이 즉시 결론 작성 |
| 기존 발언 및 도구 기록 | 완벽히 보존됨 | 완벽히 보존됨 | 완벽히 보존됨 |
| 적용 상한선 | `+extra` (최대 130회) | 기존 상한 유지 | 기존 상한 유지 |

사용자가 `request_stop()`을 호출한 경우, 대기 중이던 모든 결정 요청은 **즉시 '추가 확장 없음'으로 자동 처리**됩니다. 이미 중단을 요청한 사용자에게 추가 실행 여부를 되묻는 모순을 방지하기 위함입니다.

개별 요청은 고유 ID로 식별되므로 복수의 결정 요청을 동시에 큐에서 유지할 수 있습니다. 특히 병렬 지시 전략에서는 여러 에이전트가 동일한 시점에 한도에 도달할 수 있으므로, 다중 요청 처리가 지원되지 않으면 나머지 에이전트들이 3분 타임아웃을 무의미하게 대기해야 하는 병목이 발생합니다.

계층 경계를 넘어 공유되는 런타임 제어 상태는 `TurnControl` 객체 하나뿐이며, 동일한 asyncio 이벤트 루프 내에서만 안전하게 읽고 쓰므로 **별도의 스레드 락(Lock)을 필요로 하지 않습니다.**

## 계획 승인 (Plan Approval, ADR-028)

오케스트레이터의 계획(0라운드)이 기록되면 엔진은 토론 단계로 넘어가기 **전에** 승인 카드를 엽니다. 사람이 답하기 전에는 어떤 전문가도 발언하지 않습니다. 요청을 잘못 읽은 계획이 여러 라운드를 돈 뒤에야 드러나는 일을 막기 위한 단계이며, `plan_approval.enabled` 로 켜고 끕니다 (기본값: 켜짐).

```text
계획 발언 기록
   │  도구 없는 호출 1회: 계획 → 전문가별 과업(JSON)
   ▼
_approve_plan()  ──▶ on_event: plan_approval_requested ──▶ UI 화면 (계획 승인 카드)
   │                                                           │
   │  control.ask_plan_approval(timeout=plan_approval.timeout)  │
   ▼                                                           ▼
 비동기 대기 ◀──── control.resolve_plan_approval(id, 결정, 과업, 의견) ◀── 사용자 선택
   │
   ├─ 승인      → 카드에서 고친 과업·완료 기준을 승인 기록으로 남기고 토론 시작
   ├─ 수정 요청 → 의견을 유저 발언으로 기록 → 계획을 다시 작성 → 카드를 다시 엶
   ├─ 정지      → 승인 없이 넘어가 곧바로 최종 합성
   └─ 무응답    → 아무것도 실행하지 않고 턴을 멈춰 둠 ('이어서 진행' 으로 같은 카드를 다시 엶)
```

| 사용자 응답 | 승인 | 수정 요청 | 거부 | 무응답 (타임아웃) |
| :--- | :--- | :--- | :--- | :--- |
| 전문가 발언 | 승인된 분담으로 시작 | 다시 쓴 계획의 승인을 기다림 | 시작하지 않음 | 시작하지 않음 |
| 기록 | 승인 기록 (`plan_approval`) | 유저 발언 (`plan_revision`) + 새 계획 | 요청과 계획을 삭제 (긴급 종료) | 턴이 `approval` 단계로 멈춤 |
| 카드에서 고친 값 | 그대로 승인된 분담이 됨 | 수정 요청에 함께 실림 | 버려짐 | 다시 열면 제안 값으로 돌아감 |

**승인은 의견을 싣지 않습니다.** 의견 칸에 글이 있는 동안에는 승인 버튼이 사라지고 수정 요청 버튼이 나타납니다. 의견을 적은 채 승인하면 그 글이 읽히지 않고 버려지기 때문입니다.

**승인된 분담이 실행을 이끕니다.** 승인된 과업과 완료 기준은 계획 고정문에 함께 실려 모든 발언자의 맥락에 남고, 각 전문가의 차례 지시 끝에 자기 과업이 한 번 더 붙습니다. 사람이 카드에서 고친 값이 계획 본문과 다르면 승인된 쪽이 우선한다고 명시합니다. 최종 합성 프롬프트에는 과업별 완료 기준과 함께 **엔진이 기록에서 센** 발언 횟수와 응답 실패 여부가 실리고, 보고서에 "과업별 완료 확인" 이 추가됩니다.

**묻지 않는 경우**는 다음과 같습니다: 설정이 꺼져 있을 때, 답할 사람이 없는 실행(화면 없이 엔진만 호출)일 때, 계획이 없거나 실패했을 때, 과업을 받을 전문가가 없을 때.

순수 로직(분담표 해석, 답의 반영, 문구)은 `app/orchestration/plan_gate.py` 에, 대기와 응답은 `TurnControl` 에, 기록과 계획 재작성은 `OrchestratorEngine._approve_plan` 에 있습니다.

## 동적 발언자 지명 메커니즘 (오케스트레이터 지명 전략)

일반 전략은 사전에 정의된 결정론적 순서로 발언자를 결정하지만, `orchestrator_led` 전략에서는 오케스트레이터 모델에게 직접 질의하여 **해당 시점에 가장 필요한 전문 에이전트만을 선별적으로 지명**합니다.

```python
selector = orchestrator.model_copy(update={...})   # 도구 및 단계적 사고를 비활성화한 경량 복제본
```

**지명 질의 시에는 도구 실행 권한과 단계적 사고 기능이 비활성화된 경량 복제본 에이전트를 사용합니다.** 이 호출은 다음 발언자 키 목록이 담긴 단 한 줄의 JSON 응답을 얻기 위한 가벼운 라우팅 호출이기 때문입니다. 여기에 도구를 부여하면 발언자를 지명하기 전에 파일을 읽는 등 엉뚱한 행동을 하거나, 단계적 사고 프로토콜이 주입되면 장황한 사고 과정을 생성하느라 정해진 JSON 출력 형식을 놓치는 문제가 발생합니다.

### 지명 실패 시의 투명한 폴백(Fallback)

```text
지명 실패 (엔드포인트 미응답 / 식별 가능한 에이전트 키를 반환하지 못함)
   │
   ├─ 우선순위 기본 순서로 안전 폴백
   └─ 대화 피드에 명시적 기록:
        [발언자 지명 실패] {원인 메시지}
        우선순위 순서로 진행합니다: 아키텍트, 엔지니어, 리뷰어
```

**가장 피해야 할 동작은 실패 사실을 숨긴 채 임의의 다른 순서로 조용히 전환하는 것입니다.** 정상적으로 지명되었을 때뿐만 아니라 실패로 인해 폴백할 때에도 그 사유와 대상 에이전트 목록을 대화 피드에 명확히 기록합니다:

```text
[Round 2 발언권] Senior Python Engineer → Security & Quality Critic
(이번 라운드 미지명: System Architect)

1라운드에서 아키텍처는 합의되었고, 지금은 구현과 검증이 필요합니다.
```

## 최종 합성 (Synthesis) 및 산출물 추출

```text
_build_synthesis_prompt(state, orchestrator)
   │  전체 대화 기록 + 도구 실행 관측 결과 + 발언 실패 에이전트 목록 전달
   │  (컨텍스트 한도에 맞춰 정밀 축소하되 핵심 지시문은 반드시 보존)
   │  요구사항: 최종 합의 결론 도출 + 종합 Mermaid 아키텍처 다이어그램 1개 작성. 코드 재작성 금지
   ▼
오케스트레이터 LLM 호출
   │
   ▼
synthesis_has_content()  ── 본문이 비어 있으면 "합성 실패 (빈 응답)" 기록
   │
   ▼
_extract_artifacts_from_synthesis()
   │  종합 결론 / 시스템 다이어그램 / 전문가 구현 코드 / 구조화 요약 JSON 파싱
   │  합성 실패 시 결론 대신 전문가별 마지막 발언을 산출물로 보존
   ▼
ArtifactModel로 DB 저장 → 산출물 뷰어 패널에 즉시 렌더링
```

오케스트레이터 모델의 역할은 **토론 전체의 종합 결론을 도출하고 시스템 구조를 한눈에 보여주는 종합 Mermaid 다이어그램을 작성하는 것까지**입니다. 실제 소스 코드는 이미 앞선 전문가 에이전트들의 발언 및 작업 공간 파일에 온전히 존재하므로, 오케스트레이터는 파일 경로, 모듈명, 핵심 함수명 수준으로만 코드를 참조하도록 프롬프트로 엄격히 통제합니다. 만약 합성 단계에서 전체 코드를 다시 작성하도록 허용하면 LLM 응답 토큰 한도를 불필요하게 소진할 뿐만 아니라, 다음 대화 턴의 컨텍스트 창을 거대한 코드 블록으로 급격히 소진시키는 원인이 됩니다.

합의 도달 플래그(`is_consensus_reached`)는 **발언에 실패한 에이전트가 없고, 사용자의 조기 중단이 발생하지 않았으며, 최종 합성이 유의미한 결론을 도출했을 때만** 엄격하게 `True`로 판정됩니다. 세 에이전트 중 두 명이 침묵했거나 결론이 비어 있는 상태에서 '합의 완료'로 잘못 표시되는 심각한 정보 왜곡을 원천 방지합니다.

자세한 내용은 [산출물 생성과 내보내기](../04-workflows/04-artifact-and-export.md) 문서를 참고하십시오.

## 작업 공간별 다중 세션 동시 실행

각 세션이 서로 다른 작업 공간 디렉터리를 지정하더라도 완전한 동시 토론 실행이 가능합니다. 작업 공간 경로는 MCP 서버 기동 시점에 프로세스에 고정되므로, 시스템은 **각 작업 공간마다 독립된 MCP 서버 묶음(Runtime)을 격리 구동**하며 토론 턴이 시작될 때 해당 묶음을 대여하고 턴이 종료되면 즉시 반납합니다.

```python
pool = get_runtime_pool()
workspace = await self._session_workspace(session_id)
await pool.acquire(workspace, holder=session_id)
try:
    return await self._run_turn(session_id, user_prompt, workspace, on_event, control)
finally:
    await pool.release(session_id, workspace)
```

런타임 자원의 반납은 턴이 **어떠한 형태로 종료되든(정상 완료, 사용자 정지, 비정상 예외 발생 등)** `finally` 블록을 통해 100% 보장됩니다. 반납 누락이 발생하면 유휴 런타임이 프로세스 종료 시까지 메모리를 점유하는 자원 누수로 이어지기 때문입니다.

런타임 풀에서 동시 유지 가능한 최대 묶음 수는 `MCP_MAX_RUNTIMES` (기본 4개)로 제한됩니다. 여유 슬롯이 부족하면 유휴 런타임을 우선 정리하며, 모든 런타임이 활발히 사용 중인 경우 시스템은 `RuntimeCapacityError`를 발생시켜 요청을 명시적으로 거부합니다 (현재 런타임을 점유 중인 세션 목록을 안내함).
