# LLM 통합

> 상위: [핵심 기술 개관](README.md) · 이전: [에이전트 풀과 페르소나](02-agent-pool.md) · 다음: [MCP 호스트](04-mcp-host.md)
>
> 관련 소스: `app/agents/llm.py` (401줄)

`LLMCaller`는 단일 에이전트의 발언 턴을 전담하여 처리합니다. LiteLLM 라이브러리를 래핑하여 시스템 프롬프트를 동적으로 조립하고, 도구 호출 루프를 실행하며, 오류 발생 시 실패 상태를 명확히 전파합니다.

## 발언 실행 파이프라인

```text
call_agent(agent, messages, custom_instructions, session_id)
   │
   ├─ 1. 시스템 프롬프트 조립
   │      페르소나 + 단계적 사고 프로토콜 + 세션 전용 커스텀 지침 결합
   │
   ├─ 2. fit_context_window()      컨텍스트 한도 초과 시 오래된 중간 발언부터 축소
   ├─ 3. merge_consecutive_roles() 동일 역할(Role)이 연속되면 하나로 병합
   │
   ├─ 4. 도구 목록 조회            allowed_mcp_servers 기반 OpenAI Tool 스펙 변환
   │
   ├─ 5. is_live 상태 확인 ────────▶ False인 경우 즉시 LLMUnavailableError 발생
   │
   ├─ 6. _run_litellm_loop()       도구 호출 루프 (최대 max_tool_iterations 회)
   │
   └─ 7. _apply_show_steps()       show_steps=false인 경우 추론 과정을 숨기고 결론만 추출
          │
          ▼
     (최종 응답 텍스트, 도구 호출 이력 목록)
```

## 시스템 프롬프트 동적 조립

```python
def build_system_prompt(self, agent, custom_instructions=""):
    parts = [agent.system_prompt]

    st = agent.sequential_thinking
    if st.enabled and st.mode in ("prompt", "mcp"):
        parts.append(st.render_prompt())          # {max_steps} 치환
        if st.mode == "mcp":
            parts.append(f"각 사고 단계는 반드시 '{st.mcp_server}' MCP 서버의 "
                         "sequentialthinking 도구를 호출해 기록한 뒤 진행하세요.")

    if custom_instructions:
        parts.append(f"[Session Custom Instructions]:\n{custom_instructions}")

    return "\n\n".join(p for p in parts if p)
```

시스템 프롬프트는 크게 세 계층으로 구성됩니다: **에이전트 기본 페르소나** → **단계적 사고 프로토콜** → **해당 세션 전용 커스텀 지침**. 여기에 오케스트레이션 엔진이 발언 차례마다 동적으로 생성하는 전략 지침(`turn_instruction`)이 추가로 결합됩니다.

## 컨텍스트 창(Context Window) 제어

토론 라운드가 진행될수록 전체 대화 기록이 급격히 길어져 모델의 최대 컨텍스트 길이를 초과하게 되며, 외부 LLM 엔드포인트는 `maximum context length ... however you requested ...` 에러와 함께 HTTP 400 응답을 반환하게 됩니다.

```python
budget = (agent.max_context_window
          - effective_max_tokens(agent)              # 실제 API 요청에 실리는 응답 토큰 한도
          - 512                                      # 안전 마진
          - tool_schema_tokens(agent.model, tools))  # 요청마다 동봉되는 도구 스키마 정의 토큰
```

```python
head, tail = messages[:2], messages[-1:]   # 초기 목표/시스템 프롬프트 및 이번 차례 발언 지침
middle = messages[2:-1]
while middle and estimate_tokens(...) > budget:
    middle.pop(0)                          # 오래된 발언부터 순차적으로 축소
```

**대화의 초기 목표가 담긴 맨 앞부분(Head)과 이번 발언 지침이 담긴 맨 뒷부분(Tail)은 절대 삭제하지 않습니다.** 그 사이의 오래된 중간 발언부터 순차적으로 축소하며, 어떤 내용이 생략되었는지를 프롬프트 내에 명시적으로 모델에 안내합니다.

v0.7.0 이전 버전에서는 컨텍스트 예산 계산 시 다음 두 가지 요소가 누락되어 있었습니다:

- **도구 스키마(Tool Definitions)**: 도구 정의는 매 LLM API 요청마다 페이로드에 포함되어 전송됩니다. `filesystem`, `memory`, `git` 등 기본 도구만 활성화해도 35개 이상의 도구 정의가 약 5,000토큰을 차지합니다. 과거에는 이 토큰량이 예산 계산에서 빠져 있어, 대화가 길어지면 실제 요청 크기가 컨텍스트 창을 초과하여 HTTP 400 에러가 발생하거나 `finish_reason='length'`로 응답이 중단되는 문제가 있었습니다.
- **실제 응답 한도(Effective Max Tokens)**: `native` 추론 모드에서 사고 예산(Thinking Budget)이 별도로 할당되는 경우, 실제 요청에는 설정된 `max_tokens`에 사고 예산이 합산되어 전송됩니다. 과거에는 설정값만 단순 차감했으나, 현재는 `effective_max_tokens()` 함수를 통해 실제 합산 토큰을 정확히 차감하며, 로그에도 `8,192 (설정 4,096 + 사고 예산 4,096)`과 같이 산출 근거를 상세히 기록합니다.

```text
[앞선 발언 7건은 컨텍스트 한도로 생략되었습니다.
 남은 기록만으로 판단하고, 생략된 내용을 지어내지 마세요.]
```

이러한 명시적 안내가 없으면 모델이 누락된 맥락을 환각(Hallucination)으로 채워 넣는 문제가 발생합니다.

토큰 수 계산은 1차적으로 `litellm.token_counter()`를 사용하며, 모델 정보를 알 수 없어 실패할 경우에는 글자 수 기반 근사 계산식을 사용합니다 (한국어는 토크나이저 특성에 따라 문자당 1~1.5토큰 수준이므로 넉넉하게 산정합니다). **토큰 계산 단계의 실패가 LLM 호출 자체를 중단시켜서는 안 되기 때문입니다.**

### 처리 순서의 중요성

```python
formatted = fit_context_window(agent, formatted)      # 1. 컨텍스트 크기에 맞춰 축소
formatted = merge_consecutive_roles(formatted)        # 2. 동일 역할 메시지 병합
```

컨텍스트 생략 안내문이 `user` 역할(Role)의 메시지로 주입되므로, 연속된 동일 역할 메시지 병합(`merge_consecutive_roles`)은 반드시 컨텍스트 축소 이후에 수행되어야 합니다. 특히 Anthropic Claude 계열 API는 `user`와 `assistant` 역할이 엄격하게 교대로 나타나지 않으면 요청을 거부하기 때문입니다.

## 도구 호출 루프 (Tool Loop)

```text
┌─────────────────────────────────────────────┐
│ iteration 1..max_tool_iterations (기본 30회) │
│                                             │
│   [예산 고지] 잔여 호출 횟수를 프롬프트에 주입│
│   litellm.acompletion(messages, tools)      │
│              │                              │
│              ├─ tool_calls 없음 → 루프 종료 ──┼──▶ 최종 응답 텍스트 반환
│              │                              │
│              └─ tool_calls 있음             │
│                   │                         │
│                   ├─ MCPManager.execute_tool()  (병렬 실행)
│                   ├─ 실행 결과를 messages에 추가 │
│                   └─ on_tool_call 콜백 호출 → UI 렌더링
└─────────────────────────────────────────────┘
              │
              ▼ 호출 한도 소진 시
     budget_arbiter → 유저에게 예산 확장 여부 승인 요청
              │
              ├─ 확장 승인 → 한도를 늘려 그 자리에서 루프 지속
              │
              └─ 거절 또는 3분 무응답 → 도구(tools) 없이 1회 추가 호출 진행
                                       "지금까지 얻은 관측만으로 결론을 도출하라"
```

### 안전장치 1: 잔여 호출 횟수 사전 고지

도구 루프의 매 반복(Iteration)이 시작되기 전에 모델이 인지할 수 있도록 잔여 도구 호출 횟수를 시스템 안내로 주입합니다 (`tool_budget_notice`). 잔여 횟수가 임계치에 가까워질수록 안내 빈도가 높아집니다.

| 잔여 호출 횟수 | 고지 방식 및 내용 |
| :--- | :--- |
| 루프 시작 시 | 전체 할당량 안내 (`총 30회`) |
| 100 / 80 / 60 / 50 / 40 / 30 / 20 / 10회 | 잔여 횟수 알림 및 계획 재조정 요청 |
| 5 / 4 / 3 / 2회 | 잔여 횟수 경고 및 마무리 준비 요청 |
| 1회 남음 | **마지막 실행 기회** 강력 경고 |

잔여 예산을 명확히 인지해야 모델 스스로 도구 탐색을 적절한 시점에 마무리하고 최종 결론을 도출할 계획을 수립할 수 있습니다. 사전 경고 단계가 부족하면 모델은 여유가 충분하다고 오판하여 탐색만 반복하다가 마지막 턴에서 갑작스럽게 응답이 끊기게 됩니다.

### 안전장치 2: 한도 소진 시 기존 발언 보존 및 유저 중재

과거에는 도구 호출 한도를 초과하면 즉시 `LLMUnavailableError`를 발생시켰습니다. 그러나 이 경우 그때까지 에이전트가 스트리밍으로 작성한 텍스트와 실행한 유의미한 도구 관측 결과가 **모두 실패 메시지로 덮어씌워져 소실되는 문제**가 있었습니다. 특히 도구를 많이 활용한 중요한 발언일수록 데이터 손실이 극심했으며, 그 근본 원인 역시 실제 LLM 장애가 아니라 시스템 안전 상한선 도달 때문이었습니다. 상한선은 무한 루프 폭주를 방지하기 위한 것이지, 기여한 작업 결과를 폐기하기 위한 것이 아닙니다.

현재는 `budget_arbiter` 비동기 콜백을 통해 UI 화면의 유저에게 예산 연장 여부를 직접 확인합니다 (엔진의 `TurnControl` 제어 큐와 연계됩니다. 자세한 내용은 [오케스트레이션 엔진](05-orchestration-engine.md) 문서를 참고하십시오).

- **연장 승인 시**: 도구 반복 상한선을 늘려 해당 발언 턴을 중단 없이 즉시 이어서 진행합니다. 단, 시스템 절대 상한인 `TOOL_ITERATION_CEILING` (130회)을 초과할 수는 없습니다.
- **거절 또는 3분 무응답(Timeout) 시**: 도구 목록(`tools`) 파라미터를 완전히 제거한 상태로 마지막 1회 추가 호출을 수행합니다. 이때 "새로운 도구를 호출하지 말고, 지금까지 확보한 관측 결과만을 종합하여 최종 결론을 작성하라"는 지침이 전달됩니다. 도구 목록을 계속 제공하면 모델이 또다시 도구 호출을 시도하여 무의미하게 거절되기 때문입니다.

어느 방향으로 처리되든 그때까지 생성된 발언 내용과 도구 실행 이력은 완벽하게 데이터베이스에 보존되며, 발언 말미에 중단 사유가 명확히 기록됩니다. 배치 작업이나 자동화 테스트처럼 `budget_arbiter`가 등록되지 않은 환경에서는 유저 대기 없이 즉시 최종 결론 도출 단계로 직행합니다.

## 도구 루프 내 컨텍스트 포화 제어 및 메모리 오프로딩

컨텍스트 창 포화는 다음과 같이 **총 3개 지점**에서 발생할 수 있습니다. 과거에는 단순 경고 로그(`logger.warning`)만 남긴 채 처리되어, 유저가 토론 내용의 누락 사실을 즉각 인지하기 어려웠습니다:

| 발생 지점 | 관련 제어 함수 | 축소 및 관리 단위 |
| :--- | :--- | :--- |
| 발언 시작 직전 | `fit_context_window()` | 개별 메시지 (오래된 중간 발언부터) |
| 도구 루프 반복 도중 | `fit_tool_loop_context()` | **`assistant`와 종속된 `tool` 결과 묶음 전체** |
| 최종 합성 프롬프트 생성 시 | `_build_synthesis_prompt()` | 에이전트별 이전 발언 (오래된 순) |

1번과 3번 지점은 기존에도 관리되었으나, **2번 루프 내부 지점**에 대한 관리가 누락되어 있었습니다. `fit_context_window()`는 발언 시작 시점에 1회만 실행되는 반면, 도구 루프는 반복마다 `assistant`와 `tool` 메시지를 계속 누적합니다. 도구 실행 결과가 수십 KB에 달하는 경우 루프 도중 컨텍스트 한도를 초과하게 되고, 결국 엔드포인트가 HTTP 400 에러를 반환하여 발언 전체가 유실되는 원인이 되었습니다.

### 도구 호출 쌍(Pair) 단위 보존 원칙

OpenAI 및 호환 엔드포인트 규격상, `role: 'tool'` 메시지는 반드시 바로 앞선 `role: 'assistant'` 메시지 내의 `tool_calls`와 정확히 1:1로 대응되어야 합니다.

```text
messages with role 'tool' must be a response to a preceding message with 'tool_calls'
```

만약 단순한 메시지 단위로 오래된 항목을 하나씩 잘라내면, 앞선 호출 정의가 없는 고아 `tool` 결과 메시지가 남아 엔드포인트로부터 거부당합니다. 이 문제는 목(Mock) 기반 단위 테스트에서는 발견되지 않고 **실제 LLM 엔드포인트 연동 시에만 HTTP 400 오류를 발생**시킵니다.

따라서 `fit_tool_loop_context()`는 도구 호출을 요청한 `assistant` 메시지와 그에 종속된 모든 `tool` 응답 메시지를 하나의 원자적 묶음(Block)으로 그룹화하여 오래된 블록부터 제거합니다. 이때도 시스템 프롬프트가 포함된 맨 앞부분과 가장 최근의 도구 실행 블록은 온전히 보존합니다. 가장 최근의 관측 데이터가 현재 에이전트의 추론에 가장 직접적인 근거가 되기 때문입니다.

### 안전장치 1: 컨텍스트 압박률 단계별 사전 고지

컨텍스트 사용률이 각 임계 구간을 **처음 진입할 때만** 알림을 주입합니다 (`context_pressure_notice`). 매 반복마다 안내를 반복하면 안내 문구 자체가 컨텍스트를 과도하게 소비하기 때문입니다.

| 사용률 구간 | 주입 안내 내용 |
| :--- | :--- |
| 50% 초과 | 핵심 요점 위주로 간결하게 기술하도록 안내 |
| 70% 초과 | 대량의 출력을 발생시키는 도구 호출을 자제하도록 유도 |
| 85% 초과 | 임박한 컨텍스트 생략 경고 및 **지식 그래프 메모리 오프로딩 권고** |
| 95% 초과 | 추가 도구 호출을 즉시 중단하고 최종 결론 작성 지시 |

### 안전장치 1-b: 컨텍스트 유실 전 Memory 그래프로의 오프로딩 (Offloading)

메모리(Memory) MCP 서버는 **세션 단위 전역 스코프**로 동작합니다 (`AGENT_SCOPED_SERVERS`로 격리되는 대상은 `sandbox`뿐입니다). 즉, 단일 대화 세션 내에서 하나의 지식 그래프를 모든 에이전트가 공유하므로, 아키텍트가 그래프에 기록한 관측 내용은 다음 라운드의 크리틱이나 최종 합성 단계에서 그대로 검색하여 활용할 수 있습니다.

컨텍스트 사용률이 85% 구간에 진입하고 해당 에이전트에게 메모리 기록 권한이 있는 경우, "지금까지의 핵심 결론, 판단 근거, 미해결 쟁점을 한 번의 `add_observations` 도구 호출로 그래프에 기록한 후 계속 진행하라"는 안내를 주입합니다. 이후 실제로 컨텍스트가 축소될 때의 안내문 역시 "앞선 내용이 생략되었습니다. 필요 시 `search_nodes` 도구로 지식 그래프에서 조회하십시오"로 전환됩니다.

> [!NOTE]
> **메모리에 기록한다고 해서 현재 대화의 컨텍스트 사용량이 즉시 감소하지는 않습니다.**
> 기존 대화 메시지는 그대로 유지되기 때문입니다. 오프로딩의 진정한 목적은 향후 컨텍스트가 축소되더라도 **핵심 정보가 영구 소실되지 않도록 외부 저장소로 안전하게 이전해 두는 것**입니다. 따라서 시스템 안내 문구 역시 공간을 "확보한다"가 아니라 정보를 "옮겨 둔다"로 명문화하고 있습니다.

메모리 도구 존재 여부는 서버 이름(`memory`) 대신 **해당 에이전트에게 실제 부여된 도구 스펙 목록**에서 `add_observations` 또는 `create_entities` 함수가 존재하는지를 직접 검사합니다 (`memory_write_tool`). 서버가 비활성화되었거나 연결 실패, 또는 설정 키 이름이 변경되었을 때 모델에게 존재하지 않는 도구 호출을 유도하지 않기 위함입니다.

또한 오프로딩 역시 **도구 호출 예산을 1회 소비**합니다. 따라서 잔여 도구 호출이 `TOOL_BUDGET_FINAL_COUNTDOWN` (5회) 이하이거나 이미 95% 한계 구간에 도달한 상황에서는 오프로딩을 지시하지 않습니다. 최종 결론을 작성해야 할 소중한 호출 기회를 박탈하거나 여유 공간이 전혀 없는 상태에서 메시지를 추가하는 부작용을 막기 위함입니다.

### 안전장치 2: 컨텍스트 축소 전 유저 중재 (Context Arbiter)

컨텍스트 초과로 인해 실제 대화 기록이 축소되기 직전, `context_arbiter` 비동기 콜백을 통해 유저에게 컨텍스트 창 확장 여부를 확인합니다.

| 선택지 | 진행 중인 에이전트 발언 | 기존 텍스트 및 도구 기록 |
| :--- | :--- | :--- |
| **컨텍스트 상향 승인** | 확장된 컨텍스트 창 내에서 발언을 계속 진행합니다. | 완벽히 보존됩니다. |
| **지금 마무리 선택** | 도구 목록을 제거하고 즉시 최종 결론을 작성합니다. | 완벽히 보존됩니다. |
| **3분 무응답 (타임아웃)** | 오래된 중간 내용을 축소한 뒤 **토론을 계속 진행**합니다. | 완벽히 보존됩니다. |

유저가 응답하지 않을 때(3분 타임아웃) 강제 종료하지 않고 **생략 후 계속 진행**하는 점이 도구 예산 중재와 다릅니다. 유저가 자리를 비웠다고 해서 전체 토론 프로세스를 중단시킬 필요는 없기 때문입니다.
또한 이 확인 절차는 **해당 턴에서 단 1회만 질의**합니다. 토론이 심화되면 모든 에이전트가 동일한 한계에 도달하므로, 첫 번째 결정값(`DebateState.context_grant`)을 해당 턴의 나머지 에이전트 발언에도 동일하게 재사용합니다.

> [!WARNING]
> 도구 호출 횟수와 달리, 컨텍스트 창 크기는 **해당 모델이 지원하는 실제 하드웨어/아키텍처 한계를 초과하여 무한정 늘릴 수 없습니다.**
> `context_headroom()` 함수는 `litellm.get_model_info()`를 통해 모델의 물리적 최대 컨텍스트 길이를 조회하여 확장 가능한 잔여 여유분만을 유저에게 제안합니다. 한도를 초과하여 설정하면 안전한 컨텍스트 축소 대신 외부 엔드포인트의 HTTP 400 에러를 유발하기 때문입니다. 사설 게이트웨이나 vLLM, 커스텀 별칭 등 모델 정보 조회가 불가능한 엔드포인트의 경우에는 현재 설정값의 50% 확장을 제안하며, **실제 상한을 확인하지 못했다는 주의 문구를 화면에 함께 명시**합니다.

---

도구 호출 실행 시에는 항상 `session_id`와 발언자 키(`agent_key`)가 격리 스코프로 함께 전달됩니다. 이 스코프 정보가 누락되면 MCP 서버가 세션을 식별하지 못해 **타 세션의 지식 그래프나 샌드박스 파일을 오염시키는 심각한 결함**이 발생할 수 있습니다. 자세한 내용은 [MCP 호스트](04-mcp-host.md#스코프-격리) 문서를 참고하십시오.

## LLM 요청 파라미터 매핑

`build_completion_kwargs()` 함수는 `Agent` 모델의 필드를 LiteLLM 요청 인자로 매핑합니다.

| Agent 모델 필드 | LiteLLM 파라미터 | 상세 설명 |
| :--- | :--- | :--- |
| `model` | `model` | `<provider>/<model>` 형식의 전체 모델 식별자 |
| `api_base` | `api_base` | 사용자 정의 엔드포인트 URL (미지정 시 프로바이더 기본값) |
| `api_key` | `api_key` | 인증 키 (로컬 엔드포인트의 경우 더미 키 자동 주입) |
| `provider` | `custom_llm_provider` | 프로바이더 강제 지정 필요 시 사용 |
| `temperature`, `top_p`, `max_tokens` | 동일 | 표준 텍스트 생성 파라미터 |
| `timeout`, `num_retries` | 동일 | 네트워크 타임아웃 및 실패 시 재시도 횟수 |
| `drop_params` | `drop_params` | 공급자가 지원하지 않는 파라미터 자동 무시 여부 |
| `extra_headers`, `extra_body` | 동일 | 사설 AI 게이트웨이 인증 및 라우팅용 추가 페이로드 |
| `sequential_thinking` (native) | `reasoning_effort` / `thinking` | 모델 추론 모드에 따른 네이티브 파라미터 |

**인증 키가 불필요한 로컬 엔드포인트 처리**: vLLM이나 LM Studio 등 로컬 LLM 서버는 별도의 API 키를 요구하지 않지만, LiteLLM 내부 파이프라인은 `api_key` 필드가 비어 있으면 유효성 검사에서 예외를 발생시킵니다. 따라서 키가 설정되지 않은 로컬 환경의 경우 시스템에서 더미 자리표시자 키(`sk-no-key-required`)를 자동으로 주입하여 정상 호출을 보장합니다.

## 단계적 사고 (Sequential Thinking)

| 모드 (`mode`) | 구현 메커니즘 | 적용 대상 모델 |
| :--- | :--- | :--- |
| `prompt` | 단계적 사고 프로토콜 문구를 시스템 프롬프트에 주입 | 모든 범용 LLM |
| `native` | 모델 고유의 `reasoning_effort` 또는 `thinking` 파라미터 전달 | 네이티브 추론 지원 모델 (o1, o3, Claude Thinking 등) |
| `mcp` | sequential-thinking MCP 도구 사용을 시스템 프롬프트로 강제 | 해당 MCP 서버 활성화 환경 |

`show_steps: false`로 설정된 경우, 모델 응답 본문에서 결론 시작 마커(`## 최종 결론` 등)를 탐색하여 그 이전의 장황한 사고 과정을 제거하고 최종 결론만 추출합니다. 모델의 심층 추론 능력은 그대로 활용하되, 유저 대화 피드에는 정돈된 핵심 결론만 깔끔하게 노출하기 위함입니다.

```python
def _apply_show_steps(self, agent, content):
    st = agent.sequential_thinking
    if not content or not st.enabled or st.show_steps:
        return content
    for marker in CONCLUSION_MARKERS:
        idx = content.find(marker)
        if idx != -1:
            return content[idx:].strip()
    return content
```

만약 응답 본문에서 결론 마커를 발견하지 못한 경우에는 원문 전체를 그대로 보존합니다. 어설프게 내용을 잘라내어 정보가 훼손되는 것보다 전체 내용을 보여주는 것이 안전하기 때문입니다.

## 오류 및 예외 처리 체계

모든 LLM 호출 실패는 `LLMUnavailableError` 표준 예외로 일원화하여 상위 엔진으로 전달됩니다.

```python
if not agent.is_live:
    raise LLMUnavailableError(agent,
        "api_base 도 api_key 도 설정되어 있지 않습니다. "
        f"conf.json 의 llm 또는 agents.{agent.key} 에 엔드포인트를 지정하세요.")
```

주요 발생 조건은 다음과 같습니다:

- `is_live` 속성이 False인 경우 (엔드포인트 및 API 키 미설정)
- LiteLLM 호출 과정에서 예외가 발생한 경우 (네트워크 단절, 타임아웃, 인증 실패 등)
- 도구 루프 한도 소진 후 **최종 마무리 호출까지** 실패하고 생성된 응답 텍스트도 전무한 경우 (단순 도구 한도 도달 자체는 정상 처리 대상임)

오케스트레이션 엔진은 이 예외를 가로채어 **대화 피드의 해당 발언 위치에 명시적인 연결 실패 알림을 기록**하며, 실패한 에이전트 키를 `state.failed_agent_keys` 집합에 등록합니다. 이 실패 목록은 다음 두 가지 핵심 로직에 직접 반영됩니다:

1. **최종 합성 프롬프트 생성**: "특정 에이전트가 장애로 인해 발언하지 못했음"을 합성 오케스트레이터 모델에게 명확히 인지시킵니다.
2. **합의 도달(`is_consensus_reached`) 판정**: 실패한 에이전트가 단 하나라도 존재하면 정상적인 전원 합의로 인정하지 않습니다.

서버 로그에는 상세한 진단 정보(모델명, 엔드포인트 URL, 구체적인 원인 에러 메시지)가 빠짐없이 기록됩니다:

```text
LLM call failed for System Architect
(model=anthropic/claude-3-5-sonnet-20241022, api_base=provider default): APIConnectionError: ...
```
