# LLM 통합

> 상위: [핵심 기술 개관](README.md) · 이전: [에이전트 풀과 페르소나](02-agent-pool.md) · 다음: [MCP 호스트](04-mcp-host.md)
>
> 관련 소스: `app/agents/llm.py` (401줄)

`LLMCaller`는 단일 에이전트의 발언 턴을 전담하여 처리합니다. LiteLLM 라이브러리를 래핑하여 시스템 프롬프트를 동적으로 조립하고, 도구 호출 루프를 실행하며, 오류 발생 시 실패 상태를 명확히 전파합니다.

## 발언 실행 파이프라인

```text
call_agent(agent, messages, custom_instructions, session_id)
   │
   ├─ 1. 시스템 프롬프트 조립
   │      페르소나 + 단계적 사고 프로토콜 + 세션 전용 커스텀 지침 결합
   │
   ├─ 2. fit_context_window()      컨텍스트 한도 초과 시 오래된 중간 발언부터 축소
   ├─ 3. merge_consecutive_roles() 동일 역할(Role)이 연속되면 하나로 병합
   │
   ├─ 4. 도구 목록 조회            allowed_mcp_servers 기반 OpenAI Tool 스펙 변환
   │
   ├─ 5. is_live 상태 확인 ────────▶ False인 경우 즉시 LLMUnavailableError 발생
   │
   ├─ 6. _run_litellm_loop()       도구 호출 루프 (최대 max_tool_iterations 회, agents/llm_loop.py)
   │      판마다: 창 맞추기 → 한도 안내 → LLM 한 판 → 답 마무리 또는 도구 실행 → 상한이면 확장 요청
   │
   └─ 7. _apply_show_steps()       show_steps=false인 경우 추론 과정을 숨기고 결론만 추출
          │
          ▼
     (최종 응답 텍스트, 도구 호출 이력 목록)
```

## 시스템 프롬프트 동적 조립

```python
def build_system_prompt(self, agent, custom_instructions=""):
    parts = [agent.system_prompt]

    st = agent.sequential_thinking
    if st.enabled and st.mode in ("prompt", "mcp"):
        parts.append(st.render_prompt())          # {max_steps} 치환
        if st.mode == "mcp":
            parts.append(f"각 사고 단계는 반드시 '{st.mcp_server}' MCP 서버의 "
                         "sequentialthinking 도구를 호출해 기록한 뒤 진행하세요.")

    if custom_instructions:
        parts.append(f"[Session Custom Instructions]:\n{custom_instructions}")

    return "\n\n".join(p for p in parts if p)
```

시스템 프롬프트는 크게 세 계층으로 구성됩니다: **에이전트 기본 페르소나** → **단계적 사고 프로토콜** → **해당 세션 전용 커스텀 지침**. 여기에 오케스트레이션 엔진이 발언 차례마다 동적으로 생성하는 전략 지침(`turn_instruction`)이 추가로 결합됩니다.

### 파일 생성 및 부분 수정 지침

파일 조작 도구를 보유한 에이전트에게는 세션 지침 직전에 상시 파일 가이드라인이 자동으로 주입됩니다. 에이전트가 실제로 할당받은 도구 구성에 맞춰 동적으로 지침이 생성되므로, 보유하지 않은 도구의 호출을 지시하지 않습니다. 세션 커스텀 지침이 시스템 프롬프트 최하단에 배치되므로, 다른 작업 방식을 적용하려면 세션 지침에 명시하면 됩니다.

| 보유 도구 | 신규 및 대용량 파일 작성 | 기존 파일 부분 수정 |
| :--- | :--- | :--- |
| `filesystem` + `sandbox` | `write_workspace_file`로 파일 초안 작성 후 `append_workspace_file`로 내용 추가 | `edit_file`로 변경 대상 블록 부분 교체 |
| `filesystem` 단독 | `write_file`로 파일 초안 작성 후 `edit_file`로 추가/수정 | `edit_file`로 변경 대상 블록 부분 교체 |
| `sandbox` 단독 | `write_workspace_file`로 파일 초안 작성 후 `append_workspace_file`로 내용 추가 | 지침 없음 |
| 파일 쓰기 도구 없음 | 지침 없음 | 지침 없음 |

대용량 파일에서 일부 라인만 수정할 때 파일 전체를 다시 출력하면 불필요한 레이턴시가 발생하고 모델의 최대 출력 토큰 한도(`max_tokens`)를 초과할 위험이 있습니다. 따라서 `edit_file` 도구가 할당된 에이전트는 수정 대상 영역만 전송하여 효율적으로 편집하고, 파일의 대다수 영역을 재작성해야 하는 경우에 한해서만 전체를 다시 작성합니다.

`edit_file` 사용 시 유의할 점은 다음과 같습니다.

- **라인 번호 기반이 아닌 문자열 치환 방식입니다.** 기존 문자열(`oldText`)을 검색하여 대상 블록을 교체하는 방식이며, 파일 내에서 최초로 일치하는 위치 1곳만 치환됩니다. 프롬프트 지침을 통해 고유성을 보장할 수 있도록 수정 대상의 앞뒤 맥락 라인을 충분히 포함하고 실행 후 diff 결과를 검토하도록 유도합니다.
- **CRLF 개행 문자가 LF로 정규화됩니다.** 공식 파일시스템 도구 서버가 저장 시 LF 개행을 적용하기 때문입니다. Windows 환경에서 작성된 CRLF 파일을 에이전트가 수정할 경우 Git diff 상에서 전체 라인의 개행이 변경된 것으로 표시될 수 있습니다.

도구 보안 정책은 `write_file`과 동일하게 작업 공간 내부 쓰기 규칙이 적용되며, `.pptx`나 이미지 등 바이너리 파일에 대한 편집 시도는 사전 검증 단계에서 안전하게 차단됩니다.

## 컨텍스트 창(Context Window) 제어

토론 라운드가 진행될수록 전체 대화 기록이 급격히 길어져 모델의 최대 컨텍스트 길이를 초과하게 되며, 외부 LLM 엔드포인트는 `maximum context length ... however you requested ...` 에러와 함께 HTTP 400 응답을 반환하게 됩니다.

```python
budget = (agent.max_context_window
          - effective_max_tokens(agent)              # 실제 API 요청에 실리는 응답 토큰 한도
          - 512                                      # 안전 마진
          - tool_schema_tokens(agent.model, tools))  # 요청마다 동봉되는 도구 스키마 정의 토큰
```

```python
head, tail = messages[:2], messages[-1:]   # 초기 목표/시스템 프롬프트 및 이번 차례 발언 지침
middle = messages[2:-1]
while middle and estimate_tokens(...) > budget:
    middle.pop(0)                          # 오래된 발언부터 순차적으로 축소
```

**대화의 초기 목표가 담긴 맨 앞부분(Head)과 이번 발언 지침이 담긴 맨 뒷부분(Tail)은 절대 삭제하지 않습니다.** 그 사이의 오래된 중간 발언부터 순차적으로 축소하며, 어떤 내용이 생략되었는지를 프롬프트 내에 명시적으로 모델에 안내합니다.

초기 구현에서는 컨텍스트 예산 계산 시 다음 두 가지 요소가 누락되어 있었습니다:

- **도구 스키마(Tool Definitions)**: 도구 정의는 매 LLM API 요청마다 페이로드에 포함되어 전송됩니다. `filesystem`, `memory`, `git` 등 기본 도구만 활성화해도 35개 이상의 도구 정의가 약 5,000토큰을 차지합니다. 과거에는 이 토큰량이 예산 계산에서 빠져 있어, 대화가 길어지면 실제 요청 크기가 컨텍스트 창을 초과하여 HTTP 400 에러가 발생하거나 `finish_reason='length'`로 응답이 중단되는 문제가 있었습니다.
- **실제 응답 한도(Effective Max Tokens)**: `native` 추론 모드에서 사고 예산(Thinking Budget)이 별도로 할당되는 경우, 실제 요청에는 설정된 `max_tokens`에 사고 예산이 합산되어 전송됩니다. 과거에는 설정값만 단순 차감했으나, 현재는 `effective_max_tokens()` 함수를 통해 실제 합산 토큰을 정확히 차감하며, 로그에도 `8,192 (설정 4,096 + 사고 예산 4,096)`과 같이 산출 근거를 상세히 기록합니다.

```text
[앞선 발언 7건은 컨텍스트 한도로 생략되었습니다.
 남은 기록만으로 판단하고, 생략된 내용을 지어내지 마세요.]
```

이러한 명시적 안내가 없으면 모델이 누락된 맥락을 환각(Hallucination)으로 채워 넣는 문제가 발생합니다.

**도구 스키마 온디맨드 로딩 (ADR-039)**: 다수의 도구가 할당된 에이전트의 경우, 자주 사용하는 핵심 도구 스키마만 선별하여 상시 로드하고 보조 도구는 `tools__load_tools` 도구의 요약 목록으로 제공합니다. 에이전트가 필요에 따라 로드한 도구 스키마는 해당 세션 동안 유지됩니다. `filesystem`, `memory`, `git` 도구 세트 기준 요청당 스키마 토큰이 5,292토큰에서 2,175토큰으로 약 59% 절감됩니다. 기능 비활성화는 `tool_loading.enabled: false`로 설정하며, 컨텍스트 예산 산정 시 실제 주입된 도구 스키마의 토큰만 차감합니다.

**과거 대용량 파일 읽기 결과의 스텁 압축 (ADR-040)**: 도구 루프 내 컨텍스트 사용률이 임계치(`tool_output_compaction.min_usage`, 기본값 50%)를 초과하면, 일정 턴(`stale_rounds`, 기본값 3) 이상 경과하고 크기가 기준(`min_chars`, 기본값 8,000자) 이상인 대용량 파일 읽기 결과를 요약 스텁(Stub) 메시지로 압축합니다. 사용자에게 컨텍스트 창 확장을 요청하거나 과거 대화를 강제 삭제하기 전에 선제적으로 압축을 적용하여 컨텍스트 윈도우를 확보합니다. 모델에게 전달되는 프롬프트 메시지만 교체되며 UI 도구 카드와 데이터베이스 이력에는 원본 결과가 그대로 보존됩니다. 셸 명령 실행이나 웹 검색 등 재생성할 수 없는 관찰 결과는 압축 대상에서 제외됩니다. 기능 비활성화는 `tool_output_compaction.enabled: false`로 설정합니다.

토큰 수 계산은 1차적으로 `litellm.token_counter()`를 사용하며, 모델 정보를 알 수 없어 실패할 경우에는 글자 수 기반 근사 계산식을 사용합니다 (한국어는 토크나이저 특성에 따라 문자당 1~1.5토큰 수준이므로 넉넉하게 산정합니다). **토큰 계산 단계의 실패가 LLM 호출 자체를 중단시켜서는 안 되기 때문입니다.**

### 처리 순서의 중요성

```python
formatted = fit_context_window(agent, formatted)      # 1. 컨텍스트 크기에 맞춰 축소
formatted = merge_consecutive_roles(formatted)        # 2. 동일 역할 메시지 병합
```

컨텍스트 생략 안내문이 `user` 역할(Role)의 메시지로 주입되므로, 연속된 동일 역할 메시지 병합(`merge_consecutive_roles`)은 반드시 컨텍스트 축소 이후에 수행되어야 합니다. 특히 Anthropic Claude 계열 API는 `user`와 `assistant` 역할이 엄격하게 교대로 나타나지 않으면 요청을 거부하기 때문입니다.

## 도구 호출 루프 (Tool Loop)

```text
┌─────────────────────────────────────────────┐
│ iteration 1..max_tool_iterations (기본 30회) │
│                                             │
│   [예산 고지] 잔여 호출 횟수를 프롬프트에 주입│
│   litellm.acompletion(messages, tools)      │
│              │                              │
│              ├─ tool_calls 없음 → 루프 종료 ──┼──▶ 최종 응답 텍스트 반환
│              │                              │
│              └─ tool_calls 있음             │
│                   │                         │
│                   ├─ MCPManager.execute_tool()  (병렬 실행)
│                   ├─ 실행 결과를 messages에 추가 │
│                   └─ on_tool_call 콜백 호출 → UI 렌더링
└─────────────────────────────────────────────┘
              │
              ▼ 호출 한도 소진 시
     budget_arbiter → 사용자에게 예산 확장 여부 승인 요청
              │
              ├─ 확장 승인 → 한도를 늘려 그 자리에서 루프 지속
              │
              └─ 거부 또는 3분 무응답 → 도구(tools) 없이 1회 추가 호출 진행
                                       "지금까지 얻은 관측만으로 결론을 도출하라"
```

### 안전장치 1: 잔여 호출 횟수 사전 고지

도구 루프의 매 반복(Iteration)이 시작되기 전에 모델이 인지할 수 있도록 잔여 도구 호출 횟수를 시스템 안내로 주입합니다 (`tool_budget_notice`). 잔여 횟수가 임계치에 가까워질수록 안내 빈도가 높아집니다.

| 잔여 호출 횟수 | 고지 방식 및 내용 |
| :--- | :--- |
| 루프 시작 시 | 전체 할당량 안내 (`총 30회`) |
| 100 / 80 / 60 / 50 / 40 / 30 / 20 / 10회 | 잔여 횟수 알림 및 계획 재조정 요청 |
| 5 / 4 / 3 / 2회 | 잔여 횟수 경고 및 마무리 준비 요청 |
| 1회 남음 | **마지막 실행 기회** 강력 경고 |

잔여 예산을 명확히 인지해야 모델 스스로 도구 탐색을 적절한 시점에 마무리하고 최종 결론을 도출할 계획을 수립할 수 있습니다. 사전 경고 단계가 부족하면 모델은 여유가 충분하다고 오판하여 탐색만 반복하다가 마지막 턴에서 갑작스럽게 응답이 끊기게 됩니다.

### 안전장치 2: 한도 소진 시 기존 발언 보존 및 사용자 중재

과거에는 도구 호출 한도를 초과하면 즉시 `LLMUnavailableError`를 발생시켰습니다. 그러나 이 경우 그때까지 에이전트가 스트리밍으로 작성한 텍스트와 실행한 유의미한 도구 관측 결과가 **모두 실패 메시지로 덮어씌워져 소실되는 문제**가 있었습니다. 특히 도구를 많이 활용한 중요한 발언일수록 데이터 손실이 극심했으며, 그 근본 원인 역시 실제 LLM 장애가 아니라 시스템 안전 상한선 도달 때문이었습니다. 상한선은 무한 루프 폭주를 방지하기 위한 것이지, 기여한 작업 결과를 폐기하기 위한 것이 아닙니다.

현재는 `budget_arbiter` 비동기 콜백을 통해 UI 화면의 사용자에게 예산 연장 여부를 직접 확인합니다 (엔진의 `TurnControl` 제어 큐와 연계됩니다. 자세한 내용은 [오케스트레이션 엔진](05-orchestration-engine.md) 문서를 참고하십시오).

- **연장 승인 시**: 도구 반복 상한선을 늘려 해당 발언 턴을 중단 없이 즉시 이어서 진행합니다. 단, 시스템 절대 상한인 `TOOL_ITERATION_CEILING` (130회)을 초과할 수는 없습니다.
- **거부 또는 3분 무응답(Timeout) 시**: 도구 목록(`tools`) 파라미터를 완전히 제거한 상태로 마지막 1회 추가 호출을 수행합니다. 이때 "새로운 도구를 호출하지 말고, 지금까지 확보한 관측 결과만을 종합하여 최종 결론을 작성하라"는 지침이 전달됩니다. 도구 목록을 계속 제공하면 모델이 또다시 도구 호출을 시도하여 무의미하게 거부되기 때문입니다.

어느 방향으로 처리되든 그때까지 생성된 발언 내용과 도구 실행 이력은 완벽하게 데이터베이스에 보존되며, 발언 말미에 중단 사유가 명확히 기록됩니다. 배치 작업이나 자동화 테스트처럼 `budget_arbiter`가 등록되지 않은 환경에서는 사용자 대기 없이 즉시 최종 결론 도출 단계로 직행합니다.

## 도구 루프 내 컨텍스트 포화 제어 및 메모리 오프로딩

컨텍스트 창 포화는 다음과 같이 **총 3개 지점**에서 발생할 수 있습니다. 과거에는 단순 경고 로그(`logger.warning`)만 남긴 채 처리되어, 사용자가 토론 내용의 누락 사실을 즉각 인지하기 어려웠습니다:

| 발생 지점 | 관련 제어 함수 | 축소 및 관리 단위 |
| :--- | :--- | :--- |
| 발언 시작 직전 | `fit_context_window()` | 개별 메시지 (오래된 중간 발언부터) |
| 도구 루프 반복 도중 | `fit_tool_loop_context()` | **`assistant`와 종속된 `tool` 결과 묶음 전체** |
| 최종 합성 프롬프트 생성 시 | `SynthesisPhaseExecutor.build_synthesis_prompt()` | 에이전트별 이전 발언 (오래된 순) |

1번과 3번 지점은 기존에도 관리되었으나, **2번 루프 내부 지점**에 대한 관리가 누락되어 있었습니다. `fit_context_window()`는 발언 시작 시점에 1회만 실행되는 반면, 도구 루프는 반복마다 `assistant`와 `tool` 메시지를 계속 누적합니다. 도구 실행 결과가 수십 KB에 달하는 경우 루프 도중 컨텍스트 한도를 초과하게 되고, 결국 엔드포인트가 HTTP 400 에러를 반환하여 발언 전체가 유실되는 원인이 되었습니다.

### 도구 호출 쌍(Pair) 단위 보존 원칙

OpenAI 및 호환 엔드포인트 규격상, `role: 'tool'` 메시지는 반드시 바로 앞선 `role: 'assistant'` 메시지 내의 `tool_calls`와 정확히 1:1로 대응되어야 합니다.

```text
messages with role 'tool' must be a response to a preceding message with 'tool_calls'
```

만약 단순한 메시지 단위로 오래된 항목을 하나씩 잘라내면, 앞선 호출 정의가 없는 고아 `tool` 결과 메시지가 남아 엔드포인트로부터 거부당합니다. 이 문제는 모의(Mock) 기반 단위 테스트에서는 발견되지 않고 **실제 LLM 엔드포인트 연동 시에만 HTTP 400 오류를 발생**시킵니다.

따라서 `fit_tool_loop_context()`는 도구 호출을 요청한 `assistant` 메시지와 그에 종속된 모든 `tool` 응답 메시지를 하나의 원자적 묶음(Block)으로 그룹화하여 오래된 블록부터 제거합니다. 이때도 시스템 프롬프트가 포함된 맨 앞부분과 가장 최근의 도구 실행 블록은 온전히 보존합니다. 가장 최근의 관측 데이터가 현재 에이전트의 추론에 가장 직접적인 근거가 되기 때문입니다.

### 안전장치 1: 컨텍스트 압박률 단계별 사전 고지

컨텍스트 사용률이 각 임계 구간을 **처음 진입할 때만** 알림을 주입합니다 (`context_pressure_notice`). 매 반복마다 안내를 반복하면 안내 문구 자체가 컨텍스트를 과도하게 소비하기 때문입니다.

| 사용률 구간 | 주입 안내 내용 |
| :--- | :--- |
| 50% 초과 | 핵심 요점 위주로 간결하게 기술하도록 안내 |
| 70% 초과 | 대량의 출력을 발생시키는 도구 호출을 자제하도록 유도 |
| 85% 초과 | 임박한 컨텍스트 생략 경고 및 **지식 그래프 메모리 오프로딩 권고** |
| 95% 초과 | 추가 도구 호출을 즉시 중단하고 최종 결론 작성 지시 |

### 안전장치 1-b: 컨텍스트 유실 전 Memory 그래프로의 오프로딩 (Offloading)

메모리(Memory) MCP 서버는 **세션 단위 전역 스코프**로 동작합니다 (`AGENT_SCOPED_SERVERS`로 격리되는 대상은 `sandbox`뿐입니다). 즉, 단일 대화 세션 내에서 하나의 지식 그래프를 모든 에이전트가 공유하므로, 아키텍트가 그래프에 기록한 관측 내용은 다음 라운드의 크리틱이나 최종 합성 단계에서 그대로 검색하여 활용할 수 있습니다.

컨텍스트 사용률이 85% 구간에 진입하고 해당 에이전트에게 메모리 기록 권한이 있는 경우, "지금까지의 핵심 결론, 판단 근거, 미해결 쟁점을 한 번의 `add_observations` 도구 호출로 그래프에 기록한 후 계속 진행하라"는 안내를 주입합니다. 이후 실제로 컨텍스트가 축소될 때의 안내문 역시 "앞선 내용이 생략되었습니다. 필요 시 `search_nodes` 도구로 지식 그래프에서 조회하십시오"로 전환됩니다.

> [!NOTE]
> **메모리에 기록한다고 해서 현재 대화의 컨텍스트 사용량이 즉시 감소하지는 않습니다.**
> 기존 대화 메시지는 그대로 유지되기 때문입니다. 오프로딩의 진정한 목적은 향후 컨텍스트가 축소되더라도 **핵심 정보가 영구 소실되지 않도록 외부 저장소로 안전하게 이전해 두는 것**입니다. 따라서 시스템 안내 문구 역시 공간을 "확보한다"가 아니라 정보를 "옮겨 둔다"로 명문화하고 있습니다.

메모리 도구 존재 여부는 서버 이름(`memory`) 대신 **해당 에이전트에게 실제 부여된 도구 스펙 목록**에서 `add_observations` 또는 `create_entities` 함수가 존재하는지를 직접 검사합니다 (`memory_write_tool`). 서버가 비활성화되었거나 연결 실패, 또는 설정 키 이름이 변경되었을 때 모델에게 존재하지 않는 도구 호출을 유도하지 않기 위함입니다.

또한 오프로딩 역시 **도구 호출 예산을 1회 소비**합니다. 따라서 잔여 도구 호출이 `TOOL_BUDGET_FINAL_COUNTDOWN` (5회) 이하이거나 이미 95% 한계 구간에 도달한 상황에서는 오프로딩을 지시하지 않습니다. 최종 결론을 작성해야 할 소중한 호출 기회를 박탈하거나 여유 공간이 전혀 없는 상태에서 메시지를 추가하는 부작용을 막기 위함입니다.

### 안전장치 2: 컨텍스트 축소 전 사용자 중재 (Context Arbiter)

컨텍스트 초과로 인해 실제 대화 기록이 축소되기 직전, `context_arbiter` 비동기 콜백을 통해 사용자에게 컨텍스트 창 확장 여부를 확인합니다.

| 선택지 | 진행 중인 에이전트 발언 | 기존 텍스트 및 도구 기록 |
| :--- | :--- | :--- |
| **컨텍스트 상향 승인** | 확장된 컨텍스트 창 내에서 발언을 계속 진행합니다. | 완벽히 보존됩니다. |
| **지금 마무리 선택** | 도구 목록을 제거하고 즉시 최종 결론을 작성합니다. | 완벽히 보존됩니다. |
| **3분 무응답 (타임아웃)** | 오래된 중간 내용을 축소한 뒤 **토론을 계속 진행**합니다. | 완벽히 보존됩니다. |

사용자가 응답하지 않을 때(3분 타임아웃) 강제 종료하지 않고 **생략 후 계속 진행**하는 점이 도구 예산 중재와 다릅니다. 사용자가 자리를 비웠다고 해서 전체 토론 프로세스를 중단시킬 필요는 없기 때문입니다.
또한 이 확인 절차는 **해당 턴에서 단 1회만 질의**합니다. 토론이 심화되면 모든 에이전트가 동일한 한계에 도달하므로, 첫 번째 결정값(`DebateState.context_grant`)을 해당 턴의 나머지 에이전트 발언에도 동일하게 재사용합니다.

> [!WARNING]
> 도구 호출 횟수와 달리, 컨텍스트 창 크기는 **해당 모델이 지원하는 실제 하드웨어/아키텍처 한계를 초과하여 무한정 늘릴 수 없습니다.**
> `context_headroom()` 함수는 `litellm.get_model_info()`를 통해 모델의 물리적 최대 컨텍스트 길이를 조회하여 확장 가능한 잔여 여유분만을 사용자에게 제안합니다. 한도를 초과하여 설정하면 안전한 컨텍스트 축소 대신 외부 엔드포인트의 HTTP 400 에러를 유발하기 때문입니다. 사설 게이트웨이나 vLLM, 커스텀 별칭 등 모델 정보 조회가 불가능한 엔드포인트의 경우에는 현재 설정값의 50% 확장을 제안하며, **실제 상한을 확인하지 못했다는 주의 문구를 화면에 함께 명시**합니다.

---

도구 호출 실행 시에는 항상 `session_id`와 발언자 키(`agent_key`)가 격리 스코프로 함께 전달됩니다. 이 스코프 정보가 누락되면 MCP 서버가 세션을 식별하지 못해 **타 세션의 지식 그래프나 샌드박스 파일을 오염시키는 심각한 결함**이 발생할 수 있습니다. 자세한 내용은 [MCP 호스트](04-mcp-host.md#스코프-격리) 문서를 참고하십시오.

## LLM 요청 파라미터 매핑

`build_completion_kwargs()` 함수는 `Agent` 모델의 필드를 LiteLLM 요청 인자로 매핑합니다.

| Agent 모델 필드 | LiteLLM 파라미터 | 상세 설명 |
| :--- | :--- | :--- |
| `model` | `model` | `<provider>/<model>` 형식의 전체 모델 식별자 |
| `api_base` | `api_base` | 사용자 정의 엔드포인트 URL (미지정 시 프로바이더 기본값) |
| `api_key` | `api_key` | 인증 키 (로컬 엔드포인트의 경우 더미 키 자동 주입) |
| `provider` | `custom_llm_provider` | 프로바이더 강제 지정 필요 시 사용 |
| `temperature`, `top_p`, `max_tokens` | 동일 | 표준 텍스트 생성 파라미터 |
| `timeout`, `num_retries` | 동일 | 네트워크 타임아웃 및 실패 시 재시도 횟수 |
| `drop_params` | `drop_params` | 공급자가 지원하지 않는 파라미터 자동 무시 여부 |
| `prompt_cache` | 메시지·도구의 `cache_control` | Claude 연동 프롬프트 캐시 수명(TTL) (하단 설명 참조) |
| `extra_headers`, `extra_body` | 동일 | 사설 AI 게이트웨이 인증 및 라우팅용 추가 페이로드 |
| `sequential_thinking` (native) | `reasoning_effort` / `thinking` | 모델 추론 모드에 따른 네이티브 파라미터 |

**Claude 프롬프트 캐시 (ADR-045).** 공통 접두사를 자동 캐시하는 OpenAI·Gemini·vLLM과 달리, Claude는 `cache_control` 마커가 명시된 지점까지만 캐시를 생성합니다. MADO는 Anthropic·Bedrock·Vertex·Azure의 Claude 연동 시 후속 요청에서도 불변으로 유지되는 위치에 캐시 마커를 주입합니다.

| 마커 위치 | 캐시 재사용 대상 (Hit 대상) |
| :--- | :--- |
| 마지막 도구 정의 | 동일 모델 및 동일 도구를 공유하는 타 에이전트 호출 |
| 시스템 프롬프트 | 해당 에이전트의 모든 호출 |
| 목표 메시지의 끝 | 대화 이력이 갱신되더라도 이후 라운드에서 재사용 |
| 마지막 자체 발언 | 다음 라운드 발언 호출 |
| 도구 루프의 마지막 메시지 | 동일 발언 내 후속 도구 호출 루프 |

캐시 마커는 요청당 최대 4개로 제한되므로, 5개 후보 위치가 모두 존재하는 경우 도구 정의의 마커를 제외합니다. 시스템 프롬프트의 마커가 선행하는 도구 정의까지 포괄하여 캐시하기 때문입니다. `openai/claude-…`와 같이 게이트웨이를 경유하는 프록시 경로는 LiteLLM이 마커를 제거하여 전달하므로 대상에서 제외되며, 그 외 다른 연결의 요청 페이로드 구조는 기존과 동일하게 유지됩니다.

`prompt_cache`의 기본값은 `"5m"`입니다. 에이전트의 후속 발언이 마지막 요청 이후 5분 이상 경과하여 시작되는 경우가 빈번하다면 `"1h"`가 유리하지만, 캐시 생성(쓰기) 단가가 입력 단가의 1.25배에서 2배로 상승합니다. 사설 게이트웨이가 이 필드를 거절할 경우 `"off"`로 설정하십시오. 캐시 적중량 및 생성량은 발언 카드 툴팁의 `캐시`와 `캐시 쓰기` 지표로 확인할 수 있습니다.

**인증 키가 불필요한 로컬 엔드포인트 처리**: vLLM이나 LM Studio 등 로컬 LLM 서버는 별도의 API 키를 요구하지 않지만, LiteLLM 내부 파이프라인은 `api_key` 필드가 비어 있으면 유효성 검사에서 예외를 발생시킵니다. 따라서 키가 설정되지 않은 로컬 환경의 경우 시스템에서 더미 자리표시자 키(`sk-no-key-required`)를 자동으로 주입하여 정상 호출을 보장합니다.

## 단계적 사고 (Sequential Thinking)

| 모드 (`mode`) | 구현 메커니즘 | 적용 대상 모델 |
| :--- | :--- | :--- |
| `prompt` | 단계적 사고 프로토콜 문구를 시스템 프롬프트에 주입 | 모든 범용 LLM |
| `native` | 모델 고유의 `reasoning_effort` 또는 `thinking` 파라미터 전달 | 네이티브 추론 지원 모델 (o1, o3, Claude Thinking 등) |
| `mcp` | sequential-thinking MCP 도구 사용을 시스템 프롬프트로 강제 | 해당 MCP 서버 활성화 환경 |

`show_steps: false`로 설정된 경우, 모델 응답 본문에서 결론 시작 마커(`## 최종 결론` 등)를 탐색하여 그 이전의 장황한 사고 과정을 제거하고 최종 결론만 추출합니다. 모델의 심층 추론 능력은 그대로 활용하되, 사용자 대화 피드에는 정돈된 핵심 결론만 깔끔하게 노출하기 위함입니다.

```python
def _apply_show_steps(self, agent, content):
    st = agent.sequential_thinking
    if not content or not st.enabled or st.show_steps:
        return content
    for marker in CONCLUSION_MARKERS:
        idx = content.find(marker)
        if idx != -1:
            return content[idx:].strip()
    return content
```

만약 응답 본문에서 결론 마커를 발견하지 못한 경우에는 원문 전체를 그대로 보존합니다. 어설프게 내용을 잘라내어 정보가 훼손되는 것보다 전체 내용을 보여주는 것이 안전하기 때문입니다.

## 오류 및 예외 처리 체계

모든 LLM 호출 실패는 `LLMUnavailableError` 표준 예외로 일원화하여 상위 엔진으로 전달됩니다.

```python
if not agent.is_live:
    raise LLMUnavailableError(agent,
        "api_base 도 api_key 도 설정되어 있지 않습니다. "
        f"conf.json 의 llm 또는 agents.{agent.key} 에 엔드포인트를 지정하세요.")
```

주요 발생 조건은 다음과 같습니다:

- `is_live` 속성이 False인 경우 (엔드포인트 및 API 키 미설정)
- LiteLLM 호출 과정에서 예외가 발생한 경우 (네트워크 단절, 타임아웃, 인증 실패 등)
- 도구 루프 한도 소진 후 **최종 마무리 호출까지** 실패하고 생성된 응답 텍스트도 전무한 경우 (단순 도구 한도 도달 자체는 정상 처리 대상임)

오케스트레이션 엔진은 이 예외를 가로채어 **대화 피드의 해당 발언 위치에 명시적인 연결 실패 알림을 기록**하며, 실패한 에이전트 키를 `state.failed_agent_keys` 집합에 등록합니다. 이 실패 목록은 다음 두 가지 핵심 로직에 직접 반영됩니다:

1. **최종 합성 프롬프트 생성**: "특정 에이전트가 장애로 인해 발언하지 못했음"을 합성 오케스트레이터 모델에게 명확히 인지시킵니다.
2. **합의 도달(`is_consensus_reached`) 판정**: 실패한 에이전트가 단 하나라도 존재하면 정상적인 전원 합의로 인정하지 않습니다.

서버 로그에는 상세한 진단 정보(모델명, 엔드포인트 URL, 구체적인 원인 에러 메시지)가 빠짐없이 기록됩니다:

```text
LLM call failed for System Architect
(model=anthropic/claude-3-5-sonnet-20241022, api_base=provider default): APIConnectionError: ...
```

## 모델 연결 상태 확인

`is_live`는 연결 정보가 *적혀 있는지*만 판정합니다. 키가 틀렸거나 모델 이름이 잘못된 경우는 토론 도중 `LLMUnavailableError`로 처음 드러나는데, 그 시점에는 어느 모델이 왜 실패했는지 파악하기 어렵습니다. `app/agents/model_status.py`는 설정에 있는 연결마다 아주 짧은 요청을 보내 미리 확인하며, 전문가·체험·쉬운 화면 상단의 `모델 연결 상태` 버튼(`app/ui/components/model_status.py`)이 그 결과를 보여 줍니다.

**연결 묶기.** `collect_targets()`는 전역 기본값(`llm`)과 활성화된 에이전트를 훑어 모델·`api_base`·`api_key`·`api_version`·`provider`·`extra_headers`·`extra_body`가 모두 같은 것을 연결 하나(`ModelTarget`)로 묶습니다. 에이전트 다섯이 같은 모델을 쓰면 요청은 한 번이고, 한 에이전트만 개별 모델을 쓰면 그 에이전트가 따로 한 줄이 됩니다. 환경 변수가 치환된 뒤의 값을 쓰므로 `.env`로 준 값과 `conf.json`에 적은 값을 구분하지 않습니다.

**확인 요청.** `probe()`는 실제 호출과 같은 연결 정보(키·주소·버전·Provider·추가 헤더와 본문)로 `ping` 한 마디에 `max_tokens=16`인 요청을 한 번 보냅니다. 도구·스트리밍·재시도는 없고, 모델마다 허용 값이 다른 `temperature`와 사고 옵션은 넣지 않습니다. LiteLLM 예외는 사람이 조치할 수 있는 갈래로 분류됩니다.

| 상태 | 화면 표기 | 판정 근거 |
| --- | --- | --- |
| `ok` | 연결됨 | 응답 수신 (응답 시간 기록) |
| `not_configured` | 연결 정보 없음 | `is_live`가 False — 요청을 보내지 않음 |
| `auth` | 인증 실패 | `AuthenticationError`·`PermissionDeniedError`, HTTP 401/403, "API key" 문구 |
| `model` | 모델 이름 확인 | `NotFoundError`, HTTP 404, "LLM Provider NOT provided"(접두사 오류) |
| `rate_limited` | 한도 초과 | `RateLimitError`, HTTP 429 |
| `unreachable` | 연결 실패 | `APIConnectionError`, "Connection error" 문구(서버가 꺼진 경우 LiteLLM이 `InternalServerError`로 올림) |
| `timeout` | 응답 없음 | `Timeout`, 30초 초과 |
| `rejected` | 요청 거절 | `BadRequestError` 등 HTTP 400/422 |
| `server_error` | 서버 오류 | HTTP 5xx |
| `busy` | 확인 보류 | 동시 요청 상한이 차서 3초 안에 자리를 얻지 못함 |

**동시 요청 상한 준수.** 헬스체크 요청 역시 `LLMGate`의 동시성 슬롯을 점유합니다. 슬롯 여유가 없으면 대기 큐에 진입하지 않고 즉시 `busy`를 반환하며(토론이 진행 중이면 해당 모델은 정상 가동 중인 것으로 간주), 동시성 상한이 설정된 엔드포인트에서는 헬스체크 간 경합을 방지하기 위해 직렬로 순차 검사합니다.

**상태 현황판.** `ModelStatusBoard`는 프로세스 전역 싱글턴입니다. 헬스체크는 한 번에 1개 사이클만 실행되며(복수 UI 화면이 열려 있어도 동일 보드 공유), 점검 결과는 180초간 캐싱되고, `다시 확인` 요청도 10초 이내에는 재요청되지 않습니다. 설정 변경으로 새로운 엔드포인트가 감지되면 즉시 갱신하고, 설정에서 제거된 엔드포인트 결과는 캐시에서 삭제합니다.

**노출 범위.** 화면은 `describe_row(row, detail=...)`가 만든 값만 그립니다. `detail`은 소유자의 화면에서만 켜지며, 꺼져 있으면 주소와 오류 원문이 화면으로 가는 자료에 아예 담기지 않습니다. API 키는 어느 경우에도 내보내지 않고, Provider가 오류 문구에 되돌려 보낸 키와 `extra_headers` 값도 `safe_detail()`이 가립니다.

## 컨텍스트 절약 장치가 치른 값 — 도구 불러오기와 다시 읽기 횟수

도구 스키마 지연 로딩(ADR-039)과 지난 파일 읽기 압축(ADR-040)은 입력 토큰을 아끼는 대신 값을 치릅니다. 목록의 도구를
처음 쓸 때 판이 하나 더 들고, 줄여 둔 파일이 다시 필요하면 한 번 더 읽어야 합니다. 실제 모델이 얼마나 자주 그러는지는
모델마다 다르므로, 발언과 턴의 사용량 기록(`llm_meta.usage`, `turns.usage`)에 토큰과 함께 셉니다.

| 값 | 뜻 |
| --- | --- |
| `tool_load_calls` | `tools__load_tools` 를 부른 횟수 (한 번마다 판 하나) |
| `tool_loads` | 불러온 도구 정의 수 — 목록의 도구를 곧바로 불러 정의가 실린 것 포함 |
| `compacted_reads` | 스텁으로 줄인 파일 읽기 결과 수 |
| `rereads_after_compaction` | 줄인 읽기와 같은 도구·같은 인자로 다시 읽은 횟수 |

일어나지 않은 값은 기록에 칸을 만들지 않으므로, 그런 일이 없던 발언의 기록은 예전과 같습니다. 끊긴 발언을 이어 갈 때
되살리는 도구는 새로 불러온 것으로 세지 않습니다.

**어디서 보는가.** 토큰·시간 분석의 `크게 보기` 창 합계 아래에 `도구 불러오기 2회(정의 3개) · 읽기 압축 4건 · 압축 뒤 다시
읽기 1회` 처럼 한 줄로 나오고, Bench 보고서에는 `도구 컨텍스트` 열로 나옵니다. 같은 창은 **대화 3개 이상에서 되풀이해
불러온 도구**를 `tool_loading.core_tools` 후보로 알려 줍니다. 후보를 `core_tools` 에 더하면 그 도구는 처음부터 실려
불러오는 판이 사라집니다. 제안일 뿐이고 설정은 사람이 바꿉니다.

**읽는 법.** 압축 뒤 다시 읽기가 압축 건수에 견줘 많으면 `tool_output_compaction.stale_rounds` 나 `min_usage` 를 올립니다.
도구 불러오기가 발언마다 일어나는데 모델이 목록을 잘 쓰지 못한다면(적합성 점검의 `도구 목록에서 불러오기` 가 주의)
`tool_loading.enabled` 를 끕니다.

## 모델 적합성 점검 (ADR-054)

연결 상태는 모델이 **응답하는지**만 봅니다. 응답하는 모델이 도구를 쓸 수 있는지, 잘린 답을 잘렸다고 알려 주는지는 다른 문제이고, 지금까지는 토론이 실패한 뒤에야 알았습니다. `app/agents/model_check.py`는 연결 하나에 짧은 요청 8건을 보내 그것을 미리 확인합니다. 폐쇄망에 새 모델을 들인 날 한 번 돌리면 됩니다.

```bash
python -m app.modelcheck                  # conf.json 의 연결 전부
python -m app.modelcheck --agent coder    # 그 에이전트가 쓰는 연결만 (여러 번 줄 수 있음)
python -m app.modelcheck --json           # 스크립트용. 실패한 검사가 있으면 끝남 값 1
```

화면에서는 `모델 연결 상태` 창의 줄마다 있는 `적합성 점검` 버튼이 같은 일을 합니다. 소유자의 화면에만 있고, 연결된 줄에서만 눌리며, 한 번에 한 연결만 점검합니다. 결과는 양쪽 모두 `data/modelcheck/<연결 id>.json`에 남습니다.

| 검사 | 통과 조건 | 어긋났을 때 |
| --- | --- | --- |
| 기본 응답 | 답이 옴 | 실패 — 나머지는 묻지 않음 |
| 추론과 본문 | 추론이 없거나 본문과 갈라져 옴 | 주의: 추론이 한도를 다 씀 → `max_tokens` 상향 / 답이 추론 안에만 있음·`<think>` 가 본문에 섞임 → 서버의 reasoning parser |
| 스트리밍 | 글이 조각으로 옴 | 주의: 발언마다 스트리밍 없이 한 번 더 묻게 됨 |
| 잘림 알림 | 16토큰에서 끊으면 `finish_reason='length'` | 주의: 이어 쓰기와 잘림 안내가 동작하지 않음 |
| 연속된 user 메시지 | 같은 역할 둘을 받음 | 참고: MADO 가 합쳐 보내므로 영향 없음 |
| 도구 호출 | `tool_calls` 로 오고 인자가 읽힘 | 실패: 본문으로 샘·도구 요청 거절 / 주의: 글로만 답함 |
| 도구 결과 뒤 마무리 | 도구 결과가 담긴 대화를 `tool_choice="none"` 으로 받음 | 실패 또는 주의 |
| 도구 목록에서 불러오기 | `tools__load_tools` 를 부르거나 목록의 도구를 곧바로 부름 | 주의 → `tool_loading.enabled: false` |
| 이미지 입력 | 단색 그림의 색을 답함 | 참고. 그 연결에 이미지 모달을 켠 에이전트가 있으면 주의 |
| 컨텍스트 창 | 서버가 말한 창(`/models` 의 `max_model_len` 등)이 설정 이상 | 실패 → `max_context_window` 하향 / 서버가 말해 주지 않으면 건너뜀 |

결정 LLM(Jev·Laya)은 요청 한 번으로 noul·choice·score 답의 모양을 한 줄씩 확인합니다.

**결과 읽기.** 검사마다 `통과 · 참고 · 주의 · 실패 · 건너뜀` 가운데 하나와 한 줄 설명이 나오고, 고칠 것이 있으면 `→` 로 시작하는 권장 설정이 붙습니다. vLLM 의 `--tool-call-parser`·`--reasoning-parser` 처럼 서버에서 고쳐야 하는 것은 글로만 안내합니다. **점검 결과는 권고일 뿐 동작을 바꾸지 않습니다.** conf.json 은 사람이 고치고, 고친 뒤 다시 점검해 확인합니다.

**판정 방식.** LLM 이 채점하지 않습니다. 응답의 필드·종료 사유·표식과 정해 둔 낱말만 봅니다. 요청은 실제 토론이 보내는 모양 그대로이며(도구 호출 풀이·지연 로딩 목록·마무리 호출), 그래서 점검이 통과한 기능은 토론에서도 동작합니다. 모델이 일을 잘하는지는 여기서 재지 않습니다 — 그것은 Bench 로 비교합니다.

**한계.** 검사마다 요청 한 건이라 가끔만 나타나는 결함은 통과로 나올 수 있습니다. 컨텍스트 창은 서버가 말한 값을 그대로 믿으며, 게이트웨이가 `/models` 를 막으면 건너뜁니다. 기록 파일에는 상태와 크기, 키를 가린 오류 원문만 있고 모델이 쓴 글은 없으므로 폐쇄망 밖으로 들고 나오기에 적합합니다.

## 개별 모델 연결 실패 시 전역 모델로 폴백

`llm.fallback.enabled`가 켜져 있으면, 자기만의 연결(모델·주소·키)을 쓰는 에이전트의 호출이 **연결 문제로** 실패했을 때 전역 기본 연결(`llm`)이 같은 페르소나로 대신 답합니다 (`app/agents/llm_fallback.py`, ADR-030). 기본은 꺼져 있습니다.

`LLMUnavailableError`가 대체 응답을 만들지 않는 원칙은 유지됩니다. 폴백은 실제 모델의 응답이지만 **누가 답했는지가 달라졌다는 사실**은 실패와 같은 무게로 남아야 하므로, 켜야만 동작하고 전환할 때마다 기록과 화면에 남깁니다.

**판단 위치.** `LLMCaller.call_agent()`가 `_call_agent_once()`(기존 호출 본문)를 감쌉니다. 발언·계획·지명·합성·쉬운 화면의 도우미까지 모든 호출이 이 한 곳을 지나므로, 엔진의 `except LLMUnavailableError` 처리부는 그대로입니다.

| 조건 | 동작 |
| --- | --- |
| 폴백이 꺼져 있음 · 에이전트가 `allow_fallback: false` · 이미 전역 연결을 씀 · 전역에 연결 정보 없음 | 기존과 동일 (콜백도 감싸지 않고 그대로 통과) |
| 첫 요청이 인증 실패·모델 이름·연결 실패·응답 없음·서버 오류로 실패 | 전역 연결로 같은 발언을 처음부터 다시 받음 |
| 한도 초과(429)·요청 거절(400)로 실패 | 물러서지 않음 |
| 텍스트가 이미 클라이언트로 스트리밍되었거나(`streamed`), 1회 이상의 라운드 응답을 수신한 뒤(`rounds`) 실패 | 폴백을 적용하지 않고 예외 발생 — 중복 응답 누적 및 모델 간 도구 호출 컨텍스트 불일치 오류 방지 |
| 중단된 발언을 재개하는 중(`resume_state`) | 폴백을 적용하지 않고 예외 발생 (동일 사유) |
| 전역 대체 연결도 실패 | 원본 에이전트의 `LLMUnavailableError`를 발생시키고 두 실패 사유를 함께 기록 |

"출력 개시 이전" 상태는 `_SpeechProgress`(컨텍스트 변수)로 판별합니다. `_complete_once()`가 단일 라운드 응답 수신을 완료할 때마다 `rounds`를 증가시키고, 스트리밍 청크를 발행할 때 `streamed` 플래그를 설정하며, LLM 호출 단계에서 실패한 경우 `llm_failed`를 설정합니다 (도구 루프의 타 단계에서 발생한 예외는 폴백 대상에서 제외). 연결 장애로 최초 요청이 실패한 경우에는 동일 엔드포인트로의 비스트리밍 재시도 단계도 생략합니다 (`_will_fall_back`). 단, 서버 오류(5xx)의 경우 스트리밍 미지원 엔드포인트일 가능성을 고려하여 기존과 같이 1회 비스트리밍 재시도 후 폴백을 수행합니다.

**대체 에이전트.** `substitute_for()`는 연결(`model`, `api_base`, `api_key`, `api_version`, `provider`, `extra_headers`, `extra_body`)과 그 모델의 용량·전송 설정(`max_tokens`, `max_context_window`, `timeout`, `num_retries`, `drop_params`, `prompt_cache`)만 **현재의** 전역 값으로 바꾼 사본을 만듭니다. 페르소나·도구·스킬·온도·도구 루프 상한은 그대로이고, Provider 고유의 사고 옵션(`native`)을 쓰던 에이전트는 전역의 단계적 사고 설정을 따릅니다. 처음부터 다시 부르므로 시스템 프롬프트와 컨텍스트 자르기도 대체 모델의 한도로 다시 계산됩니다.

**차단기.** 죽은 연결을 발언마다 다시 기다리면 그때마다 `timeout × (num_retries + 1)`을 치릅니다. `FallbackBreaker`는 실패한 연결(`connection_id`)을 `retry_after`초 동안 건너뛰게 하고, 지나면 다음 호출이 원래 모델을 한 번 다시 부릅니다. `모델 연결 상태` 창에서 그 연결이 응답하는 것을 확인하면 즉시 닫히고, 건너뛰는 동안에는 그 창의 해당 줄에 남은 시간이 표시됩니다.

**알림과 기록.** 전환은 `llm_fallback.listening(...)`으로 걸어 둔 곳에 `FallbackNotice`로 전달됩니다 (`call_agent`의 인자를 늘리지 않으려고 컨텍스트 변수로 둡니다). 엔진의 `SpeechRunner.speak()`는 이를 받아 다음을 수행합니다.

1. `llm_fallback` 이벤트를 내보내 흘러나오는 발언 카드에 `기본 모델로 응답` 배지를 붙입니다 (기본 모델을 부르기 전).
2. 발언이 성공하면 `MessageModel.llm_meta`에 `{"fallback": true, "model", "intended_model", "reason", "reason_label"}`을 기록합니다. 주소와 키는 담지 않습니다. 전역 모델까지 실패한 발언에는 기록하지 않습니다.
3. `DebateState.fallback_agent_keys`에 올려 `turn_completed` 이벤트와 토론 요약 JSON의 `fallback_agents`로 내보냅니다. 폴백 발언은 실패(`failed_agent_keys`)로 세지 않습니다.

저장 문서(`build_session_markdown`)는 해당 발언 본문 앞에 같은 사실을 한 줄로 적습니다.
