# 토론 전략

> 상위: [핵심 기술 개관](README.md) · 이전: [오케스트레이션 엔진](05-orchestration-engine.md) · 다음: [데이터베이스와 세션 스냅샷](07-persistence.md)
>
> 관련 소스: `app/orchestration/strategies.py` (281줄)

토론 전략(Debate Strategy)은 다음 두 가지 핵심 요소를 결정합니다: **누가 어떤 순서로 발언권을 얻는가**, 그리고 **각 발언 턴마다 어떤 지침(Turn Instruction)이 프롬프트에 주입되는가**. 전략 간의 본질적인 질적 차이는 바로 이 동적 지침에서 비롯됩니다.

또한 병렬 지시 전략(`parallel_dispatch`)의 경우 세 번째 요소인 **에이전트들이 순차적으로 발언하는가, 동시에 병렬로 작업을 수행하는가**까지 결정합니다.

---

## 발언 순서와 진영 속성의 객체화

과거 설계에서는 전략 코드 내에 다음과 같은 고정 순서 매핑 테이블이 하드코딩되어 있었습니다:

```python
{"architect": 0, "coder": 1, "critic": 2}   # 과거 방식의 고정 매핑
```

그러나 사용자가 UI 화면에서 에이전트를 동적으로 자유롭게 추가/수정할 수 있게 되면서 이러한 방식은 한계에 부딪혔습니다. 테이블에 명시되지 않은 신규 에이전트는 모두 우선순위 기본값으로 묶여 **항상 발언 순서의 맨 뒤로** 밀려났고, 대립 토론에서는 찬성 측도 반대 측도 아닌 무소속(`others`)으로 누락되는 문제가 발생했습니다.

현재는 발언 순서와 진영 정보가 에이전트 객체 자신의 속성으로 직접 관리됩니다.

| 필드명 | 의미 및 동작 | UI에서의 변경 방법 |
| :--- | :--- | :--- |
| `debate_priority` | 라운드 내 발언 우선순위. 값이 작을수록 먼저 발언하며, 동일할 경우 `conf.json` 등록 순서 유지 | 로스터 관리 화면에서 **에이전트 카드 드래그 앤 드롭** |
| `debate_stance` | 대립 토론에서의 진영 배정 (`proponent` / `critic` / `neutral`) | 에이전트 카드의 우측 상단 더보기(⋮) 메뉴에서 진영 선택 |

```python
def order_by_priority(agents):
    return sorted(agents, key=lambda a: a.debate_priority)
```

Python의 `sorted()` 함수는 안정 정렬(Stable Sort)을 보장하므로, 사용자가 별도의 우선순위를 지정하지 않은 기본 상태(모든 에이전트의 priority가 기본값 100인 경우)에서는 **`conf.json` 설정 파일에 기술된 순서 그대로** 발언권이 부여됩니다.

현재 소스 코드 전체에서 특정 에이전트 키가 직접 참조되는 곳은 다음 단 한 줄뿐입니다:

```python
ORCHESTRATOR_KEY = "orchestrator"   # 토론 라운드 외부에서 동작 (계획 수립과 최종 합성 전담)
```

이는 특정 페르소나 역할을 지칭하는 것이 아니라, 라운드 외부에서 계획 수립과 최종 합성을 전담하는 **시스템 구조적 역할자**를 분리하기 위한 식별자입니다.

## 4가지 핵심 토론 전략

### 1. 순차 토론 (`sequential_debate`) — 기본 전략

우선순위 순서에 따라 모든 활성 에이전트가 순차적으로 1회씩 발언합니다. 각 에이전트는 **직전 에이전트의 발언 내용을 직접적인 입력으로** 받아 자신의 전문 영역에서 이를 발전시키거나 검증합니다.

```text
라운드 1:  아키텍트 ──▶ 엔지니어 ──▶ 리뷰어
             (설계)      (구현)      (검증)
                │           │           │
                └───────────┴───────────┘
               앞 에이전트의 결론을 인계받아 검증 및 보완
```

| 발언 순서 | 주입되는 인수인계 지침 |
| :--- | :--- |
| **첫 순서** | "뒤 순서가 이어받아 검증할 수 있도록, 결론과 그 근거·가정을 명확히 구분해 제시하세요." |
| **중간 순서** | "바로 앞 순서인 {이름}({역할})의 발언을 **입력으로** 받아 이어가세요. 새 주제를 여는 대신, 그 결론이 옳은지 당신의 전문 영역에서 검증하고 필요한 부분을 보강하거나 반증하세요." |
| **마지막 순서** | 중간 순서 지침 + "당신이 이번 라운드의 마지막 순서이므로, 라운드의 결론을 정리해 남기세요." |

**이러한 체계적인 인수인계 지침이 없으면 토론 라운드는 단순한 독백의 나열로 전락합니다.** 동일한 사용자 요청만을 바라본 채 각자 일방적인 주장만 펼치게 되며, 앞선 에이전트의 제안과 결론을 검증하거나 계승하는 유기적인 협업이 완전히 무너지게 됩니다.

### 2. 디베이트 (`adversarial_debate`)

제안자(찬성 측)와 비판자(반대 측)가 번갈아 가며 발언권을 얻습니다. 각 진영 내부에서는 우선순위 순서대로 발언합니다.

```text
proponents: [아키텍트, 엔지니어]     critics: [리뷰어]
                    │
                    ▼
      아키텍트 ─▶ 리뷰어 ─▶ 엔지니어 ─▶ (중립 에이전트 목록)
        제안       비판       제안
```

| 진영 (`debate_stance`) | 주입되는 전략 지침 |
| :--- | :--- |
| `proponent` (찬성/제안) | "구체적인 안을 내고, 앞서 제기된 비판이 있다면 **회피하지 말고 정면으로 답하세요**." |
| `critic` (반대/비판) | "직전 제안의 가정·빈틈·실패 조건을 구체적으로 짚고, **막연한 우려 대신 재현 가능한 반례나 근거**를 제시하세요." |
| `neutral` (중립) | 중립적 관점 유지 및 쟁점 요약 |

`neutral`(중립) 진영 에이전트는 찬반 대립이 한 차례 완료된 이후에 종합 및 보완 발언을 수행합니다.

만약 **찬성 또는 반대 진영 중 한쪽이 완전히 비어 있는 경우**, 정상적인 대립 구도가 성립할 수 없으므로 우선순위 순서에 따른 순차 토론 방식으로 안전하게 자동 전환(폴백)됩니다. 진영을 미처 지정하지 않은 사용자 환경에서 발언이 누락되는 현상을 방지하기 위함입니다.

### 3. 오케스트레이터 지명 (`orchestrator_led`)

매 라운드마다 오케스트레이터 모델이 현재 논의 진척도를 평가하여 다음 발언자와 순서를 동적으로 선별합니다. 문제 해결에 필요한 경우 **특정 라운드에 단 한 명의 전문가만 집중 호출**할 수도 있습니다.

```python
class OrchestratorLedStrategy(BaseDebateStrategy):
    orchestrator_selects_speakers = True   # 엔진 계층에서 LLM에 발언자 선별을 질의함
```

실제 LLM 질의와 에이전트 선택은 **오케스트레이션 엔진**이 주관합니다. 전략 객체 자체는 순수 함수로 동작해야 하므로 외부 네트워크 호출을 포함하지 않습니다. 오케스트레이터 호출이 실패하거나 유효하지 않은 응답을 반환할 경우, 시스템은 기본 우선순위 순서로 즉시 폴백하여 토론의 연속성을 보장합니다. 자세한 내용은 [오케스트레이션 엔진](05-orchestration-engine.md#동적-발언자-지명-메커니즘-오케스트레이터-지명-전략) 문서를 참고하십시오.

### 4. 병렬 지시 (`parallel_dispatch`)

오케스트레이터가 **서로 겹치지 않는 독립적인 과업**을 에이전트들에게 분배하고, 지목된 에이전트들이 **동시에 병렬로** 각자의 작업을 수행합니다. 라운드 종료 시점에 오케스트레이터가 취합 발언을 작성합니다.

```text
라운드 1:
              ┌──▶ 아키텍트  "인증 흐름 및 데이터 모델 설계"         ─┐
오케스트레이터 ├──▶ 엔지니어  "JWT 토큰 갱신 스켈레톤 코드 작성"       ─┼─▶ 오케스트레이터
(과업 동시 분배)└──▶ 리뷰어    "세션 고정 및 토큰 탈취 취약점 점검"   ─┘        (라운드 취합)
                         동일 시각에 병렬 실행 · 서로의 중간 결과는 격리
```

순차 토론은 앞선 에이전트의 완료를 기다려야 하므로 라운드 총 소요 시간이 **각 에이전트 발언 시간의 합계**가 되지만, 병렬 지시 전략에서는 **가장 오래 걸린 에이전트 1명의 소요 시간**으로 대폭 단축됩니다.

```python
class ParallelDispatchStrategy(BaseDebateStrategy):
    orchestrator_dispatches_parallel = True   # 엔진이 병렬 라운드 실행 파이프라인으로 전환
```

**에이전트 프롬프트에 주입되는 정보 구성**

| 전달 항목 | 상세 내용 |
| :--- | :--- |
| **개별 할당 과업** | "[병렬 지시] 오케스트레이터가 이번 라운드에 당신에게 맡긴 과업입니다: ..." |
| **동시 진행 현황** | 누가 어떤 과업을 맡아 동시에 작업 중인지에 대한 **목록** (타인의 결과물은 미포함) |
| **주의 및 제약 지침** | "남의 과업을 대신 하지 말고, 다른 과업의 결과가 필요하면 추측해 채우지 말고 어떤 가정을 두었는지 명시하세요" |

동일 라운드 내에서 생성된 다른 에이전트의 **답변 내용은 서로 참조할 수 없습니다.** 해당 라운드의 모든 프롬프트는 **첫 번째 비동기 코루틴이 실행되기 직전에 일괄 사전 생성**됩니다. 코루틴 실행 도중 동적으로 프롬프트를 조립하면, 먼저 처리를 마친 동료의 발언이 뒤늦게 시작한 에이전트의 컨텍스트에 부분적으로 노출되어 동일 라운드 내의 정보 비대칭이 발생하기 때문입니다.

**라운드 취합 발언이 필수적인 이유**

에이전트들이 서로의 중간 과정을 보지 못한 채 병렬로 작업했기 때문에, 라운드 말미의 오케스트레이터 취합 발언이 해당 라운드의 전체 결과물을 조망하는 유일한 중심점이 됩니다. 오케스트레이터는 이 발언을 통해 ① 취합된 현재 단계의 결론, ② 에이전트 간 상충 지점과 그에 대한 판정, ③ 미검증된 가정, ④ 다음 라운드로 이관할 과업을 명확히 정리하며, 이는 **다음 라운드 작업 분배의 직접적인 입력 컨텍스트**로 활용됩니다. 이 취합 단계가 누락되면 개별 작업들이 파편화되고 상호 모순이 방치되다가 최종 합성 단계에 이르러서야 뒤늦게 발견되는 문제가 발생합니다.

**동시 실행 상한 (Concurrency Limit)**

UI 로스터 패널의 **동시 실행** 수치(`sessions.parallel_limit`, 기본 3)를 통해 한 번에 동시에 구동할 에이전트 코루틴 수를 제어합니다. 상한을 초과하는 작업은 **폐기되지 않고 세마포어 큐에서 안전하게 순차 대기**합니다. 로컬 단일 LLM 엔드포인트(Ollama, vLLM, LM Studio 등)에 과도한 동시 요청을 전송하면 GPU 메모리 고갈(OOM)이나 요청 타임아웃이 발생하여 에이전트 연결 실패로 이어질 수 있으므로, 하드웨어 사양에 맞춰 동시 실행 수를 적절히 제한해야 합니다.

**오케스트레이터 분배 실패 시의 폴백(Fallback)**

| 발생 상황 | 시스템의 폴백 동작 |
| :--- | :--- |
| 엔드포인트 무응답 또는 유효한 에이전트 키 식별 불가 | 세부 과업 분배 없이 **모든 에이전트 동시 실행**, 폴백 발생 사실을 피드에 명시 |
| `assignments` JSON 출력 형식 손상 | 본문에서 식별 가능한 에이전트 키만을 추출하여 과업 없이 안전 진행 |
| 활성 상태인 전문가 에이전트가 1명뿐인 경우 | 분배 질의 자체를 생략하고 해당 에이전트 즉시 단독 실행 |

**개입 메모 및 정지 요청은 라운드 경계에서만 반영됩니다.** 순차 토론과 달리 병렬 토론은 라운드 진행 중 모든 에이전트가 동시에 실행 중이기 때문입니다. 라운드 도중 사용자가 정지를 요청하면 현재 진행 중인 병렬 실행이 완료된 후 취합 단계를 건너뛰고 즉시 최종 합성 단계로 직행합니다.

## 전략 선택 가이드

| 적용 상황 및 요구사항 | 권장 토론 전략 |
| :--- | :--- |
| 요구사항 분석 → 아키텍처 설계 → 코드 구현 → 품질 검증처럼 단계가 명확히 이어지는 경우 | **순차 토론** |
| 두 가지 상충하는 기술 스택이나 아키텍처 대안 중 최선의 안을 도출하고 잠재 위험을 검증해야 하는 경우 | **디베이트** |
| 토론 라운드마다 필요한 전문 영역이 달라져 유연한 발언자 선택이 필요한 경우 | **오케스트레이터 지명** |
| 토론 라운드 수와 LLM API 호출 비용을 절감하고자 하는 경우 (불필요한 에이전트 호출 생략) | **오케스트레이터 지명** |
| 서로 직접적인 종속성이 없는 다중 작업(예: 스키마 설계, API 핸들러 작성, 보안 취약점 점검)을 신속히 동시 진행하려는 경우 | **병렬 지시** |
| 전체 턴의 응답 대기 시간을 최소화하고자 하는 경우 | **병렬 지시** |

토론 전략은 UI 로스터 패널의 전략 선택 드롭다운에서 세션별로 자유롭게 변경할 수 있으며, `sessions.strategy` 컬럼에 영구 저장됩니다.

---

## 레거시 전략 통합 이력

과거에는 **자유 토론(`free_debate`)**과 **순차 검증(`sequential_review`)**이 별도 전략으로 존재했습니다. 순서가 에이전트 키 하드코딩으로 결정되던 시절에는 둘의 순서가 달랐으나, 발언 순서가 `debate_priority` 단일 체계로 통합되면서 두 전략은 **완전히 동일한 순서로 동일한 에이전트들을 호출**하게 되었습니다. 실제 동작이 동일함에도 불구하고 명칭만 달랐던 것입니다.

이에 따라 두 전략을 `sequential_debate`로 통일하였으며, 기존 대화 세션의 호환성을 보장하기 위해 레거시 별칭 매핑(`LEGACY_STRATEGY_ALIASES`)을 유지하고 있습니다:

```python
LEGACY_STRATEGY_ALIASES = {
    "free_debate": "sequential_debate",
    "sequential_review": "sequential_debate",
}
```

이를 통해 과거 세션을 조회할 때 전략 설정이 유실되지 않고 안전하게 순차 토론으로 매핑됩니다.

## 신규 토론 전략 구현 가이드

```python
class MyStrategy(BaseDebateStrategy):
    name = "my_strategy"
    display_name = "사용자 정의 전략"

    def get_speakers_for_round(self, active_agents, round_num, state):
        specialists = order_by_priority(specialists_of(active_agents))
        return specialists

    def turn_instruction(self, agent, speakers, index, state):
        return "[사용자 정의 전략 지침] ..."

STRATEGY_MAP["my_strategy"] = MyStrategy()
```

전략 구현 시 준수해야 할 핵심 개발 규칙은 다음과 같습니다:

- `specialists_of()` 헬퍼를 사용하여 발언 대상에서 오케스트레이터를 반드시 제외하십시오.
- 발언자 목록으로 빈 리스트를 반환하지 마십시오 (아무도 발언하지 못해 라운드가 정지됩니다).
- 특정 에이전트 키를 코드 내에 하드코딩하지 마십시오. 항상 에이전트 객체의 `debate_priority` 및 `debate_stance` 속성을 읽어 판단해야 합니다.
- LLM 모델 호출이 필요한 경우 전략 객체 내부에서 직접 호출하지 말고 전용 플래그를 활성화하십시오. 발언자 선별이 필요하면 `orchestrator_selects_speakers = True`, 라운드 병렬 디스패치가 필요하면 `orchestrator_dispatches_parallel = True`로 설정하며, 실제 호출 및 예외 폴백 처리는 엔진 계층이 전담합니다.
