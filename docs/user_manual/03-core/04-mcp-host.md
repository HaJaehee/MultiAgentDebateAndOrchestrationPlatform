# MCP 호스트

> 상위: [핵심 기술 개관](README.md) · 이전: [LLM 통합](03-llm-integration.md) · 다음: [오케스트레이션 엔진](05-orchestration-engine.md)
>
> 관련 소스: `app/mcp/manager.py` (431줄) · `app/mcp/client.py` (561줄)

**Model Context Protocol (MCP)**은 LLM에게 외부 도구 실행 역량을 표준화하여 제공하는 프로토콜입니다. MADO는 MCP **호스트(Host)**로서 외부 도구 서버를 하위 자식 프로세스로 구동하고 표준 입출력(stdio) 또는 원격 HTTP를 통해 통신합니다.

---

## 프로세스 분리의 필요성 및 이점

에이전트가 로컬 파일을 읽고 코드를 실행하는 도구 기능을 애플리케이션 메인 프로세스 내에 직접 내장하면, 도구 코드가 메인 서버와 동일한 전체 시스템 권한으로 동작하게 되어 심각한 보안 및 안정성 문제를 초래합니다. 별도 독립 프로세스로 분리함으로써 다음과 같은 강력한 이점을 얻을 수 있습니다:

- `filesystem` 서버가 **지정된 작업 공간 디렉터리 외부 경로에 대한 접근을 자체적으로 원천 차단**합니다.
- Python 코드 실행 중 샌드박스 커널이 충돌로 비정상 종료되더라도 MADO 메인 서버 프로세스는 안전하게 보호됩니다.
- 신규 도구 추가 시 애플리케이션 코드를 수정할 필요 없이 설정 파일에 실행 명령 한 줄만 정의하면 됩니다.
- 도구 서버 구현 언어에 제약이 없습니다 (현재 시스템에서도 Node.js와 Python 서버가 유기적으로 혼용됩니다).

## 2계층 아키텍처

```text
MCPManager  (프로세스 전역 싱글턴)
  │  서버 생애주기 관리 · 도구 네임스페이스 색인 · 작업 공간 런타임 전환
  │
  ├── MCPClientConnection("filesystem")  ── stdio ──▶ node .../server-filesystem
  ├── MCPClientConnection("memory")      ── stdio ──▶ node memory-scoped.mjs
  ├── MCPClientConnection("git")         ── stdio ──▶ python -m mcp_server_git
  └── MCPClientConnection("sandbox")     ── stdio ──▶ python .../server.py
```

`MCPClientConnection`은 개별 MCP 서버와의 1:1 통신 세션을 전담합니다. 초기 연결 수립, 도구 스키마 목록 조회, 실제 도구 실행 요청, 비정상 종료 시 재연결, 자식 프로세스의 표준 에러(stderr) 스트림 캡처 및 버퍼링을 담당합니다.

### 공식 Memory 서버를 포크(Fork)하여 개선한 이유

공식 `@modelcontextprotocol/server-memory` 서버는 프로세스당 단 1개의 고정된 지식 그래프 파일만을 다룹니다. 따라서 동일 서버 인스턴스를 공유하면 이후의 다른 대화 세션이 이전 대화의 기억을 그대로 읽거나 오염시키는 중대한 결함이 발생합니다.
MADO 프로젝트의 `mcp_servers/memory_scoped/` 커스텀 포크는 지식 그래프를 세션 ID별 독립 파일로 분리 관리하며, 도구 호출 요청 메타데이터에 포함된 세션 스코프를 기반으로 적절한 그래프 파일을 동적으로 로드합니다.

### Sandbox 커널의 2중 격리 구조

Python 실행 샌드박스의 커널 네임스페이스는 **대화 세션 × 발언자(에이전트)** 단위로 엄격히 분리됩니다. 메모리 내의 변수 상태는 대화 기록에 텍스트로 보존되지 않기 때문에(다음 발언자의 프롬프트에는 이전 발언의 텍스트 본문만 주입됨), 에이전트 간에 커널 상태를 직접 인계하면 아무도 검증하거나 재현할 수 없는 블랙박스 상태가 발생하기 때문입니다. 에이전트 간의 데이터 인계는 항상 작업 공간(Workspace) 내의 파일 형태로 명시적으로 수행되어야 합니다.

시스템에서 유지되는 최대 활성 커널 수는 `SANDBOX_MAX_KERNELS` (기본 16)로 제한됩니다. 기본 구성에서는 `coder`와 `critic` 2개 에이전트가 샌드박스를 사용하므로, 16개 커널 기준 최대 8개의 동시 토론 세션을 원활히 지원합니다. 한도를 초과하면 LRU(가장 오랫동안 사용되지 않은 순) 정책에 따라 오래된 커널부터 메모리에서 해제됩니다.

## 스코프 격리 (Scope Isolation)

도구 호출 실행 시에는 항상 해당 호출이 **어느 대화 세션의, 어느 에이전트로부터 비롯되었는지**를 나타내는 메타데이터가 동봉됩니다.

```python
AGENT_SCOPED_SERVERS = frozenset({"sandbox"})

def compose_scope(server_name, scope, actor):
    if not scope:
        return None
    if server_name in AGENT_SCOPED_SERVERS and actor:
        return f"{scope}-{actor}"     # 샌드박스: 대화 세션 × 발언자 단위
    return scope                      # 그 외 도구: 대화 세션 단위
```

| 서버 식별자 | 스코프 격리 단위 | 격리 사유 |
| :--- | :--- | :--- |
| `memory` | 대화 세션 단위 | 합의된 지식과 사실은 해당 토론 세션 고유의 자산입니다. |
| `sandbox` | 대화 세션 × 발언자 단위 | 커널 메모리 변수는 에이전트 간 직접 공유가 불가능합니다. |
| `filesystem`, `git` | 작업 공간 단위 (스코프 무관) | 동일 작업 공간 내 파일 변경 사항과 버전 이력은 협업을 위해 공유되어야 합니다. |

이 스코프 정보가 누락되면 MCP 서버가 세션을 식별하지 못해 **타 세션의 지식 그래프를 잘못 읽거나 오염시키는 중대한 사고**가 발생할 수 있습니다.

## 도구 네임스페이스 및 이름 해석 규칙

서로 다른 MCP 서버 간의 도구 함수명 충돌을 방지하기 위해 시스템 내부에서는 `서버명__도구명` 형태의 정규화된 네임스페이스 식별자를 사용합니다.

```text
filesystem__read_text_file
sandbox__execute_python_code
git__git_diff
```

`execute_tool()` 함수는 네임스페이스가 포함된 이름과 단순 함수명을 모두 유연하게 처리합니다. 만약 등록된 색인에서 도구를 찾을 수 없다면 `__` 구분자를 파싱하여 서버를 직접 탐색하며, 최종적으로 도구를 찾지 못한 경우 **현재 사용 가능한 전체 도구 목록을 오류 메시지에 함께 포함하여 반환**합니다. 이를 통해 LLM 모델이 반환된 오류를 인지하고 올바른 도구 이름으로 스스로 재시도(Self-correction)할 수 있도록 돕습니다.

## 도구 오류의 투명한 피드백 메커니즘

```python
except MCPToolError as e:
    return e.message, "error"      # MCP 서버가 반환한 오류 본문 유지
except Exception as e:
    return f"Tool execution failed ({type(e).__name__}): {e}", "error"
```

도구 실행 중 발생한 오류는 Python 예외(Exception)로 throw하지 않고, **결과 문자열(텍스트) 형태로 래핑하여 모델에게 전달**합니다. 모델이 에러 메시지를 직접 확인하고 잘못된 파라미터를 수정하여 다음 턴에서 재시도할 수 있도록 유도하기 위함입니다. 예를 들어 "파일을 찾을 수 없음"과 같은 오류는 시스템 장애가 아니라 모델에게 유의미한 관측 정보에 해당합니다.

또한 `_StderrTee` 모듈이 자식 프로세스의 표준 에러(stderr) 스트림 앞 4줄과 뒤 8줄을 항시 버퍼에 갈무리합니다. 덕분에 서버 기동이나 연결 실패 시 UI 화면의 상태 칩 툴팁에 실제 근본 원인이 즉시 표시됩니다.

```text
Cannot find package '@modelcontextprotocol/sdk' imported from .../memory-scoped.mjs
```

## 작업 공간(Workspace)별 독립 런타임 풀 (MCPRuntimePool)

`filesystem` 서버는 허용 작업 디렉터리를 명령행 인자(**argv**)로 전달받고, `sandbox` 서버는 작업 경로를 환경변수(**env**)로 전달받습니다. 두 설정 모두 자식 프로세스 기동 시점에 영구 고정되므로, 이미 실행 중인 프로세스의 작업 경로를 동적으로 변경하는 것은 불가능합니다.
따라서 대화 세션이 작업 디렉터리를 변경할 때마다 매번 공용 서버를 재기동하는 대신, **각 작업 디렉터리마다 독립된 MCP 서버 묶음(Runtime)을 격리 관리하는 풀링 체계**(`MCPRuntimePool`)를 운영합니다.

```python
manager = await get_runtime_pool().acquire(workspace, holder=session_id)
try:
    ...  # 해당 토론 턴의 모든 도구 호출이 획득한 전용 매니저를 통해 안전하게 실행됨
finally:
    await get_runtime_pool().release(session_id, workspace)
```

신규 런타임 묶음을 생성할 때는 기존의 이미 치환된 문자열을 역추적하여 변경하지 않고, **설정 원본 JSON 템플릿을 해당 작업 공간 경로를 기준으로 재치환(Re-resolve)**합니다. 설정 내에 `${WORKSPACE_DIR}` 환경변수가 여러 번 중첩되어 있더라도 동일한 파서가 100% 일관되게 경로를 해석합니다. 이때 전역 `conf.json` 파일은 전혀 수정되지 않습니다. 작업 공간 경로는 개별 대화 세션의 컨텍스트일 뿐, 서버 전체의 배포 설정이 아니기 때문입니다.

**서로 다른 작업 폴더를 사용하는 토론 세션은 완전한 병렬 실행이 가능합니다.** 동일한 작업 폴더를 지정한 세션끼리는 동일한 런타임 묶음을 공유하되(작업 디렉터리 파일은 협업을 위해 공유됨), 요청 메타데이터의 대화 스코프 분리를 통해 지식 그래프와 샌드박스 커널 네임스페이스는 철저히 독립적으로 유지됩니다.

런타임 풀에서 유지할 수 있는 최대 묶음 수는 `MCP_MAX_RUNTIMES` (기본 4개)로 제한되며, 참조 세션이 없는 유휴 묶음은 `MCP_RUNTIME_IDLE_TTL` (기본 300초) 동안 대기한 후 안전하게 정리됩니다. 만약 풀이 가득 찬 상태에서 모든 런타임이 활발히 점유 중인 경우 시스템은 `RuntimeCapacityError`를 발생시켜 요청을 거절하며, 이때 오류 메시지에 현재 런타임을 점유 중인 세션 목록을 함께 안내합니다.

## 실시간 연결 상태 모니터링

```python
manager.connection_status()
# {"filesystem": {"connected": True, "available": True, "tool_count": 14, "error": None},
#  "memory":     {"connected": False, ..., "error": "Cannot find package ..."}}
```

| 상태 칩 표시 | 의미 및 동작 상세 |
| :--- | :--- |
| 🟢 **연결됨** | 프로세스 구동 및 핸드셰이크 완료, 도구 호출 즉시 가능 |
| 🔴 **실패** | 서버 기동 또는 연결 실패. 마우스 오버 툴팁에 stderr 원인 표시 |
| ⚪ **비활성** | `conf.json` 설정에서 `"enabled": false`로 명시된 상태 |
| ⚪ **미기동** | **해당 대화 세션의 작업 공간**에 아직 런타임 묶음이 생성되지 않음 (첫 토론 턴 실행 시 기동) |

UI 화면의 상태 칩이 표시하는 것은 전역 프로세스가 아니라 **해당 대화 세션이 실제로 바인딩된 런타임 묶음**의 상태입니다. 작업 공간 디렉터리가 다르면 구동되는 프로세스 자체가 상이하므로, 아직 기동되지 않은 세션에 다른 작업 공간의 서버 상태를 대신 표시하여 도구가 준비된 것처럼 오인하게 만드는 부작용을 방지합니다.

MCP 서버들은 애플리케이션 시작 시점이 아니라 각 세션의 첫 토론 턴 실행 시점에 지연 구동(Lazy Start)되므로, 프론트엔드는 **2초 주기로 런타임 상태를 폴링하여 변경 시에만 화면을 재렌더링**합니다. 따라서 첫 토론이 진행되면서 서버가 백그라운드에서 기동되면 "미기동" 상태가 즉시 "연결됨"으로 자연스럽게 갱신됩니다.

**특정 MCP 서버의 연결 실패가 애플리케이션 전체의 실행을 중단시키지 않습니다.** 해당 도구를 사용하려던 에이전트는 해당 도구 권한만을 일시 배제한 채 정상적으로 발언을 이어갑니다.

## MCP Roots

MADO 호스트는 MCP 표준 사양인 `roots/list` 프로토콜 요청에 대해 현재 바인딩된 작업 공간 디렉터리 경로를 반환합니다. 이를 통해 각 도구 서버 프로세스는 자신이 접근 및 조작 가능한 공식 루트 디렉터리 경계를 명확하게 확인합니다.

## 신규 MCP 서버 등록 방법

신규 도구 서버는 UI 화면(로스터 관리 → MCP 서버 추가)에서 등록하거나 `conf.json` 파일의 `mcp_servers` 블록에 직접 작성할 수 있습니다:

```json
"everything": {
  "command": "${PYTHON_BIN:-python}",
  "args": ["-m", "server_everything"],
  "env": { "API_KEY": "${SOME_API_KEY}" },
  "enabled": true
}
```

서버를 등록하는 것만으로는 에이전트가 도구를 즉시 사용할 수 없습니다. 해당 도구를 사용해야 하는 에이전트의 `allowed_mcp_servers` 권한 배열에 서버 식별자 이름을 명시적으로 추가해야 합니다. 자세한 내용은 [로스터 편집](../04-workflows/03-roster-editing.md) 문서를 참고하십시오.

> [!CAUTION]
> 폐쇄망(Airgap) 환경에서는 `npx` 명령어를 절대 사용하지 마십시오. 필요한 패키지가 로컬 캐시에 존재하지 않을 경우 외부의 공용 npm 레지스트리로 접속을 시도하여 긴 타임아웃이나 오류를 유발합니다. 반드시 로컬에 미리 번들링된 진입점 JavaScript 파일을 `node` 명령어로 직접 구동하십시오.

## 원격(HTTP/SSE) MCP 서버 연동

모든 MCP 서버가 동일한 로컬 장비 내에서 프로세스로 실행될 필요는 없습니다. 사내 공용 AI 게이트웨이나 외부 SaaS처럼 **이미 네트워크상에 구동 중인 원격 서버**를 연동할 때는 로컬 프로세스 기동 명령어(`command`) 대신 엔드포인트 주소(`url`)를 지정합니다.

```json
"gateway": {
  "url": "${REMOTE_MCP_URL}",
  "headers": { "Authorization": "Bearer ${REMOTE_MCP_TOKEN}" },
  "transport": "auto",
  "timeout": 30,
  "enabled": true
}
```

**단일 서버 설정에서 `command`와 `url`을 동시에 지정할 수 없습니다.** 둘 다 명시되거나 둘 다 누락된 경우 시스템은 Pydantic 유효성 검사 단계에서 설정을 즉시 거절합니다. 시스템이 임의로 한쪽을 선택해 버리면 유저가 자신이 설정한 값이 무시된 이유를 파악하기 어렵기 때문입니다.

| 설정 필드 | 의미 및 설명 |
| :--- | :--- |
| `url` | `http://` 또는 `https://`로 시작하는 대상 MCP 엔드포인트 주소 |
| `headers` | 매 HTTP 요청마다 동봉되는 추가 헤더 (Bearer 인증 토큰 등) |
| `transport` | `auto` (기본값) · `http` (Streamable HTTP) · `sse` (구형 HTTP+SSE) |
| `timeout` | 단일 도구 요청에 대한 응답 대기 제한 시간 (초 단위, 기본 30초) |

`transport: "auto"` 설정은 최신 **Streamable HTTP 전송 방식을 우선 시도하고, 실패 시 구형 HTTP+SSE 방식으로 자동 폴백**합니다. 동일한 엔드포인트 URL에서 두 규격을 모두 지원하거나 어느 프로토콜을 사용하는지 사전에 알기 어려운 경우가 흔하기 때문입니다. 대상 서버의 프로토콜 규격을 명확히 알고 있다면 `http` 또는 `sse`로 명시하는 것이 불필요한 핸드셰이크 지연을 방지할 수 있습니다.

한 번 정상적으로 연결된 세션이 네트워크 순단 등으로 끊어진 경우에는 프로토콜 방식을 임의로 교체하지 않습니다. 이는 프로토콜 불일치가 아니라 일시적인 원격 서버 장애이므로, 다음 도구 호출 시 기존에 성공했던 동일한 전송 방식으로 재연결을 시도합니다.

### 인증 토큰은 환경변수로 분리 관리하십시오

`headers`의 Authorization 값 등에 실제 인증 토큰을 평문으로 직접 기재하지 마십시오. `${환경변수}` 표기를 사용하고 실제 보안 토큰은 로컬 `.env` 파일에 보관해야 합니다. `conf.json`은 화면에서 설정을 변경할 때마다 파일이 갱신되며 소스 코드 저장소나 배포 패키지에 포함될 수 있지만, `.env`는 버전 관리에서 제외되기 때문입니다. 파일을 읽는 런타임 메모리에서만 환경변수가 치환되므로 설정 파일 원본의 보안이 유지됩니다.

### 폐쇄망 배포 시 주의점

원격 HTTP 서버는 **외부 네트워크 아웃바운드 연결**을 발생시킵니다. 기본 `conf.json`에 포함된 `remote_example` 서버는 비활성화(`"enabled": false`) 상태로 제공되며, 인터넷이 단절된 폐쇄망 환경에서는 이를 활성화하지 마십시오.

### UI 화면에서의 간편 추가

로스터 관리 화면의 **서버 추가** 대화상자에서 로컬 프로세스(`stdio`) 방식과 원격(`HTTP`) 방식을 탭으로 선택하여 손쉽게 등록할 수 있습니다. 유저의 주 관심사는 '어떤 MCP 서버를 붙일 것인가'이지 내부 전송 프로토콜 분류가 아니므로, 단일 인터페이스 내에서 설정 항목이 직관적으로 전환되도록 설계되어 있습니다.
