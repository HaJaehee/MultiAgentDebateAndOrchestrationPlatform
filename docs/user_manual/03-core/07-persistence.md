## 데이터베이스 관계형 스키마

```text
sessions ─────┬──▶ messages ──────▶ tool_calls
              │         ▲                │
              │         └────────────────┘  (message_id 외래키, ON DELETE SET NULL)
              ├──▶ artifacts
              ├──▶ tool_calls
              ├──▶ turns                   (발언·도구 기록이 turn_id 로 가리킴)
              └──▶ session_agents          (session_id + agent_key 복합 유니크 제약)
```

모든 하위 테이블 관계에는 `cascade="all, delete-orphan"` 옵션이 적용되어 있어 상위 세션을 삭제하면 연관된 모든 메시지, 도구 실행 이력, 산출물 데이터가 함께 안전하게 삭제됩니다. 또한 모든 ORM 관계는 `lazy="selectin"` 로딩 전략을 사용합니다. SQLAlchemy 비동기 세션 환경에서 기본 지연 로딩(Lazy Loading)을 시도하면 `MissingGreenlet` 예외가 발생하므로 연관 엔티티를 사전에 즉시(Eager) 함께 조회하도록 구성되어 있습니다.

### `sessions` 테이블

| 컬럼명 | 데이터 타입 | 설명 및 역할 |
| :--- | :--- | :--- |
| `id` | str(36) | 세션 고유 식별자 (UUID v4) |
| `title` | str(255) | 대화 세션 제목 |
| `strategy` | str(50) | 적용된 토론 전략 식별자 (`sequential_debate` 등) |
| `max_rounds` | int | 세션의 최대 토론 라운드 상한 |
| `active_agents` | JSON | 세션에서 활성화된 에이전트 키 목록 |
| `known_agents` | JSON | **해당 세션 생성 당시에 존재하던** 전체 에이전트 키 목록 |
| `custom_instructions` | Text | 해당 대화 세션 전용 커스텀 지침 |
| `personas_locked` | bool | 첫 메시지 전송 시 `True`로 전환되는 세션 잠금 플래그 |
| `workspace_dir` | Text | 세션 전용 작업 공간 디렉터리 경로 (미지정 시 기본 작업 공간 사용) |
| `decision_ledger` | Text | 결정 장부 본문 (오케스트레이터가 매 라운드 및 합성 완료 시 갱신, v0.8.3) |
| `ledger_through_id` | str(36) | 현재 결정 장부에 반영 완료된 마지막 발언 메시지 ID |
| `transcript_summary` | Text | 컨텍스트 한도로 인해 축소된 이전 대화의 누적 압축 요약문 |
| `summary_through_id` | str(36) | 요약문에 포함 완료된 마지막 발언 메시지 ID |

**`known_agents` 컬럼의 존재 이유**: `active_agents`는 활성화된 에이전트 목록만을 저장하는 허용 리스트입니다. 만약 이 컬럼만 존재한다면 목록에 포함되지 않은 에이전트 키가 "사용자가 의도적으로 비활성화한 에이전트"인지, 아니면 "해당 세션 생성 당시에는 시스템에 존재하지 않았던 신규 에이전트"인지 구분할 방법이 없습니다. 이로 인해 과거에는 `conf.json`에 새로운 에이전트를 추가하면 과거 대화 세션에서 해당 에이전트가 **사용자가 직접 꺼둔 것으로 오인**되는 버그가 발생했습니다. 세션 생성 시점의 전체 에이전트 목록(`known_agents`)을 함께 보존함으로써 두 상태를 명확히 판별할 수 있습니다.

**`workspace_dir` 경로는 세션 잠금 이후에도 고정되지 않습니다.** 페르소나 설정과 달리 작업 디렉터리는 토론 진행 도중에도 사용자의 필요에 따라 유연하게 변경할 수 있어야 하기 때문입니다.

**결정 장부와 누적 요약문은 해당 턴이 온전히 완료되었을 때만 저장합니다.** 사용자가 토론 도중 "요청 되돌리기(Rollback)"를 실행하면 해당 턴의 발언들이 취소 및 삭제되는데, 취소된 발언이 이미 장부에 반영되어 저장되어 있다면 실제로 합의되지 않은 유령 결정 사항이 장부에 남게 되기 때문입니다. 장부와 요약이 어느 발언까지 반영되었는지는 단순 개수가 아니라 고유 발언 ID(`ledger_through_id`, `summary_through_id`)로 정밀하게 추적합니다.

### `messages` 테이블

| 컬럼명 | 설명 |
| :--- | :--- |
| `sender_key` / `sender_name` / `sender_role` | 발언자 식별자 및 표시명 (`user`, `orchestrator`, 각 에이전트 키/이름/역할) |
| `content` | 발언 메시지 본문 (마크다운 텍스트) |
| `round_number` | 발언이 속한 라운드 번호 (목표 계획 발언은 0) |
| `msg_type` | 메시지 분류 (`user` / `orchestrator` / `agent` / `system` / `error`) |
| `started_at` | 발언 생성이 실제로 **시작된** 타임스탬프 (UTC) |
| `finished_at` | 발언 생성이 실제로 **완료되거나 중단된** 타임스탬프 (UTC) |
| `turn_started_at` | **턴을 마무리한 최종 합성 발언에만 기록**: 해당 턴을 시작한 사용자 요청이 등록된 시각 |
| `created_at` | **대화 기록 정렬 기준 타임스탬프** (실제 발언 시각이 아님, 하단 설명 참고) |
| `turn_id` | 이 기록이 속한 턴 (`turns.id`). 기능 도입 이전의 기록은 NULL |
| `turn_meta` | 해당 기록이 턴의 흐름에서 맡은 역할 (JSON). `kind`는 `opening` · `interjection` · `plan` · `speech` · `merge` · `gate` · `nomination` · `assignment` · `note` · `failure` · `interrupted` · `synthesis` 중 하나이며, 지명(`speakers`)과 병렬 분배(`tasks`)는 결과를 값으로 함께 기록합니다 |

메시지 테이블에는 에이전트의 내부 키(`sender_key`)뿐만 아니라 당시의 표시 이름(`sender_name`)과 역할명(`sender_role`)을 함께 영구 기록합니다. 훗날 관리자가 에이전트를 삭제하거나 이름을 변경하더라도 과거 토론 기록 속의 발언자 정보는 원형 그대로 보존되어야 하기 때문입니다.

**`created_at` 컬럼을 실제 발언 시작 시각으로 해석해서는 안 됩니다.** 데이터베이스 레코드는 LLM의 스트리밍 응답 생성이 완전히 완료된 **직후**에 삽입되므로 실제로는 완료 시점에 가깝습니다. 특히 병렬 라운드에서는 각 에이전트의 응답 완료 순서가 불규칙하므로, DB 커밋 시각을 정렬 키로 사용할 경우 브라우저를 새로고침할 때마다 발언 순서가 뒤바뀌는 문제가 발생합니다. 이를 방지하기 위해 병렬 라운드에서는 `라운드 기준 시각 + 지시 순번(ms)` 형태로 타임스탬프를 명시적으로 부여합니다. 대화 기록을 재조회하여 정렬할 때는 `created_at`을 기준으로 삼으며, 사용자 화면에 표시되는 발언 구간 시각은 `started_at`과 `finished_at`을 사용합니다.

- **사용자 발언 및 시스템 지명 기록**처럼 LLM 응답 대기 시간이 없는 레코드는 두 타임스탬프가 동일합니다.
- **`turn_started_at`을 별도 기록하는 이유**: 토론 도중 사용자의 개입 메모 역시 `msg_type="user"`로 저장되며, 계획 직후의 개입은 초기 요청과 동일하게 `round_number=0`으로 기록됩니다. 단순 쿼리로 '마지막 round 0 사용자 발언'을 턴 시작 시각으로 추론할 경우 사용자가 도중에 개입했을 때 턴의 총 소요 시간이 비정상적으로 축소 계산됩니다. 따라서 최종 합성 발언에 해당 턴을 시작한 최초 요청의 타임스탬프를 명시적으로 기록하고, 다른 메시지 행은 NULL로 유지합니다.
- **병렬 라운드**에서는 여러 에이전트 발언의 시작~종료 시간 구간이 서로 중첩되며, 이는 실제 병렬 실행이 이루어졌음을 정확히 반영합니다.
- 두 타임스탬프 컬럼이 **NULL**인 경우는 해당 기능 도입 이전(v0.6.1.1 이하)에 생성된 레거시 데이터입니다. 마이그레이션 시 임의의 기본값을 채워 넣으면 과거 발언들이 마이그레이션 시점에 동시에 시작하고 끝난 것처럼 왜곡되므로 NULL을 그대로 유지하며, 화면 표시 시에도 시작/종료 라벨 없이 `created_at` 시각만 단일 표시합니다.

### `tool_calls` 테이블

| 컬럼명 | 설명 |
| :--- | :--- |
| `agent_key` | 해당 도구를 호출한 에이전트 식별자 |
| `tool_name` | 실행된 MCP 도구 함수명 (`filesystem__read_text_file` 등) |
| `arguments` | 도구 호출 시 전달된 인자 딕셔너리 (JSON) |
| `output` | 도구 실행 결과 문자열 또는 오류 메시지 본문 |
| `status` | 도구 실행 결과 상태 (`success` / `error`) |
| `message_id` | 도구를 호출한 상위 메시지 ID (`ON DELETE SET NULL`) |
| `turn_id` | 도구를 호출한 턴 (`turns.id`) |

**도구 호출은 실행되는 즉시 데이터베이스에 기록됩니다.** 이때는 `message_id`를 비워두고, 발언이 완료되어 메시지가 커밋될 때 동일한 트랜잭션 내에서 외래키를 채웁니다. 과거에는 발언이 완전히 끝날 때 메시지와 함께 일괄 저장했기 때문에, 발언 도중 서버가 비정상 종료되면 이미 실행된 도구(사용자 승인을 거친 파일 쓰기 등)의 실행 이력이 유실되는 문제가 있었습니다. 턴이 중단된 후에도 `message_id`가 비어 있는 레코드는 완료되지 못한 발언이 실행한 도구 호출이며, 이후 해당 턴을 재개하면 도구 단위로 복구된 발언에 연결되고, 강제 마무리할 경우 "발언 중단" 안내 기록에 연결됩니다.

`message_id` 외래키에 `ON DELETE SET NULL`이 지정된 이유: 사용자가 특정 발언을 삭제하거나 되돌리더라도, **해당 발언 중에 도구가 실제로 실행되었다는 사실과 그 결과는 데이터베이스에 영구 보존**되어야 하기 때문입니다. 이미 디스크 상의 파일이 실제로 변경되었거나 외부 작업이 실행되었기 때문입니다.

### `turns` 테이블

사용자 요청 하나로 시작하여 최종 합성으로 끝나는 토론 턴의 생애주기를 관리합니다 ([ADR-024](../../../lectures/05-adr/ADR-024-resume-interrupted-turns.md)). 턴을 시작하는 사용자 요청과 **동일한 트랜잭션** 내에 기록됩니다.

| 컬럼명 | 설명 |
| :--- | :--- |
| `status` | `running` · `completed` · `failed`(엔진 예외) · `interrupted`(서버 중단) · `abandoned`(중단된 채로 방치하고 새 요청 전송) |
| `phase` | `planning` · `debating` · `synthesizing` · `completed`. 중단된 턴을 어디서부터 재개할지 결정하는 1차 기준입니다 |
| `opening_message_id` | 턴을 시작한 사용자 요청 메시지 ID |
| `config` | 턴 시작 시점의 실행 구성 (참여 에이전트, 전략, 라운드 수, 동시 실행 상한, 커스텀 지침, 작업 공간). 턴 진행 중 로스터를 변경하더라도 해당 턴은 이 구성 그대로 완료됩니다 |
| `stopped_early` | 합성 단계 진입 시 사용자의 중단 요청으로 조기 종료된 턴인지 여부 |
| `paused_seconds` · `resumed_count` | 중단 상태로 머문 누적 시간(초)과 재개 횟수. 최종 보고서의 총 경과 시간에 함께 기록됩니다 |
| `error` | `failed` 상태일 때의 예외 사유 |

서버가 기동되면 `running` 상태로 남아 있는 턴을 정리합니다. 단일 프로세스 아키텍처이므로 기동 시점에 여전히 `running`인 턴은 비정상 종료된 턴으로 간주됩니다. 합성 발언까지 정상 기록된 턴은 `completed`로, 나머지는 `interrupted`로 갱신합니다.

### `speech_drafts` 테이블

도구를 호출하는 발언의 단계별 초안(Draft)을 저장하는 테이블입니다 ([ADR-025](../../../lectures/05-adr/ADR-025-resume-speeches-by-tool-step.md)). 도구 루프에서 도구를 호출하거나 실행 결과를 수신할 때마다, LLM 컨텍스트 메시지와 루프 상태 메트릭(호출 횟수, 증액된 한도, 확장된 윈도우, 단계별 생성 텍스트)을 보존합니다.

| 컬럼명 | 설명 |
| :--- | :--- |
| `id` | 해당 발언이 기록될 `messages.id`. 중단되기 전에 기록된 도구 호출이 재개된 발언과 올바르게 연결되도록 미리 식별자를 할당합니다 |
| `turn_id` · `session_id` | 소속된 턴 ID 및 세션 ID |
| `agent_key` · `kind` · `round_number` · `graph_node_id` | 어느 발언의 초안인지 식별하기 위한 메타데이터 |
| `started_at` | 발언이 최초로 시작된 시각. 재개된 발언의 카드 경과 시간도 이 시각부터 계산됩니다 |
| `state` | 도구 루프의 내부 상태(버전 정보 포함) 및 이미 기록된 도구 호출 ID 목록 |

발언이 정상적으로 커밋되면 동일한 트랜잭션 내에서 초안 행이 삭제되므로, 테이블에 남아 있는 레코드는 완료되지 못한 발언을 의미합니다. 최종 결론 생성, 요청 취소, 신규 요청 전송, 턴 강제 종료 시에도 함께 정리됩니다.

| 컬럼명 | 설명 |

| `artifact_type` | 산출물 유형 분류 (`code` / `markdown` / `mermaid` / `json`) |

### `session_agents` — 핵심 스냅샷 테이블

```python
class SessionAgentModel(Base):
    __table_args__ = (UniqueConstraint("session_id", "agent_key"),)

    agent_key: str
    name: str                       # 세션별 페르소나 표시 이름
    role: str                       # 세션별 페르소나 역할 설명
    system_prompt: str              # 세션별 에이전트 시스템 프롬프트
    card_color: str                 # 세션 내 카드 색상 (빈 문자열인 경우 키 기반 자동 배정)
    icon_path: str                  # 세션 내 아이콘 (Material Icon 명칭 또는 로컬 이미지 경로)
    config_snapshot: Optional[Any]  # 세션 잠금 시점에 영구 고정된 AgentConfig 전체 모델 사본
```

`card_color`와 `icon_path` 외형 정보는 `config_snapshot` JSON 내부에도 포함되어 있지만 독립된 별도 컬럼으로 중복 보존합니다. UI 로스터 및 피드에서 에이전트 카드를 렌더링할 때 매번 거대한 JSON 스냅샷을 파싱하지 않고 가볍게 조회할 수 있어야 하며, 스냅샷 기능이 도입되기 전의 레거시 세션 데이터와의 하위 호환성을 보장하기 위함입니다.

`config_snapshot`에는 **세션 잠금 시점의 `AgentConfig` Pydantic 모델 전체**가 직렬화되어 저장됩니다. 모델명, 엔드포인트 URL, API 키, 샘플링 파라미터, 허용된 MCP 서버 권한 목록까지 포함됩니다. 이 스냅샷이 존재함으로써 각 대화 세션은 외부 환경 변화로부터 완전히 독립된 자기완결적(Self-contained) 상태를 갖추게 됩니다.

스냅샷 컬럼이 `None`인 세션은 기능 도입 이전에 생성된 레거시 세션이며, 이 경우 현재 활성 상태인 `conf.json`의 전역 설정을 참조합니다 (기존 DB 데이터는 서버 기동 시 스키마 자동 마이그레이션이 안전하게 수행됩니다).

## 자기완결적 대화의 보장 가치

```text
       세션 생성                첫 메시지 전송 시점             이후 토론 진행
           │                            │                            │
    ┌──────┴──────┐              ┌──────┴──────┐             ┌───────┴────────┐
    │ conf.json 설정을 │              │ 모든 에이전트의 │             │ session_agents │
    │ 실시간으로       │  ──────────▶ │ AgentConfig 전체를│  ────────▶ │ 테이블만 참조   │
    │ 참조 및 반영    │              │ 영구 고정 저장 │             │ conf.json 무관 │
    └─────────────┘              └─────────────┘             └────────────────┘
       🟢 편집 가능 단계             🔒 personas_locked=True
```

### 무엇을 방지하는가

| 전역 `conf.json` 변경 내역 | 이미 시작된 대화 세션 | 아직 시작되지 않은 신규 대화 세션 |
| :--- | :--- | :--- |
| 에이전트 삭제 | 영향 없음 (스냅샷으로 토론 지속) | 에이전트 목록에서 완전히 삭제됨 |
| 에이전트 비활성화 | 영향 없음 | 토론 참여에서 제외됨 |
| 모델 및 엔드포인트 변경 | 영향 없음 | 신규 설정값 적용 |
| MCP 도구 권한 변경 | 영향 없음 | 신규 설정값 적용 |
| 카드 색상 및 아이콘 변경 | 영향 없음 | 신규 설정값 적용 |
| 신규 에이전트 추가 | 참여하지 않음 | 토론 참여 가능 |

이러한 격리 보장이 없으면 **어제 완료된 대화를 오늘 다시 열었을 때 전혀 다른 시스템으로 변질되는 심각한 재현성 문제**가 발생합니다. 토론 기록 속의 'System Architect'는 어제 특정 경량 모델과 특정 도구로 발언했는데, 오늘 세션을 재개했을 때 다른 모델과 다른 도구 권한으로 대화가 이어지면 논리적 일관성과 신뢰성이 완전히 파괴되기 때문입니다.

### 예외적 구제 수단 (설정 갱신)

스냅샷이 영구 고정되어 곤란한 예외 상황이 발생할 수 있습니다. 예를 들어 외부 LLM 엔드포인트 주소가 변경되었거나 API 키가 만료된 대화 세션입니다. 로스터 관리 패널의 **설정 갱신(Refresh Config)** 버튼을 누르면, 현재 `conf.json`의 최신 인프라 설정값으로 스냅샷을 다시 덮어씁니다. 이때 **사용자가 조율한 페르소나(이름, 역할, 시스템 프롬프트)는 전혀 건드리지 않으므로** 토론 기록 상의 발언자 정체성은 완벽히 유지됩니다.

## 비동기 데이터베이스 엔진

```python
# app/database/session.py
engine = create_async_engine(db_url)           # sqlite+aiosqlite 비동기 엔진
get_session_factory() -> async_sessionmaker
await init_db(db_url)                          # 테이블 자동 생성 (미존재 시)
```

`db_url` 설정값을 통해 데이터베이스 엔진을 유연하게 교체할 수 있습니다. 기본 SQLite(`sqlite+aiosqlite`) 환경뿐만 아니라 프로덕션 환경의 고성능 PostgreSQL(`postgresql+asyncpg`)로 전환할 때에도 설정 문자열만 변경하면 동일하게 동작합니다:

```json
"db_url": "postgresql+asyncpg://user:pass@host/dbname"
```

모든 시간 데이터는 데이터베이스 내부에서 **철저히 UTC 기준으로 저장**되며(`utc_now()`), 사용자 브라우저 화면에 렌더링되거나 내보내기 문서를 생성할 때 비로소 로컬 시간대로 변환됩니다(`export.to_local()`). 저장 계층과 표시 계층의 타임존 처리를 명확히 분리함으로써 시각 왜곡을 원천 방지합니다.

### 무중단 스키마 마이그레이션 (`_ADDED_COLUMNS`)

SQLAlchemy의 `create_all()` 메서드는 기존에 이미 존재하는 테이블에 신규 컬럼을 자동으로 추가하지 못합니다. 따라서 MADO는 서버 기동 시점에 `_ADDED_COLUMNS` 딕셔너리에 정의된 신규 컬럼들을 `PRAGMA table_info`로 직접 확인하고, 누락된 컬럼이 있다면 `ALTER TABLE ... ADD COLUMN` DDL을 멱등(Idempotent)하게 자동 실행합니다. 사용자는 데이터베이스를 수동으로 수정하거나 초기화할 필요 없이 최신 애플리케이션 버전으로 즉시 업그레이드할 수 있습니다 (`session_agents.card_color`, `icon_path` 등 신규 필드도 이 메커니즘을 통해 무중단으로 반영되었습니다).
