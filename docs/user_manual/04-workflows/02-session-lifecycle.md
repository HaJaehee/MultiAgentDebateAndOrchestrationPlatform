## 세션 생애주기 3단계 흐름

```text
  ① 세션 생성                 ② 첫 메시지 전송              ③ 이후 토론 지속
      │                            │                            │
  ┌───▼──────────────┐     ┌───────▼──────────┐     ┌───────────▼────────────┐
  │ 🟢 자유 편집 단계 │     │ 🔒 세션 잠금      │     │ 🔒 잠긴 스냅샷으로 격리  │
  │ · 페르소나 초안  │────▶│ 모든 에이전트의   │────▶│ session_agents 테이블만│
  │ · 참여 에이전트  │     │ AgentConfig 전체 │     │ 참조 (conf.json 무관)  │
  │ · 전략 / 라운드  │     │ 를 DB 스냅샷으로 │     │                        │
  │ · 작업 공간 지정 │     │ 영구 고정        │     │ 작업 공간은 언제든 변경│
  └──────────────────┘     └──────────────────┘     └────────────────────────┘
```

## ① 신규 대화 세션 생성

좌측 사이드바의 **+ New Chat** 버튼을 클릭하여 새로운 대화 세션을 생성합니다.

```python
SessionModel(
    title="New Debate Session",
    strategy="sequential_debate",
    max_rounds=3,
    active_agents=[...],      # 현재 켜져 있는 활성 에이전트 목록
    known_agents=[...],       # 해당 시점에 시스템에 존재하던 전체 에이전트 목록
    personas_locked=False,
)
```

이 단계에서 자유롭게 설정할 수 있는 항목은 다음과 같습니다:

| 설정 항목 | UI 조작 위치 | 세션 잠금 이후 변경 가능 여부 |
| :--- | :--- | :--- |
| 참여 에이전트 활성화 여부 | 로스터 패널의 에이전트 토글 스위치 | 잠금 이후 변경 불가 (고정) |
| 토론 전략 | 로스터 패널의 전략 선택 드롭다운 | **언제든 변경 가능** |
| 최대 토론 라운드 수 | 로스터 패널의 라운드 슬라이더 | **언제든 변경 가능** |
| 세션 커스텀 지침 | 로스터 패널의 텍스트 입력창 | **언제든 변경 가능** |
| 작업 공간 디렉터리 | 로스터 패널의 작업 공간 경로 입력창 | **언제든 변경 가능** (턴 실행 중 제외) |
| 페르소나 (이름, 역할, 프롬프트) | `/personas/{session_id}` 편집 페이지 | 잠금 이후 변경 불가 (고정) |

### `known_agents` 컬럼의 필요성

`active_agents`는 활성화된 에이전트 목록만을 저장하는 허용 리스트입니다. 만약 이 컬럼만 존재한다면 목록에 포함되지 않은 에이전트 키가 "유저가 의도적으로 비활성화한 에이전트"인지, 아니면 "해당 세션 생성 당시에는 시스템에 존재하지 않았던 신규 에이전트"인지 구분할 방법이 없습니다. 이로 인해 과거에는 `conf.json`에 새로운 에이전트를 추가하면 과거 대화 세션에서 해당 에이전트가 **유저가 직접 꺼둔 것으로 오인**되는 버그가 발생했습니다. 세션 생성 시점의 전체 에이전트 목록(`known_agents`)을 함께 보존함으로써 두 상태를 명확히 판별할 수 있습니다.

## ② 페르소나 조율 (첫 메시지 전송 전)

`/personas/{session_id}` 페이지에서 세션 맞춤형 인격을 자유롭게 조율합니다.

| 편집 가능 (세션별 인격) | 편집 불가 (서버 인프라 설정) |
| :--- | :--- |
| `name` — 대화 피드에 표시되는 에이전트 이름 | `model`, `api_base`, `api_key` |
| `role` — 에이전트의 세부 역할 정의 | `allowed_mcp_servers` |
| `system_prompt` — 세션 고유의 행동 지침 프롬프트 | `temperature`, `max_tokens` 등 샘플링 값 |
| `card_color`, `icon` — 카드 색상 및 아이콘 | |

운영 및 인프라 설정은 `conf.json`이 유일한 원본입니다. 대화의 성격을 결정하는 본질은 에이전트의 인격과 프롬프트이지 네트워크 엔드포인트가 아니기 때문입니다.

수정한 내용은 `session_agents` 테이블에 **초안(Draft)** 형태로 저장되며, 유저의 편의를 위해 `conf.json`의 전역 기본값에도 함께 반영됩니다. 별도로 조율하지 않은 에이전트는 `conf.json`의 기본 프롬프트를 그대로 사용합니다.

**되돌리기**: 초안을 삭제하면 언제든 `conf.json`의 기본값으로 즉시 복원할 수 있습니다.

## ③ 세션 잠금 (첫 유저 메시지 전송 시점)

```text
유저가 첫 번째 메시지를 전송함
        │
        ▼
prepare_agents_for_turn(db, session_model, pool, active_keys)
        │
        ├─ 모든 활성 에이전트에 대해:
        │     초안이 존재하면 초안 값을, 없으면 conf.json 기본값을
        │     session_agents 테이블에 영구 기록
        │     └─ config_snapshot = AgentConfig Pydantic 모델 전체 사본 저장
        │          (모델명, 엔드포인트 URL, API 키, 샘플링 파라미터, MCP 도구 권한)
        │
        └─ sessions.personas_locked = True 플래그 설정
```

이 순간부터 **해당 대화 세션은 외부의 `conf.json` 파일을 더 이상 읽지 않습니다.**

> [!NOTE]
> 잠금이 예외적으로 해제되는 단 한 가지 경우가 있습니다. 첫 번째 턴에서 **긴급 종료(Emergency Stop)**를 실행하여 세션 내에 발언이 하나도 남지 않게 된 경우, 해당 세션은 토론 시작 전 상태로 완벽히 복원되어 잠금이 다시 풀립니다(`discard_turn`). 기존에 생성되었던 `session_agents` 레코드는 정리되며, 차후 새로운 첫 메시지가 전송될 때 당시의 `conf.json` 설정으로 다시 굳어집니다. 자세한 내용은 [토론 한 턴의 생애주기](01-debate-turn.md#정지stop와-긴급-종료emergency-stop의-차이점) 문서를 참고하십시오.

### 잠금 이후 전역 `conf.json`이 변경되었을 때의 영향

| `conf.json` 변경 작업 | 이미 잠긴 기존 대화 세션 | 아직 시작되지 않은 신규 대화 세션 |
| :--- | :--- | :--- |
| 에이전트 삭제 | 영향 없음 (스냅샷으로 토론 정상 지속) | 목록에서 즉시 제거됨 |
| 에이전트 비활성화 | 영향 없음 | 토론 참여에서 제외됨 |
| 모델 및 엔드포인트 변경 | 영향 없음 | 신규 설정값 적용 |
| API 키 변경 | 영향 없음 | 신규 설정값 적용 |
| MCP 도구 권한 변경 | 영향 없음 | 신규 설정값 적용 |
| 신규 에이전트 추가 | 참여하지 않음 | 토론 참여 가능 |

### 스냅샷 아키텍처의 설계 이유

이러한 격리 보장이 없으면 **어제 종료된 대화를 오늘 다시 열었을 때 전혀 다른 시스템으로 변질되는 심각한 재현성 문제**가 발생합니다. 토론 기록 속의 'System Architect'는 어제 특정 경량 모델과 특정 도구로 발언했는데, 오늘 세션을 재개했을 때 다른 모델과 다른 도구 권한으로 대화가 이어지면 논리적 일관성과 신뢰성이 완전히 파괴되기 때문입니다.

토론 기록은 **생성 당시의 특정 구성 하에서 완성된 결과물**이므로, 이후 이어지는 추가 발언 역시 동일한 구성 상태에서 이루어져야 합니다.

## ④ 세션 재개 및 복원

과거 대화 세션을 다시 선택하여 열면 다음 과정이 진행됩니다:

```text
사이드바에서 과거 대화 세션 선택
   │
   ├─ 발언 기록, 도구 실행 이력, 최종 산출물을 DB에서 로드
   ├─ session_agents 테이블의 config_snapshot을 기반으로 에이전트 객체 복원
   └─ 백그라운드 진행 중인 토론이 있다면 TurnRun 메모리 스냅샷으로 화면 즉시 복원
```

브라우저를 새로고침하거나 다른 페이지로 이동하더라도 백그라운드 토론은 중단 없이 계속 진행됩니다 (`DebateRunner`가 브라우저 세션과 완전히 분리된 비동기 태스크로 구동되기 때문입니다). 다시 접속한 브라우저 화면은 메모리의 정본 스냅샷을 기반으로 피드를 즉시 복원합니다.

### 해당 세션에만 남아 있는 에이전트 처리

서버의 `conf.json`에서 이미 삭제되었으나 해당 세션의 스냅샷에는 남아 있는 에이전트는 로스터에 정상 표시되며 토론에 계속 참여합니다. 이때 발언자 정렬 우선순위는 다음과 같습니다:

```text
1. 오케스트레이터 (항상 최우선 배치)
2. conf.json에 정의된 우선순위 순서
3. 해당 세션 스냅샷에만 잔존하는 에이전트
```

## 구제 수단 — 설정 갱신 (Refresh Config)

스냅샷이 영구 고정되어 곤란한 예외 상황이 발생할 수 있습니다:

- 사내 AI 게이트웨이 주소가 변경된 경우
- 사용 중이던 API 키가 만료된 경우
- 해당 세션이 사용하던 LLM 모델이 공급자 측에서 서비스 종료(Deprecated)된 경우

로스터 패널의 **설정 갱신(Refresh Config)** 버튼을 누르면, 현재 `conf.json`에 저장된 최신 인프라 설정값으로 스냅샷을 안전하게 재동결(Re-freeze)합니다.

```text
갱신되는 인프라 속성      갱신되지 않고 보존되는 속성
· 모델 식별자 (model)     · 표시 이름 (name)
· 엔드포인트 URL (api_base)· 역할 정의 (role)
· API 인증 키 (api_key)   · 시스템 프롬프트 (system_prompt)
· MCP 도구 권한
· 샘플링 파라미터
```

**에이전트의 인격은 전혀 건드리지 않으므로 토론 기록 상의 화자 정체성은 완벽히 유지됩니다.** 또한 `conf.json`에서 이미 삭제된 에이전트의 스냅샷은 강제로 삭제되지 않고 안전하게 보존됩니다.

## ⑤ 세션 삭제

사이드바에서 유저가 명시적으로 대화 세션을 삭제합니다. 데이터베이스 외래키에 `cascade="all, delete-orphan"`이 적용되어 있어 연관된 모든 메시지, 도구 실행 이력, 산출물, 페르소나 데이터가 함께 안전하게 삭제됩니다.

단, 디스크 상의 작업 공간(Workspace) 폴더 자체는 **절대 자동으로 삭제되지 않습니다.** 에이전트들이 생성한 프로젝트 소스 코드 및 산출물 파일은 대화 기록과 독립된 유저의 영구 자산이며, 복수의 대화 세션이 동일한 작업 폴더를 공유하고 있을 수도 있기 때문입니다.

---

## 작업 공간(Workspace) 격리 운영 규칙

대화 세션마다 독립된 작업 폴더를 유연하게 지정할 수 있습니다. 로스터 관리 화면의 **작업 공간** 입력 칸에 로컬 디렉터리 경로를 입력하면, 해당 대화의 모든 MCP 도구 서버(`filesystem`, `git`, `sandbox`, `memory`)가 해당 폴더를 작업 루트로 바라보게 됩니다.

- 설정된 경로는 `sessions.workspace_dir` 컬럼에 세션별로 영구 저장되며, 전역 `conf.json` 파일은 변경되지 않습니다.
- 경로를 비워 둘 경우 `conf.json`에 정의된 기본 `WORKSPACE_DIR` 경로를 상속받습니다.
- **페르소나와 달리 세션 잠금 이후에도 언제든 변경할 수 있습니다.** 단, 해당 세션에서 토론 턴이 진행 중인 동안에는 변경이 일시 제한됩니다 (실행 중인 턴이 해당 폴더에 바인딩된 MCP 서버를 이미 대여 중이기 때문입니다).
- MCP 서버 묶음은 작업 폴더마다 격리되어 독립 구동되므로, **서로 다른 작업 폴더를 사용하는 토론 세션들은 완벽한 동시 실행이 가능합니다.**
