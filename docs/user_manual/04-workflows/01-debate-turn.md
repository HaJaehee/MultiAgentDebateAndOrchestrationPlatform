# 토론 한 턴의 생애주기

> 상위: [워크플로우 개관](README.md) · 다음: [세션 생애주기](02-session-lifecycle.md)
>
> 구현 원리는 [오케스트레이션 엔진](../03-core/05-orchestration-engine.md) 참고

사용자가 채팅창에 메시지를 입력하여 전송한 후 최종 산출물이 생성되기까지의 전체 과정을 시간 순서대로 상세히 설명합니다.

---

## 전체 실행 파이프라인 개요

```text
 사용자 입력
     │
 ┌───▼────────────────────────────────────────────────┐
 │ 0. 준비 단계 (Turn Initialization)                │
 │    세션 로드 · 작업 공간 바인딩 · 페르소나 잠금 · 대화 기록 로드 │
 └───┬────────────────────────────────────────────────┘
     │
 ┌───▼──────────────┐
 │ 1. 계획 (round 0) │  오케스트레이터의 목표 분석 및 작업 분배
 └───┬──────────────┘
     │
 ┌───▼──────────────────────────────────────┐
 │ 2. 라운드 루프 (1 .. max_rounds)          │
 │      발언자 결정 → 순차/병렬 발언 (도구 실행)│
 │      매 발언 사이에 사용자 정지·개입 확인   │
 └───┬──────────────────────────────────────┘
     │
 ┌───▼──────────────┐
 │ 3. 최종 합성      │  전체 맥락 종합 분석 → 코드 블록을 아티팩트로 추출
 └───┬──────────────┘
     │
 ┌───▼──────────────┐
 │ 4. 완료 판정      │  전원 합의 도달 여부(is_consensus_reached) 검증
 └──────────────────┘
```

## 입력 단계: @언급(Mention) 및 파일 업로드 (v0.8.0)

입력창에서 `@` 문자를 입력하면 자동완성 팝업이 활성화되어 이번 토론에 참여하는 전문가 에이전트, 사용할 수 있는(켜져 있는) 스킬, **해당 대화 세션의 작업 공간** 내 파일/폴더 목록이 이 순서로 표시됩니다.

| 키보드 조작 | 자동완성 팝업 활성화 시 동작 |
| :--- | :--- |
| ↑ / ↓ 방향키 | 추천 후보 목록 탐색 이동 |
| Enter · Tab | 선택한 후보 자동완성 적용 (메시지가 전송되지 않음) |
| Esc | 자동완성 팝업 닫기 (해당 `@` 위치에서는 다시 열리지 않음) |

선택 가능한 후보가 없는 일반 상태에서는 Enter 키 입력 시 메시지가 즉시 전송됩니다. 한국어 IME 조합 중의 Enter 키는 글자 조합 확정에 사용되므로 메시지가 의도치 않게 전송되지 않도록 IME 상태를 정확히 감지합니다.

메시지 전송 시(신규 턴 요청이든 토론 진행 중 개입 메모이든) `expand_mentions()` 함수가 텍스트 내의 `@` 언급을 해석하여 메시지 말미에 정형화된 `[@참조]` 블록을 자동으로 첨부합니다. 이때 **파일은 본문 내용이 아닌 상대 경로와 메타데이터만** 주입됩니다. 사용자 메시지는 모든 에이전트의 프롬프트 및 최종 합성에 매 라운드 반복 복사되므로, 파일 내용을 직접 포함시키면 입력 단계에서부터 컨텍스트 창이 조기 포화되기 때문입니다. PDF, 오피스 문서 등도 자유롭게 언급할 수 있으며, 실제 파일 내용을 읽고 파싱하는 작업은 해당 포맷을 지원하는 MCP 도구 서버가 담당합니다.

```text
@src/cache.py 그리고 @"System Architect" 끝

[@참조]
참조 파일 — 작업 공간: D:\work\proj
- src/cache.py (3 KB)
파일 내용은 붙이지 않았습니다. 필요하면 그 형식을 다루는 파일 도구로 이 경로를 직접 읽으세요.

지목한 전문가
- System Architect (Architecture)
사용자가 이 전문가를 직접 지정했습니다. 요청 중 이 전문가에게 해당하는 부분은 이 전문가가 맡아 답하게 하세요.
```

| 특수 상황 | 시스템의 처리 방식 |
| :--- | :--- |
| 작업 공간 외부 경로 (`..`, 절대 경로, 외부 심볼릭 링크 등) | 참조 목록에 포함하지 않고 보안 경고 알림 표시 |
| 디스크에 존재하지 않는 경로 | 참조 목록에서 제외하고 사용자 알림 표시 |
| 이번 세션에서 비활성화된 에이전트 | 참조 목록에서 제외하고 사용자 알림 표시 |
| 마크다운 코드 블록, 인라인 코드, 이메일 주소 내부의 `@` | 단순 텍스트로 인식하여 자동완성 및 치환 대상에서 제외 |
| 1MB 이상의 대용량 파일 | "필요한 부분만 읽으세요"라는 모델 주의 안내문 추가 |
| 꺼져 있거나 오류가 있는 스킬 | 자동완성 후보에 표시하지 않으며, 직접 입력한 경우 지정에서 제외하고 사용자 알림 표시 |
| 함께 언급한 전문가가 없는 스킬 | 지정하지 않고 사용자 알림 표시 (예: `@전문가 @스킬`) |
| 긴급 종료로 되돌아온 입력 텍스트 | 기존 참조 블록을 제거한 순수 원문으로 복원 (재전송 시 새로 생성) |

### 스킬 지정: `@전문가 @스킬` (v1.1.1)

전문가와 스킬을 함께 언급하면, 해당 전문가가 이번 턴에 그 스킬을 반드시 사용하도록 지정할 수 있습니다.

```text
@"System Architect" 는 @mermaid-diagrams 로 구조도를 그리고, @"Senior Python Engineer" 는 @csv-profile 로 요약해 주세요
```

- **짝짓기 규칙:** 스킬은 같은 줄에서 바로 앞에 언급한 전문가에게 지정됩니다. 앞에 전문가가 없으면 같은 줄에서 뒤에 오는 첫 전문가에게, 그 줄에 전문가가 전혀 없으면 앞 줄들 중 가장 가까운 전문가에게 지정됩니다.
- **이번 턴에만 적용됩니다.** 에이전트 설정의 `allowed_skills` 에 없는 스킬도 이번 턴에 한해 사용할 수 있으며, 대화에 고정된 에이전트 설정은 변경되지 않습니다. 다음 턴부터는 원래 설정으로 돌아갑니다.
- **앱이 스킬을 먼저 불러 둡니다.** 지정된 전문가가 발언할 때마다 첫 응답 전에 앱이 `skills__load_skill` 을 대신 호출하여 스킬 지침을 전달합니다. 채팅창에는 일반 도구 호출과 같은 접이식 카드로 표시됩니다.
- **스킬의 켜기·끄기 설정이 우선합니다.** 꺼져 있는 스킬은 지정할 수 없으며, 전송 후 꺼진 스킬은 해당 발언부터 불러오지 않습니다.
- 토론 진행 중 개입 메모에서 지정한 경우에는 남은 발언부터 적용됩니다. 서버 중단 등으로 끊긴 턴을 이어 가더라도 지정은 유지됩니다.

참조 블록에는 다음과 같이 지정 내역이 추가되어, 오케스트레이터가 해당 작업을 지정된 전문가에게 배정하도록 안내합니다. 설계 근거는 [ADR-027](../../../lectures/05-adr/ADR-027-designate-skills-from-the-input-bar.md)을 참고하십시오.

```text
지정한 스킬
- System Architect → mermaid-diagrams
- Senior Python Engineer → csv-profile
```

**전문가 에이전트 지목은 프롬프트 지침 텍스트를 통해서만 전달됩니다.** 오케스트레이터의 계획 수립, 발언자 동적 지명, 개별 에이전트 발언 시 이 참조 블록을 읽고 맥락에 반영하지만, 토론 전략이 정의한 물리적 발언 순서를 임의로 변경하지는 않습니다. 또한 오케스트레이터는 토론 진행자이므로 사용자 지목 대상에서 제외됩니다.

**파일 목록 캐싱 메커니즘**: 서버가 작업 공간 디렉터리를 스캔하여 입력어와 일치하는 상위 30개 항목만을 클라이언트로 전송합니다. `.git`, `node_modules`, Python 가상환경(`.venv`) 등 불필요한 디렉터리와 최상위 `.gitignore` 규칙(단순 규칙 기준)을 자동으로 건너뛰며, 최대 2만 개 파일에서 스캔을 중단하고 5초 동안만 결과를 메모리에 캐싱합니다. 이를 통해 토론 도중 에이전트가 새롭게 생성한 파일도 곧바로 자동완성 목록에 노출됩니다.

**작업 공간 파일 업로드 (입력창 좌측 버튼)**: 파일을 업로드하면 `<작업 공간>/uploads/` 디렉터리에 안전하게 저장되고 입력창에 자동으로 `@경로`가 삽입됩니다. 업로드 즉시 파일 목록 캐시가 초기화되므로 새로 업로드된 파일이 즉각 후보에 반영됩니다. 파일명의 경로 탐색 문자(`..`), 시스템 금지 문자, Windows 예약 파일명은 사전에 안전하게 필터링되며, 파일명 충돌 시 `파일명 (2).확장자` 형태로 자동 회피합니다. 단일 파일의 최대 업로드 용량은 100MB로 제한됩니다.

## 0. 준비 단계 (Turn Initialization)

```text
DebateRunner.start(session_id, prompt)
   │
   ├─ asyncio.Task 생성 (브라우저 연결과 무관하게 백그라운드에서 지속 실행)
   │
   └─ engine.run_turn()
        ├─ MCP 런타임 풀 대여   해당 대화 세션의 작업 폴더에 매핑된 서버 묶음 획득
        │                      (미기동 시 지연 기동, 가득 찬 경우 RuntimeCapacityError)
        │                      턴이 어떠한 형태로 종료되든 finally 블록에서 안전 반납
        ├─ 세션 데이터 로드     토론 전략, max_rounds, active_agents, 커스텀 지침
        ├─ 전략 식별자 정규화   레거시 전략 이름(free_debate 등)을 표준 이름으로 치환
        ├─ prepare_agents_for_turn()   ◀── 첫 턴 실행 시 페르소나 및 구성 스냅샷 영구 잠금
        └─ 이전 대화 기록 로드   누적 맥락 보존을 위한 메시지 이력 조회
```

사용자 메시지가 DB에 영구 기록되는 순간 해당 세션의 `personas_locked = True`로 전환되어 설정이 잠깁니다. 자세한 내용은 [세션 생애주기](02-session-lifecycle.md) 문서를 참고하십시오.

## 1. 계획 수립 (Planning, Round 0)

오케스트레이터 모델이 사용자의 초기 목표를 구조적으로 분해하고 각 전문가 에이전트에게 전달할 구체적인 발언 지침을 작성합니다.

효율적인 과업 분배를 위해 오케스트레이터에게 **이번 턴에 참여하는 활성 전문가 에이전트 목록**을 함께 전달합니다. 이때 에이전트의 표시 이름, 역할, 그리고 사용 가능한 MCP 도구 서버 목록만을 간결하게 제공하며 시스템 프롬프트 본문은 제외합니다 (에이전트당 수십~수백 토큰을 절약하기 위함입니다). 도구 서버 목록을 제공함으로써 오케스트레이터는 파일 쓰기 등 도구가 필요한 작업을 해당 권한을 가진 전문가에게 정확히 할당할 수 있습니다. 단, 단계적 사고(Sequential Thinking)는 모델 내부 추론 보조 도구이므로 업무 분배 목록에서 제외됩니다. 발언자 지명 및 과업 분배 API 호출 시에도 동일한 형식을 활용합니다.

**이전 대화 이력이 존재하는 경우**, 직전 턴의 최근 6개 발언을 250자 단위로 정밀 압축하여 프롬프트 맥락으로 함께 제공합니다:

```text
[이전 대화 맥락]:
System Architect(High-Level Architecture): 이벤트 소싱 대신 CRUD 로 시작하고...
Senior Python Engineer(Implementation): FastAPI 라우터를 도메인별로 나누되...

[신규 User Request]:
인증을 JWT 로 바꿔 주세요

[이번 토론 참여 전문가]
- System Architect (High-Level Architecture & Tech Stack) · 도구: 없음
- Senior Python Engineer (Implementation & Code Refinement) · 도구: filesystem

위의 이전 세션 논의 맥락과 새로운 사용자 요청을 종합 분석하여 이번 토론의 핵심 목표,
접근 방향, 각 전문가에게 부여할 발언 지침을 작성하세요. 위 전문가 각각에게, 목록의 이름
그대로 불러 이번 턴에 맡을 일과 산출물을 한두 문장으로 지시하세요. 도구가 필요한 일(파일
쓰기 등)은 그 도구를 가진 전문가에게 맡기고, 목록에 없는 역할에는 일을 주지 마세요.
```

네트워크 단절 등으로 에러로 기록된 발언(`msg_type == "error"`)은 계획 프롬프트 맥락에서 완전히 제외됩니다. 연결 실패 안내문은 실제 토론 내용이 아니기 때문입니다.

계획 발언이 완료되고 첫 번째 토론 라운드가 시작되기 직전 구간 역시 **사용자 개입 메모가 즉시 반영될 수 있는 안전한 지점**입니다.

## 2. 라운드 루프 (Round Loop)

```text
for round_num in 1..max_rounds:
    │
    ├─ 정지 요청 확인? ──▶ 루프 즉시 탈출 (stopped_early = True)
    │
    ├─ 발언자 결정
    │    · 일반 전략: 전략 규칙에 따라 결정론적 배정 (debate_priority 순 / 진영 교대)
    │    · orchestrator_led 전략: 오케스트레이터에게 다음 발언자 질의
    │         질의 실패 시 우선순위 순서로 안전 폴백하고 그 사실을 대화 피드에 기록
    │
    └─ for index, agent in speakers:
         │
         ├─ 정지 요청 확인? ──▶ 루프 즉시 탈출
         ├─ 개입 메모 확인? ──▶ 사용자 발언 형태로 입력 컨텍스트에 삽입
         │
         ├─ 컨텍스트 조립
         │    시스템 프롬프트 (에이전트 페르소나 + 사고 프로토콜 + 세션 커스텀 지침)
         │    + 지금까지의 누적 전사 (컨텍스트 제어 및 코드 블록 요약 반영)
         │    + 전략 인수인계 지침 (turn_instruction)
         │
         ├─ LLM 호출 (스트리밍 텍스트 생성)
         │    └─ 도구 호출 루프: tool_calls 발생 시 MCP 도구 실행 → 결과를 컨텍스트에 추가
         │                      최대 max_tool_iterations (기본 30회)
         │
         ├─ 호출 성공 시 → 발언을 DB에 저장하고 실시간 웹소켓 이벤트 발행
         │  호출 실패 시 → 연결 끊김 알림을 발언 위치에 기록하고 failed_agent_keys에 등록
         │
         └─ 도구 실행 이력을 DB에 저장 (message_id 외래키 바인딩)
```

### 발언 하나에 주입되는 인수인계 지침 (순차 토론 예시)

```text
[순차 토론] 바로 앞 순서인 System Architect(High-Level Architecture)의 발언을
입력으로 받아 이어가세요. 새 주제를 여는 대신, 그 결론이 옳은지 당신의 전문
영역에서 검증하고 필요한 부분을 보강하거나 반증하세요.
```

이러한 지침이 없으면 토론 라운드는 단순한 3개의 독백으로 전락하게 됩니다. 자세한 내용은 [토론 전략](../03-core/06-debate-strategies.md) 문서를 참고하십시오.

## 3. 최종 합성 (Synthesis)

```text
_build_synthesis_prompt(state, orchestrator)
   │
   │  전체 토론 전사 기록
   │  + 도구 실행 관측 결과
   │  + 발언하지 못한 에이전트 목록      ← 존재하지 않는 허구의 의견을 임의로 생성하지 않도록 방지
   │  + 조기 중단 여부                   ← 논의가 불완전한 상태임을 인지하도록 안내
   │
   │  컨텍스트 창 한도에 맞춰 정밀 축소하되 산출물 포맷 지시문은 반드시 보존
   ▼
오케스트레이터 LLM 호출
   ▼
_extract_artifacts_from_synthesis()
   │  ``` 마크다운 코드 블록 파싱
   │  언어 식별자(language) 기반 산출물 유형 판정
   ▼
ArtifactModel로 데이터베이스에 저장
```

| 코드 블록 language | 추출되는 artifact_type |
| :--- | :--- |
| `mermaid` | `mermaid` (아키텍처 및 플로우차트) |
| `python`, `py`, `typescript`, `javascript`, `bash`, `shell`, `json`, `toml`, `sql` | `code` (전문가 구현 소스 코드) |
| 그 외 식별자 또는 미지정 | `markdown` (종합 분석 보고서) |

합성 호출 자체가 외부 엔드포인트 장애로 실패할 경우, 잘못된 아티팩트를 임의 생성하지 않고 명시적인 실패 상태를 데이터베이스에 기록합니다.

## 4. 완료 판정 및 합의 검증

```python
state.is_consensus_reached = not state.failed_agent_keys and not state.stopped_early
```

**발언에 실패한 에이전트가 전혀 없고, 사용자가 도중에 중단하지도 않았을 때만** 정상적인 전원 합의로 인정합니다. 3명의 에이전트 중 2명이 침묵했음에도 '합의 도달'로 표시되는 심각한 신뢰도 훼손을 방지하기 위함입니다.

```python
if state.failed_agent_keys:
    state.error_message = ("다음 에이전트가 LLM 엔드포인트에 닿지 못했습니다: "
                           + ", ".join(state.failed_agent_keys))
```

### 최종 합성 도중 도착한 사용자 개입 처리 (`interjections_deferred`)

최종 합성 단계가 이미 시작된 이후에 도착한 사용자의 개입 메모는 현재 턴의 토론 맥락에 실시간으로 반영될 수 없습니다. 그렇다고 이 입력을 임의로 폐기하면 사용자는 다음 턴에 반영된다는 안내만 확인하고 메모 내용이 유실될 위험이 있습니다.
시스템은 이 개입 메모를 데이터베이스에 안전하게 보존해 두며(`interjections_deferred`), 사용자가 다음 턴을 시작할 때 초기 맥락으로 자동 로드하여 반영합니다.

## 실시간 웹소켓 이벤트 스트리밍

| 이벤트 식별자 | 발생 시점 및 의미 |
| :--- | :--- |
| `status_changed` | 상태 머신 상태 전환 시 (`planning` / `debating` / `synthesizing`) |
| `message_started` / `message_chunk` / `message_completed` | 에이전트 발언 텍스트 스트리밍 수신 및 완료 |
| `tool_call` | 에이전트의 MCP 도구 호출 실행 및 결과 반환 |
| `interjections_deferred` | 사용자의 개입 메모가 다음 턴으로 안전하게 이관됨 |
| `artifacts_synthesized` | 최종 아티팩트 파싱 및 생성 완료 |
| `turn_completed` | 턴 전체 종료 (실패한 에이전트 목록 및 진행 라운드 수 포함) |

이벤트 스트림은 `TurnRun`을 통해 **정본 스냅샷 메모리**(신규 접속 및 새로고침 브라우저가 즉시 복원하는 용도)와 **화면별 구독 큐**(각 클라이언트 브라우저로 실시간 푸시하는 용도)로 안전하게 분기되어 전달됩니다.

### 진행 중(In-progress) 시각적 피드백 체계

이벤트가 **발생하지 않는 유휴 구간**에 대한 처리가 매우 중요합니다. 모델이 첫 토큰을 생성하기까지 대기하는 시간, 또는 복잡한 MCP 도구 하나가 30초 이상 실행되는 동안 화면에는 아무런 텍스트 이벤트도 도달하지 않습니다. 사용자가 이 정적 상태를 '서버가 멈췄다'고 오인하여 브라우저를 새로고침하면 웹소켓 구독만 끊기게 됩니다 (백그라운드 토론은 정상 진행 중임에도 불구하고).

따라서 시스템은 3가지 시각적 인디케이터를 동시 활성화합니다:

| 표시 요소 | 배치 위치 | 설계 근거 |
| :--- | :--- | :--- |
| 상태 막대 맥동 애니메이션 | 피드 최상단 (스크롤과 무관하게 상시 고정) | 시스템이 유휴 대기 상태가 아님을 표시 |
| 진행 게이지 바 | 상태 막대 바로 하단 | 사용자의 주변 시야에서도 즉시 동작 인지 가능 |
| 생성 상태 텍스트 + **경과 초 카운터** | 입력창 바로 위 | 사용자의 시선이 집중되는 영역 |

경과 시간 표시는 서버 이벤트가 아니라 **프론트엔드 자체 1초 타이머**가 계산합니다. 서버로부터 이벤트가 오지 않는 침묵 구간에서도 초 단위 숫자가 계속 올라가야 사용자가 프로세스가 정상 동작 중임을 인지할 수 있기 때문입니다. 발언자가 전환되면 타이머는 0초부터 다시 카운트하여 '현재 발언자가 얼마나 오랫동안 작업을 수행 중인가'를 명확히 보여줍니다.

### 스트리밍 자동 스크롤 제어 규칙

사용자가 자동 스크롤 추적을 일시 해제하는 조건은 두 가지입니다:

| 사용자 조작 신호 | 조작의 의미 | 자동 스크롤 재개 방법 |
| :--- | :--- | :--- |
| 이전 발언 카드를 **직접 펼침** | "현재 이 발언 내용을 정독하고 있음" | 해당 카드를 다시 접기 |
| 마우스 휠 또는 터치로 **스크롤 조작** | "화면의 특정 위치를 직접 탐색하고 있음" | 화면 우측 하단의 `맨 아래로 · 따라가기 재개` 버튼 클릭 |

마우스 휠 스크롤은 **회전 방향을 따지지 않습니다.** 아래로 휠을 굴리는 것 역시 사용자가 화면 영역을 직접 탐색하겠다는 명시적 의사 표현이며, 아래쪽 스크롤 시 자동 스크롤을 섣불리 재부착하면 최하단 부근에서 스크롤이 끊임없이 진동하는 버그가 발생합니다. 스크롤 절대 위치를 기준으로 판단하지 않는 이유도 동일합니다. 텍스트 청크 수신 시 화면을 아래로 밀어내는 주체가 자동 스크롤 자체이므로, 위치 기반 판단은 스크롤 부착과 해제를 무한 반복하게 만듭니다.

자동 스크롤이 멈춰 있는 동안에는 상태 바 버튼에 일시 정지 사유와 복귀 방법이 친절하게 안내됩니다. 해당 버튼은 스크롤 고정만 해제할 뿐, 사용자가 직접 펼쳐 둔 카드를 강제로 접지 않습니다.

> [!NOTE]
> 자동 스크롤 추적 시에는 **정확히 화면 최하단 바닥까지** 이동합니다. 과거에는 Quasar UI 프레임워크가 캐시한 컨테이너 높이로 퍼센트를 환산하여 방금 수신된 글자 높이(200px 이상)만큼 덜 이동하여 마지막 카드가 잘리는 현상이 있었습니다. 현재는 충분한 픽셀 단위로 스크롤을 명령하여 브라우저가 바닥에서 안전하게 잘라내도록 처리하며, 화면 렌더링 배치가 끝난 직후 미세 오차를 한 번 더 재보정합니다.

## 토론 도중 사용자 개입 및 정지 제어

| 조작 기능 | 실행 결과 및 상태 |
| :--- | :--- |
| **정지 (Stop)** | 진행 중인 현재 발언은 끝까지 완료한 뒤, 남은 라운드를 안전하게 건너뛰고 **최종 합성 단계로 진입**합니다. 그때까지의 토론을 기반으로 정상 산출물이 도출됩니다. |
| **개입 메모 (Note)** | 다음 발언자의 입력 컨텍스트에 사용자 발언 메시지 형태로 자연스럽게 삽입됩니다. |
| **긴급 종료 (Emergency Stop)** | 발언 생성 중이라도 즉시 프로세스를 강제 중단하고, **이번 턴에서 생성된 모든 데이터(발언, 도구 기록, 산출물)를 DB에서 롤백하여 완전히 삭제**합니다. 보낸 입력 텍스트는 입력창으로 안전하게 복원됩니다. |
| **태스크 취소 (`cancel()`)** | asyncio 백그라운드 태스크를 직접 강제 종료합니다. 최종 합성이 실행되지 않아 산출물이 생성되지 않습니다 (내부 예외 처리용). |

정지 요청이 태스크 취소보다 훨씬 유용한 이유가 여기에 있습니다.

### 정지(Stop)와 긴급 종료(Emergency Stop)의 차이점

두 기능 모두 토론을 즉시 멈추지만, **목적과 데이터 처리 방식**이 근본적으로 다릅니다:

| 비교 항목 | 일반 정지 (Stop) | 긴급 종료 (Emergency Stop) |
| :--- | :--- | :--- |
| 사용 전제 | "지금까지의 논의로 충분하니 여기서 마무리하자" | **"초기 요청이나 전제 자체가 완전히 틀렸다"** |
| 진행 중인 에이전트 발언 | 끝까지 정상 완료 대기 | 즉시 강제 중단 |
| 최종 합성 단계 | **정상적으로 실행함** | 실행하지 않음 |
| 데이터베이스 기록 | 그때까지의 모든 발언과 도구 기록 보존 | 이번 턴이 생성한 모든 발언·도구 이력·산출물을 **완전 삭제** |
| 전송했던 사용자 입력 | 대화 피드에 그대로 유지됨 | **입력창으로 원문 복원** (수정 후 재전송 가능) |

긴급 종료를 통해 첫 번째 요청을 완전히 취소하여 대화 세션이 빈 상태가 되면, 해당 세션은 **토론 시작 전 상태로 완벽히 복원**됩니다. 즉, 페르소나 잠금이 해제되어 에이전트 목록과 시스템 프롬프트를 다시 자유롭게 편집할 수 있습니다. 기존에 기록되었던 스냅샷은 정리되며, 차후 새로운 첫 메시지가 전송될 때 당시의 `conf.json` 설정을 기반으로 신규 스냅샷이 생성됩니다.

> [!CAUTION]
> 긴급 종료는 데이터베이스에서 실행 이력을 영구 삭제하는 비가역적 작업이므로 반드시 사용자 확인 대화상자를 거칩니다. 단, 삭제 범위는 **해당 턴에서 생성된 데이터에만 국한**되며 이전 턴에서 완료된 과거 대화 기록은 완벽히 안전하게 보존됩니다.
