# 4-7. 실패를 설계하기

> 상위: [4강. 핵심 기술](README.md) · 이전: [4-6. 영속화](06-persistence.md) · 다음: [5강. 아키텍처 결정 기록](../05-adr/README.md)

앞의 여섯 절에서 계속 같은 질문이 나왔습니다. "이게 실패하면 어떻게 되지?" 이 절은 그 답들을 한데 모아
원칙으로 정리합니다. 멀티 에이전트 시스템은 외부 의존이 많습니다. LLM 엔드포인트, 도구 서버 프로세스,
파일 시스템, 브라우저 연결 중 무엇이든 언제든 실패합니다. 실패를 없앨 수는 없으니, 실패가 어디까지 번지고
무엇을 남기는지를 설계해야 합니다.

---

## 1. 한 문장짜리 원칙

> 도구 실패는 에이전트가 읽고 고칠 **관찰 결과**다. 발언, 토론, 프로세스를 끝낼 이유가 아니다.
> 유일한 예외는 취소다. 취소는 실패가 아니라 **명령**이고, 언제나 전파되어야 한다.

이 문장이 v0.5.0에서 정리되기 전까지, 도구 오류 하나가 발언하던 에이전트를 죽이고, 가끔은 백엔드 전체를
죽였습니다. 방어가 한 겹뿐이었고 그 한 겹에 구멍이 두 개 있었습니다.

## 2. 파이썬 예외 계층과 두 개의 구멍

이 사고를 이해하려면 파이썬 예외 계층을 조금 알아야 합니다.

```text
BaseException
 ├─ Exception                  대부분의 "오류"
 │   └─ ...
 ├─ asyncio.CancelledError     취소 신호 (파이썬 3.8부터 Exception이 아님)
 ├─ KeyboardInterrupt
 ├─ SystemExit
 └─ BaseExceptionGroup         여러 예외를 묶은 것 (3.11)
     └─ ExceptionGroup         Exception만 묶은 경우
```

anyio나 `asyncio.TaskGroup`처럼 여러 태스크를 한꺼번에 관리하는 구조는, 안에서 난 예외들을 **예외 그룹**으로
묶어서 올립니다. MCP SDK의 stdio 연결이 바로 이 구조 위에 있습니다.

**구멍 1: `except Exception`은 `BaseExceptionGroup`을 잡지 못한다.** 묶인 예외 중 하나라도 `Exception`이 아니면
그룹 전체가 `BaseExceptionGroup`이 되고, `except Exception`을 그대로 통과합니다. 이 예외가 MCP 매니저, 엔진의
발언 처리, 토론 실행기를 차례로 뚫고 올라가 토론 태스크를 죽였습니다. 화면은 "토론 중..."에 영원히 멈춰 있었습니다.

**구멍 2: `except BaseException`은 취소를 삼킨다.** 반대로 넓게 잡은 곳에서는 취소 신호까지 잡아서 삼켰습니다.
취소가 아무 일도 하지 않으니, 앱 종료 시 실행기는 영원히 끝나지 않는 태스크를 기다렸고, 수명 관리 코드가
멈췄고, Uvicorn이 강제 종료되었습니다. 겉으로는 서버가 죽은 것과 똑같아 보였습니다.

두 구멍은 방향이 반대입니다. 하나는 너무 좁게 잡아서, 하나는 너무 넓게 잡아서 생겼습니다. 올바른 경계는
이런 모양입니다.

```python
# 개념 예시: 실패를 결과로 바꾸는 경계
try:
    result = await call_tool(...)
    return result, "success"
except asyncio.CancelledError:
    raise                        # 취소는 명령이다. 반드시 다시 올린다
except BaseException as exc:     # 예외 그룹까지 포함해 나머지는 모두 결과로
    return describe(exc), "error"
```

`except BaseException`은 `KeyboardInterrupt`나 `SystemExit`도 잡는다는 점에 주의하세요. 이 패턴은 "여기서
무슨 일이 나도 위층을 죽이지 않는다"가 확실히 필요한 **경계 지점**에만 씁니다. 코드 곳곳에 뿌리면 오히려
문제를 숨깁니다.

## 3. 여러 겹의 경계

원칙을 한 곳에만 두면, 그 한 곳이 바뀌거나 우회될 때 무너집니다. MADO는 같은 규칙을 여러 층에서 다시
지킵니다.

| 층 | 보장하는 것 |
| :--- | :--- |
| MCP 매니저 | **첫 번째 경계.** 무슨 일이 나도 "오류 결과"를 돌려줍니다. 취소만 다시 올립니다 |
| LLM 호출기의 도구 실행 | 같은 규칙을 한 번 더. 매니저가 테스트 대역으로 바뀌었거나, 도구 조회 자체가 예외를 던져도 |
| LLM 호출기의 호출 해석 | 깨진 도구 호출(객체나 딕셔너리 모양, 깨진 인자 JSON, 빠진 호출 ID)을 흡수. 빈 호출 ID는 **다음** 요청을 400으로 만듭니다 |
| LLM 호출기의 화면 알림 | 화면 콜백이 죽어도, 실제로 실행된 도구의 관찰 결과는 버리지 않습니다 |
| 엔진의 발언 처리 | 발언 하나가 실패하면 실패 발언으로 기록하고 다른 에이전트는 계속. DB 커밋 실패는 롤백해 세션을 망가진 채로 두지 않습니다 |
| 토론 실행기 | 예외 그룹도 "실패"로 보고하고 조용히 죽지 않습니다. 취소는 최대 20초까지만 기다립니다 |
| 앱 진입점 | 이벤트 루프와 스레드의 처리되지 않은 예외를 기록합니다. MCP 초기화가 실패해도 앱은 뜹니다 |

"같은 규칙을 왜 여러 번?"이라는 질문이 나올 만합니다. 각 층은 **바로 아래 층이 그 규칙을 지킨다고 가정하지
않습니다.** 아래 층은 바뀔 수 있고, 테스트에서는 가짜로 대체되고, 예상하지 못한 경로로 예외를 낼 수 있습니다.
경계를 겹으로 두는 비용은 코드 몇 줄이고, 한 겹이 뚫렸을 때의 비용은 토론 전체입니다.

## 4. 정직한 실패

실패를 잡는 것만큼 중요한 것이 **실패를 실패라고 말하는 것**입니다. MADO에서 가장 오래 살아남은 원칙이
"없는 것을 지어내지 않는다"입니다.

### 흉내 내지 않는다

초기의 시뮬레이터는 엔드포인트에 닿지 못하면 페르소나에 맞춘 그럴듯한 답을 만들어 냈습니다. 엔드포인트가
500을 돌려줘도 토론은 성공한 것처럼 보였고, 지어낸 발언은 다음 에이전트의 입력이 되고 최종 합성 보고서에까지
들어갔습니다. 시뮬레이터를 없애고, 연결 실패는 "응답 없음"으로 기록합니다
([ADR-007](../05-adr/ADR-007-no-simulated-answers.md)).

### 물러섰으면 물러섰다고 적는다

| 대체 경로 | 기록하는 것 |
| :--- | :--- |
| 발언자 지명 실패 → 우선순위 순서 | "지명에 실패해 우선순위 순서로 진행" |
| 과업 분배 실패 → 과업 없이 전원 동시 실행 | 같은 방식으로 기록 |
| 게이트 판정 형식 오류 → 기본 분기 | 판정 메모에 그 사실 |
| 지식 그래프 인계 실패 | 인수인계 노트에 "없는 기억을 있다고 가정하지 마세요" |
| 합성 빈 응답 → 전문가 발언 모음 | "합성 실패"라는 제목, 합의 아님 |
| 응답 한도에서 잘림 | 발언 끝에 잘림 안내와 무엇을 늘려야 하는지 |
| 다이어그램 수리 실패 | 제목 앞의 ⚠ |

대체 경로는 좋은 설계입니다. **조용한** 대체 경로는 나쁜 설계입니다. 사용자는 화면에 보이는 것을 시스템이
의도한 결과로 믿기 때문입니다.

### 상태 값은 사람을 위한 것이다

초기 버전에서 도구 실행이 실패하면 오류 문구를 "성공" 상태로 감싸 에이전트에게 넘겼습니다. 모델은 문구를
읽을 수 있으니 기능은 거의 같았지만, 화면과 DB의 상태 표시는 모두 초록색이었습니다. 모델에게 전달되는
내용과 사람에게 보이는 상태는 별개의 정보이고, 둘 다 정확해야 합니다.

## 5. 결과물을 지킨다

실패가 나도 그때까지 만든 것은 지킵니다. 이 원칙이 곳곳에 같은 모양으로 나타납니다.

| 상황 | 지키는 것 |
| :--- | :--- |
| 도구 예산 소진 | 스트리밍으로 나온 글과 실행된 도구 기록. 사용자에게 확장을 묻고, 아니면 도구 없이 결론을 쓰게 함 |
| LLM 연결이 도중에 끊김 | 끊기기 전까지 도착한 글을 실패 안내 위에 보존 |
| 이어 쓰기 호출 실패 | 이미 받은 글 |
| 다이어그램 수리 등 후처리 실패 | 원래 본문 |
| DB 기록 실패 | 파일로 보존하고 알림 |
| 브라우저 연결 끊김 | 토론 자체. 새로고침한 화면이 다시 붙음 |

공통된 문장으로 줄이면 이렇습니다. **복구를 시도하다 실패하더라도, 복구하려던 대상을 잃으면 안 된다.**

## 6. 사람이 원인을 찾을 수 있게

실패를 잡아서 기록하는 것으로 끝이 아닙니다. 기록이 원인을 가리켜야 합니다.

- **표준 오류 요약.** 도구 서버 기동 실패는 "태스크 그룹에서 처리되지 않은 오류" 같은 무의미한 예외로
  올라옵니다. 진짜 원인은 자식 프로세스의 표준 오류에 있으므로 앞 4줄과 뒤 8줄을 보관해 상태 칩에 보여 줍니다.
- **요청 지문.** 엔드포인트가 이유를 숨기면, 우리가 보낸 요청의 모양(역할 순서, 토큰 대 예산, 도구 수, 가장
  큰 메시지)을 크기로만 남깁니다(4-2 참고).
- **예산 사용 내역.** 응답이 한도에 닿으면 본문, 추론, 인자, 프롬프트가 각각 얼마를 썼는지 남깁니다.
- **오류 메시지에 예외 타입을 넣는다.** 어떤 예외는 메시지가 비어 있습니다. 타입 이름이라도 있어야 검색할 수
  있습니다.
- **로그에는 크기만, 내용은 남기지 않는다.** 진단에 필요한 것은 양이고, 소스 코드나 대화 내용이 로그로
  새면 안 됩니다.
- **한 번만 경고하는 경고를 오염시키지 않는다.** 화면 프레임워크의 "삭제된 클라이언트를 아직 쓰고 있다"
  경고는 프로세스당 한 번만 뜹니다. 사라진 페이지에 사이드바를 그리던 무해한 버그가 이 경고를 먼저 써
  버리면, 다음번의 진짜 버그는 경고 없이 지나갑니다. 무해해 보여도 고칩니다.

## 7. 조용한 실패 찾기

이 프로젝트에서 가장 비쌌던 버그들은 오류를 내지 않았습니다. 목록으로 모으면 공통점이 보입니다.

| 증상 | 실제 원인 | 왜 조용했나 |
| :--- | :--- | :--- |
| 샌드박스 변수가 다음 호출에서 사라짐 | 호출마다 서버 프로세스를 새로 띄움 | 서버는 "재사용한다"고 응답했습니다 |
| 에이전트가 쓴 파일을 샌드박스가 못 찾음 | 같은 상대 경로를 두 프로세스가 각자 다르게 해석 | 두 서버 모두 정상 동작했습니다 |
| 다음 대화가 이전 대화의 기억을 앎 | 기억 서버가 프로세스 단위로 그래프 하나 | 기능은 정상이었고 결과만 틀렸습니다 |
| 긴 대화에서 사용자 지시를 어김 | 오래된 순서로 메시지 삭제 | 로그에 경고 한 줄 |
| 파일 시스템 서버가 허용 폴더 없이 뜸 | Windows 확장 길이 경로를 URI로 바꾸며 깨짐 | "초기 요청 실패" 로그 한 줄 |
| 테스트가 개발자 DB에 대화를 씀 | 싱글턴 엔진의 기본 경로 | 테스트는 모두 통과했습니다 |
| 잘린 도구 호출이 반복됨 | 해석 못 한 인자를 그대로 되돌려 보냄 | 게이트웨이가 400을 500으로 감싸 이유를 버렸습니다 |

이런 버그를 찾는 데 도움이 된 습관들입니다.

1. **"성공"이라는 응답을 믿지 말고 결과를 확인한다.** 서버가 재사용한다고 하면, 정말 두 번째 호출에서 변수가
   있는지 봅니다.
2. **같은 설정이 여러 프로세스에 전달되면, 각 프로세스가 실제로 받은 값을 확인한다.**
3. **실제 환경에서 확인한다.** 연속 `user` 메시지 거부, 도구 정의 없는 도구 기록 거부는 OpenAI에서는 재현되지
   않았습니다. Windows 경로 문제는 Windows에서만 났습니다.
4. **재현 테스트를 먼저 만든다.** 사용자 지시를 잊는 문제는 "8k 창, 턴1 제약, 턴2 세 라운드"라는 재현 테스트로
   고정한 뒤에 고쳤고, 고친 방법(고정 기능)을 끄면 테스트가 다시 실패하는 것까지 확인했습니다.
5. **진단 도구를 먼저 만든다.** 요청 지문은 만들자마자 다음 장애의 원인을 한 줄로 짚었습니다.

## 정리

- 실패는 관찰 결과로 바꾸고, 취소만은 반드시 전파합니다.
- `except Exception`은 예외 그룹을 놓치고, `except BaseException`은 취소를 삼킵니다. 경계 지점에서 둘을 모두
  고려합니다.
- 같은 규칙을 여러 층에서 다시 지킵니다. 각 층은 아래 층을 믿지 않습니다.
- 대체 경로는 좋지만 조용한 대체 경로는 나쁩니다.
- 복구를 시도하다 실패해도 복구 대상을 잃지 않습니다.
- 기록은 원인을 가리켜야 하고, 크기만 남기고 내용은 남기지 않습니다.
- 가장 비싼 버그는 조용합니다. 성공 응답을 믿지 말고 결과를 확인합니다.

## 생각해 볼 문제

1. 여러분의 프로젝트에서 `except Exception:`이 있는 곳을 하나 골라, 그 안에서 `BaseExceptionGroup`이나
   `CancelledError`가 날 수 있는지 따져 보세요.
2. "조용한 대체 경로"를 금지하면 로그와 화면이 안내 문구로 시끄러워질 수 있습니다. 알려야 할 대체와 알리지
   않아도 될 대체를 가르는 기준을 세워 보세요.
3. 7절의 표에 여러분이 겪은 조용한 실패를 하나 추가해 보세요. 그 실패를 더 일찍 알아챌 수 있었던 신호는
   무엇이었나요?
