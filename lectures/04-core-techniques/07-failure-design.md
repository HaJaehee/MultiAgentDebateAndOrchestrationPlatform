# 4-7. 실패를 설계하기

> 상위: [4강. 핵심 기술](README.md) · 이전: [4-6. 영속화](06-persistence.md) · 다음: [5강. 아키텍처 결정 기록](../05-adr/README.md)

앞의 여섯 절에서 계속 같은 질문이 나왔습니다. "이 작업이 실패하면 어떻게 되는가?" 이 절에서는 그에 대한 답들을 한데 모아 아키텍처 원칙으로 정립합니다. 멀티 에이전트 시스템은 수많은 외부 요소에 의존합니다. LLM 엔드포인트, 도구 서버 프로세스, 파일 시스템, 브라우저 웹소켓 연결 중 어느 것이든 언제라도 실패할 수 있습니다. 시스템 운영 중 실패를 원천 차단할 수는 없으므로, 실패의 전파 범위를 어디까지로 제한하고 어떤 기록을 보존할 것인지를 정밀하게 설계해야 합니다.

---

## 1. 한 문장짜리 원칙

> 도구 실패는 에이전트가 읽고 스스로 수정해야 할 **관찰 결과**입니다. 발언, 토론 세션, 백엔드 프로세스를 중단시킬 이유가 아닙니다.
> 유일한 예외는 취소입니다. 취소는 오류가 아니라 사용자의 **명령**이므로, 언제나 상위로 즉시 전파되어야 합니다.

이 원칙이 v0.5.0에서 명문화되기 전까지는, 단 하나의 도구 실행 오류가 발언 중이던 에이전트를 중단시키고 심한 경우 백엔드 프로세스 전체를 비정상 종료시켰습니다. 방어 계층이 단 한 겹에 불과했던 데다, 그 한 겹의 방어막에도 치명적인 구멍이 두 개 존재했기 때문입니다.

## 2. 파이썬 예외 계층과 두 개의 구멍

이 문제를 정확히 이해하려면 파이썬의 예외 계층 구조를 살펴볼 필요가 있습니다.

```text
BaseException
 ├─ Exception                  대부분의 표준 "오류"
 │   └─ ...
 ├─ asyncio.CancelledError     비동기 취소 신호 (파이썬 3.8부터 Exception 상속 해제)
 ├─ KeyboardInterrupt          키보드 인터럽트
 ├─ SystemExit                 프로세스 종료 신호
 └─ BaseExceptionGroup         복수 예외를 묶은 그룹 (파이썬 3.11 도입)
     └─ ExceptionGroup         Exception 인스턴스만 묶인 경우
```

anyio 라이브러리나 `asyncio.TaskGroup`과 같이 여러 비동기 태스크를 동시에 총괄하는 런타임 구조는 내부에서 발생한 예외들을 **예외 그룹(ExceptionGroup)** 형태로 취합하여 상위로 전달합니다. MCP SDK의 stdio 클라이언트 연결 역시 바로 이 구조 위에서 구동됩니다.

**구멍 1: `except Exception`은 `BaseExceptionGroup`을 포착하지 못합니다.** 취합된 예외 중 단 하나라도 `Exception`이 아닌 예외(예: 하위 태스크의 취소 등)가 포함되어 있으면 그룹 전체가 `BaseExceptionGroup` 타입이 되며, 이는 일반적인 `except Exception` 블록을 그대로 통과합니다. 초기 시스템에서는 이 미처리 예외가 MCP 매니저, 엔진의 발언 처리기, 토론 실행기 계층을 차례로 관통하여 백그라운드 토론 태스크 자체를 강제 종료시켰습니다. 그 결과 프론트엔드 화면은 "토론 진행 중..." 상태에 영구히 멈춰 버렸습니다.

**구멍 2: `except BaseException`은 취소 신호까지 삼켜버립니다.** 반대로 예외를 지나치게 포괄적으로 잡았던 계층에서는 취소 신호(`CancelledError`)까지 정상 오류로 흡수해 버렸습니다. 취소 신호가 상위 태스크에 도달하지 못하자, 애플리케이션 종료 시 실행기는 영원히 끝나지 않는 백그라운드 작업을 무한정 대기했고, 수명 주기 관리 코드가 멈추면서 결국 Uvicorn 프로세스가 타임아웃으로 강제 종료되었습니다. 외부에서 볼 때는 서버 프로세스가 비정상 크래시된 것과 완전히 동일한 증상이었습니다.

이 두 구멍은 문제의 방향이 정반대였습니다. 하나는 예외 범위를 너무 좁게 잡아서 발생했고, 다른 하나는 너무 넓게 잡아서 발생했습니다. 시스템 경계 계층에서 채택해야 하는 올바른 예외 처리 패턴은 다음과 같습니다.

```python
# 개념 예시: 실패를 결과로 변환하는 경계 계층
try:
    result = await call_tool(...)
    return result, "success"
except asyncio.CancelledError:
    raise                        # 취소는 명령이므로 반드시 상위로 다시 전달합니다
except BaseException as exc:     # 예외 그룹을 포함한 기타 모든 실패는 관찰 결과로 변환합니다
    return describe(exc), "error"
```

`except BaseException`은 `KeyboardInterrupt`나 `SystemExit`와 같은 치명적 런타임 신호까지 흡수한다는 점을 유념해야 합니다. 따라서 이 패턴은 "이 하위 작업에서 어떤 비정상 상황이 발생하더라도 상위 오케스트레이션 엔진을 중단시키지 않는다"는 격리가 반드시 요구되는 **시스템 경계 지점**에만 제한적으로 사용해야 합니다. 코드 전반에 남용할 경우 오히려 심각한 버그를 은폐하는 부작용을 초래합니다.

## 3. 여러 겹의 경계

실패 방어 원칙을 단 한 곳에만 의존하면, 해당 모듈이 리팩터링되거나 우회 호출될 때 전체 시스템이 무너집니다. MADO는 동일한 방어 규칙을 여러 계층에 걸쳐 중첩하여 적용합니다.

| 계층 | 보장하는 불변식 |
| :--- | :--- |
| MCP 매니저 | **첫 번째 경계.** 어떤 예외가 발생하더라도 "오류 관찰 결과"를 반환하며, 취소 신호만을 상위로 전파합니다. |
| LLM 호출기의 도구 실행부 | 동일한 방어 규칙을 재적용합니다. 매니저가 테스트 대역으로 교체되었거나, 도구 메타데이터 조회 자체가 실패하더라도 안전하게 보호합니다. |
| LLM 호출기의 호출 해석부 | 비정상적인 도구 호출 형식(객체/딕셔너리 혼용, 손상된 인자 JSON, 누락된 호출 ID)을 흡수합니다. 빈 호출 ID가 누락되면 **다음** API 요청 시 400 Bad Request가 발생하기 때문입니다. |
| LLM 호출기의 화면 알림부 | UI 스트리밍 콜백이 실패하더라도, 정상 실행 완료된 도구의 실제 관찰 결과는 절대 유실하지 않습니다. |
| 엔진의 발언 처리부 | 특정 에이전트의 단일 발언이 실패하면 해당 발언만을 '실패' 상태로 기록하고 다른 에이전트의 토론은 정상 진행합니다. DB 커밋 실패 시 즉시 롤백하여 세션 데이터의 정합성을 보호합니다. |
| 토론 실행기 | 복합 예외 그룹이 발생하더라도 "토론 실패" 상태를 정상 보고하며 무응답 상태로 멈추지 않습니다. 취소 요청 시 최대 20초까지만 대기합니다. |
| 애플리케이션 진입점 | 비동기 이벤트 루프와 워커 스레드의 미처리 예외를 최종 로깅합니다. MCP 초기화가 일부 실패하더라도 메인 웹 서버는 안전하게 기동합니다. |

"동일한 방어 규칙을 왜 여러 계층에서 중복 검증하는가?"라는 의문이 들 수 있습니다. 각 계층은 **바로 아래 하위 계층이 규약을 완벽히 준수할 것이라고 전제하지 않기 때문입니다.** 하위 계층은 버전 업데이트로 변경될 수 있고, 단위 테스트 환경에서 모의 객체(Mock)로 대체될 수 있으며, 예측 불가능한 경로로 예외를 분출할 수 있습니다. 방어 경계를 다중화하는 데 드는 비용은 몇 줄의 방어 코드에 불과하지만, 방어막 하나가 뚫렸을 때 치러야 할 비용은 전체 토론의 실패입니다.

## 4. 정직한 실패

실패를 안전하게 포착하는 것 못지않게 중요한 것은 **실패를 실패라고 사용자에게 정직하게 밝히는 것**입니다. MADO 아키텍처에서 가장 오랫동안 견지되어 온 대원칙은 "존재하지 않는 가짜 결과를 지어내지 않는다"입니다.

### 흉내 내지 않는다

초기 버전의 시뮬레이터는 LLM 엔드포인트에 접속할 수 없으면 사전 정의된 페르소나를 기반으로 그럴듯한 답변을 임의로 생성했습니다. 그 결과 엔드포인트가 500 오류를 반환하더라도 토론 세션은 겉보기에 성공한 것처럼 위장되었고, 임의로 꾸며낸 허위 발언이 다른 에이전트들의 참조 입력이 되어 최종 종합 보고서에까지 반영되는 치명적인 데이터 오염이 발생했습니다. 이에 따라 시뮬레이션 폴백을 전면 폐기하고, 연결 단절 시 "응답 없음" 상태를 솔직히 기록하도록 개편했습니다 ([ADR-007](../05-adr/ADR-007-no-simulated-answers.md)).

### 물러섰으면 물러섰다고 적는다

대체 경로(Fallback)가 동작했다면 그 사실을 시스템 상태에 명확히 기록해야 합니다.

| 대체 경로 동작 상황 | 명시적으로 기록하는 내용 |
| :--- | :--- |
| 발언자 동적 지명 실패 → 우선순위 큐 적용 | "발언자 지명 실패로 우선순위 순서에 따라 발언을 배정함" 명시 |
| 과업 분배 실패 → 사전 분배 없이 전원 동시 투입 | 동일한 방식으로 사유와 분기 사실 기록 |
| 품질 게이트 판정 파싱 오류 → 보수적 기본 분기 선택 | 평가 메모에 파싱 실패 및 기본값 채택 사실 기록 |
| 지식 그래프 컨텍스트 인계 실패 | 에이전트 세션 인계 메모에 "연결된 기억이 없으므로 임의로 추정하지 마십시오" 명시 |
| 종합 단계 빈 응답 발생 → 전문가 발언 발췌본 제시 | 합의 도출본이 아니며 "종합 실패에 따른 발췌본"임을 명시 |
| 응답 토큰 한도 도달로 인한 텍스트 잘림(Truncation) | 발언 말미에 잘림 사실과 권장 토큰 증액 수치 표시 |
| 다이어그램 문법 자동 복구 실패 | 다이어그램 제목 앞에 경고 기호(⚠) 표기 |

대체 경로를 준비하는 것은 견고한 설계이지만, 사용자 모르게 슬그머니 작동하는 **조용한 대체 경로**는 위험한 설계입니다. 사용자는 화면에 표시되는 모든 산출물을 시스템이 정상적으로 의도한 올바른 결과물로 신뢰하기 때문입니다.

### 상태 값은 사람을 위한 것이다

초기 버전에서는 도구 호출이 실패했을 때 오류 메시지를 "성공(success)" 상태 태그로 감싸서 에이전트에게 주입했습니다. 모델 자체는 오류 텍스트를 읽고 후속 판단을 내릴 수 있었기에 표면적인 기능은 동작했으나, 관리자 화면과 데이터베이스의 상태 지표는 온통 정상(초록색)으로 왜곡되었습니다. 모델에게 전달되는 관찰 텍스트와 사람이 모니터링하는 실행 상태 값은 명백히 분리된 정보이며, 두 영역 모두 정확한 사실을 반영해야 합니다.

## 5. 결과물을 지킨다

실패가 발생하더라도 그 시점까지 산출된 유효한 데이터는 반드시 보존해야 합니다. 이 원칙은 시스템 전반에 걸쳐 일관되게 구현되어 있습니다.

| 장애 발생 상황 | 안전하게 보존하는 대상 |
| :--- | :--- |
| 도구 호출 예산 소진 | 스트리밍을 통해 수신된 텍스트 본문과 실행 완료된 도구 호출 기록 (이후 사용자에게 추가 실행 승인을 요청하거나, 추가 도구 호출 없이 결론 작성을 유도) |
| LLM 네트워크 연결 중도 단절 | 단절 직전까지 수신된 텍스트 블록 전체를 보존하고, 그 상단에 통신 실패 경고 표기 |
| 이어 쓰기(Continuation) 요청 실패 | 앞선 단계에서 성공적으로 수신한 기존 텍스트 본문 |
| 다이어그램 문법 복구 등 후처리 작업 실패 | 복구 시도 이전의 원본 텍스트 본문 |
| 데이터베이스 트랜잭션 기록 실패 | 로컬 비상 백업 파일로 보존하고 관리자에게 알림 전송 |
| 클라이언트 브라우저 웹소켓 단절 | 백그라운드 토론 프로세스 자체 (브라우저를 새로고침하면 기존 세션에 즉시 재연결) |

이 원칙을 한 문장으로 요약하면 다음과 같습니다. **복구를 시도하다가 2차 실패를 겪더라도, 복구하려 했던 원본 산출물을 결코 유실해서는 안 됩니다.**

## 6. 사람이 원인을 찾을 수 있게

실패를 포착하여 데이터베이스에 기록하는 것만으로는 충분하지 않습니다. 남겨진 기록이 장애의 근본 원인을 정확히 가리키고 있어야 합니다.

- **표준 오류(stderr) 요약**: MCP 도구 서버 기동 실패는 흔히 "태스크 그룹 미처리 오류"와 같은 추상적인 예외로 보고됩니다. 실제 원인은 자식 프로세스의 표준 오류 스트림에 담겨 있으므로, 시작 부분 4줄과 끝부분 8줄을 추출하여 UI 상태 칩에 함께 표시합니다.
- **요청 핑거프린트(Request Fingerprint)**: 상용 LLM 엔드포인트가 내부 사유를 숨긴 채 오류를 반환할 때를 대비하여, 전송한 요청의 메타 구조(역할 시퀀스, 토큰 대비 예산 비율, 등록된 도구 목록 수, 최대 메시지 바이트 수 등)를 정량적 규격 정보로만 기록합니다 (4-2절 참조).
- **토큰 예산 상세 소비 내역**: 모델 응답이 최대 출력 한도에 도달한 경우 본문 텍스트, 추론(Reasoning) 블록, 도구 인자, 시스템 프롬프트가 각각 얼마의 토큰을 소비했는지 세부 내역을 집계합니다.
- **오류 메시지에 예외 클래스 명시**: 일부 파이썬 라이브러리 예외는 오류 메시지 문자열이 비어 있습니다. 예외 클래스 이름이라도 명확히 기록되어 있어야 장애 원인을 검색하고 추적할 수 있습니다.
- **로그에는 규격과 크기만 남기고 본문은 배제**: 시스템 진단에 필수적인 정보는 데이터의 크기와 처리 경로이며, 민감한 비즈니스 소스 코드나 개인 대화 본문이 서버 로그로 유출되지 않도록 철저히 차단합니다.
- **단발성 경고 메시지의 오염 방지**: UI 프레임워크의 "이미 소멸된 클라이언트를 참조함"과 같은 경고는 단일 프로세스 주기 동안 최초 1회만 출력됩니다. 소멸된 페이지에 사이드바를 다시 그리려던 사소한 결함이 이 단발성 경고를 먼저 소진해 버리면, 정작 나중에 발생하는 치명적인 세션 누수 경고를 놓치게 됩니다. 사소해 보이는 경고라도 원인을 규명하여 반드시 제거해야 합니다.

## 7. 조용한 실패 찾기

이 프로젝트의 개발 과정에서 가장 큰 비용을 초래했던 결함들은 실행 시점에 런타임 오류를 전혀 발생시키지 않았습니다. 이들을 분석해 보면 명확한 공통점이 발견됩니다.

| 겉으로 드러난 증상 | 근본 원인 | 왜 오류 없이 조용했는가 |
| :--- | :--- | :--- |
| 샌드박스 내부 변수가 다음 도구 호출 시 초기화됨 | 호출마다 독립된 서브프로세스를 매번 새로 기동함 | 샌드박스 서버는 "세션을 재사용함"이라고 정상 응답을 반환했습니다. |
| 에이전트가 생성한 파일을 샌드박스가 찾지 못함 | 동일한 상대 경로 문자열을 두 프로세스가 각기 다른 작업 디렉터리를 기준으로 해석함 | 두 프로세스 모두 시스템 레벨에서는 지극히 정상적으로 동작했습니다. |
| 새로운 대화 세션에 이전 대화의 기억 데이터가 누출됨 | 메모리 서버가 단일 프로세스 내에서 하나의 공용 지식 그래프 인스턴스를 공유함 | API 기능 자체는 완전히 정상 동작했으며, 반환된 데이터의 격리 범위만 어긋났습니다. |
| 긴 토론 세션 진행 중 초기 사용자 지시를 위반함 | 대화 이력이 임계치를 넘자 가장 오래된 순서대로 단순 메시지 축출을 수행함 | 콘솔 로그에 사소한 경고 한 줄만 남았을 뿐 엔진은 정상 실행을 이어갔습니다. |
| 파일 시스템 MCP 서버가 허용 디렉터리 없이 빈 상태로 기동됨 | Windows 확장 길이 경로(`\\?\`)를 URI 포맷으로 변환하는 과정에서 경로 문자열이 깨짐 | "초기화 요청 처리 실패"라는 경고 로그 한 줄만 남고 서버 프로세스는 정상 실행되었습니다. |
| 자동화 테스트가 개발자의 로컬 개발 DB에 실제 데이터를 기록함 | 싱글턴 엔진 인스턴스가 기본 프로덕션 파일 경로를 그대로 참조함 | 모든 테스트 케이스가 성공(Green)으로 통과하여 문제를 눈치채기 어려웠습니다. |
| 모델의 잘린 도구 호출 루프가 무한 반복됨 | 문법이 파싱되지 않은 도구 인자 문자열을 모델에게 원형 그대로 되돌려 보냄 | 상위 API 게이트웨이가 400 클라이언트 오류를 500 서버 오류로 둔갑시켜 세부 오류 사유를 누락시켰습니다. |

이러한 은밀한 결함들을 사전에 방지하고 조기에 식별하는 데 효과적인 실천 수칙입니다.

1. **"성공" 상태 응답을 맹신하지 말고 실제 부수 효과(Side-effect)를 검증하십시오.** 서버가 세션을 재사용한다고 응답했다면, 실제로 두 번째 호출 시 이전 변수 상태가 온전히 유지되는지 엄밀히 검증해야 합니다.
2. **동일한 환경 설정이 여러 프로세스로 분기 전달될 경우, 각 프로세스가 실제로 파싱하여 적용한 최종 값을 직접 확인하십시오.**
3. **실제 프로덕션 환경과 동일한 런타임 조건에서 검증하십시오.** 연속된 `user` 메시지 거부나 도구 스키마 없는 호출 기록 거부와 같은 엄격한 검증은 OpenAI 환경에서는 재현되지 않았습니다. Windows 파일 경로 관련 이슈 역시 Windows 런타임 환경에서만 발견되었습니다.
4. **결함을 명확히 재현하는 단위 테스트를 선제적으로 작성하십시오.** 사용자 지시 유실 문제는 "8k 컨텍스트 창, 턴 1 핵심 제약 조건, 턴 2 세 라운드 진행" 환경을 모사한 회귀 테스트를 작성하여 확인한 뒤 수정했으며, 고정(Pinning) 기능을 비활성화했을 때 해당 테스트가 다시 실패하는 것까지 검증했습니다.
5. **문제 원인을 즉각 규명할 수 있는 진단 도구를 먼저 구축하십시오.** 요청 핑거프린트(Request Fingerprint) 로깅 도구는 도입 직후 발생한 후속 장애의 원인을 단 한 줄의 로그 분석만으로 정확히 규명해 냈습니다.

## 정리

- 도구 실행 실패는 에이전트가 수습할 관찰 결과로 변환하고, 사용자 취소 신호만은 상위로 반드시 전파합니다.
- `except Exception`은 복합 예외 그룹(`BaseExceptionGroup`)을 놓치고, `except BaseException`은 취소 신호까지 삼켜버립니다. 시스템 경계 지점에서는 두 상황을 모두 고려하여 정밀하게 분기 처리합니다.
- 동일한 방어 규칙을 다중 계층에 걸쳐 중첩 적용합니다. 상위 계층은 하위 계층이 규칙을 온전히 지킬 것이라고 전제하지 않습니다.
- 대체 경로는 유용하지만, 사용자 모르게 조용히 동작하는 대체 경로는 위험합니다.
- 복구 작업을 수행하다가 2차 실패가 발생하더라도, 복구 대상이었던 원본 산출물은 반드시 보존합니다.
- 실패 기록은 근본 원인을 가리켜야 하며, 데이터의 크기와 규격 정보는 남기되 민감한 본문 내용은 철저히 배제합니다.
- 가장 큰 손실을 초래하는 결함은 오류 없이 조용히 발생합니다. 정상 응답 메시지에 안주하지 말고 최종 실행 결과를 직접 검증하십시오.

## 생각해 볼 문제

1. 여러분의 프로젝트에서 `except Exception:` 구문이 사용된 위치를 하나 선정하여, 그 내부에서 `BaseExceptionGroup`이나 `asyncio.CancelledError`가 발생할 가능성이 있는지 면밀히 검토해 보십시오.
2. "조용한 대체 경로"를 배제할 경우 시스템 로그와 UI 화면이 지나치게 많은 안내 문구로 번잡해질 수 있습니다. 사용자에게 반드시 보고해야 할 대체 동작과 시스템 내부적으로 조용히 처리해도 무방한 대체 동작을 가르는 명확한 판정 기준을 수립해 보십시오.
3. 7절의 조용한 실패 사례 표를 참고하여 여러분이 프로젝트에서 직접 겪었던 '조용한 실패' 경험을 하나 추가해 보십시오. 당시 그 실패를 더 초기에 감지할 수 있었던 전조 증상은 무엇이었는지 분석해 보십시오.
