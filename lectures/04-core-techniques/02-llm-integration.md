# 4-2. 여러 공급자의 LLM을 한 인터페이스로

> 상위: [4강. 핵심 기술](README.md) · 이전: [4-1. 설정](01-configuration.md) · 다음: [4-3. MCP 호스트](03-mcp-host.md)

MADO의 에이전트들은 서로 다른 공급자(OpenAI, Anthropic, Google, 사내 vLLM/Ollama 등)의 모델을 다양하게 조합하여 활용합니다. LiteLLM과 같은 통합 게이트웨이 라이브러리가 API 호출 인터페이스를 표준화해 주지만, 실제 멀티 에이전트 환경을 안정적으로 운영하기에는 그것만으로 충분하지 않았습니다. 이번 절에서는 LLM 호출기(Caller) 계층이 해결해야 했던 핵심 과제들을 다룹니다. 공급자별 제약에 맞추어 요청 스키마를 정제하는 일, 컨텍스트 윈도우 예산을 정밀하게 산출하는 일, 응답 한도 도달로 잘린 출력을 복구하고 이어 쓰는 일, 그리고 엔드포인트가 침묵할 때 근본 원인을 추적하는 요청 핑거프린트(Request Fingerprint) 기법을 살펴봅니다.

---

## 1. 호출 파라미터 조립

에이전트별 설정 한 세트가 LiteLLM 호출 한 번의 파라미터로 매핑됩니다.

| 설정 항목 | 호출 시 담당하는 역할 |
| :--- | :--- |
| `model` | `공급자/모델` 형식의 문자열로 대상 LLM 엔진을 식별합니다 (`openai/gpt-4o`, `anthropic/claude-3-5-sonnet` 등). |
| `api_base`, `api_key` | 엔드포인트 URL 및 인증 토큰입니다. 인증이 불필요한 로컬 추론 서버라도 빈 문자열 전송 시 401/400을 반환하는 경우가 있어 더미 키를 기본 주입합니다. |
| `drop_params` | 엔드포인트가 인식하지 못하는 파라미터를 요청 본문에서 자동으로 제거합니다. 엄격한 사내 로컬 모델 연동 시 400 거부 오류를 방지합니다. |
| `timeout` | 전체 호출 완료 시간이 아니라 **토큰 스트리밍 조각(Chunk) 사이의 최대 대기 시간**을 의미합니다. |
| `extra_headers`, `extra_body` | 사내 전용 AI 게이트웨이나 프록시가 요구하는 커스텀 헤더 및 부가 본문 필드를 주입합니다. |

특히 `timeout`의 기술적 의미를 정확히 이해하는 것이 중요합니다. 대규모 파일 작성을 수행하는 도구 호출 시, 모델은 인자 JSON 텍스트 생성이 완전히 끝날 때까지 수십 초간 스트리밍 청크를 단 한 조각도 방출하지 않을 수 있습니다. 만약 `max_tokens`를 16,000으로 설정한 상태에서 타임아웃을 120초로 짧게 잡으면, 생성 도중 "소켓 읽기 시간 초과"로 인해 발언이 강제 단절되는 문제가 발생합니다. 따라서 스트리밍 환경에서의 소켓 타임아웃은 예상되는 `max_tokens ÷ 초당 생성 토큰 수`보다 훨씬 넉넉하게(기본 600초) 설정해야 합니다.

## 2. 요청 구조 정리 계층 (Sanitization Layer)

LiteLLM은 호출 인터페이스를 단일화하지만, **공급자마다 서로 다른 대화 컨텍스트 구성 규칙**까지 통합해 주지는 못합니다. MADO는 네트워크 요청을 전송하기 직전 단계에 요청 구조를 정제하는 전용 계층을 명시적으로 두고 있습니다.

### 2.1 대화 역할 교대 (Alternating Roles) 제약 극복

멀티 에이전트 토론은 다수의 화자가 교차 발언하는 구조입니다. 그러나 표준 OpenAI 메시지 스키마에는 `system`, `user`, `assistant`, `tool`의 4가지 역할만 존재할 뿐, "제3의 다른 에이전트"를 표현하는 역할이 없습니다. 따라서 현재 발언자 자신의 이전 발언만 `assistant`가 되고, 다른 모든 에이전트의 이전 발언은 불가피하게 `user` 역할로 주입됩니다. 그 결과 3명의 전문가가 토론을 진행하면 동일한 `user` 메시지가 연속으로 3~4개씩 배치되는 현상이 발생합니다.

| LLM 공급자 | 연속된 `user` 메시지에 대한 반응 |
| :--- | :--- |
| **OpenAI** | 정상 수용 후 추론 진행 |
| **Anthropic, Gemini, 일부 오픈소스 템플릿 (llama.cpp, vLLM)** | HTTP 400 에러: "대화 역할은 반드시 교대로 배치되어야 합니다" |

이 문제는 디버깅하기 매우 까다로웠습니다. 오케스트레이터의 계획 수립 단계는 사용자의 단일 프롬프트로 시작하므로 정상 성공하지만, 전문가 토론 단계로 넘어가면 모든 에이전트의 호출이 즉시 실패했습니다. 겉보기에는 마치 "에이전트들이 네트워크 단절을 일으키는 것"처럼 보였습니다.

해결책은 연속으로 등장하는 동일한 역할(`user`) 메시지들을 개행 문자로 연결하여 단일 메시지로 안전하게 병합하는 것입니다. 각 발언의 서두에 `[에이전트명 (역할)]:` 머리말이 보존되어 있으므로 메시지를 합치더라도 모델은 발언 주체를 정확하게 인지합니다. 단, 도구 호출 요청(`tool_calls`)을 포함한 메시지와 도구 실행 결과(`tool`) 메시지는 절대로 병합해서는 안 됩니다. 도구 호출 ID의 쌍 관계가 파괴되기 때문입니다.

처리 순서 역시 엄격히 준수해야 합니다. **반드시 컨텍스트 윈도우 상한에 맞추어 먼저 자르고(Trimming), 그 이후에 연속 메시지를 병합(Merging)해야 합니다.** 만약 병합을 먼저 수행한 후 메시지를 자르게 되면, 잘려 나간 자리에 시스템이 삽입하는 "이전 N개 발언이 생략되었습니다"라는 안내용 `user` 메시지가 다른 `user` 메시지와 다시 연속 배치되면서 400 오류가 재발하기 때문입니다.

### 2.2 도구 실행 이력과 도구 정의 스키마의 정합성

도구 호출 예산을 모두 소진한 에이전트에게는 "더 이상 도구를 호출하지 말고 현재까지의 관찰 결과를 바탕으로 결론을 작성하라"고 최종 발언을 요청합니다. 초기에는 도구 사용을 강제로 차단하기 위해 요청 본문에서 도구 목록(`tools`)을 완전히 제거하여 전송했습니다.

그러나 그 시점의 대화 기록에는 이미 이전 루프에서 수행된 수많은 도구 호출 메시지와 결과 메시지가 포함되어 있습니다. Anthropic Claude의 경우 대화 이력에 도구 호출 기록이 존재하는데 요청에 도구 정의 스키마가 누락되어 있으면 즉시 HTTP 400 오류를 반환합니다. 반면 OpenAI는 이를 허용합니다. 그 결과 동일한 프롬프트 파이프라인에서 gpt-4o 오케스트레이터는 정상 동작하고 Claude 전문가만 도구를 많이 사용한 시점에 오류로 비정상 중단되는 기이한 장애가 발생했습니다.

해결책은 **도구 목록 스키마는 그대로 제공하되, 도구 호출 자체를 명시적으로 비활성화**하는 것입니다(`tool_choice: "none"`). 이 설정을 적용하면 공급자별 스키마 검증을 통과하면서도 모델이 추가 도구를 호출하지 못하도록 완벽히 통제할 수 있습니다. 동일한 규칙은 컨텍스트 초과로 발생한 "잘린 답변 이어 쓰기" 요청에도 동일하게 적용되어야 합니다.

### 2.3 도구 루프 순환 중의 동적 정제

상기 두 규칙(컨텍스트 자르기, 역할 병합)은 발언을 시작하는 최초 시점뿐만 아니라 **도구 루프가 순환하는 내부 과정에서도 실시간으로 반복 적용**되어야 합니다. 긴 도구 루프가 반복되면 도구 관찰 결과가 지속적으로 누적되어 컨텍스트 윈도우를 다시 초과할 수 있습니다.

루프 내부에서 컨텍스트를 자를 때는 반드시 **"도구 호출 메시지(`assistant`)와 그에 대응하는 실행 결과 메시지(`tool`)들을 하나의 불가분 단위"로 묶어서 제거**해야 합니다. 만약 단일 메시지 단위로 자르게 되면 응답 짝을 잃어버린 고아 도구 결과 메시지가 대화 배열에 잔존하게 되며, 이 역시 엄격한 공급자 엔드포인트에서 400 에러를 유발합니다.

## 3. 컨텍스트 윈도우 예산의 정밀 산출

전송하려는 프롬프트의 토큰 수가 모델의 최대 컨텍스트 윈도우를 초과하면, 엔드포인트는 HTTP 400을 반환하거나 남은 잔여 공간만큼만 출력을 허용합니다. 후자의 경우 "막 생성을 시작한 응답이 몇 토큰 만에 조기 종료되는" 기현상으로 나타나 원인 파악이 어렵습니다. 

MADO는 다음 공식에 따라 입력 허용 예산을 엄격하게 계산합니다.

```text
최대 허용 입력 예산 = 모델 최대 컨텍스트 윈도우 크기
                    − 실제 최대 출력 토큰 한도 (사고 예산 포함)
                    − 안전 여유 마진 (기본 512 토큰)
                    − 등록된 모든 MCP 도구 스키마가 점유하는 토큰 수
```

초기 구현에서는 도구 스키마 크기와 추론 모델의 사고 예산이 계산에서 누락되어 있었습니다.

- **도구 정의 스키마 토큰 누락**: 도구 정의 목록은 모든 요청마다 시스템 페이로드로 전송됩니다. 파일 시스템, 메모리, Git 도구만 합쳐도 35개 도구 스키마가 약 5,300토큰을 차지합니다. 이를 계산에서 제외하면 대화가 길어졌을 때 도구 정의 크기만큼 컨텍스트 창을 초과하게 됩니다.
- **추론 모델의 사고 예산(Thinking Budget)**: 추론 모델에 사고 예산을 부여하면 실제 요청 페이로드에는 `max_tokens`와 사고 예산의 합산 값이 실립니다. 예산 계산 계층이 단일한 통합 계산 함수를 참조하도록 구조화하여 불일치를 해소했습니다.

토큰 수는 LiteLLM 내장 토크나이저로 계측합니다. 토크나이저 호출이 실패할 때 적용되는 대체 계산(Fallback) 공식 역시 정교하게 보정했습니다. 단순히 "문자 수 ÷ 2"로 계산하던 초기 방식은 한글 텍스트를 절반 이하로 과소 계측하고 도구 호출 JSON 인자를 누락하는 결함이 있었습니다. 현재는 ASCII 문자는 약 3자당 1토큰, 한글 및 특수문자는 1자당 1.5토큰으로 가중치를 두고 도구 인자 텍스트까지 전수 합산하여 계측의 신뢰성을 확보했습니다.

## 4. 응답 한도(`max_tokens`) 도달과 복구 전략

`max_tokens`는 **LLM 모델이 단일 호출에서 생성할 수 있는 총 텍스트 출력량**의 상한선입니다. 도구 호출 요청 JSON 역시 모델이 생성하는 텍스트의 일부이므로, 이 두 특성이 결합할 때 다양한 예외가 발생합니다.

### 4.1 토큰 한도로 인해 잘린 도구 호출 (Truncated Tool Call)

에이전트가 대용량 파일 작성 도구를 호출할 때, 파일 본문 전체가 도구 호출 인자 JSON 문자열 내부에 포함됩니다. 이 JSON이 `max_tokens`에 도달하여 중간에 잘리면 다음과 같은 연쇄 결함이 발생합니다.

1. 인자 JSON이 미완성 상태이므로 파싱에 실패합니다.
2. 잘린 텍스트 조각을 그대로 도구 서버에 전달하면 도구 서버가 `-32602 유효하지 않은 인자` 에러를 반환합니다. 문제는 모델이 자신이 출력 한도에 도달해 잘렸다는 사실을 알지 못하므로, 동일한 크기의 전체 파일을 동일한 방식으로 재작성하다가 똑같은 위치에서 다시 잘리는 무한 실패 루프에 빠집니다.
3. 가장 치명적인 문제는 파싱에 실패한 깨진 JSON 문자열을 대화 이력에 그대로 되돌려 보냈을 때, vLLM과 같은 서빙 프레임워크가 이를 내부 채팅 템플릿에 렌더링하다가 복구 불가능한 400 에러를 일으킨다는 점입니다.

이를 해결하기 위해 다음 3단계 방어 설계를 확립했습니다.

- API 응답 메타데이터의 종료 사유(`finish_reason`)를 가장 먼저 확인합니다.
- 대화 기록에 보존하는 도구 호출 메시지는 **파싱에 성공하여 실제로 실행된 인자만으로 다시 직렬화**하여 저장합니다. 해석에 실패한 잘린 인자는 "토큰 초과로 인해 뒷부분 N글자가 생략되었습니다"라는 명확한 축약 텍스트로 대체합니다. 깨진 14KB의 쓰레기 JSON을 모델에 되돌려 보내는 것은 토큰을 낭비할 뿐만 아니라 모델의 추론을 심각하게 교란하기 때문입니다.
- 모델에게 **자연어 프롬프트로 명확한 대안 지침**을 전달합니다.

대안 지침은 해당 에이전트가 보유하고 있는 도구의 특성에 맞춤형으로 제공되어야 합니다.

| 에이전트가 보유한 도구 구성 | 모델에 제공하는 피드백 지침 |
| :--- | :--- |
| **파일 덧붙이기/부분 편집 도구 보유** | "출력 한도를 초과했습니다. 파일의 전반부만 먼저 작성하고, 나머지는 덧붙이기(append) 도구를 사용하여 분할 작성하십시오." |
| **덮어쓰기(Overwrite) 도구만 보유** | "단일 파일에 이어 쓰기가 불가능합니다. 내용을 더 작은 여러 개의 독립 파일로 분할하여 작성하거나 텍스트를 요약하십시오." |
| **파일 관련 도구 없음** | "단일 도구 호출에 전달하는 인자 크기를 줄여서 재호출하십시오." |

두 번째 항목이 매우 중요합니다. 공식 파일 시스템 MCP 도구의 `write_file`은 파일 전체를 통째로 덮어씁니다. 모델에게 단순히 "분할해서 호출하라"고 모호하게 조언하면, 모델은 이전 호출에서 작성했던 텍스트에 새로운 내용을 이어붙여 전체 내용을 매번 다시 보냅니다. 5천 자, 1만 자, 1만 5천 자로 본문이 계속 비대해지다가 똑같은 한도에 걸려 영구 실패합니다. 에이전트가 보유한 도구의 실제 동작 특성을 고려하여 조언을 차별화해야 합니다.

### 4.2 한도 도달(`finish_reason='length'`)과 실제 도구 실행의 판별

로그에 `finish_reason='length', tool='read_text_file'`이라는 기록이 남았을 때, 이는 파일 읽기 도구가 출력 한도를 넘겼다는 뜻이 아닙니다. 종료 사유는 **모델이 생성한 응답 자체**에 적용되는 값이며, 파일 내용은 다음 턴의 **입력**으로 주입됩니다. 수십 토큰에 불과한 파일 읽기 호출이 length로 종료된 이유는, 모델이 도구를 호출하기 직전에 출력한 긴 사고(추론) 과정이 `max_tokens` 예산을 거의 다 소모했기 때문입니다.

따라서 단순히 `finish_reason='length'`라는 플래그만 보고 "도구가 실행되지 않았다"고 속단해서는 안 됩니다. 시스템은 생성된 텍스트 내에서 도구 호출 JSON 인자가 온전히 닫혀 정상 파싱되었는지를 검사합니다.

| 상황 분류 | 도구 실제 실행 여부 | 모델에 제공하는 가이드 문구 |
| :--- | :--- | :--- |
| **인자 JSON 파싱 실패** | 실행되지 않음 | "도구 호출이 중간에 잘려 실행되지 않았습니다. 분할 호출 전략을 적용하십시오." |
| **length 도달했으나 인자는 완결 파싱됨** | **정상 실행 완료** | "도구는 정상 실행되었으며 결과는 상단에 있습니다. 잘린 부분은 호출 이후의 계획 텍스트이므로 결과를 확인하고 다음 행동을 진행하십시오." |

### 4.3 장문 텍스트 응답의 안전한 이어 쓰기 (Continuation)

도구를 호출하지 않는 일반 텍스트 응답(특히 최종 보고서 합성 단계)이 `max_tokens`에 도달하여 중간에 잘린 경우, 문장이 완성되지 못한 채 산출물이 끊어지게 됩니다. 

MADO는 다음과 같은 정교한 이어 쓰기 파이프라인을 가동합니다.

- 지금까지 수신된 텍스트 전체를 대화 배열의 `assistant` 메시지로 구성하고, 시스템 프롬프트를 통해 "어떠한 인사말이나 서두 요약 없이, 이전 메시지의 마지막 글자 바로 뒤에서부터 자연스럽게 이어 쓰십시오"라고 요청합니다.
- **이어 붙일 때 공백이나 개행 구분자를 임의로 삽입하지 않습니다.** 단어 중간이나 문장 중간에서 잘린 텍스트를 원형 그대로 이어붙여야 하기 때문입니다.
- 코드 블록(```)이나 마크다운 테이블 내부에서 잘린 경우, 열려 있는 블록 안에서 작성을 지속하고 완성된 마침 기호로 닫도록 지시합니다.
- 이어 쓰기 요청 시에는 도구 스키마는 전달하되 호출은 강제 차단(`tool_choice: "none"`)합니다. 텍스트를 완성하는 단계이지 새로운 탐색을 시작할 시점이 아니기 때문입니다.
- 최대 `max_continuations` 횟수(기본 2회)까지만 시도하며, 끝내 완결되지 않으면 몇 차례 이어 쓰기가 수행되었는지 명확한 주석을 본문 말미에 첨부합니다.

### 4.4 사후 수습보다 효과적인 사전 전략 주입

잘린 도구 호출을 사후에 감지하여 모델을 달래는 것은 많은 비용이 듭니다. 도구 실행 기회 1회와 왕복 통신 시간이 이미 낭비되었기 때문입니다.

따라서 파일 쓰기 권한을 보유한 에이전트의 시스템 프롬프트에는 **사전에 분할 작성 전략**을 명시적으로 주입합니다. 단순히 "토큰을 아끼라"는 지시는 모델이 따를 수 없습니다. 모델은 자신이 현재 몇 토큰을 출력하고 있는지 자체 계측할 수 없기 때문입니다. 대신 "장문의 보고서를 작성할 때는 개요를 먼저 생성한 후, 섹션별로 나누어 덧붙이기 도구를 호출하십시오"와 같이 명확한 행동 수칙을 제공해야 합니다.

## 5. 추론(Thinking) 모델의 출력 특성 제어

o1, R1 등 내부 추론(Reasoning) 과정을 거치는 모델들은 보이지 않는 사고 과정 역시 `max_tokens` 예산에서 함께 차감합니다. 모델이 지나치게 깊이 생각하면 **본문 응답 텍스트가 완전히 빈 상태에서** 토큰 한도에 도달하여 발언이 종료되는 현상이 발생합니다.

이 경우 시스템은 다음과 같이 대응합니다.
1. 본문이 비어 있음을 확인하고, 모델이 직전까지 도출했던 내부 사고 내용의 **끝부분(최대 2,000자)**을 추출하여 다음 프롬프트에 주입하며 "지금까지의 사고 내용을 바탕으로 즉시 최종 결론 텍스트를 작성하십시오"라고 재호출합니다. 처음부터 다시 질문하면 동일한 깊이로 사고하다가 똑같은 지점에서 다시 멈추기 때문입니다.
2. 서버 측 파서 결함으로 인해 모델의 최종 응답 텍스트 전체가 사고(Thinking) 블록 내부로 잘못 분류된 경우, 사고 텍스트 내에서 `## 최종 결론`과 같은 앵커 헤더를 정규식으로 탐색하여 추가 API 호출 없이 본문으로 자동 승격 복구합니다.

## 6. 일반 본문으로 누출된 도구 호출 문법 복구

추론 서버의 도구 파서가 비표준 모델의 도구 호출 형식을 인식하지 못하면, `<tool_call>{...}</tool_call>`과 같은 내부 문법이 일반 텍스트 본문으로 그대로 출력되는 현상이 일어납니다.

시스템은 도구 사용 권한이 부여된 발언에 한하여, 코드 블록 외부에서 Hermes, Qwen, Llama 3 등 주요 오픈소스 모델들의 특수 도구 호출 태그가 누출되었는지 정규식으로 감시합니다. 누출이 감지되면 해당 텍스트를 마스킹 제거하고, 모델에게 "도구 호출이 텍스트로 잘못 출력되어 실행되지 않았으니 표준 도구 호출 인터페이스를 준수하여 재호출하십시오"라는 안내를 전달합니다(최대 2회).

## 7. 사람을 위한 UI 표시와 모델을 위한 프롬프트의 분리

`show_steps` 설정은 본래 사용자 화면에 에이전트의 단계별 사고 과정을 보여줄지 여부를 제어하는 UI 옵션입니다. 그러나 초기 버전에서는 이 옵션이 켜져 있으면 에이전트의 장황한 사고 과정 전문이 대화 기록에 그대로 영구 보존되어 다음 발언자의 입력 컨텍스트로 전달되는 심각한 결합이 존재했습니다.

그 결과 몇 라운드만 지나도 컨텍스트 창의 80% 이상이 다른 에이전트의 장황한 중간 사고(추론) 과정으로 가득 차게 되었고, 핵심적인 사용자 요구사항과 아키텍처 제약 조건이 컨텍스트 슬라이딩에 의해 밖으로 밀려나는 사태가 발생했습니다.

현재 시스템은 **사람에게 보여주는 UI 렌더링 텍스트와, 후속 모델에게 전달되는 프롬프트 텍스트를 엄격하게 분리**합니다. 다음 에이전트의 프롬프트나 상위 오케스트레이터의 계획 프롬프트에는 중간 사고 과정을 완전히 필터링하고 오직 검증된 사실과 최종 주장만을 전달합니다. 3인 전문가의 3라운드 토론 기준 프롬프트 토큰 소모량이 기존 5,556토큰에서 1,848토큰으로 66% 이상 획기적으로 절감되었습니다([ADR-015](../05-adr/ADR-015-reasoning-out-of-prompts.md)).

## 8. 불투명한 업스트림 오류의 추적: 요청 핑거프린트 (Request Fingerprint)

사내 엔터프라이즈 게이트웨이가 다음과 같은 불투명한 에러를 반환하는 경우가 있습니다.

```text
Error code: 500 - {'error': "client error: 400, message='Bad Request', url='.../chat/completions'"}
```

업스트림의 서빙 엔진(vLLM 등)이 보낸 구체적인 400 에러 사유(컨텍스트 초과, 역할 순서 위반 등)가 게이트웨이의 불투명한 500 에러로 감싸지면서 완전히 유실된 것입니다. 게다가 LiteLLM은 500 에러를 일시적 장애로 판단하여 결정적인 형식 오류 요청을 계속해서 재시도하는 비효율이 발생합니다.

엔드포인트가 원인을 설명해 주지 않을 때 시스템에 남은 유일한 단서는 **우리가 전송한 요청 데이터 자체**뿐입니다. 따라서 호출이 실패하면 시스템은 요청의 구조적 특성을 압축한 **요청 핑거프린트(Request Fingerprint)**를 시스템 로그에 즉시 출력합니다.

```text
Request fingerprint for Senior Python Engineer (model=openai/qwen3-27b, api_base=http://gateway/v1):
  messages=12 roles=system,user,assistant,tool,assistant,tool,...
  tokens~124,508 / budget 123,392 (window 128,000, max_tokens 4,096)  <-- OVER BUDGET
  tools=12 tool_choice=auto
  largest: [9] tool filesystem__read_text_file 120,000 chars; [5] tool ... 64,000 chars
```

- 메시지 수 및 역할(Role)의 교대 배열 순서
- 추정 토큰 수와 최대 허용 예산 간의 대조 (예산 초과 여부 즉각 식별)
- 도구 스키마 개수와 호출 모드 설정
- 요청 내에서 가장 큰 용량을 차지하는 상위 메시지들의 크기와 도구 이름

이때 **데이터의 크기 메타데이터만 기록하고 민감한 본문 내용은 절대 기록하지 않습니다.** 작업 공간의 중요 소스 코드가 시스템 로그에 평문 노출되는 보안 사고를 방지하기 위함입니다. 이러한 요청 핑거프린트 인프라는 시스템 런타임의 불투명성을 해소하고 원인을 즉각 규명할 수 있는 강력한 관측성(Observability)을 제공합니다.

## 9. 연결 실패에 대한 정직한 사실 기록

외부 LLM 엔드포인트 연결이 최종 실패하면, 호출기는 임의의 가상 응답을 생성하지 않고 실패 원인이 명시된 예외를 상위 엔진에 투명하게 전달합니다. 엔진은 해당 발언 레코드에 "응답 없음" 사실만을 기록하고 즉시 다음 전문가에게 발언권을 넘깁니다. 

이 실패 기록은 후속 에이전트의 프롬프트와 최종 합성 프롬프트의 발언 목록에서 의도적으로 제외됩니다. 에러 메시지가 대화 배열에 포함되면 다른 에이전트들이 시스템 에러 메시지를 주제 삼아 토론을 시도하는 부작용이 발생하기 때문입니다. 대신 최종 합성 프롬프트에는 "어느 전문가가 응답에 실패하여 토론에 불참했다"는 객관적 사실을 명시하여, 오케스트레이터가 존재하지 않는 가상의 합의를 지어내지 못하도록 방어합니다([ADR-007](../05-adr/ADR-007-no-simulated-answers.md)).

## 핵심 요약

- API 호출 인터페이스 통일과 공급자별 세부 대화 규칙 준수는 서로 다른 영역이며, 그 간극은 애플리케이션의 **요청 구조 정리 계층**이 완충해야 합니다.
- 컨텍스트 예산 계산에는 모델의 최대 출력 토큰뿐만 아니라 도구 스키마 정의 토큰과 안전 마진이 반드시 포함되어야 합니다.
- 응답 한도로 인해 잘린 도구 호출은 깨진 JSON을 되돌려 보내지 않고 재직렬화하며, 에이전트의 도구 구성에 맞는 구체적인 분할 전략을 안내합니다.
- 잘린 장문 답변은 구분자 없이 매끄럽게 이어 쓰되, 도구 호출을 차단하여 텍스트 완결에 집중시킵니다.
- 사람이 모니터링하는 시각적 사고 과정과 모델에게 주입되는 프롬프트 맥락을 엄격히 분리하여 토큰 낭비와 환각을 억제합니다.
- 업스트림 시스템의 에러가 불투명할 때는 **요청 핑거프린트**를 로깅하여 원인을 정밀 추적합니다.

## 학습 점검 과제

1. 연속된 `user` 메시지 문제를 해결하기 위해 "이전 에이전트들의 모든 발언을 단 하나의 거대한 `user` 메시지로 묶어서 전달하는 방식"을 적용한다면, 현재의 개별 발언 유지 방식과 비교하여 프롬프트 캐싱 및 발언자 식별 관점에서 어떠한 장단점이 있을지 분석해 보십시오.
2. 요청 핑거프린트 생성 시 보안을 위해 본문 내용을 배제하고 크기 메타데이터만 기록하도록 설계했습니다. 만약 특정 입력 텍스트의 특수 문자열이나 인코딩 결함으로 인해 발생하는 400 에러를 진단하고자 한다면, 보안 원칙을 훼손하지 않으면서 이를 안전하게 디버깅할 수 있는 보완책을 제시해 보십시오.
3. 잘린 답변에 대한 "이어 쓰기(Continuation)" 전략 대신, 모델에게 "이전 생성을 취소하고 처음부터 핵심만 더 간결하게 요약하여 재작성하라"고 재요청하는 전략을 비교해 보십시오. 어떠한 작업 시나리오에서 후자의 접근이 더 효과적일지 설명해 보십시오.
