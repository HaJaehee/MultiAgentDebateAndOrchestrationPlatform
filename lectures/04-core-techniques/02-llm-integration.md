# 4-2. 여러 공급자의 LLM을 한 인터페이스로

> 상위: [4강. 핵심 기술](README.md) · 이전: [4-1. 설정](01-configuration.md) · 다음: [4-3. MCP 호스트](03-mcp-host.md)

MADO의 에이전트들은 서로 다른 공급자의 모델을 씁니다. LiteLLM이 호출 방법을 통일해 주지만, 그것만으로
충분하지 않았습니다. 이 절은 LLM 호출기가 떠안게 된 일들을 다룹니다. 요청을 공급자가 받아 줄 모양으로
다듬는 일, 컨텍스트 창 예산을 계산하는 일, 응답 한도에서 잘린 출력을 복구하는 일, 그리고 엔드포인트가
이유를 말해 주지 않을 때 원인을 찾는 일입니다.

---

## 1. 호출 파라미터 조립

에이전트 설정 한 벌이 LiteLLM 호출 한 번의 파라미터가 됩니다.

| 설정 | 호출에서 하는 일 |
| :--- | :--- |
| `model` | `공급자/모델` 형식의 문자열로 공급자를 고릅니다 |
| `api_base`, `api_key` | 엔드포인트와 인증. 키가 필요 없는 로컬 서버라도 빈 문자열을 거부하는 경우가 있어 더미 키를 넣어 줍니다 |
| `drop_params` | 엔드포인트가 모르는 파라미터를 조용히 뺍니다. 로컬 서버와 붙일 때 400을 막습니다 |
| `timeout` | 응답 전체가 아니라 **스트리밍 조각 사이의 최대 대기 시간**입니다 |
| `extra_headers`, `extra_body` | 사내 게이트웨이가 요구하는 헤더나 필드를 넣습니다 |

`timeout`의 의미를 잘못 알면 긴 발언이 중간에 끊깁니다. 도구 호출로 긴 파일을 쓸 때, 모델은 인자 JSON이
다 만들어질 때까지 아무 조각도 흘려보내지 않을 수 있습니다. `max_tokens`를 16,000으로 잡은 상태에서
대기 시간이 120초면, 생성 도중에 "소켓에서 데이터를 읽다가 시간 초과"로 발언이 잘렸습니다. 예시 설정의
기본값을 600초로 올린 이유입니다. 대기 시간은 `max_tokens ÷ 초당 생성 토큰 수`보다 크게 잡아야 합니다.

## 2. 요청 모양 정리

LiteLLM은 호출 방법을 통일하지만 **공급자마다 다른 대화 형식 규칙**까지 지워 주지는 못합니다. MADO는
요청을 보내기 전에 모양을 다듬는 층을 따로 둡니다.

### 2.1 역할이 교대하지 않는 대화

토론은 여러 명이 말하는 대화입니다. 하지만 OpenAI 메시지 형식에는 `system`, `user`, `assistant`, `tool`
역할만 있고 "다른 에이전트"라는 역할은 없습니다. 에이전트 자신의 발언만 `assistant`가 되고, 다른
에이전트의 발언은 모두 `user`가 됩니다. 전문가가 셋이면 `user` 메시지가 서너 개씩 연달아 생깁니다.

| 공급자 | 연속된 `user` 메시지 |
| :--- | :--- |
| OpenAI | 받아 줌 |
| Anthropic, Gemini, 일부 호환 서버(llama.cpp 서버, 일부 vLLM 템플릿) | 400: 역할이 교대해야 한다 |

증상이 고약했습니다. 오케스트레이터의 계획 호출은 사용자 메시지 하나라 성공하고, 전문가 발언만
전부 실패했습니다. 겉으로는 "에이전트들이 자꾸 연결이 끊긴다"로 보였습니다.

해결은 연달아 나오는 같은 역할 메시지를 빈 줄로 이어 하나로 합치는 것입니다. 발언마다 `[이름 (역할)]:`
머리말이 붙어 있으므로 합쳐도 누가 무슨 말을 했는지는 남습니다. 단 도구 호출을 담은 메시지와 도구
결과 메시지는 합치지 않습니다. 도구 호출 ID의 짝이 깨지기 때문입니다.

**순서를 지켜야 합니다. 먼저 자르고, 그다음 합칩니다.** 컨텍스트 창에 맞게 자를 때 "앞의 N개 발언을
생략했다"는 안내를 `user` 메시지로 넣는데, 합친 뒤에 자르면 이 안내가 다른 `user` 메시지 옆에 붙어 다시
400이 납니다.

### 2.2 도구 기록은 있는데 도구 정의가 없는 요청

도구 호출 예산을 다 쓴 에이전트에게는 "더 이상 도구를 쓰지 말고 결론을 써라"라고 한 번 더 요청합니다.
처음에는 요청에서 도구 목록을 빼는 방식으로 도구 사용을 막았습니다. 도구 목록을 주면서 "예산이
끝났다"고 하면 모델이 또 도구를 부르고, 그 호출은 실행되지 않은 채 버려지기 때문입니다.

그런데 그 시점의 대화에는 이미 실행한 도구 호출과 결과가 잔뜩 들어 있습니다. Anthropic은 도구 호출
기록이 있는 대화를 도구 정의 없이 보내면 거절합니다. OpenAI는 받아 줍니다. 그래서 gpt-4o 오케스트레이터는
멀쩡하고 Claude 전문가만, 그것도 도구를 가장 많이 쓴 발언에서만 400으로 죽었습니다. 무작위 장애처럼
보였습니다.

해결은 **도구를 정의하되 호출은 못 하게** 하는 것입니다(`tool_choice: "none"`). 두 요구 조건을 동시에
만족합니다. 같은 문제가 나중에 "잘린 답변 이어 쓰기"에서 또 나왔습니다. 이어 쓰기 요청도 도구를 뺀 채
보냈고, 도구를 한 번이라도 쓴 Claude 에이전트의 이어 쓰기는 조용히 실패하고 있었습니다. 한 곳에서
배운 규칙을 비슷한 모든 곳에 적용하는 일은 생각보다 자주 빠집니다.

### 2.3 도구 루프 안에서도 같은 규칙을

두 규칙(자르기, 합치기)은 발언을 시작할 때 한 번 적용됩니다. 그런데 도구 루프는 계속 메시지를 쌓고,
도구 결과 하나가 수십 KB가 될 수도 있습니다. 루프 안에서도 자르기가 필요한데, 루프용 자르기 함수는
생략 안내를 넣은 뒤 합치기를 하지 않고 있었습니다. 긴 도구 루프에서만, 그것도 규칙에 엄격한
엔드포인트에서만 연속 `user` 400이 다시 나타났습니다.

루프 안에서 자를 때는 **"도구 호출 메시지 + 그 결과들"을 한 덩어리로** 덜어냅니다. 메시지를 하나씩
자르면 짝 잃은 도구 결과가 남는데, 그것도 400입니다. 로컬 테스트에서는 통과하고 실제 엔드포인트에서만
터지는 종류의 버그입니다.

## 3. 컨텍스트 예산 계산

요청이 모델의 컨텍스트 창을 넘으면 엔드포인트는 400을 돌려주거나, 남은 공간만큼만 출력을 허락합니다.
후자는 "막 시작한 응답이 한도에서 잘림"으로 나타나 원인을 알기 어렵습니다. 예산은 이렇게 계산합니다.

```text
입력 예산 = 컨텍스트 창
          − 실제 출력 한도 (사고 예산 포함)
          − 여유분 512
          − 도구 정의가 차지하는 토큰
```

처음에는 마지막 두 항이 빠져 있었습니다.

- **도구 정의.** 도구 목록은 요청마다 함께 갑니다. 파일 시스템, 기억, git 서버만 합쳐도 도구 35개,
  약 5,300토큰입니다. 이걸 빼먹으면 예산을 꽉 채운 대화가 도구 목록 크기만큼 창을 넘칩니다.
- **실제 출력 한도.** 추론 모델에 사고 예산을 주면 요청에는 `max_tokens`와 사고 예산의 합이 실립니다.
  요청만 그 값을 쓰고, 예산 계산과 안내 문구와 로그는 설정값을 쓰고 있었습니다. 지금은 모든 곳이 한
  함수의 값을 읽고, 사람에게는 `8,192 (설정 4,096 + 사고 예산 4,096)`처럼 보여 줍니다.

토큰 수는 LiteLLM의 토큰 계산기로 셉니다. 계산기가 실패했을 때 쓰는 대체 계산도 문제였습니다. 처음에는
"글자 수 ÷ 2"였는데, 이러면 한국어를 실제의 절반으로 세고, 본문이 비어 있고 모든 내용이 도구 호출 인자에
들어 있는 18,000자짜리 파일 쓰기 발언을 4토큰으로 셉니다. 지금은 도구 호출 인자까지 세고, 문자 종류에
따라 가중치를 다르게 줍니다(ASCII는 3자당 1토큰, 그 밖은 1자당 1.5토큰). 대체 계산은 드물게 쓰이지만,
쓰일 때 틀리면 그 여파가 큽니다.

## 4. 응답 한도(`max_tokens`)를 둘러싼 문제들

`max_tokens`는 **생성량**의 상한입니다. 그리고 도구 호출도 생성된 텍스트입니다. 이 두 사실에서 여러
문제가 나왔습니다.

### 4.1 잘린 도구 호출

에이전트가 파일 쓰기 도구로 큰 파일을 쓰면, 파일 내용 전체가 도구 호출 인자 JSON이 됩니다. 이 JSON이
한도에 걸려 문자열 한가운데서 끊깁니다. 그 뒤로 세 가지가 연달아 잘못되었습니다.

1. 인자를 해석하지 못해 조각을 그대로 담아 도구에 넘겼습니다. 여기까지는 괜찮습니다. 깨진 호출이
   발언을 끝내면 안 되니까요.
2. 도구 서버가 인자를 거부했습니다(`-32602 입력 검증 오류`). 이것도 관찰 결과로서는 괜찮습니다. 문제는
   모델이 **왜** 거부됐는지 모른다는 것입니다. 같은 크기로 다시 쓰다가 같은 자리에서 또 잘렸습니다.
3. 가장 나빴던 것은, 잘린 원본 인자 문자열을 그대로 대화 기록에 넣었다는 점입니다. 그 뒤 이 발언의 모든
   요청에 우리가 해석하지 못한 JSON이 실려 나갔고, vLLM은 그걸 채팅 템플릿에 넣다가 400을 냈습니다.

고친 방법은 세 가지입니다.

- 응답의 종료 이유(`finish_reason`)를 확인합니다. 그전에는 한 번도 보지 않았습니다.
- 대화 기록에 넣는 도구 호출은 **실제로 실행한 인자로 다시 직렬화**합니다. 해석하지 못한 인자는 "N자를
  읽지 못해 생략했다"는 짧은 표시로 바꿉니다. 14KB의 깨진 JSON을 되돌려 보내 봐야 모델에게 알려 주는
  것은 없고 토큰만 듭니다.
- 모델에게 **말로** 알립니다. 어떤 한도에 걸렸는지, 그 호출은 실행되지 않았다는 것, 대신 무엇을 해야
  하는지를요.

"대신 무엇을 해야 하는지"는 그 에이전트가 가진 도구에 따라 다릅니다.

| 에이전트가 가진 도구 | 알려 주는 방법 |
| :--- | :--- |
| 이어 쓰기 가능한 도구(편집, 덧붙이기) | 첫 부분을 쓰고 나머지는 그 도구로 이어 붙여라. 덮어쓰는 도구로 이어 쓰지 마라 |
| 덮어쓰는 파일 쓰기 도구만 | 나눠 써도 소용없다. 여러 **파일**로 나누거나 내용을 줄여라 |
| 파일 도구 없음 | 인자를 줄여라 |

가운데 줄이 핵심입니다. 공식 파일 시스템 서버의 파일 쓰기 도구는 파일을 **통째로 덮어씁니다.** "나눠서
쓰라"는 순진한 조언을 따르면 모델은 호출할 때마다 지금까지 쓴 내용 전체를 다시 보냅니다. 5천, 1만, 1만
5천 자로 커지다가 같은 한도에 다시 걸립니다. 쓸 수 있는 도구와 쓸 수 없는 도구를 이름으로 짚어 주는
것이, 통하는 조언과 같은 실패를 반복하게 하는 조언의 차이입니다.

### 4.2 한도에 닿았지만 도구는 실행된 경우

로그에 "잘린 도구 호출: `finish_reason='length'`, 도구=`read_file`"이 찍혔습니다. 파일 읽기가 출력 한도를
넘었다는 뜻으로 읽힙니다. 그럴 수 없습니다. 종료 이유는 **응답 하나**에 대한 것이고, 파일 내용은 다음
요청의 **입력**으로 들어옵니다. 20토큰짜리 읽기 호출이 한도에 닿은 것은 같은 응답 안의 다른 무언가,
예를 들어 호출 전에 쓴 긴 추론이 예산을 먹었기 때문입니다.

예전 규칙은 "종료 이유가 length이면 인자가 잘렸다"였습니다. 그래서 멀쩡히 실행된 읽기 호출 바로 아래에
"이 호출은 실행되지 않았다, 다시 보내지 마라"라는 안내가 붙고, 하지도 않은 파일 쓰기를 나눠 쓰라는
조언까지 붙었습니다. 지금은 둘을 구분합니다.

| 상황 | 실행 여부 | 모델에게 하는 말 |
| :--- | :--- | :--- |
| 인자를 해석할 수 없음 | 실행 안 됨 | 잘렸다, 실행되지 않았다, 대신 이렇게 하라 |
| 종료 이유는 length지만 인자는 모두 해석됨 | **실행됨** | 호출은 실행되었고 결과는 위에 있다. 잘린 지점은 마지막 호출의 끝이니 그 결과를 확인하라. 그 뒤에 계획했던 것은 나가지 않았다 |

로그에도 무엇이 예산을 썼는지 크기로 남깁니다. 본문 글자 수가 크면 호출 전 추론이, 추론 글자 수가 크면
보이지 않는 사고가, 인자 크기가 크면 호출 자체가, 셋 다 작은데 프롬프트가 창에 가까우면 서버가 남은
창만큼만 출력을 허락한 것입니다. 추론이 출력의 25% 이상을 차지했으면 "추론을 짧게 하고 도구를 부르라,
추론 안에서 파일 초안을 쓰지 마라"는 한 문단을 덧붙입니다. 그 미만이면 덧붙이지 않습니다. 거의 생각하지
않는 모델에게 생각을 줄이라고 하는 것은 잡음입니다.

### 4.3 잘린 답변 이어 쓰기

도구 없이 쓰는 평범한 답변이 한도에서 잘리면, 발언은 문장 중간에서 끝납니다. 토론 중 발언 하나라면
다음 발언자가 알아서 넘어갈 수 있지만, 최종 합성 보고서는 그 자체가 산출물입니다. 그래서 잘린 답변은
이어 쓰게 합니다.

- 지금까지 쓴 글을 `assistant` 메시지로 넣고, "마지막 글자에서 바로 이어 쓰라"고 요청합니다.
- **이어 붙일 때 구분자를 넣지 않습니다.** 다른 조각들은 빈 줄로 구분하지만, 이어 쓰기는 반으로 잘린
  문장을 잇는 것이기 때문입니다.
- 지시문에 "그대로 이어 붙는다"는 사실을 적습니다. 그러지 않으면 모델이 "이어서 설명드리겠습니다"로
  시작하거나 앞 내용을 요약하고, 그 말이 본문 한가운데 박힙니다. 코드 블록이나 표 안에서 잘렸다면 그
  안에서 이어 가고 제대로 닫으라고도 적습니다.
- 도구는 정의하되 호출은 막습니다(2.2절). 문장을 마저 쓰는 중이지 새로 뭔가를 찾아볼 기회가 아닙니다.
- 최대 `max_continuations`번(기본 2) 시도하고, 그래도 끝나지 않으면 몇 번 이어 썼는지 적은 안내를
  붙입니다. 읽는 사람은 이어 쓰기 횟수를 늘릴지, `max_tokens`를 늘릴지, 요청을 줄일지 골라야 하기
  때문입니다.
- 이어 쓰기 호출이 실패해도 **이미 받은 글은 버리지 않습니다.** 고치려던 글을 수리 실패가 앗아 가면
  안 됩니다.

이어 쓰기는 수리이지 계획이 아닙니다. 호출이 한 번 더 들고, 부분 글을 다시 보내야 하고, 이음매가 완전히
매끄럽지는 않습니다. 긴 출력이 예외가 아니라 일상이라면 `max_tokens`를 올려야 합니다. 4,096토큰은 영문
기준으로 약 1만 6천 자이고 한국어는 그보다 훨씬 적습니다. 도구로 문서 전체를 쓰는 에이전트나 최종
보고서에는 좁습니다. 예시 설정의 기본값을
16,000으로 올린 이유입니다.

### 4.4 사전에 전략을 알려 주기

잘린 도구 호출을 사후에 수리하는 것만으로는 부족했습니다. 한 번 잘릴 때마다 실패한 도구 실행 한 번,
도구 예산 한 칸, 되돌려 보낼 수 없는 인자, 다시 쓰는 한 라운드가 날아갑니다.

그래서 파일 쓰기 도구를 가진 에이전트의 시스템 프롬프트에 두 줄을 넣습니다. **크기 제한이 아니라
전략**을 알려 줍니다. "인자를 짧게 하라"는 지시는 따를 수 없습니다. 모델은 자기 출력 토큰을 셀 수
없고, 억지로 줄이려 하면 내용만 나빠집니다. 대신 어떤 도구로, 어떤 단위(절, 장)로 나눠 쓰라고 알려
줍니다. 이건 토큰을 세지 않아도 따를 수 있습니다. 파일 도구가 없는 에이전트에게는 한 글자도 더하지
않습니다.

이 두 줄은 대화 전용 사용자 지침보다 **앞에** 둡니다. 사람이 이 대화에서 다르게 지시했다면 그쪽이 더
구체적인 지시이므로 이겨야 합니다.

## 5. 추론 모델이 만드는 빈 발언

추론 모델은 보이지 않는 사고를 `max_tokens`에 포함해 셉니다. 오래 생각하면 본문이 **비어 있는 채로**
한도에 닿습니다. 이어 쓸 본문이 없으니 발언은 안내 문구 하나로 끝났습니다. 지금은 이렇게 합니다.

1. 본문이 비었다는 사실을 알리고, 그 사고의 **끝부분**(최대 2,000자)을 넘기며 "여기서부터 결론을
   내라"고 요청합니다. 같은 질문을 다시 하면 같은 거리만큼 생각하다가 같은 자리에서 멈추기 때문입니다.
2. 그래도 비어 있으면 숙고 없이 바로 답하라고 한 번 더 요청합니다.
3. 끝내 아무것도 없으면 "사고가 한도를 다 썼다"고 적습니다. "잘렸다"고 적지 않습니다.

같은 빈 카드가 한도와 무관하게 생기기도 했습니다. 서버의 추론 파서가 사고 종료 표시를 찾지 못하면,
답변까지 포함한 **전체 출력**이 추론으로 분류되고 응답은 정상 종료로 끝납니다. 사고를 화면에 보이지
않는 모드에서는 발언이 통째로 비고 로그에도 아무것도 남지 않았습니다. 지금은 추론 안에 결론 표시
(`## 최종 결론`)가 있으면 추가 호출 없이 그것을 본문으로 쓰고, 없으면 답을 다시 요청합니다.

## 6. 본문으로 새어 나온 도구 호출

서버의 도구 호출 파서가 모델이 만든 호출을 읽지 못하면, 호출 문법이 일반 텍스트로 돌아옵니다. 예전에는
이것을 답변으로 받아들였습니다. 도구는 실행되지 않았고, 잘린 호출은 산문인 양 이어 쓰였고, 카드에는
`<tool_call>{...`가 그대로 남았습니다.

지금은 도구가 제공된 발언에 한해, 코드 블록 밖에서 흔한 형식을 찾아냅니다.

| 형식 | 표시 |
| :--- | :--- |
| Hermes, Qwen 2.5/3 | `<tool_call>{` |
| Mistral | `[TOOL_CALLS]` |
| Llama 3.1 내장 도구 | `<\|python_tag\|>` |
| Llama 3.x 사용자 함수 | `<function=이름>{` |
| DeepSeek V3/R1 | 전용 특수 토큰 |
| gpt-oss | `to=functions.이름` |

찾으면 그 부분을 지우고, 호출이 실행되지 않았으니 제대로 부르라고 알립니다. 최대 두 번까지입니다.
그 이상 반복된다면 서버 파서와 모델 형식이 맞지 않는다는 뜻이고, 다시 물어도 달라지지 않기 때문입니다.
코드 블록 안의 표시는 무시합니다. 도구 호출 형식을 **설명하는** 답변은 누출이 아닙니다.

## 7. 사람이 보는 것과 모델이 읽는 것을 나누기

단계적 사고(sequential thinking)는 세 가지 방식으로 켤 수 있습니다.

| 방식 | 동작 | 대상 |
| :--- | :--- | :--- |
| `prompt` | 시스템 프롬프트에 "생각 1..N을 쓰고 최종 결론을 쓰라"는 절차를 넣음 | 로컬 모델 포함 모든 모델 |
| `native` | 공급자의 추론 파라미터(추론 강도, 사고 예산)를 사용 | 추론을 지원하는 모델 |
| `mcp` | 단계적 사고 MCP 도구를 부르게 함 | 도구 호출이 되는 모델 |

`show_steps` 설정은 원래 두 가지 일을 했습니다. 사람에게 사고 과정을 보여 줄지, 그리고 (의도하지
않았지만) 다른 에이전트가 그 사고 과정을 읽을지. 켜 두면 사고 전문이 발언 본문이 되었고, 다음 발언자의
맥락에 그대로 복사되었습니다. 몇 라운드 지나면 맥락의 대부분이 남의 사고 과정이 되었고, 컨텍스트
자르기가 목표와 초기 설계 논의를 버리기 시작했습니다. 발언을 250~300자로 인용하는 계획·지명·분배
프롬프트에는 "생각 1: ..."으로 시작하는 머리말만 들어가서, 정작 결론은 한 글자도 들어가지 않았습니다.

지금 `show_steps`는 **사람이 무엇을 보는지만** 정합니다. 발언 본문이 프롬프트에 들어가는 모든 지점에서
사고 흔적을 걷어냅니다. 에이전트 자신의 이전 사고도 돌려주지 않습니다. 지난 라운드의 자기 추론을 다시
읽으면 거기에 닻을 내리게 되는데, 새 라운드의 의미는 새 증거가 들어왔다는 데 있기 때문입니다.
3명 × 3라운드 대화에서 프롬프트가 5,556토큰에서 1,848토큰으로 줄었습니다
([ADR-015](../05-adr/ADR-015-reasoning-out-of-prompts.md)).

## 8. 이유를 말해 주지 않는 엔드포인트: 요청 지문

vLLM 앞의 게이트웨이가 이런 오류를 돌려준 적이 있습니다.

```text
Error code: 500 - {'error': "client error: 400, message='Bad Request', url='.../chat/completions'"}
```

상류가 400을 줬고, 게이트웨이가 그걸 자기 500으로 감쌌고, vLLM의 원래 메시지("최대 컨텍스트 길이를
넘었다", "역할이 교대해야 한다" 같은)는 도중에 버려졌습니다. 게다가 LiteLLM은 500을 재시도 대상으로
보기 때문에, 결정적인 요청 형식 오류를 두 번 더 재시도했습니다.

엔드포인트가 이유를 말해 주지 않으면 남은 증거는 **우리가 보낸 요청**뿐입니다. 그래서 호출이 끝내
실패하면 요청의 지문을 로그에 남깁니다.

```text
Request fingerprint for Senior Python Engineer (model=openai/qwen3-27b, api_base=http://gateway/v1):
  messages=12 roles=system,user,assistant,tool,assistant,tool,...
  tokens~124,508 / budget 123,392 (window 128,000, max_tokens 4,096)  <-- OVER BUDGET
  tools=12 tool_choice=auto
  largest: [9] tool filesystem__read_text_file 120,000 chars; [5] tool ... 64,000 chars
```

| 줄 | 판정할 수 있는 것 |
| :--- | :--- |
| 역할 순서 | 연속된 `user`, 앞선 `assistant` 없는 도구 결과 |
| 토큰 대 예산 | 컨텍스트 초과, 또는 설정한 창이 모델의 실제 한계보다 커서 자르기가 동작하지 않은 경우 |
| 도구 수와 선택 방식 | 도구 기록은 있는데 도구 정의가 없는 요청 |
| 가장 큰 메시지 | 어떤 도구 결과가 요청을 부풀렸는지 |

**크기만 남기고 내용은 남기지 않습니다.** 소스 파일을 읽은 도구 결과가 로그로 복사되면 안 되고, 진단에
필요한 것은 양이지 내용이 아닙니다. 지문을 만드는 과정의 오류가 원래 호출의 실패를 가려서도 안 되므로,
지문 생성이 실패하면 한 줄만 남기고 원래 예외를 그대로 올립니다.

이 지문은 만들자마자 값을 했습니다. 다음 장애에서 지문이 찍혔는데, 컨텍스트 예산과는 한참 먼 요청의
가장 큰 메시지가 14,546자짜리 파일 쓰기 도구 호출이었습니다. 4.1절의 "잘린 인자를 그대로 되돌려 보내던"
버그가 이렇게 드러났습니다. **진단 도구를 먼저 만들고, 수리는 그다음에.** 진단 도구는 그 자체로 출시할
가치가 있습니다.

## 9. 연결 실패는 흉내 내지 않는다

엔드포인트에 닿지 못하면 호출기는 모델, 엔드포인트, 원인을 담은 예외를 올립니다. 엔진은 발언 단위로
그 예외를 잡아 "이 발언은 응답을 받지 못했다"는 기록을 남기고 다음 발언자로 넘어갑니다. 끊기기 전까지
도착한 글은 안내문 위에 보존합니다. 이 실패 기록은 다음 발언자의 맥락과 합성 프롬프트에서 빠집니다.
실패 안내를 발언처럼 읽히게 하면 다른 에이전트가 그 안내에 대해 논평을 시작하기 때문입니다. 대신 합성
프롬프트에는 누가 발언하지 못했는지 적어서, 없는 의견을 지어내지 않게 합니다
([ADR-007](../05-adr/ADR-007-no-simulated-answers.md)).

## 정리

- 호출 방법의 통일과 대화 규칙의 통일은 다른 문제입니다. 공급자별 규칙 차이는 요청 모양 정리층이 흡수합니다.
- 컨텍스트 예산에는 도구 정의와 실제 출력 한도가 들어가야 합니다.
- 잘린 도구 호출은 다시 직렬화하고, 이유와 대안을 그 에이전트가 가진 도구에 맞춰 말로 알립니다.
- 잘린 답변은 구분자 없이 이어 쓰고, 이어 쓰기가 실패해도 받은 글은 지킵니다.
- 사람에게 보여 줄 것과 모델이 읽을 것은 따로 정합니다.
- 엔드포인트가 이유를 숨기면, 우리가 보낸 요청의 지문을 크기만으로 남깁니다.

   장단점이 있을까요?

   쪽이 나을까요?
