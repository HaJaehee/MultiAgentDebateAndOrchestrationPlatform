# ADR-021. 사람이 그린 그래프로 토론 흐름을 정한다

> [ADR 목록](README.md) · 이전: [ADR-020](ADR-020-conversation-memory.md) · 다음: [ADR-022](ADR-022-knowledge-base-deferred.md)

## 상태 (Status)

채택됨 · 2026-09-17 (v0.9.0) · 관련: [ADR-006](ADR-006-airgap-first-packaging.md), [ADR-012](ADR-012-agent-owned-debate-order.md)

## 맥락 (Context)

- 기존의 4개 토론 전략(순차 토론, 디베이트, 동적 지명, 병렬 지시)은 발언 순서를 UI 카드 정렬 순서나 오케스트레이터의 동적 판단에 의존했습니다. 토론 흐름의 구조적 형태는 백엔드 전략 파이썬 코드가 고정적으로 결정했습니다.
- "기획 설계 → 구현과 보안 검토를 동시에 병렬 수행 → 두 결과를 통합하여 게이트 판정 → 판정 미통과 시 구현 단계로 롤백 재작업"과 같은 복합적인 실무 워크플로는 기존의 어떠한 단일 전략으로도 표현할 수 없었습니다. 병렬 분기(Fork), 합류(Join), 조건부 피드백 루프(Loop)가 필수적이었습니다.
- 이러한 비정형 다자간 워크플로가 요구될 때마다 새로운 전략 파이썬 코드를 매번 개별 작성하는 방식은 확장성에 한계가 있었습니다. 토론 흐름 자체를 선언적인 **데이터(Data)**로 표현할 수 있어야 했습니다.
- 워크플로 흐름을 시각적으로 저작하려면 웹 화면에 캔버스 노드 편집기가 필요했습니다. 순수 파이썬만으로 이를 구현하기는 매우 어려웠고, 완성도 높은 오픈소스 라이브러리(Vue Flow)는 통상 npm이나 공용 CDN을 통해 배포되었습니다. 그러나 외부 네트워크가 차단된 폐쇄망 환경에서는 두 방식 모두 불가능했습니다.
- 오케스트레이션 엔진은 이미 상당한 복잡성을 지니고 있었으므로, 신규 기능 추가로 인해 기존 4개 전략의 안정적 동작이 교란되어서는 안 되었습니다.

## 결정 (Decision)

**다섯 번째 전략으로 '그래프 기반 토론(Graph Debate)'을 시스템에 추가하도록 합니다.**

그래프 데이터 모델:

- 노드 유형은 시작(Start), 에이전트(Agent), 병합(Merge), 품질 게이트(Gate: Yes/No), 종료(End) 5종으로 정의합니다. 각 연결선(Edge)마다 전문 전달, 요지 전달, 코드 참조 중 어떤 컨텍스트 전달 모드를 적용할지 선언합니다.
- 그래프 정의는 애플리케이션 데이터 디렉터리 내에 독립된 JSON 파일로 저장하며, 대화 세션은 이 중 하나를 선택하여 바인딩합니다. **새로운 턴이 시작되는 시점에 해당 그래프 정의를 세션 레코드에 불변으로 동결(Freeze)합니다.** 토론 진행 도중 사용자가 원본 JSON 파일을 수정하거나 삭제하더라도 이미 시작된 턴은 전혀 영향을 받지 않습니다.
- JSON 파일에는 기본값과 상이한 속성값만을 직렬화하여 기록합니다. 관리자가 텍스트 에디터로 직접 열어보더라도 핵심 커스텀 설정만을 직관적으로 파악할 수 있도록 합니다.
- 토론에 참여하는 에이전트는 로스터 UI의 체크박스가 아니라 그래프 캔버스에 배치된 에이전트 노드에 의해 결정됩니다. 본 전략을 선택할 경우 로스터의 체크박스는 그래프 구성에 종속되어 비활성화(Lock)됩니다.

분산 DAG 스케줄러 실행 메커니즘:

- 새로운 입력을 수신한 모든 활성 노드들은 단일 슈퍼스텝(Superstep) 주기 내에서 동시 병렬로 실행됩니다 (최대 동시 실행 상한 및 실패 기록 규칙은 병렬 전략과 동일). 각 노드의 출력 데이터는 해당 스텝의 말미에 다음 노드로 일괄 라우팅됩니다.
- 복수의 선행 입력을 대기하는 병합 노드는 순방향(Forward) 입력만을 대기합니다. 피드백 루프로 인해 역방향으로 되돌아오는 백엣지(Back-edge) 연결선은 시작 노드로부터의 깊이 우선 탐색(DFS)을 통해 사전 식별하여 대기 조건에서 제외합니다.
- 품질 게이트 노드는 도구 실행 권한이 없는 경량 오케스트레이터 모델이 `판정: Yes/No, 근거: ...` 포맷으로 평가를 수행합니다. 응답 형식이 파싱되지 않을 경우 안전한 기본(False) 분기로 폴백하며 해당 사실을 시스템 로그에 기록합니다. 게이트는 판정 결과 메모와 함께 자신이 평가했던 입력 데이터를 후속 노드로 전달합니다.
- 토론 종료 조건은 종료 노드 도달, 실행 가능한 활성 노드 부재, 최대 스텝 한도 초과, 사용자 강제 중지 4가지입니다. 개별 노드 방문 횟수 상한의 기본값은 대화의 최대 라운드 수이며, 전체 스텝 상한은 모든 노드 방문 상한의 합으로 안전하게 제한합니다.

그래프 무결성 사전 검증:

- 턴 시작 시점과 UI 로스터 진입 시점에 동일한 그래프 유효성 검증을 엄격히 수행합니다. 시작 노드 유일성(정확히 1개), 종료 노드로의 도달 가능성, 배치된 에이전트의 실재성 및 활성화 여부(오케스트레이터 제외), 게이트 판정 질문의 존재, 올바른 입출력 포트 연결, 그리고 **품질 게이트를 경유하지 않는 무한 루프 순환(Cycle)의 부재**를 검증합니다.
- 검증에 실패한 비정상적인 그래프는 사용자 요청을 **데이터베이스에 기록하기 전에** 즉시 거절합니다.

엔진과의 결합도 최소화:

- 오케스트레이션 엔진은 라운드 루프에 진입하기 직전에 **단 1회만** 그래프 실행기로 분기합니다. 사전 계획 수립, 최종 종합 보고서 생성, 산출물 탭 구성, 결정 장부 갱신 로직은 기존 코드를 100% 동일하게 공유합니다.
- 그래프 스키마 선언, 무결성 검증기, 스케줄링 계산기는 LLM 호출이나 DB I/O를 전혀 모르는 부수 효과 없는 순수 모듈로 격리 구축합니다.
- 노드의 모든 발언 출력에 원본 노드 ID와 출력 포트를 메타데이터로 기록하며, 노드 방문 횟수, 게이트 분기 이력, 활성화된 연결선 경로는 **발언 레코드 이력으로부터 결정론적으로 역계산(Replay)**합니다.

내장 캔버스 편집기:

- 캔버스 UI 편집기로 Vue Flow를 채택하되, 모든 서드파티 의존성을 단일 독립 ES 모듈(156KB)로 번들링하여 **애플리케이션 내부에 정적으로 동봉**합니다. NiceGUI가 이미 내장하고 있는 Vue.js 런타임만을 바인딩하여 사용합니다. 오픈소스 라이선스 고지와 재빌드 가이드를 함께 수록합니다.
- 소스 업데이트 패키징 스크립트는 이 번들 파일이 누락될 경우 패키징을 즉시 중단합니다. 정적 자산 디렉터리명은 `vendor`로 명명하지 않습니다. 외부 런타임 패키지 혼입을 막기 위해 패키징 스크립트의 제외 금지 목록에 해당 단어가 등록되어 있기 때문입니다.
- 편집 중인 노드와 엣지의 드래그 상태는 브라우저 로컬 메모리에서만 유지하며, 서버에는 오직 최종 '저장' 버튼 클릭 시에만 일괄 전송합니다. 빈번한 드래그 이벤트로 WebSocket 대역폭이 고갈되는 것을 방지하기 위함입니다.

## 결과 (Consequences)

**좋아지는 점**

- 복잡한 병렬 분기, 다자간 합류, 조건부 검토 루프를 소스 코드 수정 없이 시각적 다이어그램 저작만으로 유연하게 구축할 수 있게 되었습니다.
- 기존 4개 전략과 카드 정렬 기반의 직관적인 사용자 경험은 조금도 훼손되지 않고 그대로 유지되었습니다.
- 실시간 스트리밍 모니터링 화면, 새로고침한 화면, 과거 이력을 다시 열람한 세션 모두가 동일하고 정확한 그래프 실행 진행도를 렌더링합니다. 발언 레코드로부터 실행 궤적을 역계산하기 때문입니다.
- 캔버스 편집기가 외부 CDN 연결이 전무한 순수 오프라인 폐쇄망에서 완벽히 구동됩니다. 통합 검증 페이지를 통해 노드 렌더링, 드래그 앤 드롭 연결, 한글 텍스트 입출력, 모든 비동기 통신이 로컬 Uvicorn 서버 내에만 머무르는 것을 엄밀히 확인했습니다.

**치르는 비용**

- 사용자가 저작한 그래프의 복잡도에 따라 턴당 모델 호출 횟수가 급격히 증가할 수 있습니다. 이에 대응하여 그래프 검증 UI 화면에서 **해당 워크플로의 턴당 최악의 LLM 호출 횟수(Worst-case Call Count)**를 사전에 계산하여 안내하도록 조치했습니다.
- 번들링된 프론트엔드 정적 라이브러리를 재빌드하는 유지보수 절차가 추가되었습니다. Vue Flow 라이브러리 버전을 업데이트하려면 인터넷이 연결된 외부 빌드 머신에서 번들링 파이프라인을 재수행해야 합니다.
- 기본 테마에서 선택된 연결선 색상이 어두운 다크 모드 캔버스 배경에서 식별하기 어려운 결함이 배포 직후 발견되었습니다 (v0.9.0.1에서 긴급 패치). 외부 UI 라이브러리를 동봉할 경우 해당 라이브러리의 기본 스타일 한계까지 호스트가 떠안아야 함을 확인했습니다.

**검증 알고리즘 설계에서 얻은 교훈**

초기 검증 로직은 "강하게 연결된 컴포넌트(SCC)마다 내부에 게이트 노드가 하나 이상 존재하는가"를 기준으로 무한 루프를 판별했습니다. 그러나 게이트가 없는 순환 루프가 게이트를 포함한 다른 대형 루프와 동일한 컴포넌트로 묶여 있을 경우, 게이트 없는 순환이 검증을 그대로 통과해 버리는 심각한 버그가 있었습니다. 현재는 **"그래프에서 모든 게이트 노드를 임시 제거했을 때, 잔여 그래프에 유향 순환(Cycle)이 전혀 존재하지 않아야 한다"**는 방식으로 알고리즘을 전면 개편했습니다. 검증 조건을 "무엇이 포함되어 있어야 한다"보다 "핵심 요소를 제거했을 때 특정 결함 패턴이 존재하지 않아야 한다"는 방식으로 전환할 때 훨씬 수학적으로 견고한 방어막을 구축할 수 있습니다.
