# ADR-045. Claude 연결에서 다음 요청에도 그대로일 자리에 프롬프트 캐시 표시를 단다

> [ADR 목록](README.md) · 이전: [ADR-044](ADR-044-runtime-queue-and-checkpoint-retention.md)

## 상태 (Status)

채택됨 · 2026-11-01 (v1.5.1) · 관련: [ADR-002](ADR-002-litellm-gateway.md), [ADR-020](ADR-020-conversation-memory.md), [ADR-025](ADR-025-resume-speeches-by-tool-step.md), [ADR-039](ADR-039-lazy-tool-schemas.md), [ADR-040](ADR-040-compact-stale-file-reads.md)

## 맥락 (Context)

- 결정 장부와 라운드 번호를 마지막 메시지로 옮겨 프롬프트 앞부분이 변하지 않게 했지만([ADR-020](ADR-020-conversation-memory.md)), 이 덕을 보는 것은 앞부분을 알아서 캐시하는 OpenAI·Gemini·vLLM뿐이었습니다. Claude는 `cache_control` 표시를 단 자리까지만 캐시하므로 Anthropic·Bedrock 연결은 매 요청을 전액으로 처리했습니다.
- Claude의 캐시는 도구 → 시스템 → 메시지 순서의 접두를 바이트 단위로 비교하고, 표시는 요청당 4개까지입니다. 바뀌는 글 뒤에 표시를 달면 쓰기 할증(입력 단가의 1.25배)만 내고 한 번도 읽히지 않으므로, 어디에 다는지가 효과를 결정합니다.
- 토론의 맥락은 라운드마다 뒤쪽만 늘어나는 구조가 아닙니다. 발언자가 다시 말하고 나면 그 전에 원문으로 받았던 남의 긴 발언이 요지로 줄어듭니다(`build_context_for_agent`의 `body_for`). 그래서 일반적인 "마지막 블록에 표시" 방식은 다음 라운드에서 읽히지 않습니다.
- `merge_consecutive_roles`는 연속된 `user` 메시지를 한 글로 합칩니다. 합친 뒤에는 목표 메시지가 어디서 끝나는지 알 수 없어, `build_completion_kwargs()`에서 표시를 달 방법이 없었습니다.

## 결정 (Decision)

### 1. 다섯 자리를 정하고, 넘치면 도구 정의의 표시를 뺀다

| 자리 | 어디서 다시 읽히는가 |
| :--- | :--- |
| 마지막 도구 정의 | 같은 모델과 같은 도구를 쓰는 다른 에이전트 |
| 시스템 프롬프트 | 이 에이전트의 모든 호출 |
| 목표 메시지의 끝 | 뒤따르는 기록이 바뀌어도 이후 라운드에서 |
| 마지막 자기 발언 | 다음 라운드 |
| 도구 루프의 마지막 메시지 | 같은 발언의 다음 호출 |

발언을 시작하는 호출의 마지막 메시지(장부와 라운드 번호가 든 이번 차례 지시)에는 달지 않습니다. 도구를 부르지 않고 끝나는 발언이면 다시 읽히지 않기 때문입니다. 도구를 불렀으면 다음 호출의 표시가 그 지시까지 함께 덮습니다.

다섯 자리가 모두 있으면 도구 정의의 표시를 뺍니다. 시스템 프롬프트의 표시가 앞선 도구 정의까지 함께 덮으므로, 잃는 것은 다른 에이전트와 나눠 쓰는 몫뿐입니다.

### 2. 표시는 요청 사본에 달되, 목표만 합치기 전에 단다

`build_completion_kwargs()`가 `with_cache_marks()`로 사본에 표시를 답니다. 도구 루프는 같은 메시지 목록에 호출을 쌓으므로, 원본에 달면 표시가 호출마다 늘어납니다.

목표의 표시만 `_call_agent_once`에서 `merge_consecutive_roles` 전에 답니다(`mark_goal`). 목표를 블록으로 바꿔 두면 합칠 때도 경계가 남고, 컨텍스트를 자를 때 덧붙는 생략 안내도 목표 글을 바꾸지 않습니다. 두 자르기 모두 이 자리를 남기므로 표시가 메시지에 남아도 발언 동안 그대로이고, 끊긴 발언을 이어 갈 때도 같은 모양으로 돌아옵니다([ADR-025](ADR-025-resume-speeches-by-tool-step.md)).

### 3. LiteLLM이 Claude 형식으로 옮겨 주는 연결에만 단다

`anthropic`, `bedrock`, `vertex_ai`, `azure_ai` 경로에서 모델 이름에 `claude`가 있을 때만 답니다(`anthropic` 경로는 별칭도 허용). LiteLLM 모델 표에 있으면 표를 따라 캐싱이 없는 옛 모델을 건너뛰고, 표에 없으면 답니다. 표는 새 모델보다 늦고 옛 이름은 표에서 빠지기도 하기 때문입니다.

`openai/claude-…`처럼 게이트웨이를 거치는 경로는 넣지 않습니다. LiteLLM이 표시를 지우고 보내므로 효과가 없고, 메시지 모양만 바뀌어 엄격한 서버에 거절될 수 있습니다. 다른 연결은 요청이 전과 한 글자도 다르지 않습니다.

### 4. 설정은 `prompt_cache` 하나로 둔다

`llm`이나 `agents.<키>`에 `"5m"`(기본), `"1h"`, `"off"` 중 하나를 적습니다. 끄는 길이 필요한 이유는 표시가 요청 모양을 바꾸는 데다, Anthropic 형식을 흉내 내는 게이트웨이가 이 필드를 거절할 수 있기 때문입니다. 수명을 고르는 길이 필요한 이유는 에이전트의 다음 발언이 5분 넘게 뒤에 시작되면 라운드 사이의 표시가 읽히지 않기 때문입니다. 표시가 모두 같은 수명이므로 "긴 수명이 앞에 와야 한다"는 규칙에 걸리지 않습니다.

폴백으로 바뀐 모델은 전역 값을 씁니다. 연결에 딸린 설정이기 때문입니다([ADR-030](ADR-030-fallback-to-the-global-model.md)).

### 5. 쓴 토큰도 센다

`Usage`에 `cache_write_tokens`를 더하고 발언 카드 툴팁에 `캐시 쓰기`로 표시합니다. 캐시가 실제로 이득인지는 읽은 양과 쓴 양을 함께 봐야 알 수 있습니다.

### 검토했지만 택하지 않은 것

- **요청 최상위의 자동 캐싱(`cache_control`)**: 표시 하나가 마지막 블록에 달립니다. 이번 차례 지시 뒤에 달려 도구를 부르지 않는 발언은 할증만 내고, 라운드 경계도 잡지 못합니다. 옛 Bedrock 경로는 이 필드를 거절합니다.
- **`merge_consecutive_roles`를 Claude에서 끄기**: LiteLLM이 어차피 블록으로 합치지만, 모든 발언의 경계가 요청 모양에 드러나 토큰 어림과 자르기가 전제하는 모양이 Claude에서만 달라집니다. 목표만 떼어 내면 충분합니다.

## 결과 (Consequences)

실제 엔진으로 전문가 3명의 토론을 돌려 나간 요청을 LiteLLM 변환에 통과시키고, Claude의 접두 규칙(표시마다 20칸까지 되짚기)을 흉내 낸 캐시로 잰 값입니다. 표시 없이 보낼 때의 입력 비용을 1로 둡니다. 읽기 0.1배, 쓰기 1.25배로 계산하며 캐시 만료는 없다고 가정합니다. 페르소나는 약 1,600자, 발언은 약 1,100자, 도구 결과는 약 1,800자이고 크기는 글자 수로 쟀습니다. **실제 API로 잰 값이 아닙니다.**

| 토론 | 전문가 호출 | 전체 호출 |
| :--- | ---: | ---: |
| 1라운드, 도구 없음 | 1.07 | 0.94 |
| 2라운드, 도구 없음 | 0.83 | 0.83 |
| 3라운드, 도구 없음 | 0.72 | 0.76 |
| 5라운드, 도구 없음 | 0.60 | 0.67 |
| 1라운드, 발언마다 도구 4번 | 0.46 | 0.50 |
| 3라운드, 발언마다 도구 4번 | 0.40 | 0.43 |
| 3라운드, 발언마다 도구 8번 | 0.29 | 0.30 |

**좋아지는 점**

- 도구 루프가 긴 발언일수록 크게 줄어듭니다. 요청 대부분이 그대로 반복되기 때문입니다.
- 도구를 쓰는 에이전트끼리 도구 정의를 나눠 읽습니다.
- `tests/test_prompt_cache.py`가 실제 엔진의 요청으로 접두 일치를 확인하므로, 프롬프트 조립을 고치다 표시 자리가 흔들리면 시험이 실패합니다.

**치르는 비용**

- 도구 없는 토론의 절감은 도구 루프보다 작습니다. 새 발언은 한 번은 전액으로 처리되고, 오래된 발언은 이미 요지로 줄어 있어 캐시로 아낄 몫이 적습니다([Conversation Memory §2.4](../../wiki/orchestration/context-memory.md)).
- 1라운드로 끝나는 도구 없는 토론에서는 전문가의 입력 비용이 약 7% 늘어납니다. 쓴 것을 읽을 다음 요청이 없기 때문입니다.
- 새 사용자 턴은 목표 메시지를 바꾸므로 기록 전체를 다시 씁니다. 도구 정의와 시스템 프롬프트의 캐시만 남습니다.
- 지연 로딩으로 도구를 불러오면 요청 맨 앞의 도구 정의가 바뀌어 그 발언에서 캐시를 한 번 다시 씁니다([ADR-039](ADR-039-lazy-tool-schemas.md)). 오래된 파일 읽기 압축과 컨텍스트 자르기도 그 뒤쪽을 다시 쓰게 합니다([ADR-040](ADR-040-compact-stale-file-reads.md)).
- 기본 수명 5분을 넘겨 다음 발언이 시작되면 라운드 사이의 표시는 쓰기 비용만 냅니다. 발언자가 많거나 도구 루프가 길면 `"1h"`를 검토해야 합니다.
- 이름에 `claude`가 없는 Bedrock ARN은 알아볼 수 없어 표시를 달지 않습니다.
