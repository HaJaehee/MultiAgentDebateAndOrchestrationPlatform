# ADR-045. Claude 연동 시 후속 요청에서 불변인 지점에 프롬프트 캐시 제어 마커를 주입하고 캐시 생성 토큰을 계측한다

> [ADR 목록](README.md) · 이전: [ADR-044](ADR-044-runtime-queue-and-checkpoint-retention.md)

## 상태 (Status)

채택됨 · 2026-11-01 (v1.5.1) · 관련: [ADR-002](ADR-002-litellm-gateway.md), [ADR-020](ADR-020-conversation-memory.md), [ADR-025](ADR-025-resume-speeches-by-tool-step.md), [ADR-039](ADR-039-lazy-tool-schemas.md), [ADR-040](ADR-040-compact-stale-file-reads.md)

## 맥락 (Context)

- 결정 장부와 라운드 번호를 마지막 메시지로 배치하여 프롬프트 접두사를 불변으로 유지하도록 개선했으나([ADR-020](ADR-020-conversation-memory.md)), 이는 공통 접두사를 자동으로 캐시하는 OpenAI, Gemini, vLLM에만 유효했습니다. Claude는 명시적으로 `cache_control` 마커가 지정된 지점까지만 캐시를 생성하므로, Anthropic 및 Bedrock 연동 시에는 매 요청마다 전체 프롬프트 비용이 발생했습니다.
- Claude의 프롬프트 캐시는 도구 정의 → 시스템 프롬프트 → 메시지 순서의 접두사를 바이트 단위로 비교하며, 마커는 요청당 최대 4개까지 지정할 수 있습니다. 가변 텍스트 뒤에 마커를 배치하면 캐시 생성 할증(입력 단가의 1.25배)만 발생하고 캐시 히트(적중)가 전혀 발생하지 않으므로, 마커 주입 위치 선정이 캐시 효율을 결정합니다.
- 토론 컨텍스트는 라운드가 진행됨에 따라 단순히 뒤쪽만 추가되는 구조가 아닙니다. 특정 발언자가 다음 턴에서 다시 발언할 때, 이전에 전문으로 전달되었던 타 에이전트의 긴 발언이 요약문으로 축약됩니다(`build_context_for_agent`의 `body_for`). 따라서 일반적인 "마지막 블록에 마커 지정" 방식은 다음 라운드에서 캐시 미스가 발생합니다.
- `merge_consecutive_roles`는 연속된 `user` 메시지를 단일 메시지로 병합합니다. 병합된 후에는 목표 메시지의 경계를 식별하기 어려워, `build_completion_kwargs()` 단계에서 마커를 지정할 수 없었습니다.

## 결정 (Decision)

### 1. 5개 캐시 마커 후보 위치 정의 및 한도 초과 시 도구 정의 마커 제외

| 마커 위치 | 캐시 재사용 대상 (Hit 대상) |
| :--- | :--- |
| 마지막 도구 정의 | 동일 모델 및 동일 도구를 공유하는 타 에이전트 호출 |
| 시스템 프롬프트 | 해당 에이전트의 모든 호출 |
| 목표(Goal) 메시지 끝 | 후속 대화 이력이 변동되더라도 이후 라운드에서 재사용 |
| 마지막 자체 발언 | 다음 라운드 발언 호출 |
| 도구 루프의 마지막 메시지 | 동일 발언 내 후속 도구 호출 루프 |

발언 시작 호출의 마지막 메시지(결정 장부와 라운드 정보가 포함된 턴 지시문)에는 마커를 지정하지 않습니다. 도구를 호출하지 않고 종료되는 단일 턴 발언의 경우 후속 재사용이 발생하지 않기 때문입니다. 도구를 호출한 경우에는 다음 루프 호출 시의 마커가 해당 지시문까지 포함하여 캐시합니다.

5개 후보 위치가 모두 존재하는 경우, 도구 정의의 마커를 제외합니다(최대 4개 제한 준수). 시스템 프롬프트의 마커가 선행하는 도구 정의까지 포함하여 캐시하므로, 타 에이전트 간 도구 정의 공유 캐시만 제외되고 에이전트 내부 캐시 효율은 유지됩니다.

### 2. 마커는 요청 페이로드 사본에 주입하되, 목표 메시지만 병합 전에 주입

`build_completion_kwargs()`가 `with_cache_marks()`를 통해 요청 사본에 마커를 주입합니다. 도구 실행 루프는 동일 메시지 목록에 호출을 누적하므로, 원본에 직접 주입하면 루프가 반복될 때마다 마커가 중복 누적됩니다.

목표(Goal) 메시지의 마커만 `_call_agent_once`에서 `merge_consecutive_roles` 실행 전에 사전 주입합니다(`mark_goal`). 목표 메시지를 콘텐츠 블록 구조로 변환해 두면 메시지 병합 시에도 블록 경계가 유지되며, 컨텍스트 자르기 과정에서 생략 안내문이 추가되더라도 목표 텍스트 자체는 변동되지 않습니다. 두 가지 자르기 전략 모두 이 위치를 보존하므로, 마커가 메시지에 잔존하더라도 발언이 진행되는 동안 불변으로 유지되며, 중단된 발언을 재개할 때도 동일한 형태로 복원됩니다([ADR-025](ADR-025-resume-speeches-by-tool-step.md)).

### 3. LiteLLM이 Claude 캐시 규격 변환을 지원하는 엔드포인트에만 주입

`anthropic`, `bedrock`, `vertex_ai`, `azure_ai` 공급자 경로에서 모델명에 `claude`가 포함된 경우에만 마커를 주입합니다(`anthropic` 경로는 별칭도 허용). LiteLLM 모델 테이블에 등록된 경우 테이블에 따라 캐싱을 지원하지 않는 구형 모델을 제외하고, 테이블에 미등록된 경우 주입을 시도합니다. 모델 테이블 갱신이 신규 모델 출시보다 지연될 수 있고 구형 모델명이 테이블에서 제거되는 경우도 있기 때문입니다.

`openai/claude-…`와 같이 게이트웨이를 경유하는 프록시 경로는 대상에서 제외합니다. LiteLLM이 해당 마커를 제거하고 전달하므로 실질적인 효과가 없고, 메시지 페이로드 구조만 변경되어 엄격한 프록시 서버에서 거절될 수 있습니다. 그 외 다른 연동 모델의 경우 기존 요청 페이로드와 완전히 동일하게 유지됩니다.

### 4. `prompt_cache` 단일 설정 옵션 제공

`llm` 또는 `agents.<key>` 섹션에 `"5m"`(기본값), `"1h"`, `"off"` 중 하나를 설정합니다. 비활성화(`"off"`) 옵션이 필요한 이유는 마커 주입이 요청 페이로드 구조를 변경하며, Anthropic 규격을 에뮬레이션하는 게이트웨이가 해당 필드를 거절할 수 있기 때문입니다. TTL 선택 옵션이 필요한 이유는 에이전트의 다음 발언이 5분 이상 경과한 후 시작될 경우 라운드 간 캐시가 만료되기 때문입니다. 모든 마커가 동일한 TTL을 공유하므로 "더 긴 TTL이 앞단에 와야 한다"는 제약 조건에 저촉되지 않습니다.

폴백(Fallback)으로 전환된 모델은 전역 기본 설정을 사용합니다. 연결 프로바이더에 종속된 설정이기 때문입니다([ADR-030](ADR-030-fallback-to-the-global-model.md)).

### 5. 캐시 생성/기록 토큰(Cache Creation Tokens) 계측

`Usage` 모델에 `cache_write_tokens` 필드를 추가하고 발언 카드 툴팁에 `캐시 쓰기`로 표시합니다. 캐시 도입의 실질적 효용을 파악하려면 캐시 적중(Read) 토큰과 캐시 생성(Write) 토큰을 함께 비교 계측해야 합니다.

### 검토했으나 채택하지 않은 대안

- **요청 최상위 수준의 자동 캐싱(`cache_control`)**: 단일 마커가 마지막 블록에만 자동 지정됩니다. 이번 턴 지시문 뒤에 마커가 배치되어 도구를 사용하지 않는 발언에서는 캐시 쓰기 할증만 발생하며, 라운드 경계 캐싱도 지원하지 못합니다. 구형 Bedrock 엔드포인트의 경우 해당 필드 자체를 거절합니다.
- **Claude 연동 시 `merge_consecutive_roles` 비활성화**: LiteLLM이 내부적으로 블록을 병합하지만, 모든 발언의 경계가 요청 페이로드에 직접 노출되어 토큰 추정치 및 컨텍스트 자르기 로직이 전제하는 메시지 구조가 Claude에서만 달라지게 됩니다. 목표 메시지만 분리하여 처리하는 것으로 충분합니다.

## 결과 (Consequences)

실제 오케스트레이션 엔진으로 전문가 3인의 토론을 수행하여 발생한 요청을 LiteLLM 변환기에 통과시키고, Claude의 접두사 규칙(마커당 20개 토큰 역추적 정렬)을 시뮬레이션한 캐시 모델로 계측한 결과입니다. 마커 없이 전송할 때의 입력 비용을 1.0으로 기준 삼아 계산했습니다. 캐시 읽기 0.1배, 캐시 쓰기 1.25배 단가를 적용하고 캐시 만료는 발생하지 않는다고 가정했습니다. 페르소나는 약 1,600자, 발언은 약 1,100자, 도구 실행 결과는 약 1,800자이며 크기는 문자 수 기준입니다. **실제 외부 API 호출로 계측된 수치가 아닌 시뮬레이션 측정값입니다.**

| 토론 시나리오 | 전문가 호출 비용 비율 | 전체 호출 비용 비율 |
| :--- | ---: | ---: |
| 1라운드, 도구 미사용 | 1.07 | 0.94 |
| 2라운드, 도구 미사용 | 0.83 | 0.83 |
| 3라운드, 도구 미사용 | 0.72 | 0.76 |
| 5라운드, 도구 미사용 | 0.60 | 0.67 |
| 1라운드, 발언당 도구 4회 호출 | 0.46 | 0.50 |
| 3라운드, 발언당 도구 4회 호출 | 0.40 | 0.43 |
| 3라운드, 발언당 도구 8회 호출 | 0.29 | 0.30 |

**도입 이점**

- 도구 실행 루프가 길어질수록 비용 절감 효과가 대폭 증가합니다. 이전 단계의 컨텍스트 대부분이 변경 없이 반복 재사용되기 때문입니다.
- 동일한 도구 세트를 사용하는 에이전트 간에 도구 스키마 정의 캐시를 공유합니다.
- `tests/test_prompt_cache.py`를 통해 실제 엔진 요청에 대한 접두사 일치 여부를 정밀 검증하므로, 프롬프트 조립 로직 수정 시 마커 위치 오차가 발생하면 테스트가 즉시 실패합니다.

**고려 사항 및 비용**

- 도구를 사용하지 않는 토론의 경우 비용 절감 폭이 도구 루프에 비해 상대적으로 작습니다. 신규 발언은 최초 1회 전체 비용이 발생하며, 이전 발언들은 이미 요약문으로 압축되어 캐시를 통한 절감 여지가 적기 때문입니다([Conversation Memory §2.4](../../wiki/orchestration/context-memory.md)).
- 1라운드로 종료되는 도구 미사용 토론에서는 전문가 에이전트의 입력 비용이 약 7% 증가합니다. 캐시에 기록된 내용을 재사용할 후속 요청이 발생하지 않기 때문입니다.
- 새로운 사용자 턴이 시작되면 목표 메시지가 변경되므로 대화 이력 전체를 다시 캐시에 기록해야 합니다. 도구 정의와 시스템 프롬프트 캐시만 유지됩니다.
- 도구 지연 로딩(Lazy Loading)으로 신규 도구를 로드하면 요청 최상단의 도구 정의가 변경되어 해당 발언에서 캐시가 1회 재생성됩니다([ADR-039](ADR-039-lazy-tool-schemas.md)). 과거 파일 읽기 결과 압축 및 컨텍스트 자르기 발생 시에도 해당 지점 이후의 캐시가 재생성됩니다([ADR-040](ADR-040-compact-stale-file-reads.md)).
- 기본 TTL인 5분을 초과하여 다음 발언이 시작되면 라운드 간 마커는 캐시 생성 비용만 발생합니다. 발언자 수가 많거나 도구 루프가 길어지는 환경에서는 `"1h"` 설정을 권장합니다.
- 모델명에 `claude`가 명시되지 않은 Bedrock ARN 엔드포인트는 자동 감지가 불가능하여 캐시 마커가 주입되지 않습니다.
