# ADR-017. 저장 실패로 결과물을 잃지 않는다

> [ADR 목록](README.md) · 이전: [ADR-016](ADR-016-per-workspace-mcp-runtime.md) · 다음: [ADR-018](ADR-018-orchestrator-writes-conclusions.md)

## 상태 (Status)

채택됨 · 2026-09-13 (v0.7.1) · 관련: [ADR-004](ADR-004-sqlite-persistence.md), [ADR-014](ADR-014-tool-failure-is-observation.md)

## 맥락 (Context)

사용자가 자리를 비워 화면 보호기가 작동하거나 화면이 잠긴 사이, 최종 종합 보고서 저장 트랜잭션이 `database is locked` 오류로 실패하는 사고가 발생했습니다. 해당 보고서 텍스트는 WebSocket을 통해 브라우저 화면에는 실시간으로 스트리밍되었기 때문에 겉으로는 아무 이상이 없는 것처럼 보였으나, 사용자가 브라우저를 새로고침하자 데이터가 흔적도 없이 사라졌습니다. 원인은 두 가지였으며, 어느 하나만으로도 데이터 유실을 유발하기에 충분했습니다.

1. **SQLite 데이터베이스를 초기 기본 설정 그대로 사용했습니다.** 트랜잭션 잠금 대기 시간(`busy_timeout`)이 고작 5초에 불과했고, 기본 롤백 저널 모드로 인해 쓰기 트랜잭션마다 파일 시스템 상에서 저널 파일을 생성하고 삭제하는 작업이 반복되었습니다. Windows 운영체제 환경에서는 타 프로세스가 읽기 핸들로 열어 둔 파일의 원자적 교체가 불가능하므로, 백신 프로그램의 실시간 검사, Windows Search 색인기, 백업 및 동기화 에이전트가 SQLite 파일을 단 몇 초만 점유해도 데이터베이스 쓰기가 즉각 실패합니다. 공교롭게도 Windows는 사용자가 입력을 멈추고 자리를 비웠을 때 바로 이러한 백그라운드 유지보수 작업을 집중 실행합니다.
2. **데이터베이스 쓰기 실패를 단순 콘솔 로그 한 줄로만 남기고 조용히 삼켜버렸습니다.** 일반 발언 하나가 저장에 실패했다고 해서 전체 토론 프로세스를 강제 중단하면 뒤이어 나올 모든 후속 발언까지 유실되므로, 당시의 예외 처리 의도 자체는 타당했습니다. 그러나 문제는 토론의 최종 결실인 종합 보고서 산출물마저 동일한 느슨한 예외 처리 경로를 탔다는 점입니다.

더불어, 기존 데이터베이스 기술 문서에는 소스 코드에 실제로 적용되지 않은 WAL 설정이 마치 적용된 것처럼 잘못 기술되어 있었습니다. 문서와 실제 구현의 괴리 역시 원인 분석을 지연시킨 주된 요인이었습니다.

## 결정 (Decision)

**잠금 해제를 충분히 기다리고, 실패 시 즉시 재시도하며, 끝내 실패할 경우 파일 시스템에 비상 보존한 뒤 사용자에게 영구 알림을 띄우고 토론을 지속하도록 합니다.**

연결 및 엔진 설정:

- SQLite 데이터베이스 연결 시마다 잠금 대기 시간을 30초로 대폭 증액하고, WAL(Write-Ahead Logging) 저널 모드를 활성화하며, 동기화 수준을 `NORMAL`로 구성합니다.
- 단, 데이터베이스 파일이 **네트워크 공유 스토리지**(UNC 경로, 네트워크 드라이브 등)에 위치한 경우에는 WAL 모드를 활성화하지 않습니다. WAL 모드는 OS 공유 메모리(`-shm`)를 통해 동시성을 조율하는데, 대다수 네트워크 파일 시스템은 이를 완벽히 보장하지 못해 데이터 손상이 발생할 수 있기 때문입니다. 단, 30초의 잠금 대기 시간은 네트워크 환경에서도 동일하게 적용합니다.

통합 영속화 파이프라인:

- 오케스트레이션 엔진의 모든 데이터베이스 쓰기 작업(전문가 발언, 도구 실행 로그, 최종 산출물, 사용자 개입 발언, 안내 시스템 메모)을 **단일 저장 파이프라인(Persistence Pipeline)**으로 일원화합니다.
- 데이터베이스 쓰기 실패 시 트랜잭션을 즉시 롤백하고, 2초 및 5초 간격으로 지수 백오프 재시도를 수행합니다 (SQLite 자체 30초 대기 위에 추가 적용). 롤백 수행 시 세션에 바인딩되었던 ORM 인스턴스가 분리되므로, 재시도 시마다 동일한 고유 ID를 가진 신규 모델 인스턴스를 생성하여 저장합니다.
- 모든 재시도가 최종 실패할 경우, 저장 대상 데이터 전문을 애플리케이션 데이터 디렉터리 내의 비상 미저장 폴더(`unpersisted/`)에 마크다운 파일로 즉시 비상 덤프합니다. 파일 헤더에는 세션 ID와 예외 스택트레이스를 명시하며, 최종 종합 보고서의 경우 파일명에 `synthesis` 접두사를 부여하여 관리자가 가장 먼저 식별할 수 있도록 조치합니다.
- UI 화면에 사용자가 명시적으로 닫을 때까지 화면에 고정 잔존하는 영구 경고 배너를 띄웁니다.
- 데이터베이스 기록 실패가 발생하더라도 상위 토론 엔진으로 예외를 전파하지 않습니다 (취소 신호 제외). 저장 실패 예외가 토론을 중단시킬 경우 이후 생성될 모든 후속 논의를 유실하게 되기 때문입니다.

문서화 정합성:

- 데이터베이스 아키텍처 문서를 실제 런타임 코드베이스의 동작과 일치하도록 전면 개정합니다.

## 결과 (Consequences)

**좋아지는 점**

- 타 프로세스가 SQLite 파일에 7초간 쓰기 락을 독점 점유하는 극한 상황을 모사하여 벤치마크를 수행했습니다. 개선 전에는 5.5초 만에 `database is locked` 예외가 발생하며 저장이 실패했으나, 개선 후에는 7초간 정상 대기한 뒤 트랜잭션을 완벽히 성공시켰습니다.
- 최악의 잠금 경합이 발생하더라도 생성된 최종 산출물이 디스크 파일로 안전하게 보존되며, 사용자는 저장 실패 사실과 비상 파일의 위치를 즉시 인지할 수 있습니다.

**치르는 비용**

- WAL 모드 적용으로 인해 메인 DB 파일 옆에 `-wal` 및 `-shm` 임시 파일이 상시 생성됩니다. 빌드 및 패키징 스크립트에서 이 파일들이 아카이브에 포함되지 않도록 제외 규칙을 확인했습니다.
- 네트워크 드라이브에 SQLite를 배치한 환경은 여전히 잠금 경합에 취약합니다. 운영 매뉴얼에 "SQLite DB 파일은 반드시 로컬 SSD 디스크에 배치하고, 백신 프로그램의 실시간 감시 및 클라우드 동기화 대상에서 제외할 것"을 명시했습니다.
- 비상 덤프된 마크다운 파일을 SQLite 데이터베이스로 자동 재적재하는 역동기화 기능은 별도로 제공하지 않습니다. 관리자가 내용을 직접 검토한 뒤 필요시 수동으로 반영합니다.

**교훈**

- 시스템 경고 알림은 **해당 장애가 실제로 발생하는 비즈니스 상황**에 적합하게 설계되어야 합니다. 이 장애는 대개 사용자가 자리를 비웠을 때 발생하므로, 몇 초 뒤 자동으로 사라지는 토스트 팝업은 아무런 쓸모가 없습니다.
- "실패하면 조용히 버린다"와 "실패하면 전체를 멈춘다"는 극단적인 양자택일 사이에 제3의 올바른 선택지가 존재합니다. **외부에 안전하게 비상 보존하고, 사용자에게 정직하게 알리며, 전체 시스템은 중단 없이 계속 진행하는 것입니다.**
