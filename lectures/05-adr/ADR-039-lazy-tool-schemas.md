# ADR-039. 도구 정의는 자주 쓰는 것만 싣고, 나머지는 한 줄 목록에서 불러와 그 대화에 남긴다

> [ADR 목록](README.md) · 이전: [ADR-038](ADR-038-edit-the-ledger-directly.md)

## 상태 (Status)

채택됨 · 2026-10-31 (v1.5.1) · 관련: [ADR-026](ADR-026-skills-as-host-tools.md), [ADR-025](ADR-025-resume-speeches-by-tool-step.md)

## 맥락 (Context)

- MCP 도구의 정의는 요청마다 입력 토큰으로 나갑니다. 실제 서버로 재면 filesystem·memory·git 35개가 5,292 토큰이고, sandbox 까지 42개면 8,078 토큰입니다 (`openai/gpt-4o` 토크나이저). 도구 루프가 판을 돌 때마다 다시 나가고, 컨텍스트 예산에서도 그만큼 빠집니다.
- 스킬은 이 문제를 이미 풀었습니다. 설명 한 줄만 보여 주고 본문은 부를 때 줍니다([ADR-026](ADR-026-skills-as-host-tools.md)). 도구 정의에는 같은 장치가 없었습니다.
- 그대로 옮길 수 없는 사정이 셋 있습니다.
  - 스킬 본문은 도구 결과로 돌아오지만, 도구 정의는 요청의 `tools` 에 있어야 네이티브 도구 호출이 됩니다.
  - 상시 지침과 한도 안내가 도구 이름을 짚습니다(`file_writing_guidance`, `file_editing_guidance`, `truncation_advice`, 메모리 안내, 스킬 스크립트 실행). 이름만 알려 주고 정의를 빼면 인자를 모른 채 부르게 됩니다.
  - 불러오는 한 판은 공짜가 아닙니다. 대화 전체를 다시 보내므로, 발언마다 불러오면 아낀 것보다 더 씁니다.

## 결정 (Decision)

### 1. 호스트 도구 하나로 불러온다

`tools__load_tools` 의 설명에 `- 이름: 설명의 첫 문장` 목록을 담고, 호출을 받으면 그 도구의 정의를 다음 요청의 `tools` 에 싣습니다. 결과는 불러왔다는 글뿐이고 정의 자체는 `tools` 로 갑니다. 그래야 모델이 평소처럼 네이티브 호출을 만들고, 도구 카드, 도구 보안, 잘림 처리, 초안이 그대로 동작합니다.

불러온 뒤에는 `ToolLoop.tools` 와 `schema_tokens` 를 함께 고칩니다. 컨텍스트 예산은 그 값을 보므로 이번 발언의 다음 판부터 늘어난 몫을 반영합니다.

정의를 도구 결과로 돌려주고 대리 호출 도구(`tools__call_tool`)로 실행하는 안은 버렸습니다. `tools` 가 바뀌지 않아 프롬프트 캐시에는 유리하지만, 정의가 메시지에 있어 컨텍스트를 자를 때 함께 사라지고, 호출 이름이 모두 하나가 되어 도구 보안과 잘림 처리와 기록이 전부 풀어 읽어야 합니다. 스키마 없이 JSON 을 만드는 모델의 품질도 보장되지 않습니다.

### 2. 지침이 이름을 짚는 도구는 항상 싣는다

`tools_named_by_guidance()` 가 지침과 **같은 함수로** 골라 항상 싣습니다. 그래서 나눈 목록에서 지침을 지어도 글이 같습니다(테스트가 지킵니다). `core_tools` 로 뺄 수 없습니다. 그 밖에는 `tool_loading.core_tools`(기본값은 지침이 짚지 않지만 거의 모든 발언이 쓰는 도구)와, 도구가 3개 이하인 서버를 싣습니다. 작은 서버는 몇 줄을 아끼려고 그 서버의 전부인 도구를 숨길 까닭이 없습니다.

### 3. 아낄 것이 있을 때만 나눈다

목록으로 요청당 `min_saving_tokens`(기본 1,000)를 아끼지 못하면 전부 싣습니다. 실제 서버 기준입니다.

| 서버 | 도구 | 싣는 토큰 | 아끼는 몫 |
| :--- | :--- | :--- | :--- |
| filesystem + memory + git | 35 → 11 | 5,292 → 2,175 | 59% |
| + sandbox | 42 → 16 | 8,078 → 4,465 | 45% |
| filesystem + memory | 23 → 9 | 3,731 → 1,861 | 50% |
| filesystem + sandbox | 21 → 11 | 4,868 → 3,477 | 29% |
| git | 12 → 3 | 1,563 → 479 | 69% |
| filesystem, memory, sandbox 하나씩 | 그대로 | 그대로 | 나누지 않음 |

sandbox 는 도구 대부분이 지침 대상이고 설명이 길어(`execute_python_code`, `run_python_file` 각 800 토큰) 줄어드는 폭이 작습니다.

### 4. 불러온 도구는 그 대화의 그 에이전트에게 남긴다

발언이 끝나면 도구 루프가 사라지므로, 스킬처럼 발언 단위로 두면 다음 발언이 또 한 판을 씁니다. 그래서 (대화, 에이전트) 별로 불러온 순서를 기억해 다음 발언에 싣습니다. 요청의 앞부분이 그대로이니 프로바이더의 접두사 캐시도 유지됩니다. 많이 불러 봐야 전부 싣는 지금과 같아질 뿐입니다.

기억은 프로세스 안에만 둡니다. 재시작으로 잃어도 한 번 더 불러오면 되므로 DB 에 넣지 않습니다. 끊긴 발언은 초안의 `loaded_tools` 로 되살립니다(`SPEECH_STATE_VERSION` 2).

### 5. 목록의 도구를 곧바로 불러도 실행한다

모델이 목록에서 이름을 보고 불러오지 않은 채 호출하면, 평소처럼 도구 보안을 거쳐 실행하고 그 뒤로 정의를 싣습니다. 거절하고 다시 부르게 하면 판을 하나 더 쓰는데, 인자가 맞으면 그럴 이유가 없고, 틀리면 서버가 거절합니다. 실패하면 결과 뒤에 정의를 보고 다시 부르라고 덧붙입니다. 안전은 인자 검증이 아니라 도구 보안이 맡습니다. 거부된 호출은 불러오지 않습니다.

`tools__load_tools` 자체는 파일과 네트워크를 건드리지 않아 판정을 받지 않습니다. 늘 거부될 도구는 목록을 만들기 전에 `filter_tools` 가 뺍니다. 호스트 도구이므로 `mcp_servers.tools` 는 예약어입니다.

### 6. 단계별 주입은 하지 않는다

계획, 발언자 선택, 판정, 장부, 요약은 이미 도구 없는 호출입니다(`ConversationMemory.tool_less`). 도구가 실리는 곳은 발언과 합성인데, 그 안에서 무슨 도구가 필요한지는 단계가 아니라 일이 정합니다. 단계별로 도구를 고르면 더 줄어드는 몫은 적고, 그 단계에 넣지 않은 도구를 쓰지 못하는 실패만 늡니다.

## 결과 (Consequences)

좋아지는 점:

- 도구가 많은 에이전트의 요청이 요청마다 약 3,100 토큰 가벼워지고(filesystem·memory·git), 전사가 쓸 수 있는 예산이 그만큼 늘어납니다.
- 서버를 더 붙여도 정의가 아니라 목록 줄만 늘어납니다.
- 도구가 적은 에이전트의 요청은 달라지지 않습니다.

치르는 비용:

- 목록의 도구를 처음 쓸 때 한 판이 더 듭니다. 그 판은 대화 전체를 다시 보내므로, 전사가 길고 그 대화에서 몇 판 돌지 않는 에이전트라면 손해일 수 있습니다. 실제 토론에서 불러오는 빈도는 아직 재지 않았습니다. 도구 카드에서 `tools__load_tools` 로 같은 도구를 자주 불러오면 그 도구를 `core_tools` 에 넣으세요.
- 도구를 불러오면 `tools` 가 바뀌어 프로바이더의 접두사 캐시가 그 시점에 한 번 깨집니다.
- 목록을 무시하고 도구 없이 답하는 모델이 있을 수 있습니다. 상시 지침이 막으려 하지만 보장은 아닙니다. 그런 모델을 쓰면 `tool_loading.enabled` 를 끄세요. 켜짐이 기본값입니다.
- `SPEECH_STATE_VERSION` 을 올렸으므로 이전 코드가 남긴 초안의 발언은 처음부터 다시 합니다.
- `core_tools` 는 전역 하나입니다. 에이전트별 설정과 화면 설정은 넣지 않았습니다. 필요한 도구는 첫 호출 뒤 그 에이전트에게 남습니다.
