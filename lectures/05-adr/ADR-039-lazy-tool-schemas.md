# ADR-039. 자주 사용하는 핵심 도구 스키마만 선별 로드하고 보조 도구는 온디맨드(on-demand) 지연 로딩으로 전환한다

> [ADR 목록](README.md) · 이전: [ADR-038](ADR-038-edit-the-ledger-directly.md)

## 상태 (Status)

채택됨 · 2026-10-31 · 관련: [ADR-026](ADR-026-skills-as-host-tools.md), [ADR-025](ADR-025-resume-speeches-by-tool-step.md)

## 맥락 (Context)

- MCP 도구의 JSON 스키마 정의는 LLM 요청마다 입력 프롬프트 페이로드에 고스란히 포함됩니다. 실제 서버 기준 `filesystem`, `memory`, `git` 35개 도구 스키마만으로도 약 5,292토큰을 점유하며, `sandbox`까지 포함해 42개가 되면 8,078토큰에 달합니다 (`openai/gpt-4o` 토크나이저 기준). 도구 루프가 반복될 때마다 이 스키마가 계속 재전송되며, 순수 대화에 쓸 수 있는 컨텍스트 예산이 그만큼 축소됩니다.
- 스킬(Skills) 시스템은 이 문제를 이미 해결했습니다. 프롬프트에는 1줄 요약 목록만 제공하고 본문 내용은 실제 호출 시점에 동적으로 로드합니다([ADR-026](ADR-026-skills-as-host-tools.md)). 그러나 도구 스키마에는 이와 동일한 메커니즘이 없었습니다.
- 도구 스키마 지연 로딩 시 해결해야 할 3가지 과제가 있었습니다.
  - 스킬은 반환된 본문이 도구 결과 메시지에 포함되지만, 도구 정의는 API 요청의 최상위 `tools` 배열에 존재해야만 LLM이 네이티브 도구 호출(Function calling)을 생성할 수 있습니다.
  - 시스템 상시 지침과 프롬프트 가이드에서 특정 도구 이름들을 직접 명시하고 있습니다 (`file_writing_guidance`, `file_editing_guidance`, `truncation_advice`, 메모리 안내 등). 이 도구들의 스키마를 누락하면 인자 형식을 알지 못한 채 잘못된 호출을 시도할 위험이 있습니다.
  - 도구를 동적으로 로드하는 과정 자체가 1턴의 LLM 왕복 비용을 유발하므로, 빈번한 로드는 오히려 토큰 절감 효과를 상쇄할 수 있습니다.

## 결정 (Decision)

### 1. 호스트 도구 `tools__load_tools`를 통한 동적 스키마 로드

`tools__load_tools`의 도구 설명에 `- 도구명: 요약 설명` 목록을 포함시키고, LLM이 특정 도구의 로드를 요청하면 해당 도구의 전체 스키마를 다음 API 요청의 `tools` 매개변수에 주입합니다. 반환 결과는 성공 안내 메시지이며 실제 스키마는 `tools` 배열로 들어갑니다. 이를 통해 모델이 정상적인 네이티브 함수 호출을 생성할 수 있고, 도구 승인 카드, 도구 보안 정책, 응답 잘림 처리, 장애 복구 로직이 기존과 동일하게 완벽히 작동합니다.

로드 완료 후에는 `ToolLoop.tools` 및 `schema_tokens`를 즉시 갱신하여, 이번 발언의 다음 도구 호출 단계부터 확장된 컨텍스트 예산을 정확히 반영합니다.

### 2. 시스템 지침에서 명시적으로 지목하는 도구는 항상 상시 로드

`tools_named_by_guidance()`를 통해 시스템 프롬프트 지침이 직접 참조하는 핵심 도구들(`write_file`, `edit_file` 등)을 식별하여 지연 로딩 대상에서 제외하고 항상 상시 로드합니다. 또한 `tool_loading.core_tools`에 정의된 핵심 기본 도구들과, 등록된 도구 수가 3개 이하인 소규모 서버의 도구들도 상시 로드합니다.

### 3. 유의미한 토큰 절감 효과가 있을 때만 지연 로딩 분할 적용

도구 분할로 인해 요청당 `min_saving_tokens`(기본값 1,000토큰) 이상의 절감 효과가 발생하지 않는 소규모 설정에서는 모든 도구를 한 번에 상시 로드합니다.

| 도구 구성 | 총 도구 수 | 상시 로드 도구 수 | 스키마 토큰 변화 | 절감률 |
| :--- | :--- | :--- | :--- | ---: |
| filesystem + memory + git | 35개 | 11개 | 5,292 → 2,175 | **59%** |
| + sandbox | 42개 | 16개 | 8,078 → 4,465 | **45%** |
| filesystem + memory | 23개 | 9개 | 3,731 → 1,861 | **50%** |
| filesystem + sandbox | 21개 | 11개 | 4,868 → 3,477 | **29%** |
| git 단독 | 12개 | 3개 | 1,563 → 479 | **69%** |

### 4. 로드된 도구 목록은 해당 대화 세션의 에이전트 인스턴스에 유지

발언이 끝날 때마다 로드된 도구를 초기화하면 다음 발언에서 매번 재로드가 발생하는 비효율이 생깁니다. 따라서 (세션, 에이전트) 단위로 이미 로드된 도구 목록을 메모리에 보관하여 후속 발언에서도 유지합니다. 요청 앞부분의 일관성이 유지되므로 프롬프트 접두사 캐시도 안정적으로 활용됩니다.

### 5. 목록에서 확인한 도구를 지연 로드 없이 즉시 호출하더라도 정상 처리

모델이 요약 목록에서 이름을 확인한 후 `load_tools`를 거치지 않고 곧바로 대상 도구를 호출한 경우, 도구 보안 정책을 통과하면 즉시 실행하고 사후에 해당 도구의 스키마를 `tools` 목록에 영구 주입합니다. 이를 통해 불필요한 재질의 턴 낭비를 방지합니다.

## 결과 (Consequences)

**이점**

- 대규모 MCP 도구 환경에서 매 요청마다 소모되던 도구 스키마 토큰을 30~60% 이상 대폭 절감하여 대화 컨텍스트 가용 예산을 확보했습니다.
- 자주 쓰는 핵심 도구와 지침 참조 도구는 상시 로드되므로 일반적인 작업 흐름에서 추가 로드 지연이 발생하지 않습니다.
- 프롬프트 캐시 친화적인 구조를 유지하면서 동적 도구 확장의 유연성을 확보했습니다.

## 실측 (2026-11-11 추가)

불러오기가 치르는 값(판 하나, 캐시 한 번)을 실제 모델이 얼마나 자주 치르는지는 채택 당시 재지 못했습니다. 지금은 발언과 턴의 사용량 기록에 `tool_load_calls`(`tools__load_tools` 호출 수)와 `tool_loads`(불러온 정의 수, 목록의 도구를 곧바로 부른 것 포함)가 함께 남습니다 (`llm_usage.note_tool_context`). 끊긴 발언을 이어 갈 때 되살리는 도구는 세지 않습니다.

실제 확인(2026-11-11, `deepseek-v4-flash`, filesystem·sandbox·git 을 가진 에이전트의 두 턴, 한 번 실행): `tools__load_tools` 1회로 정의 2개를 불러왔고 두 턴의 LLM 호출은 19회였습니다. 불러온 도구는 다음 턴에서 다시 불러오지 않았습니다. 한 번의 실행이라 경향으로 읽을 수는 없고 모델마다 다릅니다.

여러 대화에서 되풀이해 불러오는 도구는 토큰·시간 분석 창이 `tool_loading.core_tools` 후보로 알려 줍니다 (`usage_report.core_tool_candidates`, 대화 3개 이상). 제안일 뿐 설정은 사람이 바꿉니다.
