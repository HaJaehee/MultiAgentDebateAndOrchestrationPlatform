# ADR-022. 지식베이스(RAG) 도구는 근거를 모을 때까지 보류한다

> [ADR 목록](README.md) · 이전: [ADR-021](ADR-021-graph-debate.md) · 다음: [ADR-023](ADR-023-keep-litellm-and-own-engine.md)

## 상태 (Status)

**보류** · 2026-09-21 설계 논의에서 결정 · 재논의 예정 2026-10-05 무렵 · 관련: [ADR-003](ADR-003-mcp-tool-protocol.md)

이 ADR은 소스 코드 커밋이 아니라 아키텍처 설계 회의에서 도출된 의사결정 기록입니다. "기능을 당장 구현하지 않기로 결정한 것" 역시 중대한 아키텍처 결정이며, 기록으로 남겨둘 충분한 가치가 있다는 모범 사례로 수록합니다.

## 맥락 (Context)

- 에이전트가 사내 내부 문서를 직접 검색할 수 있도록 지원하는 지식 베이스(RAG) MCP 도구를 신규 개발하자는 기능 제안이 있었습니다. 구체적인 아키텍처 설계안까지는 합의를 마친 상태였습니다.
- 그러나 에이전트에게 필요한 문서를 주입하는 경로는 시스템에 이미 구현되어 있었습니다. v0.8.0에서 도입된 대화 입력창의 `@언급(Mention)` 기능을 통해 작업 공간 내부의 파일을 지정하면, 파일 시스템 MCP 도구를 통해 에이전트가 해당 파일을 직접 읽어 분석할 수 있었습니다. 시스템에서 실질적으로 누락된 부분은 보안(DRM)이 걸려 있는 사내 문서를 에이전트가 읽을 수 있는 텍스트 포맷으로 **자동 변환**해 주는 전처리 파이프라인뿐이었습니다.
- 검색(Retrieval) 엔진이 정말로 필수적인가는 한 가지 핵심 질문에 달려 있었습니다. **"사용자는 자신이 어떤 사내 문서를 참조해야 하는지 이미 알고 있는가?"** 사용자가 대상 문서를 이미 알고 있다면 단순 `@언급` 기능으로 충분하며, 어떤 문서를 보아야 할지 모를 때에만 검색 엔진이 진정으로 필요합니다. MADO의 실제 운영 형태는 실무자 개인이 자신이 보유한 수십~수백 건의 프로젝트 문서를 직접 다루는 워크플로였으므로, 사용자가 참조할 문서를 사전에 인지하고 있을 확률이 매우 높다고 판단했습니다.
- 검색 엔진을 고도화하려면 오프라인 폐쇄망 환경에 로컬 텍스트 임베딩 모델과 벡터 추론 런타임을 추가 반입해야 합니다. 이는 패키징 및 보안 심사 비용을 크게 증가시킵니다.
- 본 기능에서 최우선으로 고려해야 할 품질 속성은 **사용성과 학습성(Usability & Learnability)**이었습니다. 사용자가 단번에 학습해야 할 복잡한 개념(임베딩, 벡터 유사도, 청킹 등)이 일시에 늘어나는 것은 바람직하지 않았습니다.

## 결정 (Decision)

**RAG 도구의 직접 구현을 의도적으로 보류하고, 실측 사용 근거 데이터를 수집한 뒤 재논의하여 결정하도록 합니다.**

단계별 기능 발전 사다리(Capability Ladder)를 사전에 정의하고, 가장 단순한 최하위 단계부터 검증하며 필요성이 입증될 때에만 상위 단계로 순차 진입하도록 합니다. 각 단계마다 사용자가 새로 습득해야 할 개념은 최대 1개 이내로 엄격히 제한합니다.

| 단계 | 구현 범위 | 요구되는 신규 의존성 |
| :--- | :--- | :--- |
| L0 | 사내 DRM 문서를 마크다운 파일로 **변환만** 수행하여 작업 공간에 배치. 탐색은 기존 `@언급` 및 파일 시스템 도구 활용 | 신규 의존성 없음 |
| L1 | 단순 키워드 어휘 검색 (한국어 형태소 분석기 + SQLite FTS5 전문 검색) | 매우 경미한 의존성 |
| L2 | 어휘 검색과 의미론적 벡터 검색을 결합한 하이브리드 검색 (경량 온디바이스 다국어 임베딩 모델) | 폐쇄망 모델 가중치 반입 필수 |
| L3 | 사내 전용 엔터프라이즈 임베딩 서버 연동 및 실시간 자동 동기화 | 사내 중앙 인프라 연계 |

최우선적으로 L0 단계를 구축하고, 그 **실제 운영 사용 이력 로그**를 정량 분석하여 L1 단계로의 진입 여부를 판정하도록 합니다. 판정 기준 메트릭을 사전에 확정해 둡니다.

- 사내 문서 참조가 실제로 발생한 토론 세션의 절대 건수
- 그중 **사용자가 대상 문서명을 사전에 인지하지 못했던 비율**. 이 비율이 30% 미만이라면 별도의 검색 엔진은 불필요한 것으로 최종 판정합니다.
- 단일 토론 세션 진행에 요구되는 평균 문서 수. 3건을 초과할 경우 단순 `@언급` 방식이 사용자 경험상 불편한 것으로 간주합니다.
- 단순 파일명 식별만으로 원하는 문서를 찾지 못한 구체적인 사용자 실패 사례의 존재 여부

재논의 시점에 최우선으로 수행할 작업은 축적된 과거 대화 로그에 대한 정량 텍스트 분석입니다. 사용자가 입력창에 장문의 문서 텍스트를 직접 복사하여 붙여넣은 빈도, "문서", "규정", "지침"과 같은 어휘의 출현 빈도, 그리고 `@언급` 기능의 실제 사용률을 교차 검증합니다.

문서 변환 작업은 LLM에 위임하지 않고 애플리케이션 코드가 직접 결정론적 파일 변환 라이브러리를 호출하도록 합니다. 변환의 정확성과 불필요한 토큰 비용 낭비를 방지하기 위함입니다.

## 결과 (Consequences)

**좋아지는 점**

- 아직 검증되지 않은 복잡한 기술 스택(임베딩 모델 반입, 벡터 색인 관리, 변경 동기화 등)을 섣불리 도입하는 리스크를 방지했습니다.
- 향후 기능을 재평가할 때 어떤 정량 데이터를 대조해야 할지 판단 기준이 사전에 명확히 수립되었습니다. "필요해 보인다"는 주관적 감이 아니라 객관적 통계 수치로 의사결정을 내릴 수 있습니다.
- L0 단계 도입만으로도 DRM으로 잠겨 있던 사내 문서를 에이전트가 읽을 수 있게 되는 실질적인 업무 효율 개선을 즉각 달성할 수 있습니다.

**치르는 비용**

- 복잡한 대량 문서 검색이 절실히 필요한 소수의 파워 유저는 최소 2주 이상의 추가 검토 기간을 대기해야 합니다.
- 정량적 근거를 수집하기 위한 대화 세션 로그 분석 및 통계 집계 작업 공수가 별도로 소요됩니다.

**교훈**

"기술적으로 구현할 수 있는가"와 "지금 반드시 구현해야 하는가"는 완전히 분리되어야 할 서로 다른 질문입니다. 완성도 높은 기술 설계안이 마련되어 있더라도, 해당 기능이 해결하고자 하는 문제가 실제 운영 환경에 실재하는지를 검증할 수 있는 객관적 기준을 선제 수립하는 것이 올바른 아키텍처 실천입니다. 의사결정의 보류(Defer)는 **구체적인 재검토 시점과 명확한 수치 판정 기준**이 수반될 때에만 정당성을 지닙니다. 이 두 가지가 결여된 보류는 무책임하게 잊혀지는 결정에 불과합니다.
