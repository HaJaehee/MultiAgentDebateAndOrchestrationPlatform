# ADR-022. 지식베이스(RAG) 도구는 근거를 모을 때까지 보류한다

> [ADR 목록](README.md) · 이전: [ADR-021](ADR-021-graph-debate.md)

## 상태 (Status)

**보류** · 2026-09-21 설계 논의에서 결정 · 재논의 예정 2026-10-05 무렵 · 관련: [ADR-003](ADR-003-mcp-tool-protocol.md)

이 ADR은 커밋이 아니라 설계 논의에서 나온 결정입니다. "만들지 않기로 한 것"도 결정이며, 기록할 가치가 있다는 예로 싣습니다.

## 맥락 (Context)

- 에이전트에게 사내 문서를 검색해 주는 지식베이스(RAG) MCP 도구를 만들자는 제안이 있었습니다. 설계안까지는 합의했습니다.
- 그런데 에이전트에게 문서를 주는 길은 이미 있었습니다. v0.8.0의 입력창 `@언급`으로 작업 공간 파일을 지목하면, 파일 시스템
  MCP로 에이전트가 읽습니다. 빠진 것은 보안(DRM)이 걸린 사내 문서를 읽을 수 있는 형식으로 **변환**하는 부분뿐이었습니다.
- 검색이 정말 필요한지는 한 가지 질문에 달려 있었습니다. **사용자가 어느 문서가 필요한지 이미 아는가?** 알면 `@언급`으로 충분하고,
  모르면 검색이 필요합니다. 실제 사용 형태는 개인이 자기 자료 수백 건을 쓰는 경우라, 아는 경우가 많을 것으로 봤습니다.
- 검색을 제대로 하려면 폐쇄망에 임베딩 모델과 추론 런타임을 반입해야 합니다. 반입 비용이 큽니다.
- 이 기능에서 가장 중요한 품질 속성은 **사용성과 학습성**이었습니다. 사용자가 새로 익혀야 할 개념이 한꺼번에 늘면 안 됩니다.

## 결정 (Decision)

**구현을 보류하고, 근거를 모은 뒤 다시 결정한다.**

단계 사다리를 합의해 두고, 아래 단계부터 필요할 때만 올라간다. 단계마다 사용자가 새로 익힐 개념은 하나까지로 제한한다.

| 단계 | 내용 | 새 의존성 |
| :--- | :--- | :--- |
| L0 | 문서를 마크다운으로 **변환만** 해서 작업 공간에 둔다. 찾는 것은 `@언급`과 파일 도구 | 없음 |
| L1 | 단어 검색 (한국어 형태소 분석 + SQLite 전문 검색) | 작음 |
| L2 | 단어 검색과 의미 검색을 섞은 하이브리드 (소형 다국어 임베딩 모델) | 폐쇄망 반입 필요 |
| L3 | 사내 임베딩 서버 연동, 자동 동기화 | 사내 인프라 |

L0부터 만들고, 그 **사용 기록**으로 L1이 필요한지 판정한다. 판정 기준을 미리 정해 둔다.

- 문서가 필요했던 토론의 수
- 그중 **어느 문서인지 몰랐던 비율**. 30% 미만이면 검색은 필요 없다고 본다
- 토론 하나에 필요한 문서 수. 3개를 넘으면 `@언급`이 불편하다고 본다
- 파일 이름만으로 찾지 못한 사례가 있는가

재논의할 때 가장 먼저 할 일은 과거 대화 기록 분석이다. 긴 글을 붙여 넣은 빈도, "문서", "자료", "규정" 같은 말이 나온 빈도,
`@언급`을 쓴 빈도를 본다.

변환은 LLM에게 맡기지 않고 앱 코드가 직접 문서 읽기 도구를 호출한다. 정확성과 비용 때문이다.

## 결과 (Consequences)

**좋아지는 것**

- 검증되지 않은 복잡도(임베딩 모델 반입, 색인 관리, 동기화)를 들이지 않습니다.
- 다시 결정할 때 무엇을 보면 되는지가 이미 정해져 있습니다. "필요해 보인다"가 아니라 숫자로 판단합니다.
- L0만으로도 DRM 문서를 에이전트가 읽을 수 있게 되는 실질적인 개선이 먼저 들어갈 수 있습니다.

**치르는 비용**

- 정말 검색이 필요한 사용자는 최소 2주를 더 기다립니다.
- 근거를 모으는 작업(과거 대화 분석)이 따로 필요합니다.

**교훈**

"만들 수 있다"와 "만들어야 한다"는 다른 질문입니다. 설계안이 준비되어 있어도, 그 기능이 풀려는 문제가 실제로 있는지 확인하는
기준을 먼저 세우는 것이 좋습니다. 보류 결정은 **재논의 시점과 판정 기준**이 함께 있을 때 의미가 있습니다. 둘이 없으면 보류는
그냥 잊힌 결정이 됩니다.
