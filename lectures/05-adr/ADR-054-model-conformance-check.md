# ADR-054. 새 모델은 토론에 투입하기 전에 간단한 요청 몇 건으로 적합성을 점검하고, 설정을 직접 바꾸지 않고 권고안만 제시한다

> [ADR 목록](README.md) · 이전: [ADR-053](ADR-053-plan-speech-reads-only.md) · 다음: [ADR-055](ADR-055-bench-checks-and-judged-rubric.md)

## 상태 (Status)

채택됨 · 2026-11-11 · 관련: [ADR-007](ADR-007-no-simulated-answers.md), [ADR-030](ADR-030-fallback-to-the-global-model.md), [ADR-035](ADR-035-agent-input-modalities.md), [ADR-039](ADR-039-lazy-tool-schemas.md)

## 맥락 (Context)

- MADO의 운영 환경은 폐쇄망이며, 그곳의 LLM은 OpenAI 호환 엔드포인트(vLLM·사내 게이트웨이) 뒤에 배치된 여러 오픈 모델과 결정 LLM(Jev·Laya)입니다. 개발 PC에서는 DeepSeek와 Jev로 검증합니다.
- 모델과 서버 조합마다 동작 차이가 큽니다. 지금까지는 전부 **토론 중 오류가 발생한 뒤에야** 알 수 있었습니다. 도구 호출이 본문 텍스트로 누출되어 실행되지 않음(v0.7.0), 답변이 `reasoning_content` 안에만 있어 빈 카드가 됨(v0.7.0), 같은 역할이 연달아 오면 400(v0.5.0), 도구 이력이 있는데 `tools`를 빼면 400(v0.5.2), `max_context_window`가 실제 창 크기보다 커서 자르기 전에 서버가 먼저 거절(v0.5.3) — 릴리스 노트의 장애 기록이 바로 이 목록입니다.
- `모델 연결 상태`(`model_status.probe`)는 `ping` 한 번으로 **응답 여부**만 확인합니다. 응답하는 모델이 도구를 정상 사용할 수 있는지는 알려 주지 않습니다.
- 폐쇄망에서는 장애 발생 시 로그를 반출해야 원인을 확인할 수 있습니다. 모델을 반입한 당일 현장에서 바로 파악할 수 있어야 합니다.

## 결정 (Decision)

### 1. 연결 하나당 짧은 요청 8건으로 동작 특성을 확인합니다

`app/agents/model_check.py`. 생성형 연결은 아래 항목을 차례로 점검합니다 (모두 `max_tokens` 512 이하, 재시도 없음).

| 검사 | 확인 항목 | 이상 시 조치 |
| :--- | :--- | :--- |
| 기본 응답 | 응답 수신 여부, 사용량 보고 여부 | 실패 — 이후 검사는 생략합니다 |
| 추론과 본문 | `reasoning_content`가 분리되어 오는지, 본문이 비는지, `<think>`가 본문에 섞이는지 | 주의 + `max_tokens` 상향 권고 또는 서버 파서 안내 |
| 스트리밍 | `stream=True`로 텍스트 청크가 수신되는지 | 주의 — 발언마다 비스트리밍으로 재요청하게 됩니다 |
| 잘림 알림 | 16토큰에서 중단했을 때 `finish_reason='length'`인지 | 주의 — 이어 쓰기와 잘림 안내가 동작하지 않습니다 |
| 연속된 user | 같은 역할 메시지 두 개를 연달아 받는지 | 참고 — MADO가 병합해 전송하므로 영향 없음 |
| 도구 호출 | `tool_calls`로 수신되고 인자가 파싱되는지, 본문으로 누출되는지(`find_leaked_tool_call`) | 실패(누출·거절) 또는 주의 |
| 도구 결과 뒤 마무리 | 도구 결과가 담긴 대화를 `tool_choice="none"`으로 처리하는지 | 실패 또는 주의 |
| 도구 목록에서 불러오기 | 지연 로딩 목록(`catalog_tool`)을 읽고 `tools__load_tools`를 호출하는지 | 주의 + `tool_loading.enabled: false` 권고 |
| 이미지 입력 | 단색 이미지를 입력받아 해당 색상을 답하는지 | 참고, 이미지 입력을 켠 에이전트가 있으면 주의 |
| 컨텍스트 창 | `/models`의 `max_model_len` 등이 에이전트 설정값보다 작은지 | 실패 + `max_context_window` 하향 권고 |

결정 LLM은 요청 한 번에 noul·choice·score 세 질문을 보내 응답 형태를 확인합니다.

### 2. 판정은 결정적입니다 — LLM이 채점하지 않습니다

응답 필드, 종료 사유, 표식, 정해 둔 단어(`42`, `red`, 도구 결과 문자열)만 확인합니다. 모델의 작업 수행 품질은 측정하지 않습니다 (Bench의 역할). 판정 모델을 두면 폐쇄망마다 그 모델부터 검증해야 하고, 같은 서버를 두 번 점검했을 때 다른 결과가 나올 수 있습니다.

### 3. 요청은 실제 코드가 생성하는 형태 그대로 보냅니다

- 연결 정보는 `probe_kwargs`(연결 확인과 동일), 도구 호출 파싱은 `ToolCallMixin._parse_tool_call`, 목록 도구와 상시 지침은 `catalog_tool`·`tool_loading_guidance`를 그대로 사용합니다. 점검을 통과해야 실제 토론에서도 통과할 수 있기 때문입니다.
- **도구 결과 뒤 마무리 단계의 assistant 턴은 임의로 만들지 않고, 직전에 모델이 생성한 응답을 `_assistant_turn`으로 되돌려 넣습니다.** 초기 구현에서는 수동으로 만든 턴을 보냈으나, 실제 DeepSeek(thinking mode)에서 "`reasoning_content` must be passed back" 400 오류로 거절되어 정상 모델이 '실패'로 판정되었습니다. 모델이 도구를 호출하지 않았다면 이 검사는 건너뜁니다.
- 스트리밍 응답의 사용량 보고 여부는 검사하지 않습니다. LiteLLM이 서버가 보내지 않아도 마지막 청크에 토크나이저로 계산한 값을 채워 넣기 때문에, 서버가 직접 보고한 값인지 구분할 수 없습니다 (1.98·1.105에서 확인).

### 4. 결과는 권고안입니다. 런타임은 결과에 따라 달라지지 않습니다

검사마다 `통과 · 참고 · 주의 · 실패 · 건너뜀` 상태와 한 줄 설명, 그리고 권장 설정(`Suggestion`)을 출력합니다. `conf.json`으로 고칠 수 있는 항목은 설정 키와 값을 함께 제시하고(`max_context_window`, `max_tokens`, `tool_loading.enabled`, `allowed_modalities.image`), 서버 측에서 고쳐야 할 항목(vLLM의 `--tool-call-parser`, `--reasoning-parser`)은 안내 문구만 제공합니다. `conf.json`은 사용자가 직접 수정합니다.

프로파일을 읽어 요청 방식을 바꾸는 분기는 두지 않습니다. 그런 분기는 "점검을 실행한 서버"와 "실행하지 않은 서버"에서 동일한 `conf.json`이 다르게 동작하게 만들고, 장애 발생 시 어떤 요청이 전송되었는지 설정 파일만으로는 알 수 없게 만듭니다.

### 5. 어디서 돌리는가

- CLI: `python -m app.modelcheck [--agent KEY …] [--json] [--config …]`. 서버를 띄우기 전에 실행할 수 있으며, 실패한 검사가 있으면 종료 코드 1을 반환합니다.
- UI: `모델 연결 상태` 창의 항목마다 배치한 `적합성 점검` 버튼. 관리자 화면에만 제공되며(요청이 여러 건 발생함), 연결이 확인된 항목에서만 활성화되고 한 번에 한 연결만 점검합니다.
- 두 방식 모두 결과를 `data/modelcheck/<연결 ID>.json`에 저장합니다. 기록에는 상태와 크기, API 키를 가린 오류 원문 한두 줄만 남기며 모델이 생성한 본문은 저장하지 않습니다.
- 서버 전체의 동시 요청 상한(`app.llm_concurrency`)을 준수합니다. 연결 확인과 달리 빈 슬롯이 생길 때까지 대기합니다 (사용자가 직접 눌러 시작한 작업이기 때문입니다).

### 하지 않는 것

- 실제 컨텍스트 창 크기를 초과하는 요청을 보내 측정하는 작업. 128k 토큰을 한 번 보내는 것은 단일 GPU 서버에 큰 부하를 주며, vLLM은 `/models`로 해당 값을 제공합니다. 서버가 알려 주지 않으면 건너뜀으로 두고 모델 카드의 값을 입력하도록 안내합니다.
- 음성·동영상·문서 입력 점검, 프롬프트 캐시 점검.
- 점검 결과만으로 `conf.json`을 자동 수정하는 일.

## 결과 (Consequences)

**좋아지는 점**

- 새 모델을 도입한 당일, 해당 모델로 MADO의 어떤 기능이 동작하고 어떤 기능이 안 되는지를 1분 안에 표로 확인할 수 있습니다. 릴리스 노트의 장애 다섯 가지가 각각 하나의 검사 항목에 대응합니다.
- 폐쇄망에서 반출할 파일이 방대한 로그가 아니라 `data/modelcheck/*.json` 파일 하나뿐입니다. 대화 내용 없이 상태 정보만 담깁니다.

실제 확인(2026-11-11): `deepseek/deepseek-v4-flash`는 요청 8건으로 10개 검사 모두 통과, `jev/jev-1.13.0`은 요청 1건으로 4개 모두 통과했습니다.

**치르는 비용**

- 요청 한 건 기준의 결과입니다. 열 번에 한 번꼴로 도구 호출이 누출되는 모델은 통과로 나올 수 있습니다.
- 도구를 호출하라는 지시를 따르지 않는 모델은 '주의'로 판정되며, 이어지는 마무리 검사는 건너뜁니다.
- 컨텍스트 창 크기는 서버가 응답한 값을 신뢰합니다. 게이트웨이가 `/models`를 차단하면 확인할 수 없습니다.
- LiteLLM이 짝이 맞는 `<think>…</think>`를 자동으로 분리해 주므로(1.98), 본문에 섞인 추론은 닫는 태그만 온 경우에만 검출됩니다.
