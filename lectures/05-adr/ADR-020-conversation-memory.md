# ADR-020. 긴 대화는 버리기 전에 고정하고 접는다

> [ADR 목록](README.md) · 이전: [ADR-019](ADR-019-owner-token-remote-access.md) · 다음: [ADR-021](ADR-021-graph-debate.md)

## 상태 (Status)

채택됨 · 2026-09-17 (v0.8.3) · 관련: [ADR-015](ADR-015-reasoning-out-of-prompts.md), [ADR-018](ADR-018-orchestrator-writes-conclusions.md)

## 맥락 (Context)

- 초기 구현에서는 발언자마다 세션의 모든 발언 기록을 원문 그대로 프롬프트에 주입했고, 이전 턴의 기록도 DB에서 다시 조회하여 주입했습니다. 컨텍스트 윈도우 한도를 초과하면 **가장 오래된 메시지부터** 통째로 영구 삭제했습니다. 오직 생성 시점(Age)이라는 단일 기준만으로 삭제 여부를 결정했습니다.
- 그러자 한 번만 언급되고 이후 반복되지 않는 중요한 정보들부터 가장 먼저 소실되었습니다. 1턴에서 사용자가 지시한 핵심 제약 조건("Redis는 기술 스택에서 제외하십시오"), 이번 턴의 실행 계획, 이미 확정된 아키텍처 결정 사항 및 기각된 대안 등이 대표적이었습니다.
- 에이전트마다 배정된 모델의 컨텍스트 창 크기가 서로 상이하여 **정보가 유실되는 시점과 분량이 제각각이었고**, 그 결과 서로 다른 전제를 바탕으로 논점이 엇갈리는 혼선이 발생했습니다.
- 실제 재현 테스트: 8k 컨텍스트 창, 발언당 약 2,100토큰 소비, 1턴의 핵심 제약 조건 1개, 3라운드로 구성된 2턴 토론. 2턴에서 생성된 9개의 발언 중 **그 어느 발언도** 1턴의 제약 조건을 엔드포인트에 전달하지 못했습니다.
- 앞선 결정들이 일부 완화 효과를 제공하고 있었습니다. 사고 과정 흔적 제외([ADR-015](ADR-015-reasoning-out-of-prompts.md)), 오케스트레이터의 소스 코드 중복 전송 금지([ADR-018](ADR-018-orchestrator-writes-conclusions.md)). 그러나 이는 "컨텍스트에서 무엇을 끝까지 사수할 것인가"라는 질문에 대한 근본적인 해답이 되지 못했습니다.

## 결정 (Decision)

핵심 설계 원칙: **대화 이력은 잊혀질 수 있으나, 시스템 상태와 결정은 반드시 보존합니다. 사용자의 직접적인 지시는 언어 모델이 임의로 생성한 어떠한 요약문보다 항상 우선합니다.**

비용 효율적이고 권위 있는 순서에 따라 3중 계층의 보호 장치(방어 체계)를 배치하도록 합니다.

1. **사용자 발언 고정(User Prompt Pinning)**: 세션 내의 모든 사용자 지시 발언을 프롬프트 최상단의 '목표 메시지(절대 잘리지 않는 불변 영역)'에 고정 주입합니다. 원래 대화 흐름의 위치는 가벼운 참조 태그로 대체합니다. 할당 예산은 발언자 컨텍스트의 최대 25%까지로 제한하며, 초과 시 최신 사용자 발언부터 우선 고정하고 나머지는 대화 본문에 유지합니다. 이번 턴의 오케스트레이터 계획 역시 동일한 방식으로 15% 예산 내에서 고정합니다.
2. **결정 장부(Decision Ledger)**: 오케스트레이터가 5대 핵심 섹션(요구사항 및 제약 조건, 확정 결정 사항, 기각된 대안, 미해결 기술 쟁점, 담당 에이전트 및 다음 할 일)으로 구조화된 장부를 매 라운드 종료 시(최종 라운드 제외) 및 종합 완료 직후 갱신합니다. 결정 장부는 **마지막 사용자 메시지의 최서두**에 배치합니다. 시스템 프롬프트 영역에 배치하면 매 라운드 갱신될 때마다 공급자의 프롬프트 캐시(Prompt Cache)가 전면 무효화되기 때문입니다. 마크다운 형식이 어긋난 경우 이전 장부 상태를 안전하게 유지하며, **해당 턴이 정상 완료되었을 때만 데이터베이스에 영속화합니다.**
3. **영구 삭제 전 점진적 요약(Folding/Summarization)**: 요청 페이로드가 모델 예산을 초과할 경우, 가장 오래된 발언부터 누적 요약문으로 압축하여 접습니다. 에이전트별 컨텍스트 창 크기에 따라 개별 판정하므로, 컨텍스트 여유가 있는 에이전트는 원본 텍스트를 그대로 유지합니다. 요약 생성 호출이 실패할 경우에 한하여 기존의 축출 방식으로 폴백합니다.

컨텍스트 과부하를 선제 차단하기 위한 경량화 규칙:

- 모든 에이전트는 발언 말미에 3~5줄 분량의 `## 요지` 섹션을 작성하도록 프롬프트를 강제합니다 (추가 API 호출 없음).
- 최근 발언은 전문을 유지하고, 오래된 타 에이전트의 긴 발언은 요지 섹션만을 전송하며, 대규모 소스 코드 블록은 1줄짜리 파일 경로 참조로 축약합니다. 단, Mermaid 다이어그램은 구조 파악을 위해 축약하지 않습니다. 종합 오케스트레이터는 전체를 원문으로 검토합니다.
- 동적으로 빈번히 변경되는 정보(라운드 진행 카운터, 결정 장부 갱신본, 이번 차례 지침)는 캐시 적중률을 극대화하기 위해 요청 메시지 시퀀스의 **최하단(맨 뒤)**에 배치합니다.

긴 도구 실행 루프 중 지침 유실 방지:

- 발언 시작 시점의 마지막 메시지(결정 장부와 발언 지침)를 앵커(Anchor)로 기억해 두었다가, 도구 루프 내의 자동 축출로 인해 밀려나면 상단의 목표 메시지 영역에 다시 부착하여 지침 유실을 방지합니다.

## 결과 (Consequences)

**좋아지는 점**

- 재현 테스트 환경에서 1턴의 제약 조건이 2턴의 9개 발언 **모두에** 정확히 단 한 번씩 완벽하게 전달되었으며, 핵심 데이터가 유실되지 않았습니다. 고정 기능을 비활성화했을 때 동일 테스트가 다시 실패하는 것까지 검증했습니다.
- 전문가 3인이 3라운드를 진행하는 벤치마크에서 리뷰어의 최종 프롬프트 크기가 원문 대비 약 54% 수준으로 절감되었습니다.
- 라운드가 거듭되더라도 요청의 상위 프리픽스가 일정하게 유지되어 공급자의 프롬프트 캐시 적중률이 획기적으로 상승했습니다.
- 결정 장부는 세션 이어받기를 통해 차기 대화로 안정적으로 계승되며, 웹 UI에서 읽기 전용 탭으로 투명하게 열람할 수 있습니다. 장부 내용에 오류가 있다면 사용자가 대화창에 피드백을 입력하면 됩니다. 다음 장부 갱신에 즉시 반영되며, 사용자 발언 원본은 모든 프롬프트에서 장부보다 항상 높은 우선순위를 가집니다.

**치르는 비용**

- 턴당 오케스트레이터 호출 횟수가 최대 라운드 수(`max_rounds`)만큼 증가합니다 (장부 갱신 비용). 컨텍스트 요약이 필요한 장기 대화에서는 추가 호출이 발생합니다.
- 개별 발언자가 요약 지침을 충실히 이행하는가에 다소 의존합니다. 요지가 누락된 경우 코드 참조 본문으로 대체되므로 데이터가 유실되지는 않으나, 토큰 절감 효과는 일부 반감됩니다.
- 핵심 임계 상수(사용자 고정 25%, 요약 목표 60%, 최근 1개 원본 보존 등)를 정밀 벤치마크를 통해 튜닝해야 했습니다. 초기 설정값(목표 80%, 최근 3개 보존 등) 하에서는 8k 창 환경에서 매 발언마다 요약 호출을 수행하고도 메시지가 잘리는 비효율이 발생했었습니다.
- SQLite 대화 세션 테이블에 컨텍스트 메모리 관리를 위한 신규 컬럼 4개가 추가되었습니다.

**함께 발견하고 수정한 결함**

자동화 테스트 실행기가 개발자의 실제 개발용 로컬 DB에 테스트 대화 데이터를 기록하고 있던 심각한 문제를 이 과정에서 적발했습니다. SQLAlchemy 비동기 엔진이 최초 생성된 연결 경로로 고정되는 전역 싱글턴 패턴으로 구현되어 있어서, 실행 순서가 어긋난 특정 테스트가 기본 프로덕션 경로로 엔진을 초기화했던 것입니다. 모든 테스트 실행 전에 메모리 SQLite(`:memory:`)로 엔진을 강제 바인딩하도록 테스트 하네스를 전면 수정했습니다.

**교훈**

컨텍스트 엔지니어링은 "얼마나 많은 토큰을 한 번에 밀어넣을 수 있는가"가 아니라 **"어떤 핵심 정보를 시스템에서 절대 유실하지 말아야 하는가"**라는 질문에서 출발해야 합니다. 절대 잃어서는 안 될 불변의 지침을 안전한 최우선 영역에 단단히 고정하고, 그 후 비본질적인 대화 이력을 단계적으로 압축 및 잘라내는 순서로 접근해야 합니다.
