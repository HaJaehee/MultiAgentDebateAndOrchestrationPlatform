# ADR-029. 비엔지니어 화면을 체험 서버 아래에 따로 두고, 에이전트가 일하는 장면을 실제 도구로 보여 줍니다

> [ADR 목록](README.md) · 이전: [ADR-028](ADR-028-plan-approval-gate.md)

## 상태 (Status)

채택됨 · 2026-10-08 · 관련: [ADR-008](ADR-008-background-debate-runner.md), [ADR-011](ADR-011-session-config-snapshot.md), [ADR-014](ADR-014-tool-failure-is-observation.md), [ADR-016](ADR-016-per-workspace-mcp-runtime.md), [ADR-019](ADR-019-owner-token-remote-access.md), [ADR-028](ADR-028-plan-approval-gate.md)

## 맥락 (Context)

- 비엔지니어는 AI 를 챗봇으로만 압니다. 에이전트가 **생각 → 행동(도구) → 관찰** 을 되풀이하며 목표를 끝내는 행동가라는 점을 모르고, 그래서 에이전트에 페르소나·업무 지시서(system_prompt)·도구·스킬을 쥐여 주는 일도 모릅니다.
- 지금 에이전트를 만드는 곳은 전문가 화면의 로스터 폼 하나입니다. 모델, 온도, 토큰 한도, 단계적 사고까지 한 화면에 있어, 무엇을 만들지 아는 사람에게만 쓸모가 있습니다.
- 체험 서버는 비엔지니어에게 URL 하나로 토론을 보여 주지만, **도구가 없습니다** (`participant_snapshot` 이 `allowed_mcp_servers = []`). 방문자는 행동과 관찰을 한 번도 보지 못하므로, 체험이 오히려 "AI 는 챗봇" 이라는 인상을 굳힙니다.
- 엔진은 이미 필요한 것을 보냅니다. 글 조각(`message_stream_chunk`)과 실행한 도구(`tool_executed`)가 일어난 순서대로 오고, 두 화면 모두 `tool_executed` 를 그리지 않을 뿐입니다.
- 사용자의 요구는 전문가 화면·체험 화면·코어 엔진을 그대로 두는 것이었습니다. 대상은 주인과 체험 방문자 모두입니다.

## 결정 (Decision)

**비엔지니어 화면을 새 패키지(`app/easy/`)로 만들어 `/trial/easy` 아래에 둡니다. 에이전트가 일하는 장면은 녹화가 아니라 실제 LLM 과 MCP 도구로 보여 주고, 에이전트는 대화로 만들되 사람이 고칠 수 있는 설계도로 저장합니다.**

- **주소는 체험 서버 아래입니다.** 방문자 통로(`app/trial/gate.py`)가 `/trial/` 접두를 이미 열어 두고, 로그인 뒤 돌아갈 곳도 그 안쪽만 받으므로 체험 코드를 한 줄도 고치지 않습니다. 주인(서버 PC·접속 토큰)은 로그인 없이 들어옵니다. 코어와 닿는 곳은 `app/main.py` 의 `setup_easy()` 한 줄입니다.
- **생각/행동/관찰은 화면이 나눕니다.** `loop.LoopTimeline` 이 이벤트를 받은 순서대로 쌓습니다 — 도구 전의 글이 생각, 도구가 행동, 그 결과가 관찰, 뒤의 글이 다음 생각입니다. 시간으로 추측해 글을 앞 생각에 붙이는 규칙은 넣지 않습니다. 처음에는 엔진의 0.1초 조각 묶음을 보정하려 넣었는데, 다음 생각을 빨리 쓰는 LLM 에서 다음 생각 전체가 앞 생각에 붙는 것을 E2E 에서 확인했습니다. 순서를 따르는 쪽의 오차는 기껏해야 앞 생각의 마지막 몇 글자입니다.
- **도구 전에 생각을 말하게 합니다.** 모델이 말 없이 도구부터 부르면 생각 단계가 비므로, 대화 지침에 "도구를 쓰기 전에 무엇을 왜 하려는지 먼저 말하라" 를 넣습니다. 엔진 프롬프트는 건드리지 않습니다.
- **진행 방식은 '차례로 검토' 한 번으로 고정합니다.** 도구 결과 이벤트에는 발언 id 가 없어 에이전트 키로 지금 말하는 발언을 찾습니다. 동시에 둘이 말하면 그럴 수 없습니다. 더 시킬 일은 같은 대화에 이어서 요청합니다.
- **대화는 체험처럼 잠긴 대화로 만듭니다** ([ADR-011](ADR-011-session-config-snapshot.md)). 시연 에이전트와 방문자의 에이전트는 conf.json 에 없지만, 오케스트레이터의 연결을 빌린 스냅샷으로 발언합니다. 엔진은 평소대로 돌릴 뿐입니다.
- **방문자의 도구는 읽기 전용이고, 전용 폴더에서 돕니다.** 세션 모드는 `read_only`, 도구 서버는 `filesystem` 하나만 붙고, 작업 폴더는 앱에 실린 예제 파일(`app/easy/examples/`)을 복사한 `workspace/easy-guest` 입니다. conf.json 의 `tool_security.allow` 규칙은 모드보다 먼저 판정되므로(`policy.evaluate`), 실행 도구를 아예 붙이지 않는 것을 경계로 삼습니다. 주인은 `workspace/easy` 에서 conf.json 의 보안 모드와 승인 카드를 그대로 받습니다.
- **만들기는 인터뷰와 설계도입니다.** 도우미는 오케스트레이터의 연결로 도는 도구 없는 사본이고(엔진의 `_tool_less` 와 같은 방식), 답마다 ```` ```agent {json}``` ```` 설계도를 붙입니다. 화면은 그것을 걸러(없는 도구·스킬, 팔레트 밖의 색·아이콘) 카드에 옮기고, 사람이 카드를 고치면 그 값이 다음 말과 함께 도우미에게 넘어갑니다. 설계도의 칸 이름은 conf.json 과 같고, 주인에게는 "conf.json 에 이렇게 적힙니다" 미리보기가 붙습니다.
- **저장은 누구냐에 따라 갈립니다.** 주인은 `add_agent_to_conf_file` 로 conf.json 에 바로 추가하고 풀을 다시 채웁니다. 모델과 키는 적지 않아 `llm` 을 물려받습니다. 기록기가 값 범위를 보지 않으므로 `AgentConfig` 로 먼저 검사하고, 로스터와 같은 규칙으로 진행 중인 대화가 있으면 거절합니다. 방문자의 에이전트는 `easy_agents` 테이블에만 남습니다. conf.json 은 서버 전체가 읽는 설정이라, 방문자가 쓰면 다른 사람의 대화와 도구 권한이 바뀝니다.
- **승인 카드는 새로 만들지 않습니다.** 계획 승인([ADR-028](ADR-028-plan-approval-gate.md))이나 도구 승인이 오면 화면이 '전체 기록' 탭(주인 화면과 같은 `ChatFeed`)으로 넘어가 알립니다. 승인 기록은 "사람이 계획을 확인하고 승인했습니다" 한 줄로 보입니다.

**녹화 재생은 두지 않습니다.** 미리 적어 둔 장면을 재생하면 LLM 없이도 보여 줄 수 있지만, 비엔지니어가 확인해야 하는 것은 "정말로 파일을 열어 본다" 는 사실입니다. 웰컴 화면의 비교 그림이 그 자리를 맡고, 그림 속 숫자는 예제 파일로 실제로 나오는 값입니다.

## 결과 (Consequences)

**좋아지는 점**

- 방문자가 처음으로 행동과 관찰을 봅니다. 거부된 쓰기도 "관찰" 로 보여, 도구 실패가 관찰이라는 원칙([ADR-014](ADR-014-tool-failure-is-observation.md))을 화면이 그대로 가르칩니다.
- 설정 파일을 몰라도 에이전트를 만들 수 있고, 만드는 동안 페르소나·업무 지시서·도구·스킬이 각각 무엇인지, 그것이 conf.json 의 어느 칸인지를 봅니다.
- 전문가 화면, 체험 화면, 엔진은 바뀌지 않습니다. 새 저장 구조는 테이블 둘(`easy_sessions`, `easy_agents`)이고, 코어 테이블에는 칸을 더하지 않습니다.

**치르는 비용**

- 다시 연 기록에서는 생각과 행동의 순서가 사라집니다. DB 에는 발언 본문과 도구 기록만 있어, 화면은 행동을 먼저 모으고 본문을 결론으로 보이며 그 사실을 알립니다. 순서까지 남기려면 엔진의 기록 구조를 바꿔야 합니다.
- 도구가 아주 빨리 끝나면 앞 생각의 마지막 몇 글자가 다음 생각으로 넘어갈 수 있습니다. 엔진이 도구 결과를 보내기 전에 쌓인 글을 먼저 내보내면 사라지는 문제지만, 이번에는 엔진을 고치지 않았습니다.
- 방문자 대화도 작업 폴더별 MCP 런타임 하나를 띄웁니다([ADR-016](ADR-016-per-workspace-mcp-runtime.md)). 방문자들은 같은 폴더(`easy-guest`)를 같이 써서 런타임은 하나로 끝나지만, 그만큼 서로의 쓰기에서 격리되지는 않습니다 — 읽기 전용이라 쓰기가 없다는 것이 전제입니다. 주인이 쓰기 허용 규칙을 conf.json 에 넣으면 그 전제가 약해집니다.
- 진행 방식이 하나로 고정되어 있어 찬반 대결이나 병렬 지시는 쉬운 화면에서 볼 수 없습니다.
- 주인의 conf.json 저장은 진행 중인 대화가 하나라도 있으면 거절됩니다. 방문자가 많은 체험 서버에서는 저장할 틈이 적을 수 있습니다.
