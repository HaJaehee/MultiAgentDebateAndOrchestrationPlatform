# ADR-029. 비엔지니어 화면을 체험 서버 경로 하위에 분리 배치하고, 에이전트의 작업 과정을 실제 도구 실행과 함께 시각화합니다

> [ADR 목록](README.md) · 이전: [ADR-028](ADR-028-plan-approval-gate.md)

## 상태 (Status)

채택됨 · 2026-10-08 · 관련: [ADR-008](ADR-008-background-debate-runner.md), [ADR-011](ADR-011-session-config-snapshot.md), [ADR-014](ADR-014-tool-failure-is-observation.md), [ADR-016](ADR-016-per-workspace-mcp-runtime.md), [ADR-019](ADR-019-owner-token-remote-access.md), [ADR-028](ADR-028-plan-approval-gate.md)

## 맥락 (Context)

- 많은 비엔지니어 사용자는 AI를 단순 질의응답 챗봇으로만 인식합니다. 에이전트가 **생각 → 행동(도구) → 관찰**의 순환 고리를 거치며 목표를 완수하는 능동적 주체라는 점을 체감하기 어렵고, 에이전트에게 페르소나·업무 지시서(system_prompt)·도구·스킬을 부여하는 원리도 직관적으로 이해하기 힘듭니다.
- 현재 에이전트를 구성하는 방법은 전문가 화면의 로스터 폼이 유일합니다. 모델 선택, 온도(temperature), 토큰 한도, 추론 모드(thinking) 등 복잡한 엔지니어링 설정이 단일 화면에 집약되어 있어, 구조를 이미 깊이 이해하고 있는 개발자에게만 접근성이 열려 있습니다.
- 체험 서버는 비엔지니어에게 단일 URL을 통해 멀티 에이전트 토론을 제공하지만, **MCP 도구가 비활성화**되어 있습니다(`participant_snapshot`의 `allowed_mcp_servers = []`). 방문자는 에이전트의 실제 행동과 환경 관찰을 경험하지 못하므로, 오히려 "AI는 결국 텍스트만 생성하는 챗봇"이라는 고정관념을 강화하는 한계가 있었습니다.
- 반면 코어 오케스트레이션 엔진은 이미 필요한 이벤트를 완전하게 발행하고 있습니다. 텍스트 스트리밍 청크(`message_stream_chunk`)와 도구 실행 결과(`tool_executed`)가 발생 순서대로 스트리밍되지만, 기존 화면들이 이를 단계별로 분리하여 렌더링하지 않았을 뿐입니다.
- 따라서 기존 전문가 화면, 일반 체험 화면, 코어 엔진의 기존 로직을 훼손하지 않으면서, 시스템 소유자와 체험 방문자 모두를 아우를 수 있는 전용 인터페이스가 필요했습니다.

## 결정 (Decision)

**비엔지니어 전용 화면 패키지(`app/easy/`)를 신설하여 `/trial/easy` 하위에 구성합니다. 에이전트의 작업 과정은 단순 시뮬레이션(녹화)이 아닌 실제 LLM 호출 및 MCP 도구 실행으로 시각화하며, 에이전트 생성은 대화형 인터뷰를 통해 진행하되 사용자가 직접 편집 가능한 설계도 형태로 저장합니다.**

- **라우팅 경로는 체험 서버 하위(`/trial/easy`)로 구성합니다.** 기존 게스트 게이트웨이(`app/trial/gate.py`)가 `/trial/` 접두 경로를 이미 개방하고 있고 리다이렉트 처리도 자체 관리하므로, 체험 코드를 수정하지 않고 연동할 수 있습니다. 시스템 소유자(로컬 또는 접속 토큰 보유자)는 로그인 없이 바로 접근할 수 있으며, 코어 엔진과의 연결점은 `app/main.py`의 `setup_easy()` 등록 한 줄로 최소화했습니다.
- **생각·행동·관찰 단계 분리는 프론트엔드 타임라인(`loop.LoopTimeline`)이 담당합니다.** 수신된 이벤트를 발생 순서대로 적재하여 도구 실행 전 텍스트를 '생각', 도구 호출을 '행동', 도구 반환 결과를 '관찰', 후속 텍스트를 '다음 생각'으로 분류합니다. 시간 기반 추론 규칙(타임스탬프 클러스터링)은 배제하였습니다. 초기 구현 시 엔진의 0.1초 버퍼링 편차를 보정하려 했으나, 후속 사고 과정을 빠르게 생성하는 LLM의 경우 다음 발언 전체가 이전 생각으로 잘못 병합되는 현상이 E2E 테스트에서 확인되었기 때문입니다. 엄격한 발생 순서를 따르는 것이 훨씬 안정적입니다.
- **도구 실행 전 계획을 언어화하도록 프롬프트를 보강합니다.** 모델이 설명 없이 도구만 즉시 호출할 경우 생각 단계가 공백으로 남으므로, 세션 지침에 "도구를 호출하기 전에 수행 목적과 계획을 먼저 설명하라"는 안내를 주입합니다. 단, 엔진의 기본 프롬프트는 수정하지 않고 세션 커스텀 지침 수준에서 처리합니다.
- **진행 방식은 단일 라운드의 '순차적 검토(Sequential)'로 고정합니다.** 도구 실행 이벤트에는 개별 발언 ID가 포함되지 않고 발언자 키로 현재 발언을 매핑하므로, 복수의 에이전트가 동시 발언할 경우 이벤트 꼬임이 발생할 수 있습니다. 추가 작업이 필요할 때는 동일 세션 내에서 사용자가 연속 질의를 전송합니다.
- **세션은 스냅샷 기반의 격리 세션으로 생성합니다** ([ADR-011](ADR-011-session-config-snapshot.md)). 시연용 에이전트 및 게스트가 제작한 에이전트는 `conf.json`에 직접 등록되지 않지만, 오케스트레이터의 LLM 연결을 참조하는 불변 스냅샷으로 발언하므로 코어 엔진은 기본 토론과 동일하게 세션을 실행합니다.
- **체험 방문자의 도구 실행은 읽기 전용으로 제한되며 전용 작업 디렉터리에서 실행됩니다.** 세션 모드는 `read_only`, 도구는 `filesystem` 서버만 단독 연결되며, 작업 디렉터리는 번들 예제 파일(`app/easy/examples/`)이 복사된 `workspace/easy-guest`로 격리됩니다. `conf.json`의 `tool_security.allow` 화이트리스트 규칙이 읽기 전용 모드보다 우선 평가되므로(`policy.evaluate`), 방문자에게는 코드 실행 도구 등을 일절 노출하지 않는 것을 보안 경계로 설정했습니다. 시스템 소유자는 `workspace/easy`에서 기존의 보안 모드 및 승인 카드를 그대로 활용합니다.
- **에이전트 제작은 도우미 인터뷰와 대화형 설계도 방식을 채택합니다.** 도우미는 오케스트레이터의 설정을 바탕으로 도구가 제거된 복제 모델이며(엔진의 `_tool_less` 방식과 동일), 답변 끝에 ```` ```agent {json}``` ```` 설계도 블록을 첨부합니다. UI는 이 블록을 검증 및 필터링(미지원 도구/스킬 제거, 지원 색상/아이콘 보정)하여 우측 카드에 렌더링하며, 사용자가 카드를 수동 편집하면 수정된 상태가 다음 턴에 도우미에게 전달되어 반영됩니다. 설계도 필드명은 `conf.json` 스키마와 일치하며, 시스템 소유자에게는 "conf.json 설정 미리보기"가 함께 제공됩니다.
- **저장 방식은 사용자 권한에 따라 분기됩니다.** 시스템 소유자는 `add_agent_to_conf_file`을 통해 `conf.json`에 에이전트를 즉시 추가하고 런타임 풀에 동기화합니다. 모델과 API 키는 기본 `llm` 설정을 상속받습니다. 설정 기록기가 유효성 검증을 직접 수행하지 않으므로 `AgentConfig` Pydantic 모델을 통해 사전 검증하며, 진행 중인 세션이 있을 경우 저장을 안전하게 차단합니다. 반면 체험 방문자의 에이전트는 `easy_agents` DB 테이블에만 격리 보관되며 `conf.json`을 수정하지 않습니다.
- **승인 카드는 별도 컴포넌트로 중복 구현하지 않고 기존 피드를 재사용합니다.** 계획 승인([ADR-028](ADR-028-plan-approval-gate.md))이나 도구 승인 요청이 발생하면 화면이 '전체 기록' 탭(`ChatFeed`)으로 자동 전환되어 승인 카드를 노출합니다. 작업 과정 탭에서는 "사용자가 계획을 검토하고 승인했습니다"라는 요약 배너로 기록을 남깁니다.

**사전 녹화된 시뮬레이션 영상/스크립트는 사용하지 않습니다.** 사전 생성된 데이터를 보여주면 LLM API 비용은 절감되지만, 비엔지니어가 실제로 체감해야 하는 핵심 가치는 "에이전트가 실제로 파일을 열고 내용을 확인한다"는 현실감입니다. 웰컴 화면의 비교 도표가 개념적 이해를 돕고, 실행 화면에서는 실제 파일에 대한 실시간 조회가 이루어집니다.

## 결과 (Consequences)

**장점**

- 방문자가 에이전트의 실제 행동과 관찰 루프를 직접 체험할 수 있습니다. 보안 정책으로 거부된 쓰기 시도 또한 하나의 '관찰' 결과로 피드백되어, "도구 실패 역시 가치 있는 관찰이다"라는 핵심 아키텍처 원칙([ADR-014](ADR-014-tool-failure-is-observation.md))을 시각적으로 자연스럽게 전달합니다.
- JSON 설정 파일을 직접 다루지 않고도 대화만으로 완성도 높은 에이전트를 구축할 수 있으며, 제작 과정에서 페르소나·업무 지시서·도구·스킬의 개념과 `conf.json` 내 역할을 명확히 학습할 수 있습니다.
- 기존 전문가 화면, 일반 체험 화면, 코어 오케스트레이션 엔진의 코드가 온전히 보존됩니다. 신규 스키마는 전용 테이블 2개(`easy_sessions`, `easy_agents`)로 완벽히 격리되어 코어 테이블 스키마에 부작용을 주지 않습니다.

**고려할 트레이드오프**

- 세션 종료 후 다시 불러온 대화 기록에서는 생각과 행동 간의 정밀한 선후 관계가 복원되지 않습니다. 기존 DB 스키마에는 발언 본문 텍스트와 도구 호출 내역만 분리 저장되어 있으므로, 화면 복원 시 수행된 행동들을 먼저 배치하고 본문 텍스트를 결론으로 표시하며 안내 문구를 덧붙입니다. 정확한 시계열 복원을 위해서는 엔진의 메시지 저장 스키마 확장이 필요합니다.
- 도구 실행이 극히 빠르게 완료되는 경우, 이전 생각의 마지막 청크가 후속 생각 블록으로 일부 넘어갈 수 있습니다. 엔진이 도구 완료 이벤트를 전송하기 전에 버퍼링된 텍스트 청크를 강제 플러시하도록 개선하면 해결 가능하지만, 엔진 비침습 원칙에 따라 이번 범위에서는 엔진 코드를 수정하지 않았습니다.
- 방문자 세션 역시 작업 디렉터리별 MCP 런타임을 구동합니다([ADR-016](ADR-016-per-workspace-mcp-runtime.md)). 다수의 방문자가 단일 폴더(`easy-guest`)를 공유하므로 런타임 프로세스는 하나로 절약되지만, 파일 쓰기 수준의 완전한 격리는 기본적으로 읽기 전용 모드라는 전제에 의존합니다. 시스템 소유자가 `conf.json`에 파일 쓰기 허용 규칙을 등록할 경우 이 격리 전제가 약화될 수 있습니다.
- 진행 전략이 단일 순차 진행으로 고정되어 있어, 찬반 토론이나 병렬 지시 등 고급 오케스트레이션 전략은 본 간편 화면에서 지원되지 않습니다.
- 소유자의 `conf.json` 저장은 서버 내 진행 중인 활성 세션이 하나라도 있을 경우 설정 정합성을 위해 차단됩니다. 동시 접속자가 많은 공개 체험 환경에서는 설정 저장 타이밍을 잡기 어려울 수 있습니다.
