# ADR-013. 설정 형식을 TOML에서 JSON으로 바꾼다

> [ADR 목록](README.md) · 이전: [ADR-012](ADR-012-agent-owned-debate-order.md) · 다음: [ADR-014](ADR-014-tool-failure-is-observation.md)

## 상태 (Status)

채택됨 · 2026-08-30 (v0.1) · 초기 설정 형식(TOML) 선택을 대체 · 관련: [ADR-011](ADR-011-session-config-snapshot.md)

## 맥락 (Context)

- 시스템 초기 설계 시 채택했던 설정 포맷은 TOML이었습니다. 주석과 여러 줄(Multiline) 문자열을 언어 차원에서 기본 지원하므로, 사람이 장문의 시스템 프롬프트나 서버 설명을 직접 작성하기에는 JSON보다 직관적이고 편리했습니다.
- 그러나 애플리케이션이 설정 파일을 **프로그래밍 방식으로 덮어쓰기(Write-back)** 시작했습니다. 웹 UI 화면에서 페르소나를 수정하고, MCP 도구 서버를 켜거나 끄며, 신규 에이전트를 등록하고, 발언 순서를 변경하면 그 변경 사항이 로컬 설정 파일에 즉시 영속화되어야 했습니다.
- 파이썬 표준 라이브러리(`tomllib`)는 TOML을 **읽는(Parse)** 기능만 제공할 뿐, 객체를 TOML 형식으로 **직렬화하여 쓰는** 모듈이 존재하지 않았습니다. 그 결과 설정 덮어쓰기 로직이 불안정한 줄 단위 문자열 조작 코드로 구현되었습니다.
  - 섹션 구분을 파싱하기 위해 현재 라인이 여러 줄 문자열 내부인지 여부를 일일이 추적해야 했습니다. 시스템 프롬프트 내부의 `[검토 항목]`과 같은 문구를 TOML 섹션 헤더로 오인하면 안 되기 때문입니다.
  - 데이터 타입(단순 문자열, 배열, 인라인 테이블, 여러 줄 문자열)마다 수작업으로 문자열 포맷팅을 수행했습니다.
  - 내부 전용 헬퍼 함수만 12개에 달했으며, 새로운 설정 필드가 하나 추가될 때마다 이 복잡한 파서를 매번 수정해야 했습니다.
- 외부 서드파티 TOML 라이브러리(`tomlkit` 등)를 도입하는 대안도 검토되었으나, 인터넷이 단절된 폐쇄망에 반입할 의존성이 추가되는 데다 라이브러리별로 주석 보존 완성도가 불완전했습니다.

## 결정 (Decision)

시스템 설정 파일 포맷을 **표준 JSON**(`conf.json`)으로 전면 전환하고, 파이썬 표준 라이브러리 `json` 모듈만으로 읽기와 쓰기를 일관되게 처리하도록 합니다. 표준 JSON 규격에 부재한 두 가지 핵심 기능은 시스템 규칙을 통해 보완합니다.

- **주석(Comments) 보존**: 딕셔너리의 키가 `//` 접두사로 시작하면 개발자 설명 주석으로 취급하고, 애플리케이션 런타임이 설정을 읽어 들일 때 이를 필터링하여 제거합니다. 주석의 값은 단일 문자열 또는 문자열 배열로 작성합니다. 주석 자체가 유효한 JSON 키-값 쌍 데이터의 일부이므로, 파이썬 객체로 읽고 다시 덤프하는 것만으로 파일 내의 주석이 안전하게 보존됩니다.
- **여러 줄 텍스트(Multiline)**: 시스템 프롬프트와 같은 장문의 텍스트는 문자열 배열(`["line 1", "line 2"]`) 형태로 정의하고, 런타임에서 이를 읽을 때 줄바꿈(`\n`) 문자로 결합합니다.

모든 설정 쓰기 작업은 동일한 4단계 원자적 파이프라인을 준수하도록 강제합니다.

1. 사용자 입력을 메모리 상에서 먼저 철저히 검증합니다. 유효성 검증에 실패할 경우 디스크 파일에 일절 접근하지 않습니다.
2. 환경변수가 이미 치환된 런타임 메모리 객체가 아니라, **디스크 파일의 원시 텍스트**를 직접 역직렬화하여 로드합니다 (`${VAR}` 템플릿 문법과 주석 키가 그대로 보존된 상태).
3. 파이썬 딕셔너리 객체를 수정합니다. 기존 키는 제자리에서 갱신하고, 신규 키는 해당 JSON 객체의 말미에 추가합니다.
4. 동일한 파일 시스템 내의 임시 파일에 먼저 기록한 뒤, `os.replace`를 통해 원자적(Atomic)으로 파일을 교체합니다.

설정 덮어쓰기 모듈의 공개 API 시그니처는 기존과 동일하게 유지하여, 이를 호출하는 UI 계층(로스터, 페르소나 설정 화면)의 코드는 수정하지 않습니다.

## 결과 (Consequences)

**좋아지는 점**

- 복잡했던 설정 쓰기 로직이 "원문 JSON 로드 → 딕셔너리 수정 → 일괄 덤프"라는 단순하고 명확한 흐름으로 재편되었습니다. 내부 헬퍼 함수가 12개에서 5개로 대폭 간소화되었습니다.
- 본문 텍스트 내의 대괄호 등으로 인해 섹션 헤더가 오인식되던 문법적 위험이 원천 해소되었습니다.
- 비정상적인 입력 데이터는 디스크 I/O 이전에 완벽히 차단되며, 쓰기 도중 프로세스가 비정상 종료되더라도 원자적 교체 덕분에 손상된 반쪽짜리 파일이 남지 않습니다.
- JSON 문법 오류 발생 시 정확한 행과 열 번호가 콘솔에 명확히 보고됩니다.
- 실제 설정 파일을 대상으로 항목 추가, 삭제, 활성화/비활성화, 순서 및 진영 수정, 페르소나 편집을 망라한 회귀 테스트를 통과했습니다. 주석 보존, `${VAR}` 원형 보존, UI 실수로 입력된 부동소수점 `8192.0`이 정수 `8192`로 정규화되어 저장되는 점, 그리고 **신규 항목을 추가했다가 다시 삭제했을 때 파일이 바이트 단위로 100% 동일하게 복원되는 것**까지 엄밀히 검증했습니다.

**치르는 비용**

- 사람이 텍스트 에디터로 직접 작성하기에는 TOML보다 다소 번거롭습니다. 모든 키의 쌍따옴표, 후행 쉼표(Trailing Comma) 금지, 긴 문장의 배열 분할 작성 등이 요구됩니다.
- **사람이 임의로 배치한 서식 공백(빈 줄)을 잃어버립니다.** 표준 JSON 직렬화기로 다시 쓸 경우 가독성을 위해 넣어두었던 빈 줄들이 모두 제거되며, JSON 규격상 빈 줄을 보존할 수 없습니다. 따라서 저장소에 버전 관리되는 **기본 설정 예시 템플릿 파일은 프로그램이 아닌 사람이 직접 수동 편집하도록 합니다.** 애플리케이션이 덮어쓰는 실제 운영 환경의 설정 파일은 정규화된 포맷으로 재정렬되는 것을 감수합니다.
- 초기 배포 번들의 설정 예시, 패키징 스크립트, 공식 매뉴얼, 위키 문서의 모든 코드 예시를 JSON 규격으로 전면 개편해야 했습니다. 문서에 수록된 모든 JSON 조각은 자동 파싱 검증을 거쳤습니다.

**교훈**

설정 파일 포맷을 선정할 때 "사람이 편집하기 얼마나 편한가"만을 단일 기준으로 삼아서는 안 됩니다. **애플리케이션 프로그램이 해당 설정을 직접 덮어쓰는 요구사항이 존재하는가**가 훨씬 중대한 아키텍처 판단 기준이 됩니다. 프로그램의 빈번한 쓰기가 요구된다면, 런타임 언어의 표준 도구만으로 읽기와 쓰기가 모두 완벽히 지원되는 포맷을 선택하는 것이 장기적으로 훨씬 유리합니다.
