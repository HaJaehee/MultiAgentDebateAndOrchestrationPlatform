# ADR-013. 설정 형식을 TOML에서 JSON으로 바꾼다

> [ADR 목록](README.md) · 이전: [ADR-012](ADR-012-agent-owned-debate-order.md) · 다음: [ADR-014](ADR-014-tool-failure-is-observation.md)

## 상태 (Status)

채택됨 · 2026-08-30 (v0.1) · 초기 설정 형식(TOML) 선택을 대체 · 관련: [ADR-011](ADR-011-session-config-snapshot.md)

## 맥락 (Context)

- 처음 설정 형식은 TOML이었습니다. 주석과 여러 줄 문자열을 기본으로 지원하니, 사람이 긴 시스템 프롬프트와 서버
  설명을 적기에는 JSON보다 편했습니다.
- 앱이 설정을 **되쓰기** 시작했습니다. 화면에서 페르소나를 고치고, MCP 서버를 켜고 끄고, 에이전트를 추가하고,
  발언 순서를 바꾸면 그 결과가 설정 파일에 기록됩니다.
- 파이썬 표준 라이브러리에는 TOML을 **읽는** 모듈만 있고 **쓰는** 모듈이 없습니다. 그래서 되쓰기 코드가 줄 단위
  문자열 편집이었습니다.
  - 섹션 경계를 찾으려고 여러 줄 문자열 안인지 아닌지를 추적했습니다. 시스템 프롬프트 안의 `[검토 항목]` 같은
    줄을 섹션 헤더로 읽으면 안 되기 때문입니다.
  - 값의 종류(문자열, 배열, 인라인 테이블, 여러 줄 문자열)마다 직렬화를 손으로 했습니다.
  - 내부 도우미 함수만 12개였고, 설정 항목을 하나 추가할 때마다 이 장치를 다시 상대해야 했습니다.
- 서드파티 TOML 기록기를 쓰는 방법도 있었지만, 폐쇄망에 반입할 의존성이 하나 늘고 주석 보존 여부도 라이브러리마다
  달랐습니다.

## 결정 (Decision)

설정 파일을 **JSON**(`conf.json`)으로 바꾸고, 표준 라이브러리 `json`만으로 읽고 쓴다. JSON에 없는 두 가지는
규칙으로 채운다.

- **주석**: 키가 `//`로 시작하면 설명으로 보고 읽을 때 걷어낸다. 값은 문자열이나 문자열 배열이다. 설명이 데이터의
  일부이므로 읽고 다시 쓰는 것만으로 보존된다.
- **여러 줄 글**: 시스템 프롬프트 같은 긴 글은 문자열 배열로 적고, 읽을 때 줄바꿈으로 이어 붙인다.

모든 기록은 같은 네 단계를 거친다.

1. 입력을 먼저 전부 검증한다. 실패하면 파일에 닿지 않는다.
2. 해석된 값이 아니라 **파일의 원문**을 읽는다(`${VAR}`와 주석이 그대로 있는 상태).
3. 딕셔너리를 고친다. 기존 키는 그 자리에서 바꾸고, 새 키는 해당 객체 끝에 붙인다.
4. 임시 파일에 쓰고 원자적으로 교체한다.

기록기들의 공개 함수 모양은 바꾸지 않는다. 호출하는 쪽(로스터, 페르소나 화면)은 건드리지 않는다.

## 결과 (Consequences)

**좋아지는 것**

- 되쓰기가 "딕셔너리를 고치고 통째로 저장"이 되었습니다. 내부 도우미가 12개에서 5개로 줄었습니다.
- 섹션 헤더를 잘못 읽을 위험이 사라졌습니다.
- 잘못된 입력은 파일에 닿기 전에 거절되고, 쓰다가 죽어도 반쪽짜리 설정이 남지 않습니다.
- 문법 오류가 줄과 칸 번호와 함께 보고됩니다.
- 실제 설정으로 추가, 삭제, 켜고 끄기, 순서와 진영 변경, 페르소나 수정을 돌려 확인했습니다. 설명 보존, `${VAR}`
  미해석 유지, 숫자 입력 칸이 준 `8192.0`이 `8192`로 기록되는 것, **추가한 뒤 삭제하면 파일이 바이트 단위로 같아지는
  것**까지 확인했습니다.

**치르는 비용**

- 사람이 직접 쓰기에는 TOML보다 불편합니다. 따옴표, 쉼표, 배열로 쪼갠 긴 글.
- **서식을 잃습니다.** 표준 JSON 직렬화로 다시 쓰면 사람이 읽기 좋게 넣어 둔 빈 줄이 모두 사라지고, JSON에는 빈 줄을
  표현할 방법이 없어 되살릴 수도 없습니다. 그래서 저장소의 **설정 예시 파일은 프로그램이 아니라 사람이 직접 고칩니다.**
  앱이 되쓰는 운영 설정 파일은 정돈된 모양으로 바뀌는 것을 감수합니다.
- 설정 예시, 패키징 스크립트, 설명서, 위키의 표기와 예시를 모두 바꿔야 했습니다. 문서에 실린 JSON 조각은 모두 실제로
  파싱해 검증했습니다.
- 아직 배포 전이라 기존 TOML 사용자를 위한 변환기는 만들지 않았습니다. 배포 뒤였다면 이관 경로가 필요했을 것입니다.

**교훈**

설정 형식은 "사람이 쓰기 편한가"만으로 고르면 안 됩니다. **프로그램이 되쓰는가**가 더 큰 기준이 될 수 있습니다.
되쓴다면, 그 언어의 표준 도구로 읽기와 쓰기가 모두 되는 형식이 유리합니다.
