# ADR-019. 원격 접속은 주인이 발급한 토큰 하나로 연다

> [ADR 목록](README.md) · 이전: [ADR-018](ADR-018-orchestrator-writes-conclusions.md) · 다음: [ADR-020](ADR-020-conversation-memory.md)

## 상태 (Status)

채택됨 · 2026-09-15 (v0.8.2) · 관련: [ADR-001](ADR-001-python-single-process.md), [ADR-006](ADR-006-airgap-first-packaging.md)

## 맥락 (Context)

- 시스템 초기에는 사용자 인증 계층이 전혀 구현되어 있지 않았습니다. 기본 네트워크 바인딩은 로컬 루프백(`127.0.0.1`)이었으나, 동일 폐쇄망 내의 다른 PC에서 원격 접속하여 협업하기 위해 바인딩을 `0.0.0.0`으로 개방할 경우 **동일 사내망에 위치한 누구라도** 다음 행위를 수행할 수 있는 심각한 보안 취약점에 노출되었습니다.
  - 타인의 대화 세션 및 민감한 페르소나 프롬프트 열람
  - 등록된 MCP 도구 서버의 실행 명령어 확인 및 **임의의 OS 명령어로 신규 도구 서버를 등록 및 실행** (사실상 원격 코드 실행(RCE))
  - 파이썬 샌드박스 MCP 도구를 통한 임의 시스템 코드 실행
  - 작업 공간 내의 프로젝트 소스 코드 및 산출물 파일 임의 다운로드
- 실제 시스템 운용 형태는 "서버 PC 소유자 1인 + 소유자가 허락한 소수 동료" 구조였습니다. 복수의 팀이 다중 테넌트 계정으로 분할하여 운용하는 환경이 아니었습니다.
- 서버 PC 앞에 직접 앉은 로컬 사용자는 이미 해당 머신의 운영체제 파일과 환경 설정에 자유롭게 접근할 수 있는 물리적 권한을 보유하고 있습니다.
- 폐쇄망에서 사설 자체 서명 인증서(Self-signed Certificate)로 HTTPS를 활성화하더라도 브라우저가 신뢰할 수 없는 인증서 경고를 띄워 실익이 적었습니다.

## 결정 (Decision)

관리자(소유자)가 확정한 접근 제어 정책을 다음과 같이 정의합니다.

| 항목 | 결정 사항 |
| :--- | :--- |
| 로컬 루프백 (`127.0.0.1`, 서버 머신 자체) | **인증 절차 생략** (물리 콘솔 신뢰) |
| 원격 네트워크 접근 (`0.0.0.0` 외부 인입) | 소유자 비밀 토큰 기반 로그인 필수, 세션 쿠키 **7일간** 유지 |
| 토큰 규격 | `.env` 환경 파일의 단일 설정값. 영문 대소문자와 숫자로 구성된 **정확히 24자리 문자열**. 형식 유효성만 검증하고 엔트로피 강도는 제한하지 않음 |
| 토큰 누락 또는 형식 불일치 시 | 원격 네트워크 인입 요청 **전면 차단** (보수적 실패 방어: Fail-closed) |
| 토큰 재발급 및 교체 | 상단 정보 버튼 옆 열쇠 아이콘, **오직 서버 머신 로컬 화면에서만 수행 가능**. (1) `.env` 파일의 토큰을 런타임에 즉시 반영, (2) 신규 난수 토큰 생성 후 `.env` 파일에 안전하게 저장 |
| HTTPS 암호화 전송 | 현재는 기본 지원하지 않음. 신뢰할 수 없는 네트워크 경유 시 SSH 터널링 포워딩 권장 |
| 사용자별 개별 계정 및 대화 소유권 분리 | 현 단계에서는 시스템 설계 범위 밖(Out of Scope)으로 제외 |

구현 세부 원칙:

- **단일 게이트웨이 관문, 최외곽 배치**: 단 하나의 순수 ASGI 미들웨어가 UI HTML 페이지, 웹소켓 동기화 채널, REST API, 정적 아이콘 에셋, 파일 다운로드 요청을 최외곽에서 일괄 인터셉트하도록 합니다. 이 미들웨어가 최외곽에 위치함을 단위 테스트로 고정합니다.
- **로컬 루프백 요청에 대한 방어 검증**: 요청의 `Origin` 헤더가 `Host` 헤더와 불일치할 경우 즉시 거부합니다 (서버 머신의 브라우저에 열린 악성 외부 웹페이지가 루프백 권한을 탈취하여 MADO를 조종하는 CSRF 공격 방어). 루프백 IP 요청임에도 `Host` 헤더가 낯선 도메인명일 경우 거부합니다 (DNS 리바인딩 공격 차단).
- **비밀 토큰의 단 1회 노출 원칙**: 토큰은 오직 로그인 POST 본문으로만 수신하며, 타이밍 공격을 방지하기 위해 상수 시간 비교(`hmac.compare_digest`)로 검증합니다. 검증 성공 시 토큰에서 파생된 비밀 키로 서명된 세션 쿠키(`HttpOnly`, `SameSite=Strict`)를 발급합니다. 토큰 원문은 URL 쿼리, 쿠키 본문, HTTP 응답, 서버 로그 어디에도 남기지 않습니다. 토큰이 교체되면 기존에 발급된 모든 서명 쿠키는 즉시 무효화됩니다.
- **무차별 대입 공격(Brute-force) 지연 방어**: 동일 IP 주소에서 5회 연속 로그인 실패 시 해당 IP를 15분간 강제 차단합니다. 잠금 및 해제 이벤트는 보안 감사 로그 파일에 기록합니다 (클라이언트 IP, 발생 시각, 실패 횟수, User-Agent. 제출된 토큰 평문은 절대 기록하지 않음). 서버 머신의 소유자는 차단된 IP 목록을 로컬 UI에서 즉시 수동 해제할 수 있습니다.
- **원자적 파일 갱신 우선 원칙**: 신규 토큰 생성 시 `.env` 파일에 먼저 기록하고, 파일 I/O가 완벽히 성공했을 때만 메모리 런타임에 적용합니다. 메모리와 디스크 상태가 어긋나면 다음 서버 재부팅 시 토큰이 예기치 않게 변경되기 때문입니다. `.env` 파일의 타 설정 라인, 주석, 개행 형식은 그대로 보존합니다. 토큰 교체 즉시 현재 열려 있는 모든 원격 세션을 로그인 화면으로 리다이렉트합니다.
- **역방향 프록시 헤더 불신뢰**: `X-Forwarded-For` 헤더는 스푸핑 위험이 있으므로 의도적으로 무시합니다. 따라서 운영 문서에 리버스 프록시 뒷단에 직접 노출하지 말 것을 명시합니다.
- **기존 배포 인스턴스를 위한 자동 마이그레이션**: 이미 `0.0.0.0`으로 개방되어 있으나 토큰이 설정되지 않은 상태인 경우, 서버 머신에서 최초로 UI를 연 로컬 브라우저가 난수 토큰을 자동 생성하여 `.env`에 저장하고 모달 팝업으로 관리자에게 알립니다. 단, 소유자가 직접 입력했으나 형식이 잘못된 토큰은 임의로 덮어쓰지 않습니다.

## 결과 (Consequences)

**좋아지는 점**

- 동일 네트워크 대역의 불특정 비인가 사용자가 대화 세션, 도구 설정, 파이썬 샌드박스 커널, 작업 공간 파일에 접근하는 위험을 원천 차단했습니다.
- 설정 오류가 발생하더라도 시스템이 개방되는 쪽이 아니라 완전히 잠기는 쪽(Fail-closed)으로 안전하게 방어합니다.
- 관리자는 복잡한 다중 계정 관리 없이 단 하나의 비밀 토큰만으로 원격 접근을 안전하게 제어할 수 있습니다.

**치르는 비용**

- **기본 통신이 평문 HTTP로 전송됩니다.** 내부망에서 패킷 스니핑이 가능한 공격자가 존재할 경우 세션 쿠키가 탈취될 수 있습니다. 필요시 SSH 로컬 포트 포워딩 터널을 병용하도록 안내합니다.
- **단일 토큰을 공유합니다.** 특정 사용자 한 명의 접근 권한만을 선별적으로 박탈할 수 없습니다. 토큰을 변경하면 모든 원격 접속자가 일괄 재로그인해야 합니다.
- **일반적인 리버스 프록시 뒤에 배치할 수 없습니다.** 프록시를 경유할 경우 모든 원격 요청이 루프백(`127.0.0.1`)으로 유입되어 인증 없이 통과되는 치명적인 보안 결함이 발생하기 때문입니다.
- 인증을 통과한 모든 원격 사용자가 서버 소유자와 동일한 시스템 조작 권한을 부여받습니다.

**배포 후 발견한 결함**

올바른 비밀 토큰을 입력했음에도 원격 로그인이 "교차 출처 요청 거부(Origin Mismatch)" 오류로 실패하는 사고가 있었습니다. 로그인 HTML 페이지가 `Referrer-Policy: no-referrer` 헤더를 전송하고 있었는데, 이 정책이 적용되면 브라우저가 폼 POST 요청 시 `Origin: null`을 전송합니다. 인증 게이트웨이는 이를 비정상적인 외부 출처 요청으로 판단하여 차단했던 것입니다. 이에 정책을 `same-origin`으로 변경하여 해결했습니다 (타 사이트로는 여전히 Referer를 누출하지 않습니다). 단일 보안 헤더가 다른 보안 검증 로직과 충돌한 전형적인 사례이며, 보안 메커니즘은 반드시 종합적인 시나리오로 결합 테스트해야 합니다.

**교훈**

보안 아키텍처를 설계할 때 던져야 할 첫 번째 질문은 "어떤 공격을 막을 것인가"보다 **"누가 실제로 이 시스템을 사용하는가"**입니다. 운영 시나리오가 "단일 소유자와 소수의 신뢰할 수 있는 동료"라면 단일 토큰 인증이 최선의 균형점이며, 엔터프라이즈급 다중 계정 체계는 과도한 엔지니어링입니다. 도입하지 않기로 명시적으로 배제한 항목들(HTTPS, RBAC 계정 체계, 프록시 지원 등)을 기록으로 남겨두어야 향후 운영 전제가 변경되었을 때 어떤 설계부터 재검토해야 할지 명확히 파악할 수 있습니다.
