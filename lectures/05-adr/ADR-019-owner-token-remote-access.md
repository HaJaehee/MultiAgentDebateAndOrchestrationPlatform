# ADR-019. 원격 접속은 주인이 발급한 토큰 하나로 연다

> [ADR 목록](README.md) · 이전: [ADR-018](ADR-018-orchestrator-writes-conclusions.md) · 다음: [ADR-020](ADR-020-conversation-memory.md)

## 상태 (Status)

채택됨 · 2026-09-15 (v0.8.2) · 관련: [ADR-001](ADR-001-python-single-process.md), [ADR-006](ADR-006-airgap-first-packaging.md)

## 맥락 (Context)

- MADO에는 인증이 전혀 없었습니다. 기본 바인딩은 `127.0.0.1`이지만, 같은 망의 다른 PC에서 쓰려고 `0.0.0.0`으로 열면
  **같은 망의 누구나** 다음을 할 수 있었습니다.
  - 다른 사람의 대화와 페르소나 읽기
  - MCP 서버 실행 명령 보기, **임의의 명령으로 서버 추가하기** (사실상 원격 명령 실행)
  - 샌드박스 MCP로 코드 실행하기
  - 작업 공간 파일 내려받기
- 실제 사용 형태는 "서버 PC 주인 한 명 + 주인이 허락한 몇 사람"입니다. 여러 팀이 계정을 나눠 쓰는 형태가 아닙니다.
- 서버 PC 앞에 앉은 사람은 이미 그 PC의 파일과 설정에 접근할 수 있습니다.
- 사설 인증서로 HTTPS를 켜면 어차피 브라우저가 신뢰할 수 없다는 경고를 띄웁니다.

## 결정 (Decision)

주인이 정한 정책은 다음과 같습니다.

| 항목 | 결정 |
| :--- | :--- |
| 루프백(서버 PC 자신) | **인증 없음** |
| 원격 | 주인 토큰으로 로그인, **7일** 유지 |
| 토큰 | `.env`의 한 값. 영문 대소문자와 숫자로 **정확히 24자**. 형식만 검사하고 강도는 검사하지 않음 |
| 토큰이 없거나 형식이 틀리면 | 원격 요청 **전면 거부** (닫히는 쪽으로 실패) |
| 토큰 교체 | 정보 버튼 옆 열쇠 버튼, **서버 PC에서만**. (1) `.env`의 토큰 적용, (2) 새 토큰 생성 후 `.env`에 저장 |
| HTTPS | 지금은 하지 않음. 신뢰할 수 없는 망에서는 SSH 터널 |
| 사용자별 계정, 대화 소유권 | 범위 밖 |

구현 원칙은 이렇습니다.

- **관문은 하나, 가장 바깥에.** 순수 ASGI 미들웨어 하나가 화면 페이지, 화면 동기화 WebSocket, REST API, 아이콘, 다운로드를
  모두 거릅니다. 가장 바깥에 있다는 사실을 테스트로 고정한다.
- **루프백에도 검사한다.** 요청의 Origin이 Host와 다르면 거부한다(서버 PC 브라우저에 열린 악성 페이지가 루프백 권한으로
  조종하는 것을 막는다). 루프백인데 Host가 낯선 이름이면 거부한다(DNS 리바인딩).
- **토큰은 한 번만 보인다.** POST 본문으로만 받고, 상수 시간 비교로 확인하고, 성공하면 토큰에서 파생한 키로 서명한 쿠키를
  발급한다(HttpOnly, SameSite=Strict). 토큰은 URL, 쿠키, 응답, 로그 어디에도 나타나지 않는다. 토큰을 바꾸면 모든 쿠키가
  무효가 된다.
- **실패를 늦춘다.** 같은 IP에서 5회 실패하면 15분 잠근다. 잠금과 해제는 감사 기록 파일에 남긴다(IP, 시각, 실패 횟수,
  User-Agent. 제출된 토큰 값은 남기지 않는다). 서버 PC의 주인은 잠긴 IP를 바로 풀 수 있다.
- **교체는 파일 먼저.** 새 토큰은 `.env`에 먼저 쓰고, 쓰기에 성공했을 때만 적용한다. 메모리와 파일이 어긋나면 다음 재시작
  때 토큰이 조용히 바뀐다. `.env`의 다른 줄, 주석, 줄바꿈 형식은 그대로 둔다. 교체 뒤에는 열린 원격 화면을 모두 로그인으로
  돌려보낸다.
- **프록시 헤더를 믿지 않는다.** `X-Forwarded-For`는 일부러 무시한다. 그래서 리버스 프록시 뒤에 두지 말라고 문서에 적는다.
- **이미 열려 있던 서버를 위한 전환.** 이미 `0.0.0.0`으로 열었는데 토큰이 없으면, 서버 PC에서 처음 연 화면이 토큰을 만들어
  `.env`에 저장하고 팝업으로 알린다. 주인이 직접 적은 형식 틀린 값은 덮어쓰지 않는다.

## 결과 (Consequences)

**좋아지는 것**

- 같은 망의 불특정 사용자가 대화, 도구 설정, 샌드박스, 파일에 닿을 수 없습니다.
- 잘못 설정되면 열리는 쪽이 아니라 닫히는 쪽으로 실패합니다.
- 주인은 계정 관리 없이 토큰 하나로 누구에게 접속을 허락할지 정합니다.

**치르는 비용**

- **평문 HTTP입니다.** 망 안에서 트래픽을 엿볼 수 있는 사람은 쿠키를 가로챌 수 있습니다. SSH 터널을 권하는 것으로 대응합니다.
- **토큰을 공유합니다.** 한 사람의 접근만 철회할 수 없습니다. 토큰을 바꾸면 모두가 다시 로그인해야 합니다.
- **리버스 프록시 뒤에 둘 수 없습니다.** 둘 경우 모든 요청이 루프백으로 보여 인증 없이 통과합니다.
- 원격 사용자 모두가 주인과 같은 권한을 가집니다.

**배포 후 발견한 것**

올바른 토큰을 넣어도 원격 로그인이 "교차 출처 요청 거부"로 실패했습니다. 로그인 페이지가 `Referrer-Policy: no-referrer`를
보냈고, 이 정책에서는 브라우저가 폼 POST에 `Origin: null`을 붙입니다. 게이트는 그것을 다른 출처로 보고 거부했습니다. 정책을
`same-origin`으로 바꿔 해결했습니다(다른 사이트로는 여전히 Referer를 보내지 않습니다). 보안 헤더 하나가 다른 보안 검사와
부딪힌 사례입니다. 보안 장치는 조합으로 시험해야 합니다.

**교훈**

보안 설계의 첫 질문은 "무엇을 막을 것인가"보다 **"누가 이 시스템을 쓰는가"** 입니다. 사용 형태가 "주인 한 명과 허락받은
몇 사람"이라면 토큰 하나가 맞고, 계정 체계는 과합니다. 하지 않기로 한 것(HTTPS, 계정, 프록시 지원)을 명시해 두면, 그 전제가
바뀌었을 때 무엇을 다시 봐야 하는지 알 수 있습니다.
