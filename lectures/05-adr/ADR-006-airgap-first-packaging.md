# ADR-006. 폐쇄망 반입을 전제로 두 종류의 패키지를 만든다

> [ADR 목록](README.md) · 이전: [ADR-005](ADR-005-long-lived-mcp-sessions.md) · 다음: [ADR-007](ADR-007-no-simulated-answers.md)

## 상태 (Status)

채택됨 · 2026-08-26 전체 번들, 2026-08-28 소스 갱신 패키지 · 관련: [ADR-001](ADR-001-python-single-process.md), [ADR-021](ADR-021-graph-debate.md)

## 맥락 (Context)

- 운영 환경은 외부 인터넷이 원천 차단된 오프라인 폐쇄망입니다. pip, npm, 공용 CDN 등의 온라인 패키지 매니저를 전혀 사용할 수 없습니다.
- 망 내부로 반입되는 모든 파일은 엄격한 보안 심사를 거쳐야 합니다. 반입되는 파일의 용량이 클수록, 반입 빈도가 잦을수록 심사 및 운영 비용이 급격히 증가합니다.
- 기반 런타임(Python 인터프리터, Node.js 런타임, 핵심 라이브러리)은 한 번 반입하면 거의 변경되지 않지만, 애플리케이션 비즈니스 코드는 하루에도 여러 차례 수정 및 배포됩니다.
- 단순히 Python wheel 파일들을 수집하기만 한 오프라인 번들은 폐쇄망에 실제 반입된 후에야 누락된 숨은 의존성이 드러나곤 합니다. 이 경우 반입 절차를 처음부터 다시 밟아야만 합니다.
- 동봉된 샌드박스 서버의 의존성 파일에 `mcp` 패키지의 버전 상한이 명시되어 있지 않아, 제약 없이 다운로드할 경우 API가 호환되지 않는 2.x 버전이 유입되는 문제가 있었습니다.
- 개발용 PC와 실제 운영 대상 PC의 파일 디렉터리 경로 체계가 서로 상이합니다. 환경마다 별도의 설정 파일을 각각 작성하여 관리하는 방식은 지양하고자 했습니다.

## 결정 (Decision)

배포 아티팩트를 목적에 따라 **두 종류의 패키지**로 분리하여 구성하도록 합니다.

**전체 번들 (초기 설치 및 기반 런타임 변경 시)**

- 포터블 CPython, `node.exe` 단일 바이너리(npm 제외), 사전 검증된 오프라인 wheel 모음, 사전 설치된 Node MCP 서버 배포본, 샌드박스 서버 및 커널용 라이브러리, 소스 코드 전체, 운영 매뉴얼, 원클릭 기동 스크립트를 포함합니다.
- 수집된 wheel 파일들을 포터블 파이썬 환경에 **실제로 사전 설치하고 핵심 패키지들을 직접 import하여 검증합니다.** 이 과정에서 단 하나라도 실패하면 번들 생성을 즉시 중단합니다.
- pip 제약 파일(constraints)을 통해 `mcp<2` 버전을 강제합니다.
- 기본 작업 공간 디렉터리를 사전 Git 저장소로 초기화(`git init`)하여 포함합니다. Git MCP 서버는 대상 경로가 유효한 Git 저장소가 아닐 경우 기동에 실패하기 때문입니다.
- 실행 스크립트는 자체 위치를 기준으로 런타임, MCP 서버, 작업 공간 경로를 환경변수로 동적 계산하여 애플리케이션을 기동하도록 작성합니다.

**소스 업데이트 패키지 (비즈니스 코드만 수정되었을 때)**

- 패키징 대상 파일을 **엄격한 화이트리스트(허용 목록)** 방식으로 선별합니다.
- 시스템 구동에 필수적인 파일(예: 애플리케이션 내장 프론트엔드 정적 라이브러리)이 누락되었을 경우 패키징 작업을 즉시 중단합니다.
- 운영 환경의 실제 설정 파일(`conf.json`)은 패키징 대상에서 제외합니다.
- 단일 파일 크기가 2MB를 초과하거나 API 키 패턴이 감지될 경우 보안 감사 위반으로 패키징을 즉시 중단합니다.
- 포함된 모든 파일에 대한 SHA-256 무결성 체크섬 목록을 함께 동봉합니다.
- 해당 업데이트에서 신규 파이썬 의존성이 불가피하게 요구될 경우에 한하여 관련 wheel 파일만을 선택적으로 동봉할 수 있도록 허용합니다.

**공통 원칙**

- 설정 파일 내의 모든 파일 경로 및 네트워크 주소는 `${변수:-기본값}` 환경변수 치환 문법으로 작성하여, 개발 PC와 오프라인 번들이 동일한 설정 파일을 공유할 수 있도록 합니다.
- UI 화면에서 사용하는 브라우저 자바스크립트/CSS 라이브러리는 외부 CDN에 의존하지 않고 애플리케이션 내부에 정적으로 동봉합니다.

## 결과 (Consequences)

**좋아지는 점**

- 일상적인 코드 패치 작업이 수백 KB 단위의 경량 패키지로 완결됩니다. v0.5.0 배포 당시 네 가지 신규 기능을 표준 라이브러리만으로 구현하여 단 391KB 크기의 소스 패키지 하나로 성공적으로 업데이트했습니다.
- 번들 내부의 패키지 의존성 누락이나 import 실패가 빌드 머신 단계에서 사전에 완벽히 검증됩니다.
- 소스 패키지가 운영 서버의 기동 설정을 덮어쓰거나 민감한 인증 키를 유출하는 사고를 패키징 스크립트가 원천 방지합니다.

**치르는 비용**

- 전체 번들은 반드시 Windows 빌드 머신에서 생성해야 합니다. 포터블 런타임과 C 확장 wheel 파일들이 빌드 머신의 운영체제 아키텍처를 기준으로 수집되기 때문입니다.
- 외부 라이브러리 의존성이 변경되면 원칙적으로 전체 번들을 재반입해야 합니다. 이에 따라 신규 기능을 기획할 때 **파이썬 표준 라이브러리만으로 구현 가능한지를 최우선으로 검토하는** 설계 압박이 작용합니다. 이러한 제약은 시스템을 단순하게 유지하는 데 대체로 긍정적인 영향을 미쳤습니다.
- 기동 스크립트는 템플릿 생성기가 원본이며 Git 저장소의 파일은 빌드 사본입니다. 저장소 내의 스크립트 사본만 수정할 경우 실제 번들에 반영되지 않는 혼동을 유발할 수 있습니다.
- 설정 파일 예시에 새로운 옵션 항목이 추가되면 운영 환경의 실제 설정 파일에 **관리자가 직접 수작업으로 반영해야** 합니다. 이는 운영 설정을 안전하게 보호하기 위해 치러야 하는 대가입니다.

**발생했던 장애 사례**

- 다이어그램을 "독립 실행 HTML" 파일로 내보내는 기능이 내부적으로 외부 CDN에서 Mermaid 렌더러 스크립트를 로드하고 있었습니다. 그 결과 폐쇄망 환경에서는 렌더링이 실패하여 빈 화면만 나타났습니다. 이에 사전 렌더링된 순수 SVG 벡터 코드를 HTML 파일 내부에 직접 인라인으로 삽입하고 외부 네트워크 요청을 전면 제거하도록 수정했습니다. 폐쇄망 아키텍처 원칙은 메인 애플리케이션의 기동뿐만 아니라 **시스템이 외부로 출력하는 산출물 파일**에도 동일하게 적용되어야 합니다.
- 소스 패키징 스크립트가 압축 아카이브 생성을 모두 완료한 뒤 마지막 콘솔 안내 문구를 출력하는 과정에서 비정상 종료된 사례가 있었습니다. 출력을 CP949 인코딩으로 리다이렉션하던 한국어 Windows 환경에서 특수 기호 출력이 인코딩 오류(`UnicodeEncodeError`)를 일으켰고, 압축 결과물은 정상이었으나 프로세스 종료 코드가 1(실패)로 반환되어 자동화 파이프라인이 중단되었습니다. 이에 스크립트의 표준 출력 스트림을 UTF-8로 강제 전환하고, 인코딩 불가능한 문자는 대체 문자로 처리하도록 보완했습니다.
