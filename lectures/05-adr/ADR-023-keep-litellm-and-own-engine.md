# ADR-023. LangChain·LangGraph로 옮기지 않고 LiteLLM과 자체 엔진을 유지한다

> [ADR 목록](README.md) · 이전: [ADR-022](ADR-022-knowledge-base-deferred.md)

## 상태 (Status)

채택됨 · 2026-09-27 설계 논의에서 결정 · 관련: [ADR-002](ADR-002-litellm-gateway.md), [ADR-006](ADR-006-airgap-first-packaging.md), [ADR-017](ADR-017-never-lose-a-write.md), [ADR-021](ADR-021-graph-debate.md)

ADR-022와 마찬가지로 이 ADR도 소스 코드 커밋이 아니라 설계 논의에서 나온 결정입니다. 초기 설계에서 LangGraph 대신 자체 엔진을 고른 판단([4-4강 §1](../04-core-techniques/04-orchestration.md))을 다시 따져 본 기록입니다. 그 사이 엔진은 다섯 가지 토론 전략과 그래프 토론을 갖출 만큼 자랐습니다. 검토 대상은 LangChain·LangGraph 1.x입니다.

## 맥락 (Context)

- 프로젝트 명세는 두 방식을 모두 허용합니다. 오케스트레이션은 "LangGraph 또는 경량 커스텀 StateGraph 엔진", LLM 연동은 "LiteLLM 또는 LangChain / OpenAI SDK"입니다. MADO는 초기에 LiteLLM([ADR-002](ADR-002-litellm-gateway.md))과 자체 비동기 상태 머신을 골랐습니다.
- 그 뒤 엔진은 크게 자랐습니다. `engine.py`는 약 3,900줄, `llm.py`는 약 2,600줄입니다. 그래프 토론([ADR-021](ADR-021-graph-debate.md))을 만들면서는 LangGraph와 같은 슈퍼스텝 실행 모델을 직접 구현했습니다. 그래서 "이제라도 표준 프레임워크로 옮기는 편이 낫지 않은가"라는 질문이 나왔습니다.
- 두 라이브러리는 MADO와 겹치는 자리가 서로 다릅니다. LangGraph 노드 안에서도 LiteLLM을 그대로 부를 수 있으므로, 두 교체는 따로 판단해야 합니다.

| 라이브러리 | 성격 | MADO에서 겹치는 자리 |
| :--- | :--- | :--- |
| LangChain | LLM·도구·검색기를 감싼 표준 인터페이스, 그리고 미들웨어로 확장하는 도구 루프(`create_agent`) | LiteLLM과 `llm.py`의 도구 루프 |
| LangGraph | 상태 그래프 실행기(리듀서, 조건부 엣지, `Send`, 체크포인터, `interrupt`) | 오케스트레이션 엔진과 `GraphScheduler` |

- 개념을 짝지어 보면 대부분 일대일로 맞았습니다. `DebateState`는 상태 스키마에, 병렬 지시는 `Send`와 `max_concurrency`에, 그래프 토론은 슈퍼스텝 실행에 대응합니다. 다만 **의미가 다른 곳이 세 군데** 있었습니다.

| 영역 | LangGraph | MADO |
| :--- | :--- | :--- |
| 합류 | 여러 선이 모이는 노드(`add_edge([a, b], c)`)는 돌 때마다 모든 입력을 새로 기다립니다. | "모두 기다림"은 **첫 방문에만** 적용되고, 되돌아오는 선은 대기 대상에서 뺍니다. LangGraph 기본 합류를 쓰면 게이트 반려 루프에서 합류 노드가 다시 돌지 않습니다. |
| 사람 개입 | `interrupt()`가 그래프를 멈추고, 재개하면 그 노드를 **처음부터** 다시 실행합니다. | 도구를 여러 번 부른 발언 한가운데서 예산 연장을 묻고, 답을 받으면 그 자리에서 이어 갑니다(`TurnControl`). 실행 중에 메모를 끼워 넣는 개입은 LangGraph에 대응 개념이 없습니다. |
| 저장 | 체크포인트는 직렬화된 상태 덩어리입니다. | 발언 단위로 커밋하고, 화면은 그 발언 테이블을 읽습니다. 체크포인트로는 이 테이블을 대신할 수 없으므로 저장이 두 벌이 됩니다. |

- LLM 계층을 LangChain으로 바꿔도 [ADR-002](ADR-002-litellm-gateway.md) 표에 적힌 문제는 대부분 남습니다. 같은 역할 메시지의 연속 거부, 게이트웨이의 400→500 은폐, 로컬 서버마다 다른 도구 호출 파서, `reasoning_content` 처리가 그렇습니다. 오히려 계층이 하나 늘어 우회하기가 더 어려워집니다. 온프레미스 추론 서버 조합은 LiteLLM이 더 넓게 지원합니다.
- 폐쇄망([ADR-006](ADR-006-airgap-first-packaging.md)) 비용도 있습니다. langgraph, langchain-core, langsmith, 체크포인트 패키지와 네이티브 확장 wheel을 전체 번들로 다시 반입하고 검증해야 합니다. LangGraph를 고를 큰 이유인 LangGraph Studio와 LangSmith 추적은 외부 연결이 필요해 폐쇄망에서는 쓸 수 없습니다.
- LangGraph로 옮겨서 새로 얻는 기능은 **체크포인터 기반의 턴 도중 복구**와 **단계 단위 되돌리기**였습니다. MADO는 발언 단위로 기록하므로 끝난 발언은 남습니다. 하지만 서버가 턴 도중에 내려가면 그 턴은 거기서 끝나고, 화면에는 중단되었다는 표시도 남지 않습니다.
- 그래서 같은 날, 자체 엔진으로 턴 도중 복구를 구현할 수 있는지도 함께 검토했습니다. 결과는 아래와 같습니다.
  - **어디까지 돌았는지(커서)**는 기존 기록으로 대부분 재구성됩니다. 근거는 세 가지입니다. 대화 시작 시 굳힌 구성([ADR-011](ADR-011-session-config-snapshot.md))과 그래프 스냅샷, 순수 함수로 된 전략과 그래프 스케줄러, 그리고 발언마다 남긴 라운드·노드·포트 기록입니다.
  - 다만 발언자 지명과 과업 분배 결과는 사람이 읽는 문장으로만 남아 있어, 구조화된 메타데이터를 몇 칸 더해야 합니다.
  - **진행 중이던 발언의 도구 재실행**과 **메모리에만 있던 사람의 결정**은 LangGraph로 옮겨도 직접 풀어야 합니다. 체크포인터도 실행 중이던 노드는 다시 돌리고, 도구의 부작용은 되돌리지 못합니다.

## 결정 (Decision)

**LLM 계층은 LiteLLM을, 오케스트레이션은 자체 엔진을 유지합니다. LangChain과 LangGraph는 도입하지 않습니다.**

- LLM 호출을 LangChain 챗 모델로 바꾸지 않습니다. 얻는 것(구조화 출력 도우미, 일부 공급자 규칙의 흡수)이 가장 적습니다. 공급자 차이를 흡수하는 책임은 어느 쪽을 쓰든 호스트에 남습니다(ADR-002의 교훈).
- 엔진을 LangGraph로 다시 쓰지 않습니다. 프레임워크가 대신해 주는 것은 라운드 루프, 병렬 디스패치, 스케줄러의 골격 정도입니다. 결정 장부·요약, 합성, 다이어그램 수리, 합의 판정, 도구 게이트는 노드 안으로 자리만 옮길 뿐입니다. 그 위에 세 가지 의미 차이를 다시 맞추는 비용이 더해집니다.
- **턴 도중 복구가 필요해지면 자체 엔진에 구현합니다.** 복구에 필요한 근거는 이미 기록에 대부분 있고, 어려운 부분은 프레임워크가 대신 풀어 주지 않기 때문입니다.
- LangChain 생태계의 **부품**은 필요할 때 골라서 검토합니다. 예를 들어 [ADR-022](ADR-022-knowledge-base-deferred.md)의 지식베이스를 재개할 때 문서 로더나 텍스트 분할기가 필요하면 그 패키지만 반입 심사에 올립니다. 이때도 LLM 호출 경로는 LiteLLM으로 둡니다.

다음 중 하나가 생기면 이 결정을 다시 검토합니다.

- 자체 엔진으로 턴 도중 복구를 구현하는 비용이 LangGraph 전환 비용보다 크다고 드러날 때
- 폐쇄망 제약이 풀려 LangSmith·Studio 같은 관측 도구를 쓸 수 있게 될 때
- 다른 토론 전략까지 사용자 정의 그래프로 흡수해, 엔진이 사실상 범용 그래프 실행기가 될 때

## 결과 (Consequences)

**좋아지는 점**

- 폐쇄망 반입 목록이 늘지 않습니다.
- 언제 기록하고, 어디서 사람의 개입을 받고, 실패를 어떻게 남길지를 지금처럼 엔진이 직접 통제합니다. 그래프 토론, 병렬 지시, 긴급 종료 등 기존 테스트를 새 실행 모델에 맞춰 다시 쓸 필요가 없습니다.
- 공급자 차이를 흡수하는 코드가 LiteLLM 바로 앞 한 곳에 계속 모입니다.

**치르는 비용**

- 체크포인트 복원, 단계 단위 되돌리기, 실행 추적 시각화처럼 프레임워크가 기본으로 주는 기능은 필요할 때마다 직접 만들어야 합니다.
- 복구의 단위가 다릅니다. LangGraph에서 발언 하나를 모델 노드와 도구 노드로 쪼개면, 끝난 도구 호출 바로 다음부터 이어 갈 수 있습니다. 자체 엔진에서는 끊긴 발언을 처음부터 다시 하되, 이미 실행된 도구 기록을 관찰 결과로 건네는 방식이 현실적입니다.
- 새로 합류하는 개발자는 업계 표준 어휘 대신 MADO 고유의 개념(전략 객체, `TurnControl`, 그래프 스케줄러)을 익혀야 합니다. 위의 대응표가 그 부담을 덜어 줍니다.
- LangChain 생태계의 통합 부품을 쓰려면 매번 따로 반입 심사를 거쳐야 합니다.

**교훈**

그래프 토론을 설계하면서 LangGraph를 쓰지 않고도 같은 슈퍼스텝 모델에 도달했습니다. 문제의 모양이 같으면 해법의 모양도 닮아 갑니다. 그러니 프레임워크를 도입할지는 "개념이 맞는가"로 판단할 수 없습니다. **의미가 다른 곳을 맞추는 비용**과 **프레임워크만 줄 수 있는 기능의 가치**를 견줘야 합니다. 이번에는 그 기능(턴 도중 복구)을 자체 엔진으로도 만들 수 있다는 것을 먼저 확인했기 때문에 전환하지 않기로 결정할 수 있었습니다.
