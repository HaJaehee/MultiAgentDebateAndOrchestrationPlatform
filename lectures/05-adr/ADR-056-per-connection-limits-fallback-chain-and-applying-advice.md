# ADR-056. 다중 모델 배치를 위해 연결별 동시 요청을 제한하고, 폴백 연결 순서를 지정하며, 점검 권고는 사용자가 직접 눌러 적용한다

> [ADR 목록](README.md) · 이전: [ADR-055](ADR-055-bench-checks-and-judged-rubric.md)

## 상태 (Status)

채택됨 · 2026-11-12 · 관련: [ADR-030](ADR-030-fallback-to-the-global-model.md), [ADR-054](ADR-054-model-conformance-check.md), [ADR-055](ADR-055-bench-checks-and-judged-rubric.md)

## 맥락 (Context)

폐쇄망의 운영 환경에는 모델이 여러 개 배치되며, 모델마다 서버와 처리 용량이 다릅니다. 기존 설정에는 "전역 모델 하나 + 예외 몇 개"를 전제로 한 부분이 세 가지 있었습니다.

- **동시 요청 상한이 서버 전체에 하나뿐입니다** (`app.llm_concurrency`). GPU 한 장에 올린 모델은 한 번에 하나씩만 처리해야 하는데, 이 값을 1로 두면 옆의 큰 서버로 가는 요청까지 한 대기열에 묶입니다. 0으로 두면 병렬 발언 세 건이 작은 서버에 한꺼번에 몰립니다.
- **폴백 대상이 전역 연결 하나뿐입니다** (ADR-030). 모델이 세 개인 배치에서 하나가 내려가면 남은 두 모델 중 어느 쪽으로 넘길지 지정할 수 없습니다. 전역 연결이 내려간 모델과 같은 서버에 있으면 폴백할 곳이 없는 셈이 됩니다.
- **적합성 점검(ADR-054)의 권고는 안내 문구뿐입니다.** "max_context_window를 32,768 이하로"를 읽고 `conf.json`을 직접 열어 해당 연결을 쓰는 에이전트를 찾아 수정해야 합니다. 모델을 바꿀 때마다 반복해야 합니다.

## 결정 (Decision)

### 1. 연결마다 대기열을 따로 둡니다 (`max_concurrency`)

- `agents.<키>.max_concurrency`(기본값 0 = 제한 없음). 전역 `llm.max_concurrency`를 지정하면 별도 설정이 없는 에이전트가 이를 상속받습니다.
- 대기열은 **연결**(모델·주소·API 키·버전·Provider·추가 헤더 및 본문이 동일한 조합, `connection_id`)마다 하나입니다. 두 에이전트가 같은 모델을 쓰면 동일한 대기열에 섭니다.
- 상한은 연결 자체에 고정해 적지 않고 **요청이 함께 들고 갑니다.** 요청마다 "현재 이 연결에서 실행 중인 요청이 내 에이전트의 상한보다 적은가"를 확인하고, 아니면 도착 순서대로 대기합니다. 같은 연결을 공유하는 에이전트들이 서로 다른 상한을 가지더라도 요청마다 기준이 뒤바뀌지 않으며, 설정 파일에 "연결"이라는 새 섹션을 도입할 필요가 없습니다.
- 맨 앞 요청이 들어갈 수 없으면 상한이 더 넉넉한 뒤 요청도 함께 대기합니다 (추월 없음).
- 단일 호출은 **연결 대기열에 먼저** 서고, 슬롯을 확보한 뒤 서버 전체 대기열(`app.llm_concurrency`)에 섭니다. 순서를 반대로 하면 연결을 기다리는 동안 전체 슬롯 하나를 점유한 채 낭비하게 됩니다.
- 연결 정보를 읽을 수 없는 호출(테스트 대역, 외부 구동기가 넘긴 형태가 다른 에이전트)은 상한 없이 통과합니다. 대기열 처리가 호출 자체를 막아서는 안 됩니다.
- 체험 화면의 대기 순번은 서버 전체 대기열에 없으면 연결별 대기열에서 조회합니다.

### 2. 폴백 연결을 순서대로 지정합니다 (`llm.fallback.order`)

- `order`는 이름 목록입니다. 에이전트 키는 해당 에이전트의 연결을, `"llm"`은 전역 기본 연결을 가리킵니다. 비워 두면 `["llm"]`과 같아 ADR-030의 동작을 그대로 유지합니다.
- 후보는 폴백하는 에이전트의 페르소나·도구·스킬을 유지한 채 연결과 그 연결의 용량 설정(`max_tokens`, `max_context_window`, `timeout` …)만 바꾼 사본입니다.
- **다음 후보로 넘어가는 조건은 첫 폴백과 같습니다.** 연결 계층 문제이고(인증·모델명·연결 실패·응답 없음·서버 오류), 해당 후보가 아직 아무 출력도 내보내기 전일 때입니다. 텍스트가 스트리밍되었거나 도구를 호출한 뒤의 실패, 요청 거절(400)은 다음 후보로 넘기지 않습니다.
- 후보를 전환할 때마다 알림을 보냅니다. 발언 기록에는 마지막으로 응답한 모델이 기록됩니다.
- 실패한 후보는 차단기에 등록되어 `retry_after` 동안 건너뜁니다. **마지막 후보는 차단기에 걸지도 건너뛰지도 않습니다** — 더 이상 넘길 곳이 없으므로 매번 호출을 시도합니다. 순서를 지정하지 않은 배치(전역 하나)는 따라서 기존과 동일하게 동작합니다.
- **목록에 적지 않은 연결로는 폴백하지 않습니다.** 어떤 대화 내용이 어느 서버로 전송될 수 있는지는 사용자가 지정한 목록만으로 제한됩니다. `allow_fallback: false`는 기존과 같이 해당 에이전트의 폴백 전체를 차단합니다.
- 후보에서 제외하는 대상: 자기 자신의 연결, 앞서 이미 나온 연결, 연결 정보가 없는 항목, 비활성화한 에이전트, 결정 LLM을 쓰는 전문가(생성형 발언을 대신할 연결이 아닙니다).
- 설정에 없는 이름은 설정을 읽는 시점에 오류로 막지 않고 건너뛰며 한 번 경고합니다. 화면에서 에이전트를 삭제한 것만으로 앱이 기동되지 않는 상황을 방지하기 위함입니다.

### 3. 점검 권고는 사용자가 직접 눌러 적용합니다

- 설정 키가 연결된 권고 옆에 `적용` 버튼을 둡니다 (`model_check.apply_suggestion`).

| 권고 | 적용 시 동작 |
| :--- | :--- |
| `max_context_window` | 해당 연결을 쓰는 에이전트 중 설정값이 더 큰 항목만 낮춥니다 |
| `max_tokens` | 해당 연결을 쓰는 에이전트 중 설정값이 더 작은 항목만 높입니다 |
| `allowed_modalities.image` | 해당 연결을 쓰는 에이전트의 입력 모달리티에서 이미지를 제외합니다 |
| `tool_loading.enabled` | 전역 설정을 변경합니다 (다른 모델의 에이전트에도 적용됨을 알림에 명시합니다) |

- 서버 측에서 수정해야 하는 항목(vLLM 파서 옵션)에는 적용 버튼을 두지 않습니다.
- **서버 PC에서 연 화면에서만** 버튼이 표시됩니다 (전역 도구 규칙 편집과 같은 기준). 버튼을 누르는 시점에도 권한을 다시 확인합니다.
- 에이전트의 설정값은 전역에서 상속받던 것이더라도 **해당 에이전트 항목에만** 기록합니다. 같은 전역 값을 쓰는 다른 연결의 에이전트는 건드리지 않습니다. `${VAR}` 참조와 `//` 주석은 그대로 유지합니다.
- 무엇을 변경했는지 한 줄씩 알리고, 바꿀 항목이 없으면 그 사실을 안내합니다. 점검 결과는 그대로 유지하므로 `다시 점검`으로 확인합니다.
- 점검이 설정을 자동으로 바꾸지 않는다는 ADR-054의 원칙은 유지됩니다. 프로파일에 따라 런타임 동작이 달라지는 분기도 여전히 두지 않습니다. 바뀌는 것은 `conf.json`이고, 바꾸는 주체는 사용자입니다.
- 에이전트 설정값은 새 대화부터 적용됩니다 (잠긴 대화는 시작 시점의 설정으로 계속 진행됩니다).

### 4. 역할에 모델을 배치하는 순서

코드가 아니라 절차입니다. 사용 설명서에 안내합니다: 연결별 적합성 점검 → 실패·주의 항목을 적용하거나 서버에서 수정 → Bench의 `matrix`로 역할별 모델 조합을 실행해 검사와 채점으로 선별 → 선정한 조합에 `max_concurrency`와 `fallback.order` 설정. 어느 모델이 어느 역할에 적합한지는 배포 환경마다 다르므로 문서에 고정된 정답을 적지 않고 선별 방법을 설명합니다.

### 하지 않는 것

- 이름이 붙은 "연결"을 설정의 새로운 섹션으로 분리하는 일. 에이전트 키가 이미 연결 식별자 역할을 합니다.
- 부하를 보고 연결을 선택하는 라우팅, 가장 빠른 모델로 요청을 보내는 방식. 누가 답했는지가 발언마다 달라지면 토론 맥락을 일관되게 읽을 수 없습니다.
- 권고의 자동 적용, 점검 후 자동 재점검.
- 결정 LLM 호출과 적합성 점검 요청에 연결별 대기열을 적용하는 일 (각각 단일 요청이며 서버 전체 상한은 그대로 준수합니다).

## 결과 (Consequences)

**좋아지는 점**

- 작은 서버의 모델과 큰 서버의 모델을 한 토론에 함께 배치해도 작은 쪽에 요청이 넘치지 않고 큰 쪽이 불필요하게 대기하지 않습니다.
- 모델 하나가 내려가더라도 토론이 어떤 모델로 이어질지를 운영자가 미리 지정할 수 있습니다.
- 새 모델을 도입했을 때 점검 → 적용 → 다시 점검이 한 창에서 마무리됩니다.

**치르는 비용**

- 같은 연결을 쓰는 에이전트들이 서로 다른 `max_concurrency`를 가지면, 상한이 더 엄격한 쪽의 요청이 대기열 맨 앞에 있는 동안 넉넉한 쪽도 함께 기다리게 됩니다.
- 연결 대기열에서 기다린 시간은 발언의 `도구·대기` 시간에 합산되어 표시됩니다 (LLM 소요 시간에는 포함되지 않습니다).
- 폴백 체인이 길면 모든 모델이 내려간 장애 상황에서 발언 하나가 후보 수만큼 타임아웃을 겪습니다. 다음 발언부터는 차단기가 해당 후보들을 건너뜁니다.
- 대체 연결의 컨텍스트 창이 원래 연결보다 작으면 해당 발언은 더 많이 축약된 맥락으로 응답합니다 (ADR-030과 동일합니다).
- `tool_loading.enabled` 적용은 전역 설정이므로, 문제의 모델 하나 때문에 다른 모델의 요청에도 도구 정의를 모두 포함하게 됩니다.
- 검증 범위는 단위 테스트와 모의 서버를 연결한 UI 테스트까지입니다. 연결이 둘 이상인 실제 폐쇄망 배치에서는 실행해 보지 못했습니다 (개발 PC에는 생성형 연결이 하나뿐입니다).
