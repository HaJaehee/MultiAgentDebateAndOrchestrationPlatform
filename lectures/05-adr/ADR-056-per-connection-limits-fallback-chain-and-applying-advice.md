# ADR-056. 모델이 여럿인 배치를 위해 연결마다 동시 요청을 묶고, 물러설 연결을 순서로 적고, 점검의 권고는 사람이 눌러 적용한다

> [ADR 목록](README.md) · 이전: [ADR-055](ADR-055-bench-checks-and-judged-rubric.md)

## 상태 (Status)

채택됨 · 2026-11-12 · 관련: [ADR-030](ADR-030-fallback-to-the-global-model.md), [ADR-054](ADR-054-model-conformance-check.md), [ADR-055](ADR-055-bench-checks-and-judged-rubric.md)

## 맥락 (Context)

폐쇄망의 운영 환경은 모델이 여럿이고, 모델마다 서버와 용량이 다릅니다. 지금까지의 설정은 "전역 모델 하나 + 예외 몇 개" 를 가정한 곳이 셋 있었습니다.

- **동시 요청 상한이 서버 전체에 하나뿐입니다** (`app.llm_concurrency`). GPU 한 장에 뜬 모델은 한 번에 하나만 받아야 하는데, 그 값을 1 로 두면 옆의 큰 서버로 가는 요청까지 한 줄에 섭니다. 0 으로 두면 병렬 발언 셋이 작은 서버에 한꺼번에 몰립니다.
- **물러설 곳이 전역 연결 하나뿐입니다** (ADR-030). 모델이 셋인 배치에서 하나가 내려가면 남은 둘 가운데 무엇으로 받을지를 적을 수 없습니다. 전역 연결이 내려간 모델과 같은 서버에 있으면 물러설 곳이 없는 것과 같습니다.
- **적합성 점검(ADR-054)의 권고는 글입니다.** "max_context_window 를 32,768 이하로" 를 읽고 conf.json 을 열어 그 연결을 쓰는 에이전트를 찾아 고쳐야 합니다. 모델을 바꿀 때마다 되풀이됩니다.

## 결정 (Decision)

### 1. 연결마다 줄을 따로 세웁니다 (`max_concurrency`)

- `agents.<키>.max_concurrency` (기본 0 = 제한 없음). 전역 `llm.max_concurrency` 를 적으면 따로 적지 않은 에이전트가 물려받습니다.
- 줄은 **연결**(모델·주소·키·버전·Provider·추가 머리말과 본문이 같은 것, `connection_id`)마다 하나입니다. 에이전트 둘이 같은 모델을 쓰면 한 줄에 섭니다.
- 상한은 연결에 따로 적지 않고 **요청이 들고 옵니다.** 요청마다 "지금 이 연결에서 도는 요청이 내 에이전트의 상한보다 적은가" 를 보고, 아니면 온 순서대로 기다립니다. 같은 연결의 에이전트들이 다른 값을 가져도 상한이 요청마다 뒤집히지 않고, 설정 어디에도 "연결" 이라는 새 개념을 만들 필요가 없습니다.
- 맨 앞 요청이 못 들어가면 상한이 더 넉넉한 뒤 요청도 기다립니다 (새치기 없음).
- 한 판은 **연결의 줄을 먼저** 서고, 자리를 받은 뒤 서버 전체의 줄(`app.llm_concurrency`)을 섭니다. 반대로 하면 연결을 기다리는 동안 전체의 자리 하나를 쥐고 놀립니다.
- 연결을 읽을 수 없는 호출(시험 대역, 바깥 구동기가 넘긴 모양이 다른 에이전트)은 상한 없이 지나갑니다. 줄을 서는 일이 호출을 막지 않습니다.
- 체험 화면의 대기 순번은 서버 전체의 줄에 없으면 연결의 줄에서 찾습니다.

### 2. 물러설 연결을 순서로 적습니다 (`llm.fallback.order`)

- `order` 는 이름의 목록입니다. 에이전트 키는 그 에이전트의 연결이고 `"llm"` 은 전역 기본 연결입니다. 비워 두면 `["llm"]` 과 같아 ADR-030 의 동작 그대로입니다.
- 후보는 물러서는 에이전트의 페르소나·도구·스킬을 그대로 두고 연결과 그 연결의 용량(`max_tokens`, `max_context_window`, `timeout` …)만 바꾼 사본입니다.
- **다음 후보로 넘어가는 조건은 처음 물러설 때와 같습니다.** 연결의 문제이고(인증·모델 이름·연결 실패·응답 없음·서버 오류), 그 후보가 아무것도 내놓기 전일 때. 글이 흘렀거나 도구를 부른 뒤의 실패, 요청 거절(400)은 넘기지 않습니다.
- 후보마다 전환을 알립니다. 발언 기록에는 마지막으로 답한 모델이 남습니다.
- 실패한 후보는 차단기에 걸려 `retry_after` 동안 건너뜁니다. **마지막 후보는 걸지도 건너뛰지도 않습니다** — 더 물러설 곳이 없으니 매번 불러 봅니다. 순서를 적지 않은 배치(전역 하나)는 그래서 예전과 똑같이 동작합니다.
- **목록에 적지 않은 연결로는 물러서지 않습니다.** 어느 대화 내용이 어느 서버로 갈 수 있는지는 사람이 적은 목록이 전부입니다. `allow_fallback: false` 는 그대로 그 에이전트의 폴백 전체를 막습니다.
- 후보에서 빼는 것: 자기 자신의 연결, 앞에서 이미 나온 연결, 연결 정보가 없는 것, 꺼 둔 에이전트, 결정 LLM 을 쓰는 전문가(생성형 발언을 대신할 연결이 아닙니다).
- 설정에 없는 이름은 설정을 읽을 때 막지 않고 건너뛰며 한 번 경고합니다. 화면에서 에이전트를 지운 것만으로 앱이 뜨지 않게 되어서는 안 됩니다.

### 3. 점검의 권고는 사람이 눌러 적용합니다

- 설정 이름이 붙은 권고 옆에 `적용` 단추를 둡니다 (`model_check.apply_suggestion`).

| 권고 | 적용하면 |
| :--- | :--- |
| `max_context_window` | 그 연결을 쓰는 에이전트 가운데 값이 더 큰 것만 낮춥니다 |
| `max_tokens` | 그 연결을 쓰는 에이전트 가운데 값이 더 작은 것만 올립니다 |
| `allowed_modalities.image` | 그 연결을 쓰는 에이전트의 모달에서 이미지를 뺍니다 |
| `tool_loading.enabled` | 전역 설정을 바꿉니다 (다른 모델의 에이전트에도 적용 — 알림에 그렇게 적습니다) |

- 서버 쪽에서 고칠 것(vLLM 의 파서 옵션)에는 단추가 없습니다.
- **서버 PC 에서 연 화면에만** 단추가 있습니다 (전역 도구 규칙 편집과 같은 기준). 누르는 순간에 다시 확인합니다.
- 에이전트의 값은 전역에서 물려받던 것이어도 **그 에이전트에만** 적습니다. 같은 전역 값을 쓰는 다른 연결의 에이전트는 건드리지 않습니다. `${VAR}` 참조와 `//` 주석은 그대로 둡니다.
- 무엇을 바꿨는지 한 줄씩 알리고, 바꿀 것이 없으면 그렇게 말합니다. 점검 결과는 그대로 두므로 `다시 점검` 으로 확인합니다.
- 점검이 스스로 적용하지 않는다는 ADR-054 의 원칙은 그대로입니다. 프로파일에 따라 런타임이 달라지는 분기도 여전히 없습니다. 바뀌는 것은 conf.json 이고, 바꾸는 것은 사람입니다.
- 에이전트의 값은 새 대화부터 적용됩니다 (잠긴 대화는 시작할 때의 설정으로 계속 돕니다).

### 4. 역할에 모델을 배치하는 순서

코드가 아니라 절차입니다. 사용 설명서에 적습니다: 연결마다 적합성 점검 → 실패·주의를 적용하거나 서버에서 고침 → Bench 의 `matrix` 로 역할별 모델 조합을 돌려 검사와 채점으로 고름 → 고른 조합에 `max_concurrency` 와 `fallback.order` 를 적음. 어느 모델이 어느 역할에 맞는지는 망마다 다르므로 문서에 답을 적지 않고 고르는 방법을 적습니다.

### 하지 않는 것

- 이름 붙은 "연결" 을 설정의 새 구획으로 만드는 일. 에이전트 키가 이미 연결의 이름 노릇을 합니다.
- 부하를 보고 연결을 고르는 라우팅, 가장 빠른 모델로 보내기. 누가 답했는지가 발언마다 달라지면 토론을 읽을 수 없습니다.
- 권고의 자동 적용, 점검 뒤 자동 재점검.
- 결정 LLM 호출과 적합성 점검 요청에 연결별 줄을 거는 일 (요청 한 건씩이고 서버 전체의 줄은 그대로 지킵니다).

## 결과 (Consequences)

**좋아지는 점**

- 작은 서버의 모델과 큰 서버의 모델을 한 토론에 함께 두어도 작은 쪽이 넘치지 않고 큰 쪽이 기다리지 않습니다.
- 모델 하나가 내려가도 토론이 어느 모델로 이어질지를 운영자가 미리 정해 둡니다.
- 새 모델을 들였을 때 점검 → 적용 → 다시 점검이 한 창에서 끝납니다.

**치르는 비용**

- 같은 연결의 에이전트들이 서로 다른 `max_concurrency` 를 가지면, 엄격한 쪽의 요청이 줄 맨 앞에 있는 동안 넉넉한 쪽도 기다립니다.
- 연결의 줄에서 기다리는 시간은 발언의 `도구·대기` 시간에 섞여 보입니다 (LLM 시간에는 들어가지 않습니다).
- 사슬이 길면 모두 내려간 날의 발언 하나가 후보 수만큼 타임아웃을 치릅니다. 다음 발언부터는 차단기가 건너뜁니다.
- 물러선 연결의 창이 원래보다 작으면 그 발언은 더 많이 잘린 맥락으로 답합니다 (ADR-030 과 같습니다).
- `tool_loading.enabled` 의 적용은 전역이라, 그 모델 하나 때문에 다른 모델의 요청도 도구 정의를 전부 싣게 됩니다.
- 확인은 단위 테스트와 가짜 서버를 붙인 화면까지입니다. 연결이 둘 이상인 실제 폐쇄망 배치에서는 돌려 보지 못했습니다 (개발 PC 에는 생성형 연결이 하나뿐입니다).
