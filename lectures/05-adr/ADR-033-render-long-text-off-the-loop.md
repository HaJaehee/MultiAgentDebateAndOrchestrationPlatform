# ADR-033. 대용량 텍스트 렌더링을 백그라운드 단일 워커 스레드로 오프로드하고, 정규식 알고리즘 및 초기 임포트 병목을 개선한다

> [ADR 목록](README.md) · 이전: [ADR-032](ADR-032-compose-roster-and-feed.md)

## 상태 (Status)

채택됨 · 2026-10-30 · 관련: [ADR-001](ADR-001-python-single-process.md), [ADR-031](ADR-031-assemble-streams-off-the-loop.md)

## 맥락 (Context)

[ADR-031](ADR-031-assemble-streams-off-the-loop.md) 채택 이후 추가 제안이 제기되었습니다. 2만 자가 넘는 종합 보고서의 Mermaid 문법 검증(`mermaid_lint.py`), StarUML/HTML 변환(`export_mermaid.py`), LaTeX→MathML 변환(`math_markdown.py`) 작업 또한 동시 접속 증가 시 이벤트 루프를 차단할 수 있으므로, 이를 워커 스레드로 전면 오프로드하자는 의견이었습니다. 이에 작업별 실제 소요 시간을 정밀 계측했습니다.

| 작업 내용 | 실측치 | 판단 |
| :--- | :--- | :--- |
| Mermaid 탐색 및 문법 검증 | 25,000자 보고서(다이어그램 2개) 기준 1.4ms, 노드 2,000개 다이어그램 기준 23ms 소요. 문서 전체 길이가 아닌 다이어그램 크기에 비례 | 오프로드 불필요 |
| HTML 내보내기 | 48만 자 다이어그램에 1MB SVG가 포함되어도 3ms 소요 | 오프로드 불필요 |
| StarUML 변환 | 노드 100개 7ms, 2,000개 0.2초, 10,000개 2.8초 소요 (노드 수 증가율 초과) | 워커 스레드로 오프로드 |
| LaTeX→MathML 변환 | 20만 자 내 수식 3,000개 기준, 탐색과 변환 합산 79ms 소요 | 단독 분리 불필요 |
| 마크다운 전체 렌더링 | 5만 자 기준 70~135ms, 20만 자 기준 1.7~2.0초 소요. **스트리밍 중에는 카드당 초당 약 4회 렌더링** | 워커 스레드로 오프로드 |

`stalls.log`에 기록된 이벤트 루프 멈춤 현상 44건을 분석한 결과, 제안에서 지목한 연산으로 인한 병목은 발견되지 않았습니다.

- 35건: MADOWarGame 실행기가 의사결정마다 `httpx.AsyncClient`를 재생성하며 SSL 컨텍스트를 생성하는 병목 (MADO 메인 경로가 아님).
- **6건: `render_markdown` 내부의 IPython/jedi 모듈 임포트 지연.** 코드 블록 언어(` ```mermaid ` 등)가 Pygments 내장 lexer에 없으면 플러그인 전체를 탐색/임포트합니다. 프로세스 기동 후 최초 1회, 약 1.0~1.2초의 이벤트 루프 지연이 발생하며, 이는 문서 길이와 무관합니다.
- 2건: 세션 진입 시 대량의 UI 요소를 한꺼번에 인스턴스화하는 비용. 1건: 작업 공간 경로 확인 I/O.

정밀 계측 과정에서 기존에 파악되지 않았던 근본적인 3가지 문제점이 추가로 확인되었습니다.

- **$O(N^2)$ 알고리즘 병목 2곳**: 수식 자리표시자를 개별적으로 순회하며 `str.replace`를 수행하여 20만 자 보고서에서 1.6초가 소요되었습니다. 또한 인라인 코드 조각을 전체 문자열과 상호 대조하여 백틱 2만 개 기준 2.5초가 걸렸습니다. 이는 스레드로 넘길 문제가 아니라 알고리즘을 개선해야 할 코드 결함이었습니다.
- **정규식 매칭의 GIL 독점 문제**: 파이썬 `re` 모듈은 정규식 매칭 중 GIL(Global Interpreter Lock)을 해제하지 않습니다. 닫히지 않은 `\(` 2만 개에 대해 `_MATH` 정규식을 수행할 때 약 8초가 소요되었으며, 이를 백그라운드 스레드에서 실행하더라도 메인 이벤트 루프가 8초간 정지되었습니다. 반면 1.5초가 소요되는 순수 파이썬 루프 연산은 이벤트 루프를 최대 38ms 정도만 지연시켰습니다.
- **markdown2의 재귀 한도 초과**: `>` 인용 블록이 2,000개 중첩된 문서에서 `RecursionError`가 발생하여 카드 렌더링 호출 스택 전체로 예외가 전파되었습니다.

## 결정 (Decision)

**근본적인 알고리즘 결함은 코드 레벨에서 즉시 개선하고, 실측 결과 부하가 높은 대용량 텍스트 렌더링에 한해 전용 단일 워커 스레드로 오프로드하며, UI 요소마다 최신 요청만 렌더링하도록 제어합니다.**

- **렉서 플러그인 웜업**: 서버 시작 시 FastAPI `lifespan` 단계에서 `asyncio.to_thread(warm_up_lexer_plugins)`를 1회 사전 실행합니다. 이를 통해 최초 마크다운 렌더링 시 발생하는 이벤트 루프 정지 지연을 400ms에서 11ms 수준으로 대폭 단축했습니다.
- **수식 자리표시자 일괄 복원 및 인라인 코드 범위 제한**: 20만 자 보고서의 처리 시간을 1.7~2.0초에서 0.33초로 대폭 단축했습니다.
- **정규식 탐색 길이 상한 설정**: `\(` 수식은 최대 1,000자, `\[` 수식은 최대 4,000자로 탐색 길이를 제한합니다. 닫는 괄호가 누락된 비정상 문자열이 대량으로 유입되더라도 지정된 범위까지만 스캔하여 정규식 백트래킹으로 인한 GIL 독점을 방지합니다.
- **`MathMarkdown` 내부 오프로드 처리**: 호출부 인터페이스를 수정할 필요 없이 전문가/초급자/체험 화면 전체에 일관되게 적용됩니다. `OFFLOAD_CHARS`(2만 자) 미만의 일반 텍스트는 기존과 동일하게 인라인으로 즉시 렌더링합니다.
- **단일 전용 워커 스레드 채택**: 순수 파이썬 CPU 연산 특성상 스레드 수를 늘려도 처리 성능이 향상되지 않고 GIL 경합으로 인해 이벤트 루프 복귀만 지연됩니다. 따라서 단일 워커 스레드로 순차 처리합니다.
- **최신 렌더링 요청 유지(Debounce/Drop stale)**: 각 UI 요소는 한 번에 하나의 렌더링 작업만 수행하며, 워커가 작업 중일 때 추가 요청이 오면 큐에 누적하지 않고 가장 최신의 요청 내용만 반영합니다.
- **렌더링 완료 후 스크롤 위치 보정 (`on_rendered`)**: 대용량 카드는 마크다운 렌더링이 완료된 시점에 요소 높이가 확정되므로, 렌더링 완료 이벤트 수신 시점에 피드 스크롤을 하단으로 재조정합니다.
- **렌더링 실패 시 원문 텍스트 폴백**: 워커 스레드 렌더링 중 예외가 발생하더라도 화면이 빈칸으로 남지 않도록 원본 텍스트를 그대로 표시합니다.
- **StarUML 변환 작업 분리**: 사용자 버튼 클릭 시 단발성으로 호출되므로 전용 워커 대신 범용 `run.io_bound` 스레드 풀에서 실행합니다.

**다음 사항은 구현하지 않습니다.**

- Mermaid 유효성 검사, 코드 블록 탐색, HTML 내보내기는 오프로드하지 않습니다. 1~3ms 내외의 초단기 작업은 스레드 전환 오버헤드가 더 큽니다.
- 멀티프로세스 풀은 도입하지 않습니다. IPC 직렬화 비용과 Windows 프로세스 생성 오버헤드가 크고, 단일 프로세스 원칙([ADR-001](ADR-001-python-single-process.md))을 위배하기 때문입니다.
- 2만 자 미만의 일반 텍스트까지 스레드로 넘기지 않습니다. 불필요한 스레드 스위칭과 초기 깜빡임을 방지합니다.
- `ui.code` 컴포넌트는 수정하지 않습니다. NiceGUI 내부 구현에 종속적이며 발생 빈도가 매우 낮기 때문입니다.

## 결과 (Consequences)

여러 스트리밍 세션이 약 5만 자의 문서를 0.25초 간격으로 동시 재렌더링할 때의 이벤트 루프 지연 측정 결과입니다 (8초간 수식 포함 보고서 스트리밍 기준).

| 동시 스트림 수 | 인라인 렌더링 (p50 / 최대) | 광역 스레드 풀 20개 (p50 / 최대) | **단일 워커 스레드 (p50 / 최대)** |
| :--- | :--- | :--- | :--- |
| 1개 | 9ms / 71ms | 14ms / 85ms | **8ms / 28ms** |
| 3개 | 45ms / 190ms | 38ms / 210ms | **15ms / 42ms** |
| 5개 | 120ms / 480ms | 95ms / 390ms | **22ms / 65ms** |

**이점**

- 대용량 마크다운 렌더링 중에도 메인 이벤트 루프의 블로킹 지연이 1/5 이하로 대폭 감소하여 웹소켓 핑/퐁 및 사용자 UI 상호작용이 부드럽게 유지됩니다.
- 초기 실행 시 발생하는 1초 이상의 jedi/IPython 임포트 랙이 완전히 해소되었습니다.
- 정규식 상한 및 $O(N)$ 최적화를 통해 비정상적인 입력값에 대한 DoS 위험을 선제적으로 차단했습니다.
