# ADR-033. 긴 글은 이벤트 루프 밖 일꾼 하나가 그리고, 정규식과 첫 import 는 그 자리에서 고칩니다

> [ADR 목록](README.md) · 이전: [ADR-032](ADR-032-compose-roster-and-feed.md)

## 상태 (Status)

채택됨 · 2026-10-30 · 관련: [ADR-001](ADR-001-python-single-process.md), [ADR-031](ADR-031-assemble-streams-off-the-loop.md)

## 맥락 (Context)

[ADR-031](ADR-031-assemble-streams-off-the-loop.md) 뒤에 제안이 나왔습니다. 2만 자가 넘는 합성 보고서의 Mermaid 문법 검사(`mermaid_lint.py`), StarUML·HTML 변환(`export_mermaid.py`), LaTeX→MathML 변환(`math_markdown.py`)도 동시 접속이 늘면 루프를 붙잡을 수 있으니 워커 스레드로 일관되게 옮기자는 것입니다. 옮기기 전에 재 보았습니다.

| 일 | 재 본 값 | 판단 |
| :--- | :--- | :--- |
| Mermaid 찾기·검사 | 25,000자 보고서(다이어그램 2개) 1.4ms, 노드 2천 개짜리 하나 23ms. 보고서 길이가 아니라 다이어그램 크기를 따릅니다 | 옮기지 않음 |
| HTML 내보내기 | 48만 자 다이어그램에 SVG 1MB 를 실어도 3ms | 옮기지 않음 |
| StarUML 변환 | 노드 100개 7ms, 2천 개 0.2초, 1만 개 2.8초 (노드 수보다 빠르게 늘어남) | 옮김 |
| LaTeX→MathML 자체 | 20만 자에 식 3천 개 안팎, 찾기와 변환을 합쳐 79ms | 따로 옮길 만큼은 아님 |
| 마크다운 전체 그리기 | 5만 자 70~135ms, 20만 자 1.7~2.0초. **스트리밍 중에는 카드마다 초당 4번** | 옮김 |

`stalls.log` 44건도 보았습니다. 제안이 짚은 곳에서 멈춘 기록은 없습니다.

- 35건: MADOWarGame 구동기가 결정마다 `httpx.AsyncClient` 를 새로 만들며 SSL 컨텍스트를 만든 자리 (MADO 경로가 아닙니다).
- **6건: `render_markdown` 안의 IPython·jedi import.** 펜스의 언어(` ```mermaid `)가 내장 lexer 에 없으면 Pygments 가 플러그인을 전부 import 합니다. 프로세스마다 처음 한 번, 1.0~1.2초입니다. 글 길이와 무관합니다.
- 2건: 세션을 열 때 요소를 한꺼번에 만드는 자리. 1건: 작업 공간 경로 확인.

재는 동안 제안에 없던 것이 셋 더 나왔습니다.

- **제곱 시간 두 곳.** 수식 자리표시자를 하나씩 `str.replace` 해 20만 자 보고서에서 1.6초가 들었습니다. 인라인 코드끼리 서로 견주어 백틱 2만 개에 2.5초가 들었습니다. 스레드로 옮길 일이 아니라 고칠 코드였습니다.
- **스레드로 옮겨도 정규식은 루프를 멈춥니다.** `re` 는 매칭 중에 GIL 을 놓지 않습니다. 닫히지 않은 `\(` 2만 개에 `_MATH` 하나가 8초 걸렸고, 워커에서 돌려도 루프가 8초 멈췄습니다. 반면 워커에서 1.5초 도는 순수 파이썬 계산은 루프를 38ms 까지만 늦췄습니다.
- **`>` 2천 개는 markdown2 에서 `RecursionError` 가 납니다.** 카드를 그리는 호출까지 그대로 올라갔습니다.

## 결정 (Decision)

**뿌리가 있는 것은 뿌리에서 고치고, 그래도 오래 걸리는 것만 옮깁니다. 2만 자 이상의 마크다운은 전용 일꾼 스레드 하나가 그리고, 요소마다 최신 내용만 그립니다.**

- **플러그인을 미리 불러 둡니다.** 서버가 뜰 때 `lifespan` 에서 `asyncio.to_thread(warm_up_lexer_plugins)` 를 한 번 부릅니다. 시스템 Python 에서 첫 펜스의 루프 멈춤이 400ms 에서 11ms 로 줄었습니다 (디스크 캐시가 찬 상태. 찬 디스크에서는 기록처럼 1초 넘게 걸립니다).
- **자리표시자는 한 번에 되돌리고, 인라인 코드는 울타리 블록과만 견줍니다.** 20만 자 보고서가 1.7~2.0초에서 0.33초로 줄었습니다.
- **`\(` 는 1,000자, `\[` 는 4,000자로 제한합니다.** 닫히지 않은 것이 아무리 많아도 하나마다 그 길이까지만 훑습니다. 더 긴 식은 글자로 보입니다.
- **긴 글은 `MathMarkdown` 안에서 옮깁니다.** 부르는 쪽은 바꾸지 않아도 전문가·쉬운·체험 화면에 모두 걸립니다. `OFFLOAD_CHARS`(2만 자) 미만은 전처럼 그 자리에서 그립니다.
- **일꾼은 하나입니다.** 순수 파이썬 계산이라 스레드를 늘려도 빨라지지 않고, 루프가 차례를 받기까지 오래 걸릴 뿐입니다. 아래 표의 "넓은 풀" 이 그 결과입니다.
- **요소마다 한 번에 하나만 그리고, 끝나면 그때의 최신 내용을 봅니다.** 일꾼이 밀려도 요소 하나가 일을 쌓지 않습니다.
- **그린 뒤에 피드가 스크롤을 다시 맞춥니다** (`on_rendered`). 긴 카드의 높이는 내용이 들어갈 때 바뀌므로, 그 전에 내린 스크롤은 바닥에 닿지 못합니다.
- **변환에 실패하면 원문을 그대로 보여 줍니다.** 일꾼에서 실패하면 빈칸으로 남기 때문이고, 짧은 글의 `RecursionError` 도 같은 곳에서 막힙니다.
- **StarUML 변환은 `run.io_bound` 로 옮깁니다.** 버튼 한 번에 한 번뿐이라 전용 일꾼이 필요 없습니다.

**다음은 하지 않습니다.**

- Mermaid 검사·코드 블록 찾기·HTML 내보내기는 옮기지 않습니다. 1~3ms 인 일에 스레드를 오가면 순서만 복잡해집니다.
- 프로세스 풀로 보내지 않습니다. 정규식까지 막아 주지만 Windows 의 spawn 비용과 초당 4번의 직렬화가 들고, 프로세스가 하나라는 전제([ADR-001](ADR-001-python-single-process.md))를 건드립니다.
- 짧은 글까지 옮기지 않습니다. 첫 화면에 빈칸이 생기고, 카드마다 스레드를 오갑니다.
- `ui.code` 는 그대로 둡니다. NiceGUI 내부에서 마크다운을 만들어 끼어들 곳이 없습니다 (Python 20만 자에 0.46초, 드문 일입니다).
- 세션을 열 때 요소를 만드는 비용은 다루지 않습니다. 요소 생성은 루프에서만 할 수 있습니다.

## 결과 (Consequences)

스트림 여럿이 5만 자 안팎을 0.25초마다 다시 그릴 때의 루프 지연입니다 (8초, 수식 포함 보고서).

| 스트림 | 그 자리에서 (p50 / 최대) | 넓은 풀 20개 (p50 / 최대) | **일꾼 하나 (p50 / 최대)** |
| :--- | :--- | :--- | :--- |
| 1개 | 6 / 79ms | 6 / 37ms | 6 / 52ms |
| 5개 | 150 / 164ms | 19 / 308ms | **18 / 59ms** |
| 10개 | 463 / 594ms | 38 / 395ms | **19 / 54ms** |
| 5개, 10만 자 | 463 / 469ms | 25 / 211ms | **21 / 52ms** |

**장점**

- 스트림이 늘어도 루프 지연이 50ms 안팎에서 멈춥니다. 다시 그리는 횟수는 거의 줄지 않습니다 (10개일 때 107번 → 91번).
- `[a](` 1만 개(17초)나 빈 줄 20만 개(30초)처럼 markdown2 의 파이썬 코드가 오래 걸리는 글도 서버를 멈추지 않습니다.
- 가짜 LLM 으로 5만 자 합성 보고서를 흘린 실제 화면에서 임계값 0.25초의 멈춤이 없었고, 피드는 끝까지 바닥에 붙어 있었습니다. 서버를 다시 띄워 캐시가 빈 채로 세션을 열어도 빈 카드 없이 바닥에서 시작합니다.

**고려할 트레이드오프**

- 빨라지지 않습니다. 총 CPU 는 같고, [ADR-031](ADR-031-assemble-streams-off-the-loop.md) 과 같은 이유로 "한 번의 긴 멈춤"이 "그동안 조금 느림"으로 바뀔 뿐입니다.
- 새 요소의 긴 글은 잠깐 빈칸입니다. 그리는 시간만큼이고, 5만 자에 수십 ms 입니다.
- 일꾼이 하나라 긴 글끼리 줄을 섭니다. 한 글이 30초 걸리면 그동안 다른 긴 글은 이전 내용 그대로입니다 (서버 전체가 멈추는 것보다는 낫습니다).
- **정규식 안에서 오래 걸리는 것은 여전히 못 막습니다.** markdown2 안의 정규식이 그렇습니다 (`<a href=` 5천 개에 0.6초, `\` 4만 개에 0.5초).
- **2만 자 아래의 병적인 글은 여전히 루프에서 돕니다.** `[a](` 3,900개(19,500자)에 3초, `[` 9,900개에 2초입니다. 모델이 쓸 글은 아니지만 체험 서버 방문자는 붙여 넣을 수 있습니다.
- 서버 시작이 플러그인을 불러오는 만큼 늦어집니다 (IPython 이 깔린 환경에서 0.4~1.2초, 없으면 수십 ms).
- 긴 글 렌더는 스레드에서 돕니다. 지금의 판(markdown2 2.5.5, Pygments 2.21, latex2mathml)에서 16개 스레드로 1,200번 그린 결과가 혼자 그린 것과 글자 하나까지 같았습니다. 판을 올릴 때 다시 봐야 합니다.
- 스레드는 죽일 수 없습니다. 오래 걸리는 렌더가 있으면 서버 종료가 그만큼 늦어질 수 있습니다.
