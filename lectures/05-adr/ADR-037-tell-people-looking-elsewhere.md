# ADR-037. 사람을 기다리는 물음은 대화를 가리지 않는 신호로 모든 탭에 알리고, 값은 러너에서 다시 읽는다

> [ADR 목록](README.md) · 이전: [ADR-036](ADR-036-retry-one-speech-and-inline-comments.md)

## 상태 (Status)

채택됨 · 2026-10-31 (v1.5.1) · 관련: [ADR-028](ADR-028-plan-approval-gate.md)

## 맥락 (Context)

- 계획 승인, 도구 승인, 에이전트 질문, 한도 쪽지는 그 대화의 타임라인 위에만 뜨고 3~10분 안에 답해야 합니다. 다른 탭이나 다른 대화를 보고 있으면 카드가 열린 줄 모른 채 시간이 지나 턴이 멈춥니다.
- 화면의 구독(`RunBinding`)은 지금 보는 대화 하나에만 붙습니다. 다른 대화의 이벤트는 그 탭에 오지 않습니다.
- Web Notification 은 보안 컨텍스트(HTTPS 또는 localhost)에서만 쓸 수 있습니다. MADO 의 원격 접속은 평문 HTTP 이므로 원격 화면에서는 이 API 가 막혀 있습니다.
- 체험·쉬운 화면의 방문자도 같은 서버에서 턴을 돌립니다. 답할 사람은 그 방문자인데, 그 물음으로 주인 화면을 울리면 소음이고 방문자의 대화 제목이 운영체제 알림으로 나갑니다.

## 결정 (Decision)

### 1. 대화를 가리지 않는 채널에는 "이 대화가 바뀌었다" 만 싣는다

`TurnRun.publish` 가 물음이 변할 수 있는 이벤트(`WAITING_EVENTS`)에서 `WAITING_CHANNEL` 로 대화 id 만 보냅니다. 탭마다 있는 `WaitingWatcher` 는 그 신호를 받으면 `DebateRunner.waiting_by_session()` 을 다시 읽어 맞춥니다. 사건을 쌓아 해석하지 않으므로 신호가 겹치거나 빠져도 다음 신호에서 정확해지고, 턴의 끝처럼 카드가 한꺼번에 걷히는 경우를 따로 다룰 일이 없습니다.

`publish` 는 모든 길(엔진의 `on_event`, 사람이 만든 `_emit`, 턴의 끝 `announce_end`)이 지나는 한 곳이고, 늘 스냅샷을 고친 다음에 불립니다.

브라우저나 서버의 주기적 확인은 쓰지 않았습니다. 탭마다 도는 타이머가 필요하고, 백그라운드 탭의 타이머는 브라우저가 늦춥니다. 웹소켓 메시지는 늦추지 않습니다.

### 2. 물음의 정본은 `TurnRun` 의 카드 목록이다

`waiting_requests()` 는 카드 목록에서 계산합니다. 끝난 실행은 빈 목록입니다. 취소나 실패로 끝나면 `turn_completed` 가 오지 않아 도구 카드와 질문이 목록에 남기 때문입니다. 제안 범위는 계획·도구·질문이었으나, 한도 쪽지도 3분 안에 답해야 하는 같은 종류의 물음이라 함께 셉니다.

운영체제 알림으로 나가는 값이므로 `WaitingRequest` 에는 도구 인자와 질문 내용을 담지 않습니다. 대화 제목, 에이전트 이름, 도구 이름까지만 나갑니다.

### 3. 알리는 길은 셋이고, 데스크톱 알림만 조건이 있다

| 길 | 언제 | 비고 |
| :--- | :--- | :--- |
| 탭 제목 `(N) 승인 대기 — MADO` | 항상 | 모든 대화의 물음 수. 첫 응답부터 맞는 제목으로 나갑니다 |
| 사이드바 배지 `승인 대기 N` | 항상 | 툴팁에 무엇을 기다리는지 적습니다 |
| 토스트 | 이 탭이 그 카드를 그리지 않을 때 | 그리고 있으면 `ExpertEventView` 가 이미 알립니다 |
| 데스크톱 알림 | 이 탭을 보고 있지 않고 권한이 있을 때 | 판단은 브라우저가 합니다 (`document.hidden`, `hasFocus`) |

- 권한 창은 사용자 활성화 안에서 열어야 하므로 머리 줄 종 버튼의 클릭 핸들러가 서버를 거치지 않고 바로 부릅니다.
- `tag` 를 물음 id 로 두어 여러 탭이 띄워도 알림은 하나이고, 답이 나면 어느 탭에서든 닫힙니다.
- 이미 떠 있던 물음은 새로고침한 탭에서 다시 울리지 않습니다.
- 평문 HTTP 원격 화면에서는 버튼이 그 사정을 말하고, 탭 제목과 배지로 알립니다. 이 제약 때문에 HTTPS 를 도입하지는 않습니다.

### 4. 방문자의 턴은 시작할 때 주인에게 알리지 않겠다고 정한다

`DebateRunner.start` / `resume` 의 `announce_waiting=False`. 체험 화면은 늘, 쉬운 화면은 방문자일 때 그렇게 시작합니다. 코어는 체험을 모르고 이 값만 봅니다. 그 턴은 채널에 신호를 보내지 않고 `waiting_by_session()` 에서도 빠집니다.

### 5. 체험·쉬운 화면은 탭 제목만 둔다

그 화면에는 사이드바와 다른 대화가 없으니 지금 대화의 물음 수만 탭 제목에 씁니다. 전역 채널 없이 이미 붙어 있는 `RunBinding` 의 이벤트로 맞춥니다. 데스크톱 알림은 켜고 끄는 자리를 더해야 하므로 넣지 않았습니다.

## 결과 (Consequences)

좋아지는 점:

- 다른 탭이나 다른 대화를 보고 있어도 물음이 열린 것을 바로 알고, 알림을 누르면 그 대화가 열립니다.
- 모든 토론 경로의 물음이 한 목록으로 모입니다. 새 종류의 물음은 `waiting_requests()` 와 `WAITING_EVENTS` 에 더하면 세 길에 함께 나타납니다.

치르는 비용:

- 카드가 늘거나 줄 때마다 열린 탭 수만큼 사이드바를 다시 그립니다. 물음은 드물고 쌓인 신호는 한 번에 처리하므로 감당할 수 있는 양입니다.
- 평문 HTTP 원격 화면과 모바일 크롬(서비스 워커 필요)에는 데스크톱 알림이 없습니다.
- 이 탭이 포커스를 가졌는데 숨은 다른 탭이 있으면, 숨은 탭이 데스크톱 알림을 띄웁니다. 탭끼리 조율하지 않은 대가입니다.
- 브라우저가 오래 숨은 탭을 동결하거나 내리면 그 탭의 알림은 울리지 않습니다.
