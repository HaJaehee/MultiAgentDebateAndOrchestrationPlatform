# ADR-009. 작업 공간이 다른 토론은 동시에 돌리지 않는다

> [ADR 목록](README.md) · 이전: [ADR-008](ADR-008-background-debate-runner.md) · 다음: [ADR-010](ADR-010-host-defined-tool-scope.md)

## 상태 (Status)

**대체됨** · 2026-08-28 채택 · 2026-09-09 [ADR-016](ADR-016-per-workspace-mcp-runtime.md)으로 대체

이 결정은 더 이상 유효하지 않습니다. 시스템의 가용성과 데이터 정직성이 충돌했을 때 이 프로젝트가 무엇을 최우선으로 선택했는지를 보여주는 기록으로 보존합니다.

## 맥락 (Context)

- 에이전트들이 파일과 산출물을 주고받는 **작업 공간(Workspace)** 디렉터리를 대화 세션마다 독립적으로 지정할 수 있도록 지원하고자 했습니다. 작업 공간은 개별 대화 세션의 설정이지 전체 시스템의 배포 설정이 아니므로, 시스템 설정 파일은 변경하지 않고 세션 데이터베이스에 저장합니다.
- 외부 MCP 서버는 자신이 접근할 작업 루트 디렉터리를 **프로세스 기동 시점**에 전달받습니다. 파일 시스템 서버는 명령행 인자로, 샌드박스 서버는 환경변수로 각각 주입받으며, 프로세스 실행 도중에는 이를 동적으로 변경할 수 없습니다.
- 당시 아키텍처에서는 MCP 매니저가 전역에 단 하나만 존재했고, 모든 대화 세션이 동일한 서버 프로세스 풀을 공유했습니다. 따라서 다른 세션이 작업 공간을 변경하려면 기존 서버 프로세스를 종료하고 재기동해야 했습니다.
- 이로 인해 A 대화 세션이 토론을 진행하는 도중 B 대화 세션이 다른 작업 폴더로 토론을 시작하면, 도구 서버가 B의 폴더 경로로 재기동되면서 **A 세션의 에이전트 도구가 B 세션의 파일을 읽고 쓰는 치명적인 교차 오염**이 발생하게 됩니다. 시스템 차원에서는 어떠한 오류도 발생하지 않으며, 오직 결과 데이터만 조용히 왜곡됩니다.

## 결정 (Decision)

**조용히 잘못된 결과를 산출하느니, 명시적으로 실행을 거절하도록 합니다.**

- 이미 다른 작업 공간을 사용하는 토론 세션이 진행 중인 경우, 새로운 토론 시작 요청을 "작업 공간 충돌(Workspace Conflict)" 오류로 즉시 거절합니다.
- 특정 세션에서 토론이 진행되는 동안에는 해당 세션의 작업 공간 경로 수정을 원천 차단합니다.
- 작업 공간 경로를 변경할 때는 이미 환경변수가 치환된 기존 명령행 인자에서 문자열을 검색하여 바꾸지 않고, **환경변수 치환 이전의 원본 서버 설정 템플릿에 신규 경로를 다시 주입**하여 서버 프로세스를 안전하게 재기동합니다.

## 결과 (Consequences)

**좋아지는 점**

- 한 대화 세션의 에이전트 도구가 다른 세션의 프로젝트 파일을 침범하거나 오염시키는 사고가 원천적으로 차단되었습니다.
- 사용자는 세션 시작이 불가능한 기술적 이유에 대해 명확하고 정직한 안내 메시지를 수신하게 되었습니다.

**치르는 비용**

- **서로 다른 작업 공간을 사용하는 다중 대화를 동시에 실행할 수 없었습니다.** 원격 접속 사용자와 로컬 서버 PC 관리자가 각자의 프로젝트 디렉터리를 기반으로 동시에 토론을 진행하려는 운영 시나리오가 제약되었습니다.

**대체된 사유**

열흘 뒤, 작업 공간마다 독립된 MCP 서버 프로세스 풀을 동적으로 격리 기동하는 런타임 풀(Runtime Pool) 아키텍처가 도입되면서 본 거절 정책은 효력을 다했습니다 ([ADR-016](ADR-016-per-workspace-mcp-runtime.md)). 그러나 거절 규칙의 핵심 철학은 형태를 바꾸어 시스템에 여전히 존속합니다. 현재 시스템이 실행을 거절하는 이유는 "서로 다른 두 디렉터리를 동시에 열 수 없기 때문"이 아니라 "현재 호스트 머신에 서버 프로세스 풀을 추가로 기동할 메모리 예산이 부족하기 때문"입니다. 타 세션의 디렉터리를 조용히 침범하느니 차라리 작업을 명시적으로 거절한다는 기본 설계 철학은 변함없이 계승되었습니다.

**이 ADR에서 배울 점**

- 이상적인 궁극적 해결책(런타임 풀)을 즉시 구현하기 어려운 상황일 때, **잠재적 데이터 왜곡을 방치하는 대신 명시적인 실패 및 거절을 선택하는 것** 역시 중요한 아키텍처 설계입니다.
- 임시적인 성격의 의사결정이라도 반드시 기록으로 남겨야 합니다. 차후 상위 설계로 대체될 때, 시스템이 끝까지 수호해야 하는 핵심 가치(여기서는 "타 세션의 파일을 절대 침범하지 않는다")가 명문화되어 있어야 후속 설계에서도 그 불변식을 계승할 수 있습니다.
