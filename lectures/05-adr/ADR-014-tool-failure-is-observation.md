# ADR-014. 도구 실패는 관찰 결과다, 취소만 전파한다

> [ADR 목록](README.md) · 이전: [ADR-013](ADR-013-json-config.md) · 다음: [ADR-015](ADR-015-reasoning-out-of-prompts.md)

## 상태 (Status)

채택됨 · 2026-09-08 (릴리스 노트상 v0.5.0에 포함) · 관련: [ADR-005](ADR-005-long-lived-mcp-sessions.md), [ADR-007](ADR-007-no-simulated-answers.md), [ADR-008](ADR-008-background-debate-runner.md)

## 맥락 (Context)

MCP 도구 오류 하나가 발언하던 에이전트를 죽이고, 가끔은 서버 전체를 죽였습니다. 방어가 한 겹이었고, 그 한 겹에
방향이 반대인 구멍이 두 개 있었습니다.

- **너무 좁게 잡은 곳.** `except Exception`은 `BaseExceptionGroup`을 잡지 못합니다. MCP SDK의 stdio 경로가 쓰는 anyio는
  여러 태스크의 예외를 바로 이 예외 그룹으로 묶어 올립니다. 이 예외가 MCP 매니저, 엔진의 발언 처리, 토론 실행기를
  차례로 뚫고 올라가 토론 태스크를 죽였습니다. 화면은 "토론 중..."에 멈춰 있었습니다.
- **너무 넓게 잡은 곳.** `except (Exception, BaseException)`은 취소 신호(`CancelledError`)까지 삼켰습니다. 앱을 끌 때
  취소가 전달되지 않았고, 실행기는 영원히 끝나지 않는 태스크를 기다렸고, 수명 관리 코드가 멈췄고, Uvicorn이 강제
  종료되었습니다. 겉으로는 서버가 죽은 것과 같았습니다.

이 밖에도 세 가지 틈이 있었습니다.

- 응답하지 않는 서버(무한 루프 스크립트, 끊어진 원격 서버, 표준 입력을 기다리는 명령행 도구)는 턴을 영원히 붙잡았습니다.
  멈춰 있는 코루틴에는 취소도 닿지 않습니다.
- 서버가 수십 MB를 돌려주면 토큰 계산, DB 기록, 브라우저가 차례로 무너졌습니다.
- 자식 프로세스를 프로세스 번호로 정리했습니다. 이미 끝난 프로세스의 번호는 Windows가 적극적으로 재사용하므로,
  종료 신호가 엉뚱한 프로세스(운이 나쁘면 Uvicorn 작업 프로세스)에 닿을 수 있었습니다.

## 결정 (Decision)

원칙을 한 문장으로 정하고, 모든 층에서 지킨다.

> 도구 실패는 에이전트가 읽고 고칠 관찰 결과다. 발언, 토론, 프로세스를 끝낼 이유가 아니다.
> 유일한 예외는 취소다. 취소는 실패가 아니라 명령이고, 언제나 전파되어야 한다.

| 층 | 보장 |
| :--- | :--- |
| MCP 매니저 | **첫 번째 경계.** 무엇이 잘못되든 "오류 결과"를 돌려준다. 취소만 다시 올린다 |
| LLM 호출기의 도구 실행 | 같은 규칙을 다시. 매니저가 바뀌었거나 도구 조회 자체가 실패해도 |
| LLM 호출기의 호출 해석 | 깨진 도구 호출(모양, 인자 JSON, 빠진 호출 ID)을 흡수 |
| LLM 호출기의 화면 알림 | 화면 콜백이 죽어도 실행된 도구의 관찰 결과는 지킨다 |
| 엔진의 발언 처리 | 발언 하나의 실패는 오류 발언으로 기록하고 나머지는 계속. DB 커밋 실패는 롤백 |
| 토론 실행기 | 예외 그룹도 "실패"로 보고. 취소는 최대 20초만 기다린다 |
| 앱 진입점 | 이벤트 루프와 스레드의 처리되지 않은 예외를 기록. MCP 초기화 실패해도 앱은 뜬다 |

더해서,

- 도구 호출 시간 상한 180초. 넘으면 포기하고 세션을 닫았다가 다시 연다(늦게 온 응답이 다음 호출에 섞이지 않게).
  모델에게는 도구가 응답하지 않았다고 알린다.
- 도구 결과 크기 상한 20만 자. 넘으면 앞뒤를 남기고 가운데를 생략한다.
- 자식 프로세스는 기동할 때 받은 **프로세스 객체**로, 아직 살아 있을 때만 정리한다. 번호는 객체를 얻지 못한
  경우에만 쓴다.
- 두 상한은 환경변수로 조정할 수 있다.

## 결과 (Consequences)

**좋아지는 것**

- 도구 하나가 토론을 죽이지 못합니다. 모델은 오류 문구를 그대로 읽고 인자를 고쳐 다시 부릅니다.
- 앱 종료가 항상 끝납니다.
- 이 원칙이 이후의 비슷한 결정들(도구 예산 소진 시 작업 보존, 저장 실패 시 파일 보존, 후처리 실패 시 원본 유지)의
  기준이 되었습니다.

**치르는 비용**

- 같은 규칙이 여러 층에 **중복**됩니다. 의도한 중복입니다. 각 층은 아래 층이 규칙을 지킨다고 가정하지 않습니다.
  대신 "왜 여기서 또 잡지?"라는 질문에 답할 수 있게 원칙을 문서로 남겨야 합니다.
- `BaseException`을 잡는 코드는 `KeyboardInterrupt`와 `SystemExit`도 잡습니다. 이 패턴은 경계 지점에만 써야 하고,
  곳곳에 퍼지면 오히려 문제를 숨깁니다.
- 정당하게 오래 걸리는 도구(큰 빌드, 긴 분석)가 시간 상한에 걸릴 수 있습니다. 환경변수로 늘려야 합니다.

**교훈**

예외 처리의 버그는 "잡지 않아서"와 "너무 많이 잡아서" 양쪽에서 생깁니다. 파이썬의 예외 계층, 특히 취소와 예외
그룹이 어디에 있는지를 알고 경계를 설계해야 합니다.
