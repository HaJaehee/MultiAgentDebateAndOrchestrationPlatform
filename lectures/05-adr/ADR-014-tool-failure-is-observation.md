# ADR-014. 도구 실패는 관찰 결과다, 취소만 전파한다

> [ADR 목록](README.md) · 이전: [ADR-013](ADR-013-json-config.md) · 다음: [ADR-015](ADR-015-reasoning-out-of-prompts.md)

## 상태 (Status)

채택됨 · 2026-09-08 (릴리스 노트상 v0.5.0에 포함) · 관련: [ADR-005](ADR-005-long-lived-mcp-sessions.md), [ADR-007](ADR-007-no-simulated-answers.md), [ADR-008](ADR-008-background-debate-runner.md)

## 맥락 (Context)

단 하나의 MCP 도구 실행 오류가 발언 중이던 에이전트 태스크를 중단시키고, 심한 경우 서버 프로세스 전체를 비정상 종료시켰습니다. 방어막이 단 한 겹에 불과했던 데다, 그 한 겹의 방어막에도 방향이 정반대인 두 개의 치명적인 구멍이 존재했습니다.

- **예외 범위를 너무 좁게 잡은 계층**: `except Exception`은 복합 예외 그룹인 `BaseExceptionGroup`을 잡지 못합니다. MCP SDK의 stdio 전송 계층이 사용하는 anyio 라이브러리는 여러 자식 태스크에서 발생한 예외를 바로 이 예외 그룹으로 묶어서 상위로 던집니다. 이 예외가 MCP 매니저, 엔진의 발언 처리기, 토론 실행기 계층을 차례로 관통하여 백그라운드 토론 태스크 자체를 강제 종료시켰습니다. 그 결과 UI 화면은 영구히 "토론 진행 중..." 상태에 멈춰 버렸습니다.
- **예외 범위를 너무 넓게 잡은 계층**: `except (Exception, BaseException)`과 같이 무차별적으로 예외를 잡은 곳에서는 비동기 취소 신호(`CancelledError`)까지 정상 오류로 삼켜버렸습니다. 애플리케이션을 종료할 때 취소 신호가 하위 태스크에 전달되지 못했고, 실행기는 영원히 끝나지 않는 작업을 무한 대기했으며, 수명 관리 코드가 중단되면서 결국 Uvicorn 프로세스가 타임아웃으로 강제 종료되었습니다. 겉으로 보기에는 서버가 비정상 크래시된 것과 완전히 동일했습니다.

이 외에도 세 가지 잠재적 취약점이 존재했습니다.

- 무응답 상태에 빠진 도구 서버(스크립트 무한 루프, 네트워크 단절된 원격 서버, 표준 입력을 무한정 기다리는 CLI 도구 등)가 에이전트의 턴 전체를 영구히 점유했습니다. I/O 블로킹 상태의 코루틴에는 일반적인 취소 신호도 제대로 도달하지 않았습니다.
- 도구 서버가 수십 MB 규모의 과도한 텍스트 출력을 반환하면 토큰 수 계산, 데이터베이스 영속화, 브라우저 DOM 렌더링이 연쇄적으로 다운되었습니다.
- 자식 프로세스를 OS 프로세스 ID(PID) 정수 값만으로 회수했습니다. 이미 종료된 프로세스의 PID는 Windows 운영체제가 즉시 재사용하므로, 강제 종료 신호가 엉뚱한 타 프로세스(최악의 경우 Uvicorn 워커 프로세스)로 오발송될 위험이 있었습니다.

## 결정 (Decision)

아키텍처 대원칙을 한 문장으로 명문화하고, 시스템의 모든 계층에서 이를 철저히 준수하도록 합니다.

> 도구 실패는 에이전트가 읽고 스스로 수정해야 할 **관찰 결과**입니다. 발언, 토론 세션, 백엔드 프로세스를 중단시킬 이유가 아닙니다.
> 유일한 예외는 취소입니다. 취소는 오류가 아니라 사용자의 **명령**이므로, 언제나 상위로 즉시 전파되어야 합니다.

| 계층 | 보장하는 불변식 |
| :--- | :--- |
| MCP 매니저 | **첫 번째 경계.** 하위에서 어떤 장애가 발생하더라도 "오류 관찰 결과"를 반환하며, 취소 신호만을 상위로 다시 던집니다. |
| LLM 호출기의 도구 실행부 | 동일한 방어 규칙을 재적용합니다. 매니저 객체가 모의 대역으로 교체되었거나 도구 카탈로그 조회 자체가 실패하더라도 안전하게 보호합니다. |
| LLM 호출기의 호출 해석부 | 손상된 도구 호출 형식(객체/딕셔너리 혼용, 깨진 인자 JSON, 누락된 호출 ID)을 안전하게 흡수합니다. |
| LLM 호출기의 화면 알림부 | UI 스트리밍 콜백이 실패하더라도, 실제 실행된 도구의 관찰 결과는 유실하지 않고 보존합니다. |
| 엔진의 발언 처리부 | 단일 발언의 실패는 '오류 발언'으로 기록하고 나머지 에이전트의 토론은 계속 진행합니다. DB 커밋 실패 시 즉시 롤백하여 정합성을 유지합니다. |
| 토론 실행기 | 복합 예외 그룹이 발생하더라도 "토론 실패" 상태를 정상 보고하며 멈추지 않습니다. 취소 요청 시 최대 20초까지만 대기합니다. |
| 애플리케이션 진입점 | 비동기 이벤트 루프와 워커 스레드의 미처리 예외를 최종 로깅합니다. MCP 초기화가 일부 실패하더라도 메인 웹 서버는 안전하게 기동합니다. |

추가 안전장치:

- 도구 호출 1회당 실행 시간 상한을 180초로 강제합니다. 초과 시 실행을 중단하고 해당 세션을 강제로 닫은 뒤 재초기화합니다 (지연된 응답이 후속 호출에 뒤섞이는 것을 차단하기 위함). 모델에게는 도구가 응답하지 않았다는 사실을 관찰 결과로 전달합니다.
- 도구 반환 결과의 텍스트 크기 상한을 20만 자로 제한합니다. 초과할 경우 시작 부분과 끝부분을 남기고 중간을 요약 생략 처리합니다.
- 자식 프로세스 관리는 PID 정수가 아니라 프로세스 기동 시 획득한 **OS 프로세스 객체 핸들**을 기준으로 수행하며, 프로세스가 활성 상태일 때만 종료를 시도합니다. PID 정수는 프로세스 객체를 획득하지 못한 극단적인 예외 상황에서만 보조적으로 활용합니다.
- 도구 타임아웃 및 결과 크기 상한 수치는 환경변수를 통해 유연하게 증액할 수 있도록 지원합니다.

## 결과 (Consequences)

**좋아지는 점**

- 단일 도구의 실행 실패가 토론 전체를 파탄내지 못합니다. 에이전트 모델은 반환된 오류 메시지를 직접 읽고 인자를 스스로 교정하여 재호출을 시도합니다.
- 애플리케이션 종료 작업이 지연이나 교착 상태 없이 항상 정상 완료됩니다.
- 본 원칙은 이후 유사한 장애 방어 설계(도구 예산 소진 시 산출물 보존, DB 저장 실패 시 비상 파일 백업, 후처리 실패 시 원본 유지 등)의 일관된 표준 기준이 되었습니다.

**치르는 비용**

- 동일한 방어 코드가 여러 계층에 걸쳐 **중복(Redundancy)** 배치됩니다. 이는 의도된 중복입니다. 상위 계층은 하위 계층이 규칙을 완벽히 지킬 것이라고 전제하지 않습니다. 다만 "왜 여기서 동일한 예외 처리를 반복하는가?"라는 의문에 개발팀이 혼란을 겪지 않도록 설계 원칙을 문서로 명문화해야 합니다.
- `BaseException`을 포착하는 코드는 `KeyboardInterrupt`나 `SystemExit`와 같은 치명적 신호까지 잡을 수 있습니다. 따라서 이 패턴은 반드시 시스템 경계 지점에만 제한적으로 적용해야 하며, 일반 비즈니스 코드 전반에 남용할 경우 버그를 은폐하게 됩니다.
- 대규모 빌드나 장시간의 정적 분석처럼 정당하게 오랜 시간이 소요되는 정상적인 도구 작업이 타임아웃에 걸릴 수 있습니다. 이 경우 환경변수 설정을 통해 제한 시간을 늘려주어야 합니다.

**교훈**

예외 처리 관련 결함은 "예외를 잡지 않아서" 발생하는 문제와 "예외를 너무 광범위하게 잡아서" 발생하는 문제 양쪽에서 모두 기인합니다. 언어 차원의 예외 계층 구조, 특히 비동기 취소 신호와 복합 예외 그룹이 어느 위치에 포진해 있는지를 정확히 이해하고 정밀한 방어 경계를 설계해야 합니다.
