# ADR-031. 스트리밍이 끝난 답의 조립은 이벤트 루프 밖 스레드에서 합니다

> [ADR 목록](README.md) · 이전: [ADR-030](ADR-030-fallback-to-the-global-model.md)

## 상태 (Status)

채택됨 · 2026-10-29 · 관련: [ADR-001](ADR-001-python-single-process.md), [ADR-002](ADR-002-litellm-gateway.md), [ADR-008](ADR-008-background-debate-runner.md)

## 맥락 (Context)

- MADO 는 프로세스 하나, asyncio 이벤트 루프 하나로 화면(NiceGUI 웹소켓)·HTTP API·모든 대화의 토론·모든 에이전트의 LLM 스트림·MCP 통신을 함께 돌립니다 ([ADR-001](ADR-001-python-single-process.md)). asyncio 는 협력형이라, 작업 하나가 `await` 에 닿아야 다른 작업이 차례를 받습니다.
- 발언 하나의 스트리밍이 끝나면 `LLMCaller._complete_unthrottled` 가 받은 조각을 `litellm.stream_chunk_builder` 로 응답 하나로 조립합니다. 이 함수는 `await` 가 없는 동기 함수였고 루프 위에서 돌았습니다. 제공자가 사용량을 보내지 않으면 LiteLLM 이 토크나이저로 직접 세므로 긴 답일수록 오래 걸립니다.
- 그동안 같은 프로세스의 다른 일은 모두 멈췄습니다. 병렬 지시·그래프 토론에서 동시에 말하던 다른 에이전트의 스트림 읽기, 다른 대화, 다른 탭·원격 화면의 갱신, 정지·승인 클릭 처리, 웹소켓 핑 응답이 그렇습니다. 다른 에이전트의 글은 소켓 버퍼에 쌓였다가 루프가 풀린 뒤 뭉텅이로 붙었습니다. 진단 기록(`stalls.log`)의 대표 예시가 바로 이 줄에서 1.3초 멈춘 기록입니다.
- 그 발언은 어차피 조립을 기다려야 합니다. 문제는 그 발언의 대기가 아니라, 기다릴 이유가 없는 나머지까지 함께 멈추는 것입니다.

## 결정 (Decision)

**조립(`stream_chunk_builder`)을 `asyncio.to_thread` 로 기본 스레드 풀에서 돌립니다. 메시지 목록은 얕은 복사로 넘기고, 사용량 기록과 반환은 루프로 돌아와서 합니다.**

- **바꾸는 곳은 한 줄입니다.** `_complete_unthrottled` 의 시그니처와 반환은 그대로입니다. 이 메서드는 MADOWarGame 구동기가 통째로 바꿔 끼우는 재정의 지점이라 바꾸지 않습니다.
- **스레드 안전은 확인한 범위에서만 기댑니다.** litellm 1.98.0 의 `stream_chunk_builder` 는 MADO 의 호출 방식(`logging_obj` 없음)에서 비용 계산·콜백 경로를 타지 않고, 넘겨받은 조각과 메시지만 읽습니다. 조각 목록은 그 호출만의 것이고, 메시지 목록은 복사본을 넘겨 스레드가 읽는 동안 다른 쪽이 바꿀 여지를 없앱니다.
- **사용량은 루프에서 기록합니다.** 계측기(`llm_usage`)는 컨텍스트 변수에 있으므로, 조립 결과를 받아 루프로 돌아온 뒤 `note_response` 를 부릅니다.

**다음은 하지 않습니다.**

- 조립을 직접 다시 구현하지 않습니다. 제공자별 조각 모양·도구 호출 인자 이어 붙이기·사용량 계산은 LiteLLM 의 몫입니다 ([ADR-002](ADR-002-litellm-gateway.md)).
- 조각을 받는 즉시 조금씩 조립하는 방식으로 바꾸지 않습니다. 끝난 뒤의 한 번이 문제였고, 그것을 루프 밖으로 옮기면 충분합니다.
- 프로세스 풀로 보내지 않습니다. 조각 객체를 넘기는 직렬화 비용이 조립보다 클 수 있고, 프로세스가 하나라는 전제([ADR-001](ADR-001-python-single-process.md))를 건드립니다.

## 결과 (Consequences)

**장점**

- 조립하는 동안에도 다른 발언 스트림·대화·화면·정지 버튼이 움직입니다. 병렬 발언·여러 대화·원격 화면을 함께 쓸수록 차이가 큽니다.
- 조립 중에 발언을 멈추면 기다리던 쪽이 바로 빠집니다.
- 답·끝난 이유·사용량 기록은 바뀌지 않습니다. 고치기 전 코드에서 실패하는 테스트로 확인했습니다 (`tests/test_llm_offload.py`: 조립 0.5초 동안 다른 코루틴이 0번 → 여러 번 돎).

**고려할 트레이드오프**

- 빨라지지 않습니다. 조립은 순수 파이썬이라 GIL 때문에 병렬로 계산되지 않고, 루프가 5ms 마다 차례를 받을 뿐입니다. "1초 멈춤"이 "그동안 조금 느림"으로 바뀝니다. 총 CPU 는 같습니다.
- 스레드는 죽일 수 없습니다. 취소해도 스레드는 끝까지 돌고 결과만 버려지므로, 서버 종료가 그만큼 늦어질 수 있습니다.
- 마지막 조각과 발언 확정 사이에 다른 이벤트(정지 요청, 화면 갱신)가 끼어들 수 있습니다. 다른 `await` 사이에서 이미 생기던 일이라 새 종류의 상황은 아닙니다.
- git 체크포인트 등과 같은 기본 스레드 풀을 씁니다. 병렬 발언 여럿이 한꺼번에 끝나면 줄을 섭니다.
- 스레드 안전은 지금의 LiteLLM 판에서 읽은 결과입니다. LiteLLM 을 올릴 때 `stream_chunk_builder` 가 전역 상태를 건드리게 바뀌었는지 다시 봐야 합니다.
