# ADR-001. 파이썬 단일 프로세스로 API와 화면을 함께 서빙한다

> [ADR 목록](README.md) · 다음: [ADR-002](ADR-002-litellm-gateway.md)

## 상태 (Status)

채택됨 · 2026-08-26 (초기 설계) · 관련: [ADR-006](ADR-006-airgap-first-packaging.md), [ADR-008](ADR-008-background-debate-runner.md)

## 맥락 (Context)

- 프로젝트 명세가 처음부터 파이썬을 선호했습니다. 백엔드(에이전트 조율, LLM 호출, 도구 서버 관리)는
  어차피 파이썬입니다.
- 결과물은 인터넷이 없는 망에 반입해야 합니다. 반입하는 파일 하나하나가 검토 대상이라, 프런트엔드 빌드
  산출물과 Node 툴체인이 늘어나는 것은 큰 부담입니다.
- 토론은 몇 분씩 걸리고, 그동안 발언이 토큰 단위로 흘러나오는 것을 실시간으로 보여 줘야 합니다.
- 운영자는 사실상 한 명입니다. 서버를 여러 개 띄우고 맞추는 구성은 피하고 싶었습니다.
- 명세에 오른 화면 후보는 NiceGUI, Streamlit, FastHTML이었습니다. 흔한 대안인 React/Vue SPA와 FastAPI의
  조합도 있었습니다.

## 결정 (Decision)

FastAPI 애플리케이션 하나에 NiceGUI를 얹어, **Uvicorn 프로세스 하나가 API와 화면을 같은 포트, 같은 이벤트
루프에서 서빙**한다.

- 화면은 파이썬 코드로 만들고, 화면 상태는 서버의 파이썬 객체가 들고, 브라우저와는 WebSocket으로 동기화한다.
- FastAPI는 앱의 기동·종료 수명 관리, 보조 REST API, 접근 제어 미들웨어를 맡는다.
- 별도의 프런트엔드 빌드 단계는 두지 않는다. 브라우저 쪽 라이브러리가 필요하면 빌드된 결과물을 앱 안에
  동봉한다.

## 결과 (Consequences)

**좋아지는 것**

- 빌드 단계가 없습니다. 소스를 반입하면 갱신이 끝나고, 소스 갱신 패키지가 수백 KB에 머뭅니다.
- 화면 코드가 에이전트 풀, MCP 연결 상태 같은 백엔드 객체를 직접 참조합니다. API 계약과 직렬화를 따로
  관리하지 않습니다.
- 진행 상황을 화면에 밀어 넣는 코드가 평범한 파이썬 함수입니다.

**치르는 비용**

- **화면 연산이 서버 CPU를 씁니다.** v0.7.2에서 토큰마다 카드 전체를 다시 렌더링하던 코드가 2만 자 보고서
  하나에 서버 CPU 82초를 썼고, WebSocket이 끊기면서 화면이 저절로 새로고침되었습니다. 갱신을 0.25초 단위로
  묶어 해결했습니다.
- **화면의 수명과 작업의 수명이 엮이기 쉽습니다.** 클릭 핸들러 안에서 토론을 실행하자, 새로고침 한 번에 토론이
  죽었습니다. [ADR-008](ADR-008-background-debate-runner.md)로 이어집니다.
- **화면 라이브러리 버전이 다른 기능과 엮입니다.** NiceGUI가 동봉한 Mermaid 버전에 맞춰 다이어그램 검사 규칙을
  보정했기 때문에 NiceGUI 버전 범위를 좁혀야 했습니다.
- **여러 대로 늘릴 수 없습니다.** 화면 상태와 토론 상태가 한 프로세스의 메모리에 있습니다. 한 사람이 운영하는
  서버 PC라는 전제 안에서는 문제가 되지 않지만, 전제가 바뀌면 이 결정부터 다시 봐야 합니다.

**이후에 따라온 결정**

- 그래프 편집기(Vue Flow)처럼 파이썬만으로 만들기 어려운 화면은, 의존성을 하나의 ES 모듈로 묶어 동봉하는
  방식으로 풀었습니다([ADR-021](ADR-021-graph-debate.md)).
