# ADR-001. 파이썬 단일 프로세스로 API와 화면을 함께 서빙한다

> [ADR 목록](README.md) · 다음: [ADR-002](ADR-002-litellm-gateway.md)

## 상태 (Status)

채택됨 · 2026-08-26 (초기 설계) · 관련: [ADR-006](ADR-006-airgap-first-packaging.md), [ADR-008](ADR-008-background-debate-runner.md)

## 맥락 (Context)

- 프로젝트 요구 명세가 기획 초기부터 파이썬 생태계를 선호했습니다. 백엔드 핵심 로직(에이전트 오케스트레이션, LLM 호출 파이프라인, 도구 서버 관리)은 전적으로 파이썬 기반입니다.
- 최종 산출물은 인터넷이 완전히 단절된 폐쇄망 환경에 반입해야 합니다. 반입 대상 파일 하나하나가 보안 감사 대상이므로, 프런트엔드 빌드 산출물과 Node.js 툴체인이 늘어나는 것은 운영상 큰 부담이었습니다.
- 다자간 토론은 턴당 수 분씩 소요되며, 그동안 생성되는 발언들이 토큰 단위로 스트리밍되는 과정을 실시간으로 브라우저에 표시해야 합니다.
- 실무 운영자가 사실상 1인인 환경이므로, 여러 웹 서버와 API 서버를 독립적으로 기동하고 정합성을 맞추는 분산 구성은 지양하고자 했습니다.
- 명세에 오른 UI 프레임워크 후보는 NiceGUI, Streamlit, FastHTML이었습니다. 일반적인 대안인 React/Vue SPA와 FastAPI의 결합 구성도 검토 대상에 포함되었습니다.

## 결정 (Decision)

단일 FastAPI 애플리케이션에 NiceGUI를 통합하여, **단일 Uvicorn 프로세스가 동일한 포트와 비동기 이벤트 루프에서 REST API와 UI 화면을 함께 서빙하도록 합니다.**

- UI 화면은 파이썬 코드로 선언하고, 화면의 상태는 서버 프로세스 메모리의 파이썬 객체로 직접 관리하며, 클라이언트 브라우저와는 WebSocket으로 실시간 동기화합니다.
- FastAPI는 애플리케이션의 기동 및 종료 수명 주기 관리, 보조 REST API 엔드포인트 제공, 접근 제어 미들웨어 실행을 전담합니다.
- 독립적인 프런트엔드 빌드 파이프라인은 두지 않습니다. 브라우저 측 외부 라이브러리가 필요한 경우 사전 빌드된 번들 결과물을 애플리케이션 패키지 내부에 직접 동봉합니다.

## 결과 (Consequences)

**좋아지는 점**

- 별도의 프런트엔드 빌드 파이프라인이 필요 없습니다. 파이썬 소스 코드만 반입하면 패치가 완료되며, 소스 업데이트 패키지의 용량도 수백 KB 수준으로 매우 가볍습니다.
- 화면 렌더링 코드가 백엔드의 에이전트 풀, MCP 연결 상태 등의 도메인 객체를 메모리에서 직접 참조할 수 있습니다. 복잡한 API 스키마 계약이나 직렬화 계층을 별도로 유지보수하지 않아도 됩니다.
- 에이전트의 진행 상황을 화면에 실시간으로 반영하는 코드를 순수 파이썬 비동기 함수로 직관적으로 작성할 수 있습니다.

**치르는 비용**

- **UI 렌더링 연산이 서버 CPU 자원을 직접 소모합니다.** v0.7.2 당시 토큰 수신마다 카드 컴포넌트 전체를 재렌더링하던 코드가 2만 자 분량의 종합 보고서 하나를 처리하는 동안 서버 CPU를 82초간 점유했고, 그 여파로 WebSocket 핑 타임아웃이 발생하여 화면이 저절로 새로고침되는 장애가 있었습니다. 이는 화면 갱신 주기를 0.25초 단위로 배치 처리하도록 개선하여 해결했습니다.
- **UI 화면의 수명 주기와 백엔드 비즈니스 작업의 수명 주기가 결합되기 쉽습니다.** 버튼 클릭 핸들러 내부에서 토론을 직접 실행할 경우, 브라우저 새로고침 한 번으로 실행 중이던 토론 태스크가 강제 종료되는 문제가 발생했습니다. 이는 [ADR-008](ADR-008-background-debate-runner.md)의 백그라운드 실행기 분리 결정으로 이어졌습니다.
- **UI 프레임워크의 의존성 버전이 다른 시스템 기능과 강하게 결합됩니다.** NiceGUI가 내장한 Mermaid.js 버전에 맞춰 다이어그램 검사 규칙을 보정해야 했으므로, NiceGUI의 버전 업데이트 범위를 보수적으로 제한해야 했습니다.
- **수평적 다중 인스턴스 확장이 불가능합니다.** 화면 세션 상태와 토론 실행 상태가 단일 프로세스의 메모리에 종속되어 있습니다. 단일 운영자가 단일 서버 PC를 운용한다는 현행 환경에서는 문제가 되지 않으나, 다중 사용자 분산 환경으로 요구사항이 확장된다면 이 아키텍처 결정부터 근본적으로 재검토해야 합니다.

**이후에 따라온 결정**

- 그래프 시각화 편집기(Vue Flow)처럼 파이썬만으로 구현하기 까다로운 고도화된 UI 컴포넌트는 필요한 프론트엔드 의존성을 단일 독립 ES 모듈로 번들링하여 동봉하는 방식으로 해결했습니다 ([ADR-021](ADR-021-graph-debate.md)).
