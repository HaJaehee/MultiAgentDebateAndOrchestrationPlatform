# ADR-041. PostgreSQL 에서 SQLite 와 같은 규칙으로 동작하게 하고, 수평 확장은 DB 쪽까지만 준비한다

> [ADR 목록](README.md) · 이전: [ADR-040](ADR-040-compact-stale-file-reads.md)

## 상태 (Status)

채택됨 · 2026-10-31 (v1.5.1) · 관련: [ADR-001](ADR-001-python-single-process.md), [ADR-004](ADR-004-sqlite-persistence.md), [ADR-017](ADR-017-never-lose-a-write.md), [ADR-024](ADR-024-resume-interrupted-turns.md)

## 맥락 (Context)

- 문서는 `db_url` 만 바꾸면 PostgreSQL 로 옮겨 간다고 적어 왔습니다. 실제로는 검색이 SQLite 전용 FTS5 표에 묶여 있었습니다.
- 검색 말고도 문제가 있었습니다. SQLite 는 외래 키도, 문자열 길이도, NUL 문자도 검사하지 않습니다. 앱은 그 위에서 자라 왔으므로, 무엇이 깨지는지는 코드를 읽어서는 다 알 수 없습니다.
- 그래서 메모리 SQLite 를 쓰는 시험을 전부 PostgreSQL 16.9 로 돌려 보았습니다 (`tests/pg_redirect.py`). 고치기 전에 2,743건 중 25건이 실패했습니다. 15건은 아래 표의 결함이고, 나머지는 없는 대화를 가리키는 시험 자료처럼 시험 쪽 문제였습니다. 다 고친 뒤에는 2,794건이 통과하고 3건을 건너뜁니다 (메모리 SQLite 자체를 보는 시험 1건, 윈도우 심볼릭 링크 권한 2건).

| 드러난 것 | SQLite 에서 | PostgreSQL 에서 |
| :--- | :--- | :--- |
| 체험·쉬운 화면 표의 외래 키에 `ON DELETE` 없음 | 행이 남음 | 주인 화면의 대화 삭제가 실패 |
| 감사 쿼리의 `PARTITION BY arguments` (JSON) | 문자열 비교 | 보안 감사 화면 전체가 오류 |
| `String(n)` | 길이 무시 | 긴 역할 설명 하나로 그 에이전트의 발언 기록이 전부 실패 |
| 문자열 안의 NUL | 저장 | 그 발언 기록이 실패 |
| 시간대 없는 시각 | UTC 로 읽음 (`as_utc`) | asyncpg 가 현지 시각으로 읽어 9시간 밀림 |
| `_ADDED_COLUMNS` | 동작 | `PRAGMA`·`DATETIME`·`DEFAULT 0` 이 오류여서 아예 건너뜀 |
| 비밀번호가 든 `db_url` | 해당 없음 | 기동 로그에 그대로 찍힘 |

- 시험으로 드러나지 않는 것도 재 보았습니다. 순차 토론 전략의 턴 하나를 PostgreSQL 에서 돌려 보니 **LLM 호출 6번 중 5번이 `idle in transaction` 연결을 쥔 채 기다렸습니다.** 발언 직전의 코멘트 읽기가 트랜잭션을 연 채로 두었기 때문입니다. 응답은 몇 분씩 걸리므로 동시에 도는 턴이 풀 크기에 닿으면 다른 사람의 화면까지 멈추고, 그동안 VACUUM 도 막힙니다.

## 결정 (Decision)

### 1. 규칙은 하나, 찾는 길만 DB 마다 다르게 한다

규칙은 "모든 낱말이 부분 문자열로(대소문자 무시) 들어 있는 발언" 입니다. 합성어("분산캐시")와 조사가 붙은 말("캐시를")을 찾으려면 부분 문자열이어야 합니다. `SearchBackend` 가 DB 별 색인과 찾는 길을 맡고, `search_sessions` 는 어느 DB 에서나 같습니다. `tests/test_session_search.py` 의 같은 시험이 두 DB 에서 돕니다.

제안은 `pg_trgm` GIN 과 `tsvector` 였습니다. `tsvector` 만으로는 규칙을 지키지 못합니다. `simple` 파서는 "정보보안" 을 한 낱말로 보므로 "보안" 으로 찾지 못합니다. 그래서 규칙은 `ILIKE` 가 맡고, 색인은 빠르게 할 뿐입니다. `tsvector` 는 정확한 길이 시간을 넘겼을 때 쓰는 비상 경로로만 둡니다. 낱말 첫머리만 맞으므로 결과가 줄어들고, 그때는 사이드바에 그렇게 적습니다.

### 2. PostgreSQL 은 세 단계로 찾는다

| 순서 | 길 | 시간 상한 | 빠른 경우 |
| ---: | :--- | ---: | :--- |
| 1 | `pg_trgm` GIN 으로 `ILIKE` (3글자 이상이 있을 때) | 1초 | 드문 낱말 |
| 2 | `created_at` 색인으로 최근 발언부터 훑다 상한에서 멈춤 | 3초 | 흔한 낱말, 짧은 낱말 |
| 3 | `tsvector` GIN 으로 낱말 첫머리 (`partial`) | 3초 | 드문 짧은 낱말 |

처음에는 2번 없이 1번과 3번만 두었습니다. 재 보니 흔한 낱말에서 둘 다 나빴습니다. 부분 문자열은 통계로 빈도를 알 수 없어, 플래너가 흔한 낱말도 드물다고 보고 맞는 행을 전부 모아 정렬했습니다. 비상 경로는 더 느렸습니다(12~14초). 그래서 2번을 넣고 그 단계에서 비트맵·순차 스캔 플랜을 끕니다. 설정과 시간 상한은 SAVEPOINT 를 되돌려 그 질의에만 걸리게 합니다.

### 3. SQLite 가 말없이 받던 것은 같은 뜻으로 맞춘다

- `String(n)` 은 PostgreSQL 에서 `TEXT` 입니다. 앱은 길이를 지켜 본 적이 없고, 두 타입은 성능 차이가 없습니다. 길이를 지키게 하려면 값마다 자를 곳을 정해야 하는데, 에이전트 키처럼 자르면 안 되는 값이 섞여 있습니다.
- NUL 은 기록 직전에 지웁니다. 시간대 없는 시각은 UTC 로 붙입니다. 둘 다 `before_cursor_execute` 한 곳에서 합니다.
- `sessions.id` 를 가리키는 모든 외래 키는 `ON DELETE CASCADE` 입니다. 시험이 빠진 것이 없는지 지킵니다.
- `_ADDED_COLUMNS` 의 값은 SQLite 문법으로 둡니다. 다른 DB 에서는 타입을 모델에서 읽고 `NOT NULL DEFAULT ...` 만 옮깁니다. 컬럼 확인은 인스펙터로 합니다.

### 4. 긴 기다림 앞에서는 연결을 돌려준다

`SpeechRunner.speak` 는 LLM 을 부르기 직전에 커밋합니다. 세션은 커밋해도 객체를 만료시키지 않으므로 뒤의 코드는 그대로입니다. 계획 분담표를 만들기 전과 승인 카드를 띄우기 전에는 `turn_config` 가 닫습니다. DB 와 무관한 변경이고, SQLite 에서도 WAL 체크포인트를 막는 읽기 트랜잭션이 줄어듭니다.

### 5. 수평 확장은 DB 쪽까지만 준비하고, 안 되는 것은 안 된다고 적는다

한 것:

- 여러 프로세스가 함께 떠도 스키마 작업이 부딪히지 않습니다 (`pg_advisory_xact_lock`). 잠금을 빼면 시험이 실패합니다.
- 프로세스는 살아 있는 동안 공유 advisory lock 을 쥡니다. 기동할 때의 "끊긴 턴 정리" 는 혼자일 때만 합니다. 그렇지 않으면 새 프로세스가 다른 프로세스에서 도는 턴을 죽은 턴으로 적습니다.
- 연결 풀을 설정으로 뺐습니다 (`db_pool_size`, `db_max_overflow`, `pool_pre_ping`).

하지 않은 것: 여러 프로세스 운영 자체입니다. 도는 턴의 실행기와 실시간 화면 갱신(`DebateRunner`), 승인 카드 대기, `llm_concurrency`, MCP 런타임은 프로세스 메모리에 있습니다. 한 대화를 두 프로세스가 동시에 돌리는 것을 막는 장치도 없고, `conf.json` 과 작업 공간 파일은 한 기계를 전제합니다. 이것들을 옮기는 일은 [ADR-001](ADR-001-python-single-process.md) 을 다시 정하는 일이라 따로 다룹니다. 지금은 둘째 프로세스가 뜨면 기동 로그에 경고를 남깁니다.

### 6. 넣지 않은 것

- **SQLite 기록을 옮기는 도구**: 아직 배포 전이라 옮길 운영 데이터가 없습니다. `db_url` 을 바꾸면 빈 DB 에서 시작합니다.
- **Alembic**: 컬럼 추가만 하는 원칙([ADR-004](ADR-004-sqlite-persistence.md))이 그대로 통합니다.
- **`pg_bigm`·문자 n-gram `tsvector`**: 2글자도 색인할 수 있지만, 전자는 표준 배포에 없어 폐쇄망 반입 부담이 크고, 후자는 쓰기 비용이 큽니다. 2번 단계가 대부분을 처리합니다.

## 측정

발언 30만 건(평균 약 1KB, 표 293MB), 실제 스키마와 실제 `search_sessions`, PostgreSQL 16.9 기본 설정, Windows 개발 PC, `Korean_Korea.utf8` 로캘입니다. 낱말을 심어 흔한 정도를 나눴으며, 어휘가 40개뿐이라 "전체" 낱말은 실제 대화보다 훨씬 흔합니다. 질의당 프로세스 하나이고 동시 부하는 재지 않았습니다.

| 낱말 | 첫 설계 (1→3) | 지금 (1→2→3) | 일부만 찾음 |
| :--- | ---: | ---: | :--- |
| 3글자 이상, 전체에 나옴 | 3,142 ms, 일부 | 1,138 ms | 아니오 |
| 3글자 이상, 5% | 847 ms | 760 ms | 아니오 |
| 3글자 이상, 0.1% | 20 ms | 15 ms | 아니오 |
| 3글자 이상, 없음 | 5 ms | 3 ms | 아니오 |
| 2글자, 전체에 나옴 | 3,152 ms, 일부 | 153 ms | 아니오 |
| 2글자, 5% | 4,329 ms, 일부 | 275 ms | 아니오 |
| 2글자, 0.1% (발언 300건, 절반은 낱말 가운데) | 3,031 ms | 3,021 ms | **예** (150건만 찾음) |
| 2글자, 없음 | 3,017 ms | 3,017 ms | **예** |
| 드문 2글자 + 흔한 3글자 | 3,025 ms | 4,050 ms | **예** |

색인 비용: trigram 143MB(표의 절반), 낱말 52MB, `created_at` 6.6MB. 빈 표에 쌓을 때의 생성 시간은 각각 59초, 41초, 0.2초입니다. 어휘가 적은 자료라 실제 대화의 trigram 색인은 이보다 클 수 있습니다.

로캘: `C` 로캘의 `show_trgm('가나다')` 는 비어 있습니다. 한국어가 색인에 들어가지 않습니다. 결과는 같지만 훑어서 찾으므로 기동 로그에 경고를 남깁니다. 같은 자료를 처음 재 본 측정에서 `ILIKE` 는 `C` 로캘에서 약 4.5배 빨랐습니다(10.4초 → 2.3초, `created_at` 색인 없음). 로캘이 대소문자를 접는 비용으로 보이며, 한국어 색인과 맞바꾸는 값입니다.

연결: 순차 토론 전략의 턴 하나에서 연결을 쥔 채 기다린 LLM 호출이 6번 중 5번에서 0번으로 줄었습니다. 전략 4종, 그래프, 서브 토론, 이어 가기, 발언 다시 실행, 승인 대기를 `tests/test_db_connection_hold.py` 가 지킵니다.

시험이 실제로 지키는지는 고친 곳을 하나씩 되돌려 보았습니다. 처음에는 14곳 중 13곳이 실패로 잡혔고, 놓친 하나(플래너 설정)는 시험을 더해 14곳 모두 잡힙니다.

실제 앱을 PostgreSQL 로 띄워서도 확인했습니다. 가짜 LLM 이 8초씩 걸리는 턴 동안 연결은 모두 `idle` 이고 `idle in transaction` 은 없었습니다. 그 턴이 도는 중에 둘째 프로세스를 띄워도 턴은 `running` 그대로 끝까지 돌았고, 둘째의 로그에 경고가 남았습니다. 사이드바 검색, 보안 감사 창, 체험·쉬운 화면 행이 붙은 대화의 삭제도 화면에서 동작했습니다.

## 결과 (Consequences)

좋아지는 점:

- `db_url` 을 바꾸면 PostgreSQL 에서 같은 규칙으로 동작합니다. 전체 시험이 그 위에서 돕니다.
- 검색 한 번이 DB 를 붙잡는 시간에 상한이 생깁니다 (최악 약 7초, 측정 최대 4초).
- 응답을 기다리는 턴이 연결을 쥐지 않습니다. 필요한 연결 수가 진행 중인 턴 수에 묶이지 않습니다. SQLite 도 같습니다.
- 비밀번호가 로그에 찍히지 않습니다.

치르는 비용:

- 드문 2글자 낱말은 큰 DB 에서 결과가 줄어듭니다. 측정에서 300건 중 150건입니다. 화면에는 그렇게 알립니다. 시간 상한 안에 다 훑는 크기(이 PC 에서 약 20만 건)까지는 해당하지 않습니다.
- 색인 때문에 발언 기록이 느려지고 디스크를 씁니다. 쓰기 쪽 시간은 재지 않았습니다.
- 흔한 낱말은 1번 단계의 1초를 다 쓰고 2번으로 넘어갑니다. 상한을 줄이면 빨라지지만, 캐시가 식은 DB 에서 드문 낱말이 1번을 놓치면 2번도 넘겨 일부 결과로 떨어질 수 있어 1초로 둡니다. 식은 캐시의 시간은 재지 않았습니다.
- `pg_trgm` 설치에 권한이 필요합니다. 없으면 기동은 되고 훑어서 찾습니다. PgBouncer 의 transaction 모드에서는 인스턴스 잠금이 유지되지 않습니다.
- 프로세스 잠금은 전용 연결 하나를 씁니다. 그 연결이 끊기면 잠금도 사라지는데 다시 잡지는 않습니다. 여러 프로세스를 아직 지원하지 않으므로 넘어갑니다.
- 이미 만들어진 PostgreSQL 표의 외래 키에는 `ON DELETE` 가 더해지지 않습니다. 배포 전이라 그런 표가 없습니다.
- 시험에서 `:memory:` 를 돌려 쓰는 방식이라 표를 비우는 시간만큼 PostgreSQL 전체 시험이 깁니다 (약 19분). 평소 시험은 그대로 SQLite 로 돕니다.
