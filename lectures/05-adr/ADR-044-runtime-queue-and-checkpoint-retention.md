# ADR-044. 런타임 자리가 모자라면 줄을 세우고 라운드 경계에서 양보하며, 쉬는 작업 공간의 체크포인트를 정리한다

> [ADR 목록](README.md) · 이전: [ADR-043](ADR-043-code-diff-viewer.md)

## 상태 (Status)

채택됨 · 2026-11-01 (v1.5.1) · 관련: [ADR-024](ADR-024-resume-interrupted-turns.md), [ADR-028](ADR-028-plan-approval-gate.md), [ADR-043](ADR-043-code-diff-viewer.md)

## 맥락 (Context)

- `MCPRuntimePool` 은 서로 다른 작업 공간을 동시에 `MCP_MAX_RUNTIMES`(기본 4)개까지만 띄웁니다. 다섯 번째 폴더의 턴은 시작하자마자 `RuntimeCapacityError` 로 끝났습니다. 대화 분기는 분기마다 폴더를 따로 만들므로 이 상한에 쉽게 닿습니다.
- 턴은 시작부터 끝까지 런타임을 쥡니다. 그래서 자리를 비우는 일은 턴이 끝날 때만 일어납니다. LLM 응답이나 계획 승인을 기다리느라 도구를 쓰지 않는 시간도 마찬가지입니다.
- 턴마다 스냅샷을 여러 개 남깁니다 (`refs/mado/turns/<턴 id>/…`). 턴을 버리거나 대화를 지울 때만 이름을 지우므로, 수백 턴이 쌓이면 ref 파일과 loose 객체가 계속 늘어납니다.
- 런타임 회수는 다음 획득·반납이 올 때만 일어납니다. 토론이 끝난 서버에는 그런 때가 오지 않습니다.

## 결정 (Decision)

### 1. 자리가 없으면 먼저 온 순서대로 기다린다

`acquire` 는 바로 거절하지 않고 `MCP_RUNTIME_WAIT`(기본 900초) 동안 줄을 섭니다. 다 지나면 지금처럼 자리를 쥔 턴의 목록과 함께 `RuntimeCapacityError` 를 냅니다. 0 이면 예전처럼 바로 거절합니다.

- 떠 있는 폴더는 자리를 새로 요구하지 않으므로 줄과 상관없이 함께 씁니다.
- 줄이 있으면 빈자리가 나도 새치기하지 않습니다.
- 줄에 선 턴은 `RUNTIME_QUEUED` 이벤트로 순번을 화면에 알립니다. 정지를 누르면 시작하지 않고 취소로 끝납니다. 어느 쪽이든 요청이 아직 기록되지 않았으므로 글을 입력창으로 돌려줍니다.
- 기다리는 동안 풀의 락을 쥐지 않습니다. 쥐면 앞선 턴의 반납이 막혀 자리가 영영 나지 않습니다.

기본값을 15분으로 둔 이유는 계획 승인(ADR-028, 기본 10분) 때문입니다. 승인을 기다리는 턴도 자리를 쥐고 있어, 그보다 짧으면 앞 턴의 답을 기다리다 거절됩니다.

### 2. 라운드 경계에서 자리를 양보한다

줄만 두면 뒤의 턴은 앞선 턴 전체를 기다립니다. 그래서 라운드(그래프 단계)가 시작하기 직전, 줄의 맨 앞이 `MCP_RUNTIME_YIELD_AFTER`(기본 60초)를 넘게 기다렸고 자기도 그만큼 썼으면 자리를 내주고 줄 맨 뒤에 다시 섭니다 (`yield_slot`). 0 이면 양보하지 않습니다.

- 양보한 턴은 시간 제한 없이 기다립니다. 이미 시작한 턴을 자리 때문에 실패로 끝내면 그때까지의 토론이 헛일이 됩니다.
- 같은 폴더를 함께 쓰는 턴이 있으면 양보하지 않습니다. 그 턴은 지금 라운드 경계에 있지 않아 도구가 도중에 사라집니다.
- 돌아올 때는 **같은 `MCPManager` 객체**에 프로세스만 다시 붙입니다. 자문 범위처럼 턴 전체에 걸쳐 매니저를 들고 있는 쪽이 있습니다. 새 객체를 만들면 그쪽은 조용히 도구를 잃습니다.

검토한 대안: **도구를 부를 때만 빌리기** → 기각. 도구 호출은 벽시계 시간의 작은 부분이라 처리량은 가장 높지만, 세 가지 문제가 있습니다.

1. 발언 도중, 두 도구 호출 사이에 프로세스가 내려가 샌드박스 변수가 사라집니다. 모델은 앞 호출의 결과가 살아 있다고 믿고 다음 코드를 씁니다.
2. 도구 호출마다 줄을 서면 발언이 언제 끝날지 모르게 됩니다. 반대로 쉽게 포기하면 도구 실패가 늘어납니다.
3. 도구 목록을 프로세스 없이 들고 있어야 합니다. 지금은 `MCPManager.clients` 에서 읽는데, 이 값이 비는 순간 풀 밖의 코드는 기본 런타임으로 물러서 **다른 폴더의 도구**를 받을 수 있습니다 (`LLMCaller` 의 `mcp or self.mcp_manager`).

### 3. 쉬는 작업 공간의 저장소를 정리한다

마지막 턴이 끝나고 `MCP_RUNTIME_IDLE_TTL`(기본 300초) 동안 아무도 찾지 않은 작업 공간에 대해 풀이 `idle_hook` 을 부릅니다. 앱은 여기에 `session_ops.maintain_workspace` 를 겁니다.

1. **보존 기준을 넘긴 턴을 찾습니다** (`expired_turns`). 최근 `CHECKPOINT_KEEP_TURNS`(기본 200)턴과 최근 `CHECKPOINT_KEEP_DAYS`(기본 30)일 안의 턴을 남기고, 둘 다 넘긴 턴만 고릅니다. 턴의 시각은 스냅샷 커밋 중 가장 늦은 것입니다.
2. **기록을 먼저 고칩니다.** `TurnModel.checkpoint` 에서 `start`·`end` 를 지웁니다. 바뀐 파일 수(`changed`)는 턴의 기록으로 남깁니다.
3. **이름을 지웁니다** (`forget`). 순서가 반대면, 중간에 실패했을 때 스냅샷이 사라진 턴의 기록에 되돌리기가 남습니다.
4. **`git gc --auto` 를 돌립니다** (`collect_garbage`). 사용자의 gc 설정을 따르고, `gc.autoDetach=false` 로 끝을 기다립니다.

런타임을 내리는 시점과는 별개입니다. 런타임 회수는 여전히 다음 획득·반납에서 일어나고, 타이머는 저장소 정리만 부릅니다. 회수까지 타이머로 옮기면 기본 작업 공간의 런타임이 쉬는 동안 내려가, 기동 시 미리 띄워 둔 의미가 없어지고 화면의 도구 상태도 바뀝니다.

보존 기준은 두 조건을 함께 봅니다. 하루에 많이 쓰는 폴더는 턴 수만 보면 며칠 만에 되돌릴 수 없게 되고, 드물게 쓰는 폴더는 기간만 보면 전부 지워집니다.

## 결과 (Consequences)

**이점**

- 상한을 넘어도 턴이 거절되지 않고 끝납니다. 자리가 하나뿐이어도 여러 폴더의 토론이 번갈아 진행합니다.
- 체크포인트 ref 와 객체가 오래된 턴부터 정리됩니다.
- 화면과 `/api/mcp` 의 `waiting` 으로 누가 기다리는지 볼 수 있습니다.

**비용과 한계**

- **양보한 턴은 샌드박스 커널의 변수를 잃습니다.** 서버가 다시 뜨기 때문입니다. 파일과 지식 그래프는 남습니다. 자리를 두고 경쟁할 때만 일어나고, 라운드를 넘어 변수를 이어 써야 하는 환경은 `MCP_RUNTIME_YIELD_AFTER=0` 으로 끕니다. 메모리에만 상태를 두는 사용자 정의 MCP 서버도 같습니다.
- 양보할 때마다 서버를 다시 띄웁니다 (기본 서버 4개 기준 약 4초).
- 계획 승인이나 도구 승인을 기다리는 턴은 자리를 쥔 채로 있습니다. 라운드 경계가 아니기 때문입니다.
- 양보 뒤 자리를 기다리는 동안에는 정지를 눌러도 자리를 받을 때까지 합성으로 넘어가지 않습니다. 합성도 그 폴더의 도구를 쓰기 때문입니다. 바로 끝내려면 긴급 종료를 씁니다.
- 보존 기간이 지난 턴은 변경 내역을 볼 수도, 되돌릴 수도 없습니다. 그 턴에서 대화를 분기하면 지금 폴더를 복사하고 그렇다고 알립니다.
- 이름을 지워도 디스크는 바로 줄지 않습니다. `gc --auto` 는 loose 객체가 약 6,700개를 넘거나 pack 이 50개를 넘어야 움직이고, 이름 잃은 객체는 git 의 유예 기간(`gc.pruneExpire`, 기본 2주)이 지나야 지웁니다. 큰 파일 몇 개만 쌓인 저장소에서는 기준에 닿지 않을 수 있습니다.
- `app/main.py` 의 수명 주기에서만 정리를 겁니다. 엔진을 직접 구동하는 쪽(MADOWarGame, `app/bench.py`)은 지금과 같습니다.
