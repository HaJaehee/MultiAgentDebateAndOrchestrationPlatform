# ADR-044. 런타임 슬롯 경합 시 대기열 큐잉·라운드 경계 양보 및 유휴 작업 공간 체크포인트 정리 정책

> [ADR 목록](README.md) · 이전: [ADR-043](ADR-043-code-diff-viewer.md)

## 상태 (Status)

채택됨 · 2026-11-01 (v1.5.1) · 관련: [ADR-024](ADR-024-resume-interrupted-turns.md), [ADR-028](ADR-028-plan-approval-gate.md), [ADR-043](ADR-043-code-diff-viewer.md)

## 맥락 (Context)

- `MCPRuntimePool`은 서로 다른 작업 공간에 대해 최대 `MCP_MAX_RUNTIMES`(기본값 4개)까지만 프로세스 그룹을 병렬 실행합니다. 5번째 작업 공간에서 시작된 턴은 즉시 `RuntimeCapacityError` 예외가 발생하며 실패 처리되었습니다. 특히 세션 포크(대화 분기)는 분기마다 독립 작업 공간 디렉터리를 생성하므로 동시성 상한에 쉽게 도달합니다.
- 각 턴은 시작부터 종료까지 런타임 슬롯을 독점 점유합니다. 따라서 런타임 반납은 오직 턴이 완전히 종료될 때만 발생했습니다. LLM 생성 응답 대기나 계획 승인 사용자 입력 대기처럼 실제로 MCP 도구를 호출하지 않는 유휴 시간에도 슬롯이 해제되지 않았습니다.
- 매 턴마다 복수의 Git 체크포인트 스냅샷(`refs/mado/turns/<turn_id>/…`)이 생성됩니다. 세션을 완전히 삭제하거나 턴을 취소할 때만 ref가 정리되었기 때문에, 수백 턴이 누적되면 Git ref 참조 파일과 느슨한(loose) Git 객체가 디스크에 지속적으로 누적되었습니다.
- 유휴 런타임 프로세스 회수는 차기 acquire/release 호출 시점에만 트리거되므로, 모든 토론 세션이 종료된 서버에서는 유휴 리소스가 제때 회수되지 못했습니다.

## 결정 (Decision)

### 1. 런타임 슬롯 부족 시 선입선출(FIFO) 대기열 큐잉

`acquire()` 호출 시 슬롯이 부족하더라도 즉시 실패 처리하지 않고, `MCP_RUNTIME_WAIT`(기본값 900초) 동안 비동기 FIFO 큐에서 대기합니다. 제한 시간을 초과하면 현재 슬롯을 점유 중인 작업 공간 및 세션 목록을 포함하여 `RuntimeCapacityError`를 발생시킵니다. 값이 0이면 대기 없이 즉시 거절합니다.

- 이미 런타임 프로세스가 활성화되어 있는 작업 공간은 신규 슬롯 할당이 필요 없으므로 대기열 진입 없이 즉시 공유 점유합니다.
- 대기열에 선행 대기 턴이 존재하는 경우 신규 턴이 가용 슬롯을 가로채지 못하도록 선입선출 순서를 엄격히 보장합니다.
- 대기열에 진입한 턴은 `RUNTIME_QUEUED` 이벤트를 발행하여 프론트엔드 UI에 대기 순번을 실시간으로 표시합니다. 사용자가 정지(Stop)를 요청하면 턴을 시작하지 않고 안전하게 취소 처리합니다. 이 경우 DB에 턴 레코드가 아직 생성되지 않은 상태이므로 사용자 입력 프롬프트를 입력창으로 온전히 복원합니다.
- 대기열에서 슬롯을 기다리는 동안 풀의 `asyncio.Lock`을 유지하지 않습니다. 락을 유지할 경우 선행 턴의 슬롯 반납(release)이 블로킹되어 데드락이 발생하기 때문입니다.

대기 타임아웃 기본값을 15분(900초)으로 설정한 이유는 계획 승인 게이트(ADR-028, 기본 10분)의 타임아웃을 수용하기 위함입니다. 승인 대기 중인 턴 또한 슬롯을 점유하고 있으므로, 대기 시간이 이보다 짧으면 선행 턴의 사용자 승인을 기다리다 조기 타임아웃되는 문제가 발생합니다.

### 2. 라운드 경계 시점의 협업적 슬롯 양보(Yield)

단순 대기열만 도입할 경우 후속 턴은 선행 턴 전체가 완료될 때까지 장시간 블로킹됩니다. 따라서 각 라운드(또는 적응형 그래프 단계) 개시 직전, 대기열 최상위 턴의 대기 시간이 `MCP_RUNTIME_YIELD_AFTER`(기본값 60초)를 초과했고 현재 턴의 점유 시간 역시 해당 기준을 초과한 경우, 런타임 슬롯을 양보(`yield_slot`)하고 대기열의 맨 뒤로 재진입합니다. 값이 0이면 슬롯 양보를 비활성화합니다.

- 슬롯을 양보한 턴은 타임아웃 제한 없이 무기한 대기합니다. 이미 진행 중인 턴이 리소스 경합으로 인해 중도 실패할 경우 이전 라운드 토론 결과가 유실되기 때문입니다.
- 동일한 작업 공간을 공유하는 다른 실행 중인 턴이 존재하는 경우 슬롯을 양보하지 않습니다. 해당 세션은 라운드 경계 상태가 아니므로 도구 실행 도중 프로세스가 종료되는 부작용을 방지하기 위함입니다.
- 슬롯을 재획득하여 복귀할 때는 **기존의 동일한 `MCPManager` 인스턴스**를 유지한 채 프로세스만 재시작합니다. 서브 토론(자문 범위)처럼 턴 수명 주기 동안 매니저 참조를 보관하는 모듈이 존재하므로, 신규 매니저 객체로 교체할 경우 기존 참조 측에서 도구 호출 인터페이스가 단절되는 문제를 방지합니다.

검토 대안: **개별 도구 호출(Tool Call) 단위 동적 점유** → 기각. 도구 실행 시간은 전체 턴 소요 시간의 일부에 불과하여 이론상 처리량은 극대화되지만, 다음과 같은 3가지 치명적 결함으로 인해 배제했습니다.

1. 단일 발언 내 연속된 도구 호출 사이에서 프로세스가 종료될 경우 IPython 커널 내 메모리 변수가 소실됩니다. LLM은 이전 도구 호출의 런타임 상태가 보존되어 있다고 가정하고 코드를 작성하므로 실행 오류가 발생합니다.
2. 도구 호출 단위마다 대기열 경합이 발생하면 단일 발언의 응답 완료 시간을 예측하기 어렵고, 타임아웃을 짧게 둘 경우 도구 실행 실패율이 급증합니다.
3. 프로세스 비활성화 상태에서도 도구 스키마를 별도로 캐싱해야 합니다. 현재 구조상 `MCPManager.clients`가 비어 있는 순간 폴백 로직에 의해 기본 작업 공간의 도구 인터페이스(`LLMCaller`의 `mcp or self.mcp_manager`)로 잘못 전환되어 타 작업 공간의 도구를 오염 호출할 위험이 있습니다.

### 3. 유휴 작업 공간의 저장소 자동 유지보수 및 체크포인트 정리

모든 턴 실행이 완료된 후 `MCP_RUNTIME_IDLE_TTL`(기본값 300초) 동안 접근이 없는 유휴 작업 공간에 대해 런타임 풀이 `idle_hook` 콜백을 트리거합니다. 애플리케이션 진입점에서 여기에 `session_ops.maintain_workspace` 핸들러를 등록합니다.

1. **보존 정책 만료 턴 선별** (`expired_turns`): 최근 `CHECKPOINT_KEEP_TURNS`(기본 200턴) 이내이거나 최근 `CHECKPOINT_KEEP_DAYS`(기본 30일) 이내인 턴은 보존하며, 두 임계치를 모두 초과한 만료 턴만 정리 대상으로 선별합니다. 턴의 기준 시각은 해당 턴의 스냅샷 커밋 타임스탬프 중 최신값을 사용합니다.
2. **DB 메타데이터 선행 갱신**: `TurnModel.checkpoint`의 `start`, `end` Git 해시 참조를 제거합니다. 단, 수정된 파일 개수(`changed`)는 턴의 이력 통계로 계속 유지합니다.
3. **Git Ref 삭제** (`forget`): Git 네임스페이스에서 해당 턴의 스냅샷 ref들을 삭제합니다. DB 메타데이터를 먼저 갱신하지 않고 ref부터 삭제할 경우, 작업 중 장애 시 스냅샷이 소실된 턴에 롤백 UI가 잔존하는 불일치가 발생하기 때문입니다.
4. **저장소 가비지 컬렉션 수행** (`collect_garbage`): `git gc --auto` 커맨드를 실행하여 불필요한 Git 객체를 압축 정리합니다. 저장소 자체 설정을 준수하며, `gc.autoDetach=false` 옵션으로 백그라운드 분리 없이 작업 완료를 동기 대기합니다.

저장소 정리 타이머는 런타임 프로세스 회수 시점과 완전히 분리되어 동작합니다. 프로세스 회수는 차기 획득/반납 호출 시점에서 처리되며, 유휴 타이머는 Git 저장소 최적화 훅만 호출합니다. 프로세스 회수까지 유휴 타이머에 종속시킬 경우 기본 작업 공간의 상주 런타임까지 종료되어 서버 시작 시 사전 기동한 의도가 무색해지고 UI 도구 상태가 비활성화되는 부작용이 발생하기 때문입니다.

보존 기준은 턴 수와 기간 조건을 교집합(AND 만료 / OR 보존) 형태로 함께 평가합니다. 빈번하게 사용되는 세션은 턴 수 기준만 적용할 경우 며칠 만에 롤백 체크포인트가 소실되고, 간헐적으로 사용되는 세션은 경과일 기준만 적용할 경우 과거 작업 내역이 일괄 삭제되는 한계를 상호 보완합니다.

## 결과 (Consequences)

**이점**

- 동시 실행 상한을 초과하더라도 턴 요청이 조기 거절되지 않고 완료됩니다. 런타임 슬롯이 1개뿐인 환경에서도 복수 세션의 토론이 라운드 단위로 교차 실행됩니다.
- 장기 누적된 만료 턴의 Git ref 및 느슨한 객체가 주기적으로 정리되어 디스크 공간 낭비를 방지합니다.
- UI 대기 배지 및 `/api/mcp` 엔드포인트의 `waiting` 필드를 통해 현재 대기열 순번과 세션 목록을 실시간 모니터링할 수 있습니다.

**비용과 한계**

- **슬롯을 양보한 턴은 IPython 샌드박스 커널의 인메모리 변수가 소실됩니다.** 런타임 프로세스가 재시작되기 때문입니다 (작업 디렉터리의 영구 파일 및 지식 그래프 데이터는 온전히 보존됩니다). 이는 슬롯 경합이 발생할 때만 발생하며, 라운드를 넘어 메모리 상태 유지가 필수적인 워크로드는 `MCP_RUNTIME_YIELD_AFTER=0`으로 설정하여 양보를 비활성화할 수 있습니다. 메모리 기반 상태를 유지하는 커스텀 MCP 서버 역시 동일한 제약을 받습니다.
- 슬롯 재획득 시 프로세스 재기동 오버헤드가 발생합니다 (기본 MCP 서버 4개 기준 약 4초 소요).
- 계획 승인 또는 도구 실행 승인을 대기 중인 턴은 슬롯을 계속 점유합니다. 해당 상태는 라운드 개시 경계가 아니기 때문입니다.
- 슬롯을 양보한 후 재할당 대기 중에 사용자가 정지(Stop)를 요청하더라도, 슬롯을 재획득하기 전까지는 결론 합성 단계로 즉시 진입하지 않습니다. 결론 합성 또한 해당 작업 공간의 도구 컨텍스트를 참조하기 때문입니다. 즉각적인 중단이 필요할 경우 긴급 종료(Emergency Stop)를 사용할 수 있습니다.
- 보존 정책 만료로 체크포인트가 삭제된 턴은 파일 변경 내역 조회 및 롤백이 불가능합니다. 해당 만료 턴을 기점으로 대화를 포크(분기)할 경우 현재 작업 공간의 최신 스냅샷을 복제하며 UI 알림으로 이를 사용자에게 안내합니다.
- Git ref를 삭제하더라도 물리적 디스크 점유 용량이 즉각 회수되지는 않습니다. `git gc --auto`는 느슨한 객체가 약 6,700개를 초과하거나 팩 파일이 50개를 초과할 때만 가비지 컬렉션을 실제로 수행하며, 고아 객체(dangling object)는 Git 기본 만료 유예 기간(`gc.pruneExpire`, 기본 2주)이 경과해야 완전히 프루닝(삭제)됩니다. 따라서 소수의 대용량 파일만 변경된 저장소에서는 임계치에 도달하지 않을 수 있습니다.
- 저장소 자동 유지보수 훅은 `app/main.py` FastAPI 수명 주기에서만 활성화됩니다. 오케스트레이션 엔진을 직접 임포트하여 실행하는 외부 스크립트(MADOWarGame, `app/bench.py` 등)는 기존과 동일하게 동작합니다.
