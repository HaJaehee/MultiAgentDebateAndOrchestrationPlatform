# ADR-012. 발언 순서와 진영은 에이전트가 들고, 전략은 순서와 지침만 정한다

> [ADR 목록](README.md) · 이전: [ADR-011](ADR-011-session-config-snapshot.md) · 다음: [ADR-013](ADR-013-json-config.md)

## 상태 (Status)

채택됨 · 2026-08-30 (v0.1) · 관련: [ADR-011](ADR-011-session-config-snapshot.md), [ADR-021](ADR-021-graph-debate.md)

## 맥락 (Context)

- 초기 구현에서는 발언 순서가 전략 비즈니스 로직 내부에 `{"architect": 0, "coder": 1, "critic": 2}`와 같이 하드코딩되어 있었습니다.
- UI 화면에서 사용자가 에이전트를 동적으로 생성할 수 있게 되자 이 방식이 한계에 부딪혔습니다. 하드코딩된 맵에 존재하지 않는 신규 에이전트 키는 모두 동일한 기본 우선순위로 묶여 항상 맨 뒤로 밀려났고, 디베이트 전략에서는 제안자도 비판자도 아닌 어정쩡한 "기타" 진영으로 분류되었습니다. 새로 추가한 에이전트는 사실상 자유 토론 전략에서만 제 역할을 수행할 수 있었습니다.
- 에이전트별 프롬프트 컨텍스트를 생성하는 코드가 전략의 고유 특성을 참조하지 않았기 때문에, "자유 토론"과 "순차 검증" 전략은 발언 순서 제어를 제외하면 본질적으로 차이가 없었습니다. 순서 규칙을 단일화할 경우 두 전략이 완전히 동일해지는 구조적 결함이 있었습니다.
- 매 라운드마다 모든 참여 에이전트가 무조건 한 번씩 발언하는 일률적 방식은 대화가 길어질수록 불필요한 토큰 소비를 가중시켰습니다. 필요한 시점에 필요한 전문가만을 선별 호출하는 유연한 오케스트레이션 방식이 요구되었습니다.

## 결정 (Decision)

**에이전트가 자신의 발언 우선순위와 진영 속성을 직접 보유하도록 합니다.**

- 발언 우선순위(`debate_priority`, 작을수록 선순위)와 토론 진영(`debate_stance`: 제안, 비판, 중립)을 에이전트의 일급 설정 속성으로 정의합니다. 별도로 지정하지 않을 경우 모두 동일한 기본값이 부여되어 설정 파일에 등록된 순서가 그대로 유지됩니다.
- UI 로스터 화면에서 카드를 드래그 앤 드롭하면 순서 값을 10, 20, 30... 단위로 여유 있게 재부여합니다. 숫자 사이에 간격을 둠으로써 향후 에이전트를 중간에 삽입할 때 전체 목록을 재정렬하지 않아도 되도록 합니다.
- 기본 탑재 에이전트들의 배치 정보는 설정 파일(`conf.json`)에 명시합니다. 소스 코드에 종속되어 있던 도메인 지식을 선언적 설정으로 이전합니다.
- 전략 코드 내부에 고유 키로 잔존하는 에이전트는 `orchestrator` 하나로 제한합니다. 오케스트레이터는 단순한 페르소나가 아니라 시스템의 구조적 제어 주체이기 때문입니다.

**전략은 단순 순서 배정을 넘어 발언 지침(Guidance)을 주입하도록 합니다.**

- 전략 엔진은 발언 순서뿐만 아니라 발언 시점마다 에이전트에게 전달될 **맥락 지침**을 함께 생성하여 반환합니다. 이것이 개별 전략의 실질적인 차별성을 형성합니다.
- 기존의 "자유 토론"과 "순차 검증" 전략을 **순차 토론(Sequential)** 단일 전략으로 통합합니다. 우선순위 순서대로 발언하되, 직전 발언자의 이름을 직접 호명하고 그의 논거와 결론을 이어받아 반론 또는 보완하도록 지침을 강제합니다. 이러한 지침 주입이 배제되면 다자간 토론은 각자 자기 말만 늘어놓는 세 개의 독백으로 전락하기 때문입니다.
- 기존에 데이터베이스에 저장된 레거시 대화(당시 365건)들이 과거 전략 명칭을 참조하고 있으므로, **전략 별칭 매핑 테이블(Alias Table)**을 두어 신규 전략 구현체로 자동 연결합니다. 대화 이력을 외부 문서로 내보낼 때는 과거 키 대신 현재 실행되는 실제 전략 명칭을 표기합니다.

**오케스트레이터 동적 지명 전략을 신설합니다.**

- 매 라운드마다 오케스트레이터가 지금까지 축적된 토론 내용을 종합 분석하여 다음 발언에 가장 적합한 에이전트를 동적으로 선별합니다. 단 한 명의 전문가만 호출해도 무방합니다.
- 지명 전용 호출은 도구 사용과 순차적 사고 옵션을 비활성화한 경량 오케스트레이터 복제본을 활용합니다.
- 모델의 응답이 엄밀한 JSON 형식이 아니더라도, 본문 텍스트 내에서 유효한 에이전트 키를 정규식으로 감지하여 추출합니다.
- 엔드포인트 연결이 단절되었거나 유효한 에이전트 키를 하나도 식별하지 못할 경우, 우선순위 순서에 따른 정적 호출로 안전하게 폴백하며 **대체 경로로 전환되었다는 사실을 시스템에 반드시 기록합니다.**
- 전략 객체 자체는 외부 LLM을 직접 호출하지 않는 순수 함수로 유지합니다. "발언자를 오케스트레이터가 동적으로 결정한다"는 정책 플래그만을 엔진에 전달하며, 실제 모델 호출과 폴백 처리는 상위 오케스트레이션 엔진이 총괄합니다.

## 결과 (Consequences)

**좋아지는 점**

- 사용자가 새롭게 생성한 커스텀 에이전트가 모든 토론 전략에서 자신의 역할과 진영을 온전히 발휘할 수 있게 되었습니다.
- 신규 전략의 확장이 매우 수월해졌습니다. 본 결정 직후 병렬 지시 전략이 손쉽게 추가되었으며, 보름 뒤 그래프 기반 토론 전략([ADR-021](ADR-021-graph-debate.md)) 역시 동일한 아키텍처 기반 위에서 안정적으로 구축되었습니다.
- 전략 객체가 부수 효과가 없는 순수 함수로 정립됨에 따라, v0.5.0에서 도입된 **발언 순서 실시간 미리보기** UI 컴포넌트가 백엔드 엔진과 완전히 동일한 전략 함수를 공유할 수 있었습니다. 카드 배치 순서와 실제 발언 순서가 상이한 복합 전략(디베이트, 지명, 병렬)에서 사용자가 겪던 혼란을 완전히 해소했습니다.

**치르는 비용**

- 기본 에이전트의 우선순위와 진영 정보를 설정 파일에 명시하지 않으면, 디베이트 전략이 진영을 판별하지 못해 단순 직렬 순서로 다운그레이드됩니다. 소스 코드의 지식이 설정으로 이전된 만큼 기본 설정 템플릿의 품질을 엄격히 관리해야 합니다.
- 과거 전략 식별자를 지원하기 위한 별칭 변환 테이블을 지속적으로 유지보수해야 합니다.

**신규 전략 설계자를 위한 구현 지침**

- 특정 에이전트 키 문자열을 하드코딩하여 분기하지 말고, 에이전트의 도메인 속성(`priority`, `stance`)을 검사하십시오. 에이전트 키는 사용자가 임의로 지정하는 가변 값입니다.
- 전략 내부에서 LLM이나 비동기 I/O를 직접 호출하지 마십시오. 필요한 요구사항을 메타데이터로 선언하여 엔진에 위임하십시오.
- 사용을 중단한 레거시 전략 식별자는 반드시 별칭 테이블에 등록하여 이전 대화의 하위 호환성을 보장하십시오.
