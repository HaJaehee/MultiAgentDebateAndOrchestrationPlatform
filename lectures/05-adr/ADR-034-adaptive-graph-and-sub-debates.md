# ADR-034. 오케스트레이터의 적응형 실행 그래프 생성과 쟁점별 서브 토론(Sub-debate) 메커니즘을 도입한다

> [ADR 목록](README.md) · 이전: [ADR-033](ADR-033-render-long-text-off-the-loop.md)

## 상태 (Status)

채택됨 · 2026-10-30 · 관련: [ADR-021](ADR-021-graph-debate.md), [ADR-024](ADR-024-resume-interrupted-turns.md), [ADR-028](ADR-028-plan-approval-gate.md)

## 맥락 (Context)

- 그래프 토론(ADR-021)은 사용자가 사전에 정의한 정적 실행 그래프 노드만을 실행합니다. 어떤 태스크는 단순한 선형 파이프라인(설계 → 구현)으로 충분하지만, 복잡한 태스크는 병렬 기술 검토 및 수렴 루프가 필수적입니다. 그러나 요구사항에 적합한 최적의 토론 구조는 프롬프트 요청을 분석해야만 판단할 수 있으며, 매 턴마다 사용자가 캔버스에서 그래프를 직접 편집해야 하는 방식은 그래프 토론의 유연성을 충분히 활용하기 어려웠습니다.
- 토론 진행 중 두 전문가 에이전트 간에 핵심 기술 쟁점이 충돌했을 때 기존에는 두 가지 방식만 가능했습니다. 동료 자문(`peers__consult_agent`)은 1회성 단방향 질의응답(depth 1)에 불과하여 심층 논쟁이 불가능했고, 답변 또한 질의자의 도구 실행 결과로만 갇혔습니다. 반대로 전체 토론 라운드를 연장하면 해당 쟁점과 무관한 모든 전문가까지 불필요하게 발언에 참여하여 토큰 비용과 시간이 낭비되었습니다.
- MADO의 장애 복구 아키텍처는 중단된 턴을 데이터베이스 기록만으로 원자적으로 복원합니다(ADR-024). 스케줄러가 결정론적(Deterministic)으로 동작하기 때문입니다. 동적 토론 제어가 실행 도중 임의로 경로를 변경하면서 이를 상태 데이터로 영속화하지 않는다면 복구 불일치가 발생할 위험이 있었습니다.
- 모델이 그래프를 동적으로 생성한다는 것은 LLM이 전체 호출 비용을 결정한다는 의미이기도 합니다. 최대 라운드 수와 동시 실행 수는 사용자가 설정한 엄격한 통제 한도 내에 머물러야 합니다.

## 결정 (Decision)

### 1. 적응형 그래프 토론 — 6번째 전략 (`adaptive_graph`)

**계획 승인(ADR-028)이 완료된 후 본 토론 시작 직전에, 마스터 오케스트레이터가 이번 턴의 실행 그래프를 동적으로 생성하고 턴 완료 시점까지 불변으로 고정합니다.** 기존 5가지 토론 전략은 전혀 수정하지 않습니다.

- 그래프 생성 이후의 스케줄링 및 실행 라이프사이클은 기존 정적 그래프 토론과 동일합니다. 동일한 유효성 검증(`validate_graph`), 상태 전이 스케줄러, 장애 복구 로직, 시각화 컴포넌트를 그대로 재사용합니다.
- **참여 에이전트 제약**: 로스터 패널에서 체크박스로 활성화된 전문가 에이전트만 그래프 노드로 배치될 수 있습니다. 비활성화된 에이전트가 포함된 그래프는 검증 단계에서 즉시 거절됩니다.
- **기준 템플릿 그래프 지원**: 대화 세션에 사전 정의된 그래프가 이미 선택되어 있는 경우, 오케스트레이터는 해당 그래프를 기반으로 노드와 엣지를 점진적으로 조정합니다. 원본 템플릿 파일은 변경되지 않습니다.
- **비용 통제 및 상한 준수**: 노드 방문 상한은 세션의 `max_rounds` 설정을 초과할 수 없습니다. 최대 노드 수는 12개(시작/최종 합성 노드 제외), 턴당 최악의 LLM 호출 횟수는 최대 40회로 엄격히 제한됩니다.
- **견고한 폴백 메커니즘**: 그래프 생성 응답 형식이 스키마를 위반한 경우, 오류 원인을 프롬프트에 피드백하여 1회 재시도합니다. 재시도에도 실패하거나 연결이 끊어지면 기존 기준 템플릿 그래프로 폴백하며, 템플릿이 없을 경우 에이전트 우선순위 순차 연결 구조로 안전하게 전환하고 해당 사실을 UI 피드에 기록합니다.
- **상태의 영속화 보장**: 생성된 그래프 명세는 `KIND_GRAPH_DRAFT` 발언의 `turn_meta`에 데이터로 완전히 기록됩니다. 중단된 턴을 재개할 때는 추가 LLM 호출 없이 이 저장된 그래프 명세를 읽어 스케줄러를 복원합니다. 또한 `sessions.graph_snapshot`에 동기화되어 페이지 새로고침 및 내보내기 시에도 정확히 복원됩니다.

### 2. 서브 토론 메커니즘 — 전략 독립적 세션 옵션 (`sessions.sub_debates`, 기본값 false)

**라운드(그래프 전략에서는 슈퍼스텝) 경계에서 결정 장부에 미해결 쟁점이 존재할 경우, 오케스트레이터가 두 전문가 에이전트를 선별하여 쟁점 집중 토론을 개설할지 판단합니다.** 개설 시 두 전문가가 교대로 심층 발언을 주고받은 후 오케스트레이터가 합의 결론을 도출합니다.

- **독립적인 서브 토론 라운드 설정** (`sessions.sub_debate_rounds`, 1~5, 기본값 2): 1라운드는 두 전문가가 각 1회씩 발언하는 것을 의미합니다. 본 토론의 `max_rounds` 예산을 차감하지 않으며 완전히 별개의 카운터로 관리됩니다.
- **맥락 격리 및 결론만 메인 합류**: 서브 토론 내부의 세부 발언은 UI 피드와 영구 저장소에만 기록되며, 타 발언자나 결정 장부 요약, 최종 합성 단계의 프롬프트 컨텍스트에는 일절 주입되지 않습니다 (`turns.in_main_record = False`). 참여 에이전트의 차기 본 라운드 컨텍스트에도 주입되지 않으며, 도출된 핵심 결론만 결정 장부에 즉시 반영되어 메인 토론 흐름에 합류합니다.
- **그래프 전략과의 조화**: 그래프 노드는 수신 엣지의 컨텍스트만 참조하므로, 서브 토론 결론은 노드 실행 및 조건부 분기 판정 컨텍스트에 별도 시스템 주입 형태로 안전하게 전달됩니다.
- **쟁점 부재 시 불필요한 호출 방지**: 결정 장부에 미해결 쟁점이 명시되어 있을 때만 개설 여부를 질의합니다. 기능이 활성화되어 있더라도 쟁점이 없는 일반적인 턴에서는 추가적인 LLM 호출 비용이 발생하지 않습니다.
- **실행 상한 보장**: 턴당 최대 2회, 라운드 경계마다 최대 1회로 실행 빈도를 제한합니다. 토큰 예산이 소진되었거나 사용자 중단 요청이 발생한 경우 개설하지 않으며, 진행 중 예산이 소진되면 즉시 중단하고 직전 발언까지를 기반으로 결론을 작성합니다.
- **재귀적 분기 차단**: 서브 토론 내부에서는 추가적인 동료 자문(Peer consultation) 호출을 비활성화하고 도구 실행 상한을 턴당 3회로 제한하여 무한 루프를 방지합니다.
- **데이터 정직성 준수([ADR-007](ADR-007-no-simulated-answers.md))**: 한 에이전트가 응답 실패할 경우 그때까지의 발언으로 결론을 작성하며, 수신된 발언이 전혀 없으면 결론 없이 서브 토론을 종료하고 쟁점을 미해결 상태로 보존합니다.

**System 1(Jev) 판정은 두 단계입니다** (`DecisionCaller.evaluate_sub_debate`, 2026-11-11 변경). 오케스트레이터의 `decision_llm` 이 켜져 있으면 개설 여부를 생성형 LLM 대신 Jev 에 묻습니다.

1. 미해결 쟁점마다 `쟁점 [I-n] '…' 에서 두 전문가가 서로 다른 안을 내놓고 각자 자기 안을 고수하고 있습니까?` 를 묻습니다(방향은 합의하고 세부만 남았거나, 한 사람만 안을 냈거나, 유저·외부 팀 확인을 기다리는 쟁점이면 아니오). 기준을 넘는 쟁점이 없으면 열지 않으며, 호출은 이 한 번으로 끝납니다. 쟁점이 16건을 넘으면 장부 뒤쪽(최근) 16건만 묻습니다.
2. 확률이 가장 높은 쟁점 하나를 짚어 "본 토론의 다음 차례에서 풀리겠는가" 와 후보마다 "이 쟁점에서 맞선 안을 낸 당사자인가" 를 묻습니다. 풀리겠다는 확률이 기준을 넘으면 열지 않고, 아니면 당사자 확률이 높은 두 사람을 고릅니다.

기준은 게이트·발언자 지명과 같은 `decision_llm.threshold`(기본 0.5)를 그대로 씁니다. 처음에는 한 번의 호출에서 "충돌에서 비롯되어 지금 열어야 하는가" 라는 복합 질문, 쟁점 고르기, 어느 쟁점인지 말하지 않은 당사자 질문을 함께 했습니다. 실제 DeepSeek·Jev 시험에서 기록한 경계 8곳(Jev 가 판정한 2곳, DeepSeek 가 연 6곳)을 Jev 에 다시 물으니, 복합 질문은 상태와 무관하게 p=0.24~0.37 이라 일부러 대립시킨 시나리오에서도 한 번도 열리지 않았고, 당사자 질문은 늘 두 사람 모두 0.8 이상이었습니다. 쟁점별 질문은 같은 상태 안에서도 0.10~0.86 으로 갈렸습니다. "Architect 는 A, Critic 은 B" 처럼 양쪽 안이 적힌 쟁점은 0.7~0.86, "PO 결정 필요"·"한쪽 제안만 있음"·"미정" 인 쟁점은 0.10~0.30 이었습니다. 새 판정은 8곳 가운데 5곳에서 열었고(대립 시나리오 2곳 포함), 쟁점이 모두 미정·외부 확인뿐인 3곳에서는 열지 않았습니다. 당사자도 그 쟁점에 이름이 적힌 두 사람을 골랐습니다(예: coder 0.92·critic 0.81·architect 0.10). DeepSeek 가 연 6곳의 쟁점은 모두 "미정"·"미규정"·"한쪽 제안만 있음" 꼴이었습니다(쟁점별 0.13~0.38). 생성형 판정 경로는 이번에 바꾸지 않았습니다.

판정 비용은 열지 않는 경계에서 지금과 같은 한 번, 여는 경계에서 한 번 더(약 0.3초)입니다.

## 결과 (Consequences)

**이점**

- 사용자가 복잡한 토론 그래프를 매번 수작업으로 설계하지 않아도 태스크의 성격에 최적화된 동적 워크플로를 자동으로 확보할 수 있습니다.
- 생성된 그래프의 판단 근거와 엣지 구성이 UI 피드와 로스터 패널에 시각적으로 투명하게 공개됩니다.
- 두 전문가 간의 기술 충돌을 전체 토론의 라운드 낭비 없이 서브 토론을 통해 집중적으로 해결하고 핵심 결론만 메인 토론에 반영할 수 있습니다.
- 옵션을 끈 기존 세션은 기존 동작과 100% 동일성을 보장합니다.

**비용 및 트레이드오프**

- 그래프 생성 및 서브 토론 판정을 위해 오케스트레이터의 LLM 호출이 턴당 1~3회 추가될 수 있습니다.
- 서브 토론 발언은 메인 컨텍스트에서 격리되므로 전문가 에이전트가 서브 토론 도중 언급했던 세부 부가설명을 본 토론에서 다시 상기하려면 결정 장부 요약에 의존해야 합니다.
