# ADR-016. 작업 공간마다 MCP 런타임을 따로 띄운다

> [ADR 목록](README.md) · 이전: [ADR-015](ADR-015-reasoning-out-of-prompts.md) · 다음: [ADR-017](ADR-017-never-lose-a-write.md)

## 상태 (Status)

채택됨 · 2026-09-09 (v0.6.0) · [ADR-009](ADR-009-refuse-cross-workspace-debates.md)를 대체 · 관련: [ADR-005](ADR-005-long-lived-mcp-sessions.md), [ADR-010](ADR-010-host-defined-tool-scope.md)

## 맥락 (Context)

- 애플리케이션 전체에 MCP 매니저가 단 하나만 존재했고, 외부 MCP 서버는 자신이 접근할 루트 디렉터리를 프로세스 기동 시점에 고정으로 주입받았습니다. 이로 인해 작업 공간 디렉터리가 서로 다른 두 토론 세션을 동시에 실행할 수 없었고, 두 번째 토론은 즉시 거절되었습니다 ([ADR-009](ADR-009-refuse-cross-workspace-debates.md)). 데이터 오염을 막기 위한 정직한 결정이었으나, 여러 대화 세션을 동시에 운용하는 다중 작업이 원천 차단되었습니다.
- "대화마다 MCP 및 Node 런타임을 격리한다"는 요구사항은 자칫 Node.js나 Python 실행 환경을 물리적으로 여러 벌 중복 설치하라는 뜻으로 오해되기 쉽습니다. 그러나 대화 세션 간에 실제로 교차 누출되던 위험 요소는 정적 실행 파일 바이너리가 아니라 **프로세스의 동적 상태**(메모리 캐시, 프로세스 작업 디렉터리, 임시 파일 폴더, 허용된 루트 디렉터리, 지식 그래프 파일 위치, 파이썬 커널 상태)였습니다.
- 복수의 MCP 매니저 인스턴스를 동시에 구동하려면, 먼저 매니저들이 상호 간의 상태를 침범하거나 덮어쓰지 않도록 전역 오염 요소를 완전히 제거해야 했습니다. 당시 코드베이스에는 두 군데의 치명적인 전역 상태 의존성이 존재했습니다.
  - 특정 작업 공간 경로를 서버 설정에 반영하는 함수가, 자식 프로세스에 환경변수를 전달하기 위해 **파이썬 메인 프로세스의 전역 `os.environ`을 직접 수정하고 있었습니다.**
  - MCP 서버가 호스트에게 허용된 루트 폴더 목록을 질의할 때 응답하는 전역 콜백 함수가 바로 그 전역 환경변수 값을 읽고 있었습니다.

## 결정 (Decision)

**작업 공간 디렉터리마다 독립된 MCP 매니저를 동적으로 할당 및 관리하는 런타임 풀(Runtime Pool)**을 구축하도록 합니다.

- 런타임 인스턴스를 식별하고 격리하는 핵심 키는 대화 세션 ID가 아니라 **작업 공간 디렉터리 경로**입니다. 동일한 작업 폴더를 사용하는 대화 세션들은 동일한 도구 서버 묶음을 안전하게 공유합니다 (세션 간의 논리적 데이터 격리는 메타데이터 스코프 주입이 전담합니다, [ADR-010](ADR-010-host-defined-tool-scope.md)). 작업 폴더가 상이할 경우에만 독립된 전용 서버 프로세스 묶음이 별도로 기동됩니다.
- 런타임의 참조 카운트는 대화 세션 ID의 **집합(Set)** 형태로 관리합니다. 동일한 대화 세션이 토론 도중 런타임을 중복 요청하더라도 참조 카운트는 1로 안정적으로 유지됩니다.
- 각 토론 턴은 시작 시점에 풀에서 런타임을 대여하고, 턴의 종료 방식(정상 완료, 사용자 중지, 취소, 예외 발생)에 관계없이 반드시 런타임을 풀에 안전하게 반납합니다.
- 반납된 런타임 프로세스 묶음은 즉시 종료하지 않고 유휴 만료 시간(기본 300초) 동안 메모리에 살려 둡니다. 동일 작업 공간에서 연속하여 실행되는 후속 턴들이 프로세스 기동 지연을 다시 겪지 않도록 하기 위함입니다.
- 풀이 동시에 유지할 수 있는 런타임 프로세스 묶음의 총수에 엄격한 상한(기본 4개)을 둡니다. 이는 동시 토론 세션 수의 인위적 제한이 아니라, 호스트 서버 머신의 메모리 예산을 보호하기 위한 자원 상한선입니다. 신규 자리가 필요한 경우 만료된 유휴 묶음, 가장 오래 유휴 상태였던 묶음 순으로 자원을 자동 회수합니다. **현재 활발히 토론 중인 세션이 점유하고 있는 활성 런타임은 결코 강제 회수하지 않습니다.** 만약 회수 가능한 유휴 런타임이 전혀 없다면, 현재 어떤 세션들이 자원을 점유하고 있는지 진단 정보를 안내하며 신규 실행을 정직하게 거절합니다.
- 각 런타임 묶음은 자신만의 격리된 샌드박스 환경변수를 주입받아 프로세스를 띄웁니다. 허용된 작업 루트 디렉터리, 작업 공간 내부의 전용 임시 디렉터리, 독립된 npm 캐시 디렉터리, 그리고 전체 커널 허용 예산을 런타임 수로 균등 분할한 상한값을 각각 주입합니다.
- 운영체제 사용자 홈 디렉터리(`USERPROFILE`, `HOME`)는 **임의로 격리하거나 변경하지 않습니다.** Git 전역 설정 파일과 파이썬 사용자 사이트 패키지가 해당 홈 디렉터리에 위치하므로, 이를 인위적으로 격리할 경우 시스템이 격리되는 것이 아니라 정상적인 개발 환경 자체가 고장 나기 때문입니다.
- 실행 바이너리와 사전 설치된 Node/Python 패키지 파일은 모든 런타임이 안전하게 공유합니다. 런타임 실행 중에는 오직 읽기 전용(Read-only)으로만 참조되므로 교차 오염이 발생하지 않습니다.

이를 위해 선행적으로 전역 상태를 완전히 제거하도록 합니다.

- 작업 공간 경로 주입 시 프로세스 전역 `os.environ`을 변조하지 않고, 환경변수 템플릿 치환기에 명시적 오버라이드 딕셔너리를 전달하여 각 자식 프로세스의 `subprocess` 환경에만 격리 주입합니다.
- 클라이언트 루트 폴더 질의 콜백을 각 MCP 세션 연결 인스턴스에 클로저 형태로 독립 바인딩합니다.
- 작업 공간 사전 준비(Git 저장소 초기화 등)는 메인 비동기 루프를 차단하지 않도록 별도 워커 스레드에서 수행하며, 경로별 파일 잠금(Lock)을 획득하여 동일 폴더에 대한 동시 초기화 충돌을 방지합니다.
- 개별 매니저의 기동, 종료, 재연결 작업이 타 매니저의 활성 연결 레지스트리를 훼손하지 않도록 수명 주기 전용 비동기 락을 도입합니다.

## 결과 (Consequences)

**좋아지는 점**

- 서로 다른 프로젝트 디렉터리를 사용하는 복수의 토론 세션을 동일 서버에서 안전하게 동시 병렬 실행할 수 있게 되었습니다. 특정 대화를 다른 세션과 완전히 물리적으로 격리하고 싶다면 해당 대화에 전용 작업 공간 폴더를 할당하기만 하면 됩니다.
- 기존의 작업 공간 충돌 거절 정책은 아키텍처에 맞게 진화하여 계승되었습니다. "두 작업 공간을 동시에 열 수 없다"는 물리적 한계에서 "현재 호스트에 추가 런타임을 띄울 메모리 예산이 부족하다"는 자원 관리 원칙으로 전환되었습니다. 타 세션의 디렉터리를 조용히 침범하느니 명시적으로 실행을 거절한다는 데이터 정직성 대원칙은 변함없이 수호되었습니다.

**치르는 비용**

- 활성 작업 공간 수에 비례하여 시스템 프로세스 수가 증가합니다. 런타임 풀 상한을 올리는 것은 시스템 규모 확장에 따라 정당한 조치이나, 상한을 1 늘릴 때마다 단순 스레드가 아니라 4~5개의 무거운 외부 프로세스 묶음이 추가된다는 점을 상시 고려해야 합니다.
- 도구 서버의 기동 시점이 메인 애플리케이션 기동 시점에서 "해당 작업 공간의 첫 번째 토론 시작 시점"으로 지연(Lazy)되었습니다. 이로 인해 화면의 서버 상태 칩이 지연 기동을 즉시 반영하지 못하여, 실제로는 2~3초 만에 정상 기동되었음에도 턴이 완료될 때까지 "미기동" 상태로 오표시되던 결함이 발생했습니다 (v0.6.1.1에서 수정). 아직 전용 런타임이 생성되지 않은 세션에 **기본 작업 공간의 런타임 상태**를 임의로 끌어와 잘못 표시하던 버그 역시 함께 수정했습니다.
- MCP 도구 서버의 원천 설정은 시스템 전역 설정 파일(`conf.json`)이 단일 정본입니다. 관리자가 UI 화면에서 서버 설정을 수정할 경우 **현재 활성화되어 있는 모든 런타임 묶음을 즉시 재기동**해야 하므로, 진행 중인 토론이 단 하나라도 존재한다면 설정 수정을 안전하게 차단합니다.

**도중에 발견한 결함**

전역 상태를 걷어내는 리팩터링 과정에서 기존에 잠재되어 있던 Windows 경로 처리 결함이 수면 위로 드러났습니다. Windows의 `os.path.realpath`가 확장 길이 경로(`\\?\C:\...`)를 반환할 경우, 표준 URI 변환기가 이를 비정상적인 `file://?/C:/...` 포맷으로 변환하여 MCP 파일 시스템 서버가 잘못된 URL이라며 기동을 거부하는 현상이 있었습니다. 이로 인해 파일 시스템 서버가 허용 디렉터리가 하나도 바인딩되지 않은 빈 상태로 기동되었고, 시스템에는 사소한 로그 한 줄만 남았었습니다. 이에 URI 변환 직전에 `\\?\` 접두사를 안전하게 제거하도록 정규화 로직을 보완했습니다.

**교훈**

동일한 도메인 컴포넌트를 시스템 내에서 다중 인스턴스로 복제 운용하려면, 먼저 해당 컴포넌트 내부와 의존 라이브러리에 **숨겨진 전역 상태(Global State)가 존재하는지**부터 철저히 검증해야 합니다. 본 작업 공수의 절반 이상은 풀링 알고리즘 자체를 작성하는 데 든 것이 아니라, 코드베이스 전반에 암묵적으로 퍼져 있던 전역 상태를 완전히 제거하는 데 소요되었습니다.
