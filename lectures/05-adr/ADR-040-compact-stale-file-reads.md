# ADR-040. 컨텍스트 한도 도달 시 이전 도구 호출의 대용량 파일 읽기 결과를 스텁(Stub)으로 압축한다

> [ADR 목록](README.md) · 이전: [ADR-039](ADR-039-lazy-tool-schemas.md)

## 상태 (Status)

채택됨 · 2026-10-31 · 관련: [ADR-014](ADR-014-tool-failure-is-observation.md), [ADR-020](ADR-020-conversation-memory.md), [ADR-025](ADR-025-resume-speeches-by-tool-step.md), [ADR-039](ADR-039-lazy-tool-schemas.md)

## 맥락 (Context)

- 타 발언자의 지난 코드 블록은 1줄 참조로 요약되지만(`reference_code_blocks`), 단일 발언의 도구 루프 내부에는 동일한 압축 메커니즘이 없었습니다. 대용량 파일을 연속해서 읽을 경우 수만 자에 달하는 `role: "tool"` 실행 결과가 발언이 종료될 때까지 매 루프마다 계속 재전송되었습니다.
- 컨텍스트 윈도우 한도를 초과하면 `fit_tool_loop_context`가 가장 오래된 턴 덩어리부터 강제로 삭제합니다. 이 경우 도구 결과뿐만 아니라 해당 호출을 수행한 모델의 사고 텍스트까지 함께 유실되어 "앞선 기록 N건 생략" 안내문만 남게 되며, 사용자에게 컨텍스트 창 확장을 승인 요청하는 팝업이 발생했습니다.
- 그러나 파일 읽기 결과는 파일 시스템에 실물이 존재하므로 언제든 동일하게 다시 조회할 수 있는 가역적 데이터입니다. 컨텍스트를 비워야 할 때 가장 먼저 정리할 수 있는 대상임에도 가장 많은 용량을 차지하고 있었습니다.
- 대화 메시지의 앞부분을 수정하면 LLM 공급자의 프롬프트 접두사 캐시가 무효화되므로([ADR-020](ADR-020-conversation-memory.md)), 매 턴마다 불필요하게 메시지를 수정하지 않는 정교한 압축 전략이 필요했습니다.

## 결정 (Decision)

### 1. 재생성 가능한 파일 읽기 결과에 한해서만 압축을 수행한다

`read_text_file`, `read_file`, `read_multiple_files` 등 순수 파일 읽기 도구에 한정하여 압축을 적용합니다. 셸 명령 실행, 웹 검색, `git_diff` 등은 결과가 가변적이거나 사이드 이펙트가 있고 실행 자체가 고유한 관찰 기록이므로 원문을 보존합니다. 또한 도구 호출 인자 자체(`write_file`의 대용량 내용 등)는 호출-응답 쌍의 정합성을 위해 일체 변경하지 않습니다.

### 2. LLM에 전달되는 컨텍스트 메시지만 교체하고 원본 로그는 보존한다

UI 도구 카드와 데이터베이스의 도구 실행 기록(`tool_logs`)에는 원문 결과를 그대로 보존합니다. 모델에게 전달되는 발언 초안 메시지(`messages`)에서만 결과 텍스트를 요약 스텁으로 교체하므로, 중단된 발언을 재개하더라도 모델이 보던 컨텍스트 시점과 정확히 일치합니다.

### 3. 경과 라운드(Age) 기반의 안정적 상태 추적

도구 결과가 생성된 이후 경과한 도구 호출 턴 수를 기준으로 나이(Age)를 계산합니다. 가장 최근 실행 결과는 0입니다. 별도의 인메모리 플래그 없이 메시지 구조 자체에서 판별하므로 세션 재개 시에도 결정론적으로 동작합니다.

### 4. 스텁에는 대상 파일 정보와 재조회 안내를 명확히 기록한다

```text
[관측 압축] 앞서 `filesystem__read_text_file` 로 읽은 결과입니다 (인자: {"path": "export_mermaid.py"}, 전체 1,618줄 65,248자). 도구는 원문 전체를 돌려줬고 당신은 그때 전체를 봤습니다. 컨텍스트를 아끼려고 앱이 나중에 앞뒤 일부만 남기고 줄였습니다. 그때 본문에 적어 둔 값은 실제로 본 것이니 그대로 쓰고, 확인하려고 다시 읽지 마세요. 적어 두지 않은 내용이 필요하거나 이 파일을 고치려면 같은 도구로 다시 읽으세요 — 원문 전체를 다시 받습니다. 생략된 내용을 지어내지 마세요. 필요한 범위만 읽을 수 있으면 그렇게 하세요.
--- 앞 12줄
…
--- 끝 3줄
…
```

호출 인자를 정확히 명시하여 모델이 필요 시 동일한 도구 호출을 즉시 재구성할 수 있도록 돕습니다. 긴 행도 160자로 제한하여 스텁 메시지의 크기를 약 1,000자 내외로 압축합니다.

"도구는 원문 전체를 돌려줬고, 앱이 나중에 줄였다" 는 2026-11-11 에 더했습니다. 처음 문구("컨텍스트를 아끼려고 앞뒤 일부만 남겼습니다")로 실제 DeepSeek 시험을 돌리니, 모델이 "`read_text_file` 이 앞 12줄·끝 3줄만 돌려준다" 고 결론 내리고 "다시 읽어도 같은 압축 반환이 반복될 것" 이라며 줄어든 세 파일을 다시 읽지 않았습니다. 누가 줄였는지가 빠져 있어 도구의 동작으로 읽힌 것입니다. "그때 본문에 적어 둔 값은 실제로 본 것이니 그대로 쓰라" 도 같은 날 더했습니다. 아래 7항의 고지로 모델이 값을 본문에 적으며 8개를 다 읽게 되자, 이번에는 스텁에 그 줄이 안 보인다며 제가 적은 값을 "관측이 아니라 오기" 로 철회하고 같은 파일을 18번 다시 읽다가 줄어든 스텁이 쌓여 창을 넘겼습니다.

### 5. 컨텍스트 사용량이 임계치에 도달했을 때 일괄 압축하여 프롬프트 캐시 보호

단순히 시간 경과만으로 매 턴 압축하면 매번 앞단 메시지가 변경되어 프롬프트 캐시가 무효화됩니다. 따라서 컨텍스트 예산 사용량이 임계치(`min_usage`, 기본값 0.5)를 초과했을 때만 압축을 발동하며, 일정 라운드(`stale_rounds`, 기본값 3) 이상 경과하고 크기가 기준(`min_chars`, 기본값 8,000자) 이상인 도구 결과들을 일괄 압축합니다. 이후 한동안 앞단 메시지가 불변으로 유지되므로 프롬프트 캐시 효율을 극대화할 수 있습니다.

### 6. 컨텍스트 초과 강제 삭제 단계 이전에 선제적 압축 수행

`_fit_loop_context` 최우선 단계에서 압축을 실행합니다. 압축을 통해 예산 내로 진입하면 사용자 승인 팝업 없이 작업을 계속 진행하며, 기존 대화 덩어리가 강제 삭제되는 것을 방지합니다.

### 7. 사용률 고지가 압축으로 되찾을 몫을 함께 알린다 (2026-11-11 추가)

컨텍스트 사용률 고지(`context_pressure_notice`, 50·70·85·95% 띠)는 처음에 "남은 여유 약 N 토큰" 만 알렸습니다. 실제 DeepSeek 시험(창 24,000, 약 1만 1천 자 파일 8개를 차례로 읽기)에서 모델이 62% 고지를 보고 "남은 7,440 토큰으로는 파일 4개(약 12,000 토큰)를 못 읽는다" 며 4개만 읽고 멈췄고, 다른 실행은 70% 고지의 "파일 전체 읽기는 자제하라" 를 따라 6개에서 멈췄습니다. 실제로는 자리가 모자라면 지난 읽기가 스텁으로 줄어들어 8개를 다 읽을 수 있었습니다.

이제 띠를 넘을 때 예산을 넘겼을 때와 같은 방식(가장 최근 판만 남기고 줄이기)으로 되찾을 토큰을 세어(`tool_compaction.reclaimable_tokens`), 1,000 토큰 이상이면 고지에 함께 적습니다. 고지는 이런 모양입니다 (숫자는 예시).

```text
[컨텍스트] 이번 발언의 맥락이 한도의 **62%** 를 쓰고 있습니다 (남은 여유 약 7,440 토큰, 지난 파일 읽기를 줄이면 약 15,900 토큰). 자리가 모자라면 앱이 지난 파일 읽기 결과를 앞뒤 일부만 남기고 줄입니다 — 같은 도구로 다시 읽으면 원문을 다시 받습니다. 그러니 남은 여유만 보고 일찍 멈추지 말고, 읽은 파일에서 필요한 값은 다음 도구를 부를 때 본문에 한 줄로 적어 두세요. 요점 위주로 쓰고, …
```

- "필요한 값은 본문에 적어 두라" 는 줄어든 읽기의 가운데를 잃지 않게 하려는 것입니다. 본문(assistant 메시지)은 압축 대상이 아닙니다.
- 85% 띠는 "곧 지난 파일 읽기부터 줄이고, 그래도 모자라면 앞선 발언과 도구 관측을 생략한다" 로, 95% 띠는 "꼭 필요한 호출이 아니면 지금 결론을 쓰라" 로 바꿉니다. 되찾을 몫이 없으면 문구는 예전 그대로입니다.
- 세는 것은 고지할 띠를 넘은 판에서만 합니다(한 발언에 많아야 네 번). 토큰을 세는 동안 이벤트 루프가 멈추기 때문입니다.

## 결과 (Consequences)

실제 filesystem MCP 서버로 `app/` 내 가장 큰 파일 10개(36~68KB)를 순차적으로 읽는 시나리오 측정 결과입니다 (`openai/gpt-4o` 토크나이저, `max_tokens` 4,096, 총 11회 API 호출).

| 컨텍스트 윈도우 | 압축 적용 여부 | 누적 입력 토큰 총합 | 단일 최대 요청 토큰 | 강제 삭제된 턴 수 |
| :--- | :--- | ---: | ---: | ---: |
| 128,000 | 미적용 (OFF) | 715,638 | 114,471 | 1개 |
| 128,000 | **적용 (ON)** | **408,215** | **61,890** | **0개 (유실 없음)** |

**이점**

- 반복적인 대용량 파일 읽기 시 누적 입력 토큰을 약 43% 절감했습니다.
- 과거 대화 컨텍스트가 통째로 삭제되는 현상을 방지하여 복잡한 리팩터링 작업 시에도 모델의 추론 일관성을 유지합니다.
- 임계치 기반 일괄 처리로 LLM 프롬프트 접두사 캐시 적중률을 안정적으로 보존합니다.

## 실측 (2026-11-11 추가)

위 표의 호출 순서는 대본이라, 줄인 뒤에 실제 모델이 같은 파일을 얼마나 다시 읽는지는 알 수 없었습니다. 지금은 발언과 턴의 사용량 기록에 `compacted_reads`(스텁으로 줄인 읽기 결과 수)와 `rereads_after_compaction`(줄인 읽기와 같은 도구·같은 인자로 다시 읽은 횟수, `tool_compaction.reread_of_compacted`)이 남습니다. 다시 읽기는 막지 않고 셉니다.

실제 확인(2026-11-11, `deepseek-v4-flash`, 창 24,000 토큰, 약 11,600자 파일 8개를 차례로 읽는 한 턴, 한 번 실행): 읽기 결과 9건을 줄였고 그 뒤 같은 파일을 3번 다시 읽었습니다 (읽기 호출 11회 가운데). 창을 일부러 작게 잡은 시나리오의 한 번 실행이라 경향으로 읽을 수는 없습니다.

둘째 값이 첫째 값에 견줘 크면 `stale_rounds` 나 `min_usage` 를 올릴 때입니다. Bench 보고서의 `도구 컨텍스트` 열과 토론 화면의 토큰·시간 분석 창에서 봅니다.
