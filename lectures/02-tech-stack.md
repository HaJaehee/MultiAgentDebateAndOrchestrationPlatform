# 2강. 기술 스택

> 이전: [1강. 여러 LLM이 토론하는 시스템](01-introduction.md) · 다음: [3강. 아키텍처](03-architecture/README.md)

기술 스택 설명은 흔히 "무엇을 썼다"의 목록으로 끝납니다. 이번 강에서는 각 기술이 어떤 제약에서
골라졌고, 그 선택이 나중에 어떤 비용으로 돌아왔는지까지 봅니다. 좋은 선택이란 비용이 없는
선택이 아니라, 비용을 알고 치르는 선택입니다.

---

## 1. 스택 한눈에 보기

| 층 | 기술 | 이 시스템에서 맡은 일 |
| :--- | :--- | :--- |
| 런타임 | Python 3.11+ (asyncio) | 모든 코드가 하나의 이벤트 루프 위에서 돕니다 |
| 웹 서버 | FastAPI + Uvicorn | HTTP 엔드포인트, 앱의 기동·종료 수명 관리 |
| 화면 | NiceGUI (내부적으로 Vue + Quasar) | 파이썬 코드로 반응형 화면을 만들고 WebSocket으로 실시간 갱신 |

| 저장소 | SQLite + SQLAlchemy 2.0(비동기) + aiosqlite | 대화, 발언, 도구 기록, 산출물, 구성 스냅샷 |
| 설정 | Pydantic v2 + 표준 라이브러리 `json` | 설정 검증, 환경변수 치환, 화면에서 고친 값 되쓰기 |
| 도구 서버 | Node.js(공식 서버 3종), Python(git, 샌드박스) | 파일, 지식 그래프, 버전 관리, 코드 실행 |
| 화면 보조 | Mermaid(NiceGUI 동봉), Vue Flow(앱에 동봉) | 다이어그램 렌더링, 그래프 편집기 |
| 테스트 | pytest + pytest-asyncio | 가짜 LLM을 테스트 쪽에 두고 비동기 흐름 검증 |

## 2. 제약이 스택을 고른다

기술을 고르기 전에 이 프로젝트가 안고 있던 제약을 먼저 정리해 두겠습니다. 뒤의 모든 선택이 여기서
나옵니다.

1. **파이썬으로 끝까지.** 명세 단계부터 파이썬 선호가 분명했습니다. 프런트엔드를 따로 두면 언어가
   둘이 되고 빌드 체계도 둘이 됩니다.
2. **폐쇄망 반입.** 인터넷이 없는 망에 설치해야 합니다. 반입할 파일 하나하나가 검토 대상이므로
   의존성이 적을수록, 빌드 산출물이 단순할수록 좋습니다.
3. **공급자가 제각각인 LLM.** 클라우드 API, 사내 게이트웨이, 로컬 추론 서버(vLLM, Ollama)를 에이전트마다
   다르게 섞어 씁니다.
4. **도구는 늘어난다.** 오늘은 파일과 코드 실행이지만 내일은 사내 문서 검색일 수 있습니다.
5. **운영하는 사람이 적다.** 서버 PC 한 대에서 한 사람이 띄우고 관리합니다. 데이터베이스 서버나
   메시지 큐를 따로 운영할 여력이 없습니다.

## 3. 층별로 보기

### 3.1 Python과 asyncio

LLM 호출은 느립니다. 긴 발언 하나가 몇 분씩 걸리고, 그동안 프로그램은 거의 기다리기만 합니다.
이런 I/O 대기가 대부분인 작업에는 스레드보다 이벤트 루프가 잘 맞습니다. 토론 여러 개, 화면
여러 개, 도구 서버 여러 개와의 통신이 한 루프 위에서 번갈아 진행됩니다.

대가도 있습니다. 한 루프를 모두가 나눠 쓰므로, 누군가 CPU를 오래 붙잡으면 모두가 멈춥니다.
3.3절의 스트리밍 사례가 바로 그런 경우입니다. 또 asyncio의 **취소(cancellation)** 는 예외의 형태로
전파되기 때문에, 예외를 넓게 잡는 코드가 취소까지 삼켜 버리는 사고가 생기기 쉽습니다. 이 문제는
4강의 [실패를 설계하기](04-core-techniques/07-failure-design.md)에서 자세히 다룹니다.

### 3.2 FastAPI와 Uvicorn

Uvicorn은 ASGI 서버이고, FastAPI는 그 위에서 도는 웹 프레임워크입니다. MADO에서 FastAPI가 하는 일은
생각보다 적습니다.

- **수명 관리(lifespan)**: 앱이 뜰 때 설정을 읽고, DB를 준비하고, MCP 서버를 예열합니다. 내릴 때는
  돌고 있는 토론을 취소하고 도구 서버 프로세스를 정리합니다.
- **보조 API**: 상태 확인, 에이전트 목록, MCP 연결 상태, 세션별 페르소나 조회 같은 몇 개의 엔드포인트.
- **접근 제어 계층을 끼울 자리**: 원격 접속 토큰 검사는 ASGI 미들웨어로 가장 바깥에 둡니다.

화면은 FastAPI가 아니라 NiceGUI가 그립니다. 둘은 같은 앱 객체에 얹혀 같은 포트, 같은 이벤트
루프에서 돕니다.

### 3.3 NiceGUI

NiceGUI는 파이썬 코드로 화면 요소를 만들면, 서버가 화면 상태를 들고 있다가 브라우저와 WebSocket으로
동기화하는 방식의 UI 프레임워크입니다. 브라우저 쪽은 Vue와 Quasar로 렌더링되지만 개발자는
자바스크립트를 거의 쓰지 않습니다.

**얻은 것**

- 빌드 단계가 없습니다. Node 툴체인, 번들러, 별도 개발 서버가 필요 없고, 소스를 반입하면 갱신이
  끝납니다. 폐쇄망 제약에 가장 크게 기여한 선택입니다.
- 서버의 파이썬 객체(에이전트 풀, MCP 연결 상태)를 화면 코드가 직접 참조합니다. 직렬화 경계와
  API 계약을 따로 관리하지 않아도 됩니다.
- 토론 중에 발생하는 이벤트를 화면에 밀어 넣는 코드가 그냥 파이썬 함수입니다.

**치른 비용**

서버가 화면 상태를 들고 있다는 것은, 화면을 다시 그리는 연산도 서버 CPU를 쓴다는 뜻입니다.
v0.7.2에서 이 비용이 크게 드러났습니다. 스트리밍 중에 토큰이 하나 올 때마다 발언 카드 전체의
마크다운을 서버에서 HTML로 다시 변환해 통째로 보냈고, 스크롤 메시지도 토큰마다 따로 나갔습니다.
2만 자짜리 보고서 하나에 서버 CPU 82초가 들었습니다. 서버와 브라우저가 둘 다 포화되자 WebSocket이
끊겼고, NiceGUI는 재접속할 때 조건에 따라 페이지를 새로고침합니다. 사용자 눈에는 "긴 답변이 나오면
화면이 저절로 새로고침된다"로 보였습니다.

해결은 흔한 기법의 조합이었습니다. 토큰 조각은 이어 붙이기만 하고 카드 갱신은 0.25초마다 한 번,
엔진이 보내는 조각 이벤트는 0.1초 단위로 묶고, 재접속 대기 시간을 3초에서 30초로 늘렸습니다.
같은 스트림에서 렌더링 횟수가 2,668회에서 56회로, 브라우저로 가는 메시지가 3,556개에서 173개로
줄었습니다.

교훈은 이렇습니다. 서버 주도 UI 프레임워크에서 "화면을 자주 갱신한다"는 곧 "서버가 자주 일한다"입니다.
갱신 빈도는 사람이 알아챌 수 있는 속도(초당 몇 번)면 충분합니다.

**대안과 비교**

프로젝트 명세에는 NiceGUI, Streamlit, FastHTML이 함께 후보로 올라 있었고, 명세는 "파이썬만으로
Vue/Quasar 기반 SPA를 만들어 단일 Uvicorn 서버로 서빙할 수 있다"는 이유로 NiceGUI를 권했습니다.
아래 표는 그 권고를 이 프로젝트의 제약에 비추어 다시 따져 본 것입니다.

| 대안 | 이 프로젝트의 제약에 비춘 평가 |
| :--- | :--- |
| Streamlit | 상호작용마다 스크립트를 처음부터 다시 실행하는 모델입니다. 몇 분씩 걸리는 토론을 화면과 떼어 돌리고, 새로고침한 화면이 진행 중인 토론에 다시 붙게 하려면 우회가 많이 필요합니다 |
| React/Vue SPA + FastAPI | 가장 유연하지만 언어와 빌드 체계가 둘이 되고, 반입할 빌드 산출물과 의존성이 늘어납니다 |
| FastHTML | 서버가 HTML 조각을 돌려주는 방식이라 가볍습니다. 대신 드래그 정렬, 분할 창, 대화상자 같은 화면 부품을 직접 조립해야 할 몫이 큽니다 |

### 3.4 LiteLLM

에이전트마다 다른 모델을 쓰는 것이 이 시스템의 전제입니다. LiteLLM은 공급자별로 다른 API를
OpenAI 형식의 호출 하나로 덮습니다. 모델을 바꾸는 일이 코드 변경이 아니라 문자열 변경이 됩니다.

```json
"model": "openai/gpt-4o"
"model": "anthropic/claude-3-5-sonnet-20241022"
"model": "ollama_chat/qwen2.5-coder:14b"
```

로컬 모델과 붙일 때 유용한 옵션이 하나 있습니다. 엔드포인트가 모르는 파라미터를 조용히 빼 주는
기능(`drop_params`)입니다. 이게 없으면 `top_p`를 받지 않는 서버 하나 때문에 요청 전체가 400으로
실패합니다.

**추상화가 새는 곳**

LiteLLM이 호출 방법은 통일해 주지만, 공급자마다 다른 **대화 형식 규칙**까지 지워 주지는 못합니다.
MADO가 실제로 부딪힌 것들입니다.

- 토론은 여러 명이 말하는 대화인데, OpenAI 메시지 형식에는 "다른 에이전트"라는 역할이 없습니다.
  남의 발언은 모두 `user`가 되므로 `user` 메시지가 연달아 생깁니다. OpenAI는 받아 주지만 Anthropic,
  Gemini, 일부 호환 서버는 400으로 거절합니다.
- 도구 호출 기록이 들어 있는 대화를 보내면서 도구 정의를 빼면, Anthropic은 거절하고 OpenAI는
  받아 줍니다.
- 게이트웨이가 상류의 400을 자기 500으로 감싸면서 원래 이유를 버리는 경우도 있었습니다.

그래서 MADO는 LiteLLM 앞에 **요청 모양을 정리하는 층**을 따로 둡니다. 연속된 같은 역할 메시지를
합치고, 컨텍스트 창에 맞게 자르고, 도구를 정의하되 호출은 못 하게 하는 식입니다. 추상화
라이브러리를 쓰더라도 공급자 차이를 흡수하는 책임은 결국 우리 쪽에 남는다는 것, 이게 이 절의
요점입니다. 자세한 내용은 [4-2. LLM 연동](04-core-techniques/02-llm-integration.md)에 있습니다.

### 3.5 MCP Python SDK

MCP(Model Context Protocol)는 LLM 애플리케이션과 도구 서버 사이의 통신 규격입니다. JSON-RPC 위에서
"어떤 도구가 있는지 알려 달라(tools/list)", "이 도구를 실행해 달라(tools/call)" 같은 요청을
주고받습니다. 전송 방식은 두 가지입니다.

- **stdio**: 앱이 도구 서버를 자식 프로세스로 띄우고 표준 입출력으로 통신합니다. MADO의 기본 도구
  서버는 모두 이 방식입니다.
- **Streamable HTTP(과거에는 HTTP+SSE)**: 이미 떠 있는 서버에 주소로 붙습니다. 사내 게이트웨이처럼
  띄울 명령 없이 주소만 있는 경우에 씁니다. v0.2에서 추가되었습니다.

MCP를 쓰면 도구가 앱과 다른 프로세스에서 돕니다. 파일 시스템 서버는 허용된 폴더 밖 경로를 스스로
거부하고, 샌드박스의 파이썬 커널이 죽어도 앱은 살아 있습니다. 도구를 추가하는 일은 설정에 실행
명령을 적는 일이 됩니다.

버전은 `mcp>=1.29.0,<2`로 고정했습니다. 2.x에서 서버 쪽 API 하나가 이름이 바뀌었는데(`FastMCP` →
`MCPServer`), 동봉한 샌드박스 서버와 git 서버가 아직 1.x를 요구합니다. 상한 없이 두었다면 새로
만든 번들에 2.x가 깔리고, 샌드박스가 기동하자마자 죽었을 것입니다.

### 3.6 SQLite, SQLAlchemy 2.0, aiosqlite

대화 하나에 기록하는 주체는 사실상 하나(그 대화의 토론 태스크)입니다. 동시 쓰기가 적고, 운영자가
DB 서버를 따로 관리할 여력이 없고, 반입할 때 파일 하나만 옮기면 됩니다. SQLite가 맞는 조건입니다.
비동기 드라이버(aiosqlite)를 써서 DB 대기가 이벤트 루프를 막지 않게 합니다. 접속 주소가 설정값이라
나중에 PostgreSQL로 옮길 때는 드라이버 문자열만 바꾸면 됩니다.

SQLite도 기본값 그대로 쓰면 안 된다는 것을 v0.7.1에서 배웠습니다. 사용자가 자리를 비워 화면이
잠긴 사이, 백신 검사나 백업 프로그램이 DB 파일을 잠깐 열었고, 기본 5초 대기가 끝나자
`database is locked`로 최종 보고서 저장이 실패했습니다. 지금은 연결마다 대기 시간을 30초로 늘리고
WAL 저널 모드를 켭니다. 다만 네트워크 드라이브에서는 WAL이 파일을 깨뜨릴 수 있어서 켜지 않습니다.
이 사례는 [ADR-017](05-adr/ADR-017-never-lose-a-write.md)에서 다시 봅니다.

### 3.7 Pydantic v2와 표준 `json`

설정은 Pydantic 모델로 검증합니다. 필수 항목, 값 범위, 오케스트레이터 존재 여부 같은 규칙이
선언적으로 들어가 있고, 잘못된 설정은 앱이 뜨기 전에 거절됩니다.

설정 파일 형식이 JSON인 이유는 이 앱이 설정을 **쓰기도** 하기 때문입니다. 파이썬 표준 라이브러리에는
TOML을 읽는 모듈은 있어도 쓰는 모듈이 없습니다. TOML 시절에는 화면에서 고친 값을 되쓰는 코드가
줄 단위 문자열 편집이었고, 여러 줄 문자열 안에 있는 `[검토 항목]` 같은 줄을 섹션 헤더로 오인할
위험까지 떠안고 있었습니다. JSON으로 바꾸면서 쓰기가 "딕셔너리를 고치고 통째로 저장"이 되었습니다.
JSON에 없는 주석과 여러 줄 문자열은 규칙으로 보완합니다. 자세한 내용은
[ADR-013](05-adr/ADR-013-json-config.md)과 [4-1. 설정](04-core-techniques/01-configuration.md)에 있습니다.

### 3.8 도구 서버의 런타임: Node.js와 Python

기본 도구 서버는 다섯 가지입니다.

| 서버 | 런타임 | 역할 |
| :--- | :--- | :--- |
| filesystem | Node.js (공식 서버) | 작업 공간 폴더 안의 파일 읽기, 쓰기, 검색 |
| memory | Node.js (공식 서버를 조금 고친 포크) | 대화별 지식 그래프 |
| git | Python | 작업 공간의 변경 이력, diff, 커밋 |
| sandbox | Python (IPython 커널) | 상태가 유지되는 파이썬 코드 실행 |
| sequential-thinking | Node.js (공식 서버) | 단계적 사고 도구. 기본은 꺼 둠 |

공식 Node 서버들은 순수 자바스크립트라 `node.exe` 하나만 있으면 돕니다. npm은 설치 시점에만
필요하고 배포 번들에는 들어가지 않습니다. 반입할 것이 줄어듭니다.

### 3.9 화면 보조 라이브러리

- **Mermaid**: 다이어그램 렌더러. NiceGUI가 동봉한 것을 씁니다. 다이어그램 문법 검사 규칙을 이
  버전의 실제 파서로 하나하나 맞췄기 때문에, NiceGUI 버전 범위를 `>=3.16,<4`로 좁혀 두었습니다.
  NiceGUI를 올리면 Mermaid도 따라 올라가고, 그러면 검사 규칙을 다시 확인해야 합니다.
- **Vue Flow**: 그래프 토론 편집기에 씁니다. 의존성까지 합쳐 하나의 ES 모듈(156KB)로 묶어 앱 안에
  넣었습니다. NiceGUI가 이미 제공하는 Vue만 가져다 쓰므로 CDN 없이 폐쇄망에서도 열립니다.
  라이선스 고지 파일과 재빌드 방법도 함께 둡니다.

### 3.10 테스트: pytest와 가짜 LLM

초기에는 제품 코드 안의 시뮬레이터가 테스트용 LLM 역할도 겸했습니다. 시뮬레이터를 없애면서
([ADR-007](05-adr/ADR-007-no-simulated-answers.md)) 테스트 대역을 테스트 폴더로 옮겼습니다. 제품
코드에는 가짜가 없고, 테스트만 가짜를 씁니다. 이 경계가 흐려지면 "테스트에서는 되는데 실제로는
지어낸 답이 섞이는" 상황이 다시 생깁니다.

한 가지 더. DB 엔진은 프로세스 전체에서 하나만 만드는 싱글턴이라, 어떤 테스트가 먼저 기본 경로로
엔진을 만들면 개발자의 실제 DB 파일에 테스트 대화가 쌓였습니다. 지금은 테스트가 시작될 때마다
메모리 DB로 엔진을 먼저 만들어 둡니다. 싱글턴은 편하지만 "누가 먼저 만들었는가"에 결과가 달라지는
숨은 의존을 만든다는 점, 기억해 둘 만합니다.

## 4. 버전 고정 정책

`requirements.txt`의 대부분은 하한만 있습니다. 상한을 건 곳은 두 군데뿐입니다.

| 패키지 | 범위 | 근거 |
| :--- | :--- | :--- |
| `mcp` | `>=1.29.0,<2` | 2.x에서 서버 API 이름이 바뀌어 동봉 서버가 기동 실패 |
| `nicegui` | `>=3.16,<4` | 동봉 Mermaid 버전을 기준으로 다이어그램 검사 규칙을 맞춰 둠 |

상한은 구체적인 근거가 있을 때만 겁니다. 근거 없는 상한은 보안 패치를 막고, 근거 있는 상한은
그 근거를 주석으로 남겨 다음 사람이 풀 수 있게 합니다. 두 줄 모두 `requirements.txt`에 이유가
주석으로 적혀 있습니다.

## 5. 선택을 평가해 보기

| 선택 | 얻은 것 | 치른 비용 |
| :--- | :--- | :--- |
| 파이썬 단일 프로세스 (FastAPI + NiceGUI) | 빌드 없음, 반입 단순, 직렬화 경계 없음 | 화면 연산이 서버 CPU를 씀. 열린 화면마다 상태가 서버 메모리에 있음 |
| LiteLLM | 공급자 교체가 문자열 변경 | 공급자별 대화 규칙 차이는 직접 흡수해야 함 |
| MCP | 도구 격리, 규격화된 확장 | 프로세스 관리, 전송 계층 오류 처리, 버전 호환 |
| SQLite | 운영 부담 없음, 파일 하나로 이동 | Windows 파일 잠금에 약함. 설정과 재시도로 보완 |
| JSON 설정 | 표준 라이브러리로 읽고 쓰기 | 주석, 여러 줄 문자열을 규칙으로 보완 |

## 정리

- 기술 선택은 파이썬 일원화, 폐쇄망 반입, 제각각인 LLM 공급자, 도구 확장성, 적은 운영 인력이라는
  제약에서 나왔습니다.
- 모든 선택에는 비용이 따랐고, 그 비용은 대부분 실제 장애로 드러난 뒤에 보완되었습니다.
- 추상화 라이브러리(LiteLLM, MCP SDK)를 써도 경계에서 새는 차이는 우리가 책임져야 합니다.
- 버전 상한은 근거가 있을 때만 걸고, 근거를 함께 적어 둡니다.
