# 2강. 기술 스택

> 이전: [1강. 여러 LLM이 토론하는 시스템](01-introduction.md) · 다음: [3강. 아키텍처](03-architecture/README.md)

기술 스택에 대한 설명은 흔히 단순히 "어떤 기술을 채택했다"는 목록의 나열로 끝나기 쉽습니다. 이번 강의에서는 각 기술이 어떠한 현실적 제약 조건 속에서 선택되었으며, 그 선택이 향후 시스템 운영에서 어떠한 트레이드오프(비용)를 유발했는지까지 깊이 있게 살펴봅니다. 훌륭한 엔지니어링 선택이란 부작용이나 비용이 전혀 없는 이상적인 선택이 아니라, 수반되는 비용을 명확히 인지하고 감당 가능한 수준에서 내리는 선택입니다.

## 2. 기술 선정을 이끈 5대 제약 조건

구체적인 기술을 선정하기에 앞서, 본 프로젝트가 직면하고 있던 핵심 제약 조건들을 먼저 정리하겠습니다. 이후에 나오는 모든 기술적 의사결정은 바로 이 제약 조건들로부터 출발했습니다.

1. **Python 단일 생태계 고수**: 프로젝트 기획 단계부터 Python 중심의 구현 요구가 확고했습니다. 프런트엔드를 별도 기술 스택으로 분리할 경우 개발 언어와 빌드 파이프라인이 이원화되는 운영 부담이 컸습니다.
2. **폐쇄망(Air-gapped) 환경 반입**: 외부 인터넷 연결이 완전히 차단된 격리망 환경에 설치되어야 했습니다. 반입되는 모든 파일과 패키지가 보안 검토 대상이므로, 외부 의존성을 최소화하고 빌드 산출물을 단순하게 유지하는 것이 필수적이었습니다.
3. **다양한 LLM 공급자 혼용**: 상용 클라우드 API(OpenAI, Anthropic, Google)뿐만 아니라 사내 인공지능 게이트웨이, 온프레미스 GPU 추론 엔진(vLLM, Ollama 등)을 에이전트별로 자유롭게 조합할 수 있어야 했습니다.
4. **도구 확장의 유연성**: 현재는 파일 시스템 및 코드 실행 도구가 중심이지만, 향후 사내 문서 검색(RAG)이나 지식 그래프 등 새로운 도구를 유연하게 확장할 수 있어야 했습니다.
5. **최소화된 운영 리소스**: 단 한 대의 서버 머신에서 소규모 인원(사실상 1인)이 손쉽게 배포하고 유지보수할 수 있어야 했습니다. 별도의 데이터베이스 클러스터나 분산 메시지 큐 인프라를 운영할 여력이 없었습니다.

## 3. 계층별 기술 심층 분석

### 3.1 Python과 asyncio

LLM API 호출은 네트워크 I/O 바운드 작업으로 응답 대기 시간이 깁니다. 긴 발언 하나를 생성하는 데 수 분이 소요될 수 있으며, 그동안 애플리케이션은 대부분 응답 수신을 기다리는 상태가 됩니다. 이처럼 I/O 대기가 대부분인 환경에서는 멀티스레드 모델보다 단일 이벤트 루프 기반의 비동기 프로그래밍 모델이 리소스 효율성 측면에서 훨씬 적합합니다. 다수의 토론 세션, 웹 화면과의 WebSocket 통신, 여러 MCP 도구 서버와의 IPC가 단일 이벤트 루프 위에서 매끄럽게 교차 실행됩니다.

물론 이에 따른 대가(Trade-off)도 분명히 존재합니다. 모든 작업이 단일 루프를 공유하므로, 특정 작업이 CPU를 과도하게 점유하면 전체 시스템의 응답성이 일시적으로 마비됩니다. 3.3절에서 다룰 스트리밍 렌더링 병목 사례가 바로 이에 해당합니다.

또한 asyncio의 **작업 취소(Cancellation)** 메커니즘은 예외(`asyncio.CancelledError`)의 형태로 전파됩니다. 따라서 예외를 너무 광범위하게 포괄 처리(`except Exception:`)하는 코드가 존재하면 작업 취소 신호까지 삼켜버려 태스크가 정상 종료되지 않는 장애가 발생할 수 있습니다. 이와 관련된 견고한 예외 격리 설계는 4강의 [실패 설계](04-core-techniques/07-failure-design.md)에서 자세히 다룹니다.

### 3.2 FastAPI와 Uvicorn

Uvicorn은 표준 ASGI 서버이며, FastAPI는 그 위에서 구동되는 고성능 웹 프레임워크입니다. MADO 아키텍처에서 FastAPI가 직접 담당하는 영역은 의도적으로 최소화되어 있습니다.

- **애플리케이션 수명주기 관리 (Lifespan)**: 서버 기동 시 설정 파일을 읽고, 데이터베이스 연결을 초기화하며, MCP 서버들을 예열합니다. 서버 종료 시에는 진행 중인 토론 태스크를 안전하게 취소하고 하위 프로세스들을 정리합니다.
- **보조 REST API 제공**: 시스템 상태 헬스체크, 등록된 에이전트 목록 조회, MCP 연결 상태 모니터링, 세션별 페르소나 조회 등의 경량 엔드포인트를 제공합니다.
- **접근 제어 계층 삽입**: 원격 접속 보안 토큰 검증 로직을 ASGI 미들웨어 계층에 배치하여 최외곽 보안 경계를 형성합니다.

사용자 인터페이스는 FastAPI 템플릿이 아닌 NiceGUI가 담당합니다. 두 프레임워크는 동일한 ASGI 애플리케이션 객체에 통합되어 동일한 포트와 단일 이벤트 루프 내에서 구동됩니다.

### 3.3 NiceGUI

NiceGUI는 순수 Python 코드로 UI 컴포넌트를 선언하면, 서버가 화면 상태를 메모리에 유지하면서 브라우저 클라이언트와 WebSocket을 통해 양방향으로 동기화하는 서버 주도형(Server-driven) UI 프레임워크입니다. 브라우저 렌더링 계층은 내부적으로 Vue.js와 Quasar 기반으로 동작하지만, 개발자가 JavaScript를 직접 작성할 필요는 거의 없습니다.

**선택을 통해 얻은 이점**

- **프런트엔드 빌드 파이프라인의 제거**: Node.js 툴체인, 모듈 번들러, 별도의 프런트엔드 개발 서버가 전혀 필요하지 않으며, Python 소스 코드만 반입하면 즉시 기능 배포가 완료됩니다. 이는 폐쇄망 반입 제약을 충족하는 데 가장 결정적인 기여를 했습니다.
- **백엔드 인메모리 객체 직접 접근**: 에이전트 풀, 활성 토론 세션, MCP 연결 객체 등 서버 측 Python 객체를 화면 코드가 직접 참조할 수 있습니다. 불필요한 직렬화 계층과 복잡한 REST API 규격을 별도로 설계·관리하지 않아도 됩니다.
- **직관적인 이벤트 처리**: 토론 실행 중 발생하는 실시간 로그나 토큰 스트리밍 이벤트를 평범한 Python 콜백 함수 형태로 UI에 직접 반영할 수 있습니다.

**수반된 비용과 장애 극복**

서버가 모든 화면 상태를 관리한다는 것은, 화면을 다시 그리는 렌더링 연산 역시 서버 CPU를 소모한다는 뜻입니다. v0.7.2 버전에서 이로 인한 심각한 성능 병목이 발생했습니다. 

토큰 스트리밍 도중 토큰이 하나 도착할 때마다 발언 카드 전체의 Markdown 텍스트를 서버 측에서 HTML로 재변환하여 전송했고, 브라우저 스크롤 이동 명령 역시 토큰마다 개별 발송되었습니다. 그 결과 2만 자 분량의 최종 보고서를 생성하는 동안 서버 CPU가 82초 동안 100% 점유되는 현상이 발생했습니다. 서버와 브라우저가 동시에 부하를 감당하지 못하면서 WebSocket 연결이 끊겼고, NiceGUI의 기본 재접속 메커니즘으로 인해 웹 페이지가 강제로 새로고침되는 장애가 나타났습니다. 사용자 입장에서는 "긴 답변이 생성되던 중 화면이 깜빡이며 날아가는" 치명적인 문제였습니다.

이 문제는 다음과 같은 전형적인 성능 튜닝 기법들의 조합으로 해결했습니다.
1. 개별 토큰 조각은 내부 메모리 버퍼에만 누적하고, 실제 UI 발언 카드의 렌더링 갱신 주기를 0.25초 단위로 스로틀링(Throttling)했습니다.
2. 오케스트레이션 엔진이 발행하는 스트리밍 청크 이벤트를 0.1초 단위로 배치 묶음 처리했습니다.
3. 일시적인 지연으로 WebSocket 연결이 조기 종료되지 않도록 재접속 타임아웃을 기존 3초에서 30초로 상향 조정했습니다.

이 최적화를 통해 동일한 스트림 기준 렌더링 횟수는 2,668회에서 56회로, 브라우저로 전송된 WebSocket 메시지 수는 3,556개에서 173개로 급감했습니다.

여기서 얻은 핵심 교훈은 다음과 같습니다. 서버 주도형 UI 아키텍처에서 "화면을 너무 자주 갱신하는 것"은 곧 "서버 CPU에 막대한 연산 부하를 주는 것"과 같습니다. 화면 갱신 빈도는 사람이 시각적으로 부드러움을 인지할 수 있는 수준(초당 수 회)으로 제한하는 것이 필수적입니다.

**대안 기술과의 비교 평가**

| 대안 프레임워크 | 폐쇄망 및 멀티 에이전트 제약 조건 기준 평가 |
| :--- | :--- |
| **Streamlit** | 사용자 인터랙션이 발생할 때마다 전체 파이썬 스크립트를 처음부터 재실행하는 실행 모델을 갖습니다. 수 분 이상 소요되는 토론 루프를 화면과 분리하여 백그라운드로 구동하고, 페이지 새로고침 후에도 진행 중인 토론에 안전하게 재접속하도록 구현하려면 비표준적인 우회 기법이 과도하게 요구됩니다. |
| **React/Vue SPA + FastAPI** | 가장 높은 화면 유연성과 클라이언트 측 성능을 제공하지만, 개발 언어와 빌드 파이프라인이 이원화되며, 폐쇄망에 반입해야 하는 빌드 산출물과 외부 종속성이 크게 증가합니다. |
| **FastHTML** | 서버가 순수 HTML 조각을 반환하는 구조로 매우 가볍지만, 드래그 앤 드롭 정렬, 분할 패널(Splitter), 모달 대화상자 등 복잡한 인터랙티브 UI 컴포넌트를 직접 밑바닥부터 구현해야 하는 개발 공수가 큽니다. |

### 3.4 LiteLLM

에이전트별로 서로 다른 LLM 모델을 유연하게 배정하는 것은 MADO의 핵심 요구사항입니다. LiteLLM은 각양각색인 공급자별 API를 OpenAI 표준 규격의 단일 호출 인터페이스로 추상화해 줍니다. 따라서 모델을 변경하는 작업이 소스 코드 수정이 아닌 단순한 설정 문자열 변경으로 완결됩니다.

```json
"model": "openai/gpt-4o"
"model": "anthropic/claude-3-5-sonnet-20241022"
"model": "ollama_chat/qwen2.5-coder:14b"
```

로컬 추론 서버와 연동할 때 특히 유용한 설정은 엔드포인트가 지원하지 않는 부가 파라미터를 자동으로 제거해 주는 `drop_params: true` 옵션입니다. 이 설정이 활성화되어 있지 않으면, `top_p` 등의 특정 파라미터를 인식하지 못하는 사내 로컬 모델에 요청을 보냈을 때 요청 전체가 HTTP 400 에러로 거부되는 상황이 발생합니다.

**추상화 누수 (Leaky Abstraction)의 극복**

LiteLLM이 API 호출 인터페이스를 표준화해 주지만, 각 공급자가 요구하는 **대화 컨텍스트 구성 규칙**까지 완전히 숨겨주지는 못합니다. MADO 개발 중 실제로 마주했던 공급자별 세부 차이점들은 다음과 같습니다.

- **연속된 `user` 메시지 처리**: 토론 시스템은 여러 발언자가 참여하는 구조이지만, OpenAI 표준 메시지 스키마에는 "제3의 에이전트" 역할이 없습니다. 따라서 다른 에이전트의 이전 발언들이 모두 `user` 역할로 주입되면서 동일한 `user` 메시지가 연속으로 배치됩니다. OpenAI는 이를 정상 수용하지만, Anthropic, Gemini 및 일부 엄격한 추론 서버는 HTTP 400 오류를 반환하며 거절합니다.
- **도구 정의와 호출 기록의 정합성**: 이전 대화 맥락에 도구 호출 기록(`tool_calls`, `tool` 역할 메시지)이 포함되어 있을 때, 도구 스키마 정의를 생략하고 요청하면 Anthropic은 오류를 발생시키고 OpenAI는 허용합니다.
- **상류 오류 캡슐화 문제**: 일부 기업용 게이트웨이는 상류의 HTTP 400 검증 실패를 자체 HTTP 500 내부 오류로 감싸서 반환하여 근본 원인 추적을 방해합니다.

따라서 MADO는 LiteLLM을 직접 호출하기 전 단계에 **요청 구조 정리 계층(Sanitization Layer)**을 명시적으로 배치했습니다. 동일 역할 메시지를 하나로 병합하고, 컨텍스트 윈도우 크기에 맞게 히스토리를 정밀하게 잘라내며, 도구 호출 권한이 없는 단계에서는 도구 스키마를 정의하되 `tool_choice: "none"`으로 제어하는 등의 역할을 수행합니다. 추상화 라이브러리를 도입하더라도 경계면에서 누수되는 세부 차이를 완충하는 책임은 결국 애플리케이션에 남는다는 점이 핵심입니다. 세부적인 구현은 [4-2. LLM 연동](04-core-techniques/02-llm-integration.md)에서 다룹니다.

### 3.5 MCP Python SDK

MCP(Model Context Protocol)는 LLM 애플리케이션과 도구 서버 간의 표준 통신 프로토콜입니다. JSON-RPC 2.0 기반으로 도구 목록 조회(`tools/list`), 도구 호출 실행(`tools/call`) 등의 메시지를 교환합니다. MADO에서는 다음 두 가지 전송 방식을 모두 지원합니다.

- **표준 입출력 (stdio)**: 호스트 애플리케이션이 도구 서버를 자식 프로세스로 직접 실행하고 프로세스의 표준 입출력(stdin/stdout) 파이프를 통해 통신합니다. MADO에 내장된 기본 도구 서버들이 이 방식을 채택하고 있습니다.
- **Streamable HTTP**: 이미 네트워크상에 구동 중인 외부 서버의 URL 엔드포인트로 연결합니다. 별도의 프로세스 실행 명령 없이 사내 공용 게이트웨이 등에 직접 연동할 때 활용되며, v0.2에서 추가되었습니다.

MCP 프로토콜을 적용함으로써 도구 실행 환경이 메인 애플리케이션과 물리적으로 분리된 독립 프로세스로 격리됩니다. 파일 시스템 서버는 허가된 작업 공간 디렉터리 외부 경로에 대한 접근을 자체적으로 차단하며, Python 샌드박스의 커널이 메모리 초과로 크래시되더라도 메인 애플리케이션 프로세스는 안정적으로 유지됩니다. 새로운 도구를 추가하는 작업 역시 설정 파일에 실행 명령을 한 줄 추가하는 것으로 완료됩니다.

SDK 의존성 버전은 `mcp>=1.29.0,<2`로 상한을 명시하여 고정했습니다. MCP 2.x 버전에서 서버 측 API 명칭이 변경(`FastMCP` → `MCPServer`)되었는데, 번들에 포함된 기존 샌드박스 서버와 Git 서버가 1.x 규격에 의존하고 있었기 때문입니다. 만약 상한을 열어두었다면 폐쇄망용 신규 패키지 빌드 시 2.x가 설치되어 서버 기동 즉시 장애가 발생했을 것입니다.

### 3.6 SQLite, SQLAlchemy 2.0, aiosqlite

MADO의 세션 구조상 단일 대화 세션에 데이터를 쓰는 주체는 오직 하나(해당 대화를 담당하는 백그라운드 토론 태스크)입니다. 동시 다발적인 대량 쓰기 경합이 발생하지 않으며, 단일 운영자가 별도의 RDBMS 서버를 유지보수할 여력이 없고, 설치 및 이전 시 파일 하나만 복사하면 된다는 점에서 SQLite는 최적의 선택이었습니다. 또한 비동기 DB 드라이버인 `aiosqlite`와 SQLAlchemy 2.0 비동기 세션을 결합하여 데이터베이스 입출력 대기 시간 동안 asyncio 이벤트 루프가 차단되지 않도록 보장했습니다. 연결 주소는 설정 파일로 관리되므로 향후 PostgreSQL 등으로 확장하더라도 드라이버 연결 문자열만 교체하면 됩니다.

그러나 SQLite 역시 기본 설정 그대로 사용해서는 안 된다는 점을 v0.7.1 장애를 통해 확인했습니다. 사용자가 자리를 비워 화면이 잠긴 상태에서 백신 실시간 감시 프로그램이나 백업 데몬이 데이터베이스 파일을 일시 점유했고, 기본 5초 타임아웃이 초과되면서 `database is locked` 오류와 함께 최종 보고서 저장이 실패하는 문제가 발생했습니다. 현재는 연결마다 타임아웃을 30초로 대폭 늘리고 동시 읽기·쓰기를 지원하는 WAL(Write-Ahead Logging) 저널 모드를 활성화했습니다. 단, 네트워크 드라이브 환경에서는 WAL 모드가 파일 손상을 일으킬 수 있으므로 로컬 디스크 환경에서만 활성화되도록 보호하고 있습니다. 이 상세 사례는 [ADR-017](05-adr/ADR-017-never-lose-a-write.md)에서 다룹니다.

### 3.7 Pydantic v2와 표준 `json` 모듈

시스템 설정은 Pydantic v2 모델을 통해 엄격하게 검증됩니다. 필수 입력 필드, 허용 값 범위, 오케스트레이터 정의 여부 등의 유효성 검증 규칙이 선언적으로 기술되어 있으며, 잘못된 설정이 입력될 경우 애플리케이션이 구동되기 전에 즉시 실행을 차단합니다.

설정 파일의 저장 포맷으로 JSON을 채택한 이유는 시스템이 설정을 읽기만 하는 것이 아니라 화면을 통해 **직접 수정하고 다시 저장(되쓰기)**해야 하기 때문입니다. Python 표준 라이브러리에는 TOML을 파싱하는 모듈(`tomllib`)은 내장되어 있으나, 직렬화하여 파일로 다시 쓰는 모듈은 제공되지 않습니다. TOML을 사용하던 초기 버전에서는 UI에서 변경된 설정을 저장하기 위해 수작업 문자열 치환 코드를 사용해야 했으며, 시스템 프롬프트 본문 내의 `[검토 항목]` 같은 텍스트를 TOML의 테이블 헤더로 오인하여 파일이 손상되는 치명적인 위험이 상존했습니다.

반면 JSON 포맷으로 전환하면서 "메모리 상의 딕셔너리를 갱신한 후 파일 전체를 원자적으로 저장"하는 안정적인 쓰기 파이프라인을 구축할 수 있었습니다. JSON 포맷에서 지원하지 않는 주석 처리와 여러 줄 문자열은 자체적인 파싱 규칙을 정의하여 해결했습니다. 세부 사항은 [ADR-013](05-adr/ADR-013-json-config.md)과 [4-1. 설정 관리](04-core-techniques/01-configuration.md)에서 다룹니다.

### 3.8 도구 서버 런타임 환경: Node.js와 Python

시스템에 기본 내장된 MCP 도구 서버는 5종으로 구성되어 있습니다.

| 도구 서버 | 실행 런타임 | 담당 역할 |
| :--- | :--- | :--- |
| **filesystem** | Node.js (공식 오픈소스 서버) | 지정된 작업 공간 디렉터리 내 파일의 읽기, 쓰기, 탐색 및 목록 조회 |
| **memory** | Node.js (공식 서버 기반 커스텀 포크) | 세션 대화별 지식 그래프(노드-엣지) 기반 사실 관계 영구 기억 |
| **git** | Python | 작업 공간 내 Git 변경 이력 조회, diff 분석, 자동 커밋 생성 |
| **sandbox** | Python (IPython 커널) | 변수 및 세션 상태가 지속되는 대화형 Python 코드 실행 환경 제공 |
| **sequential-thinking** | Node.js (공식 오픈소스 서버) | 복잡한 다단계 논리 추론 보조 도구 (기본 설정은 비활성화) |

공식 Node.js 서버들은 순수 JavaScript로 작성되어 있어 별도의 Node 환경 구성 없이 번들된 `node.exe` 실행 파일 하나만으로 구동됩니다. npm 패키지 매니저는 빌드 타임에만 사용되며 실제 배포 번들에는 포함되지 않으므로 폐쇄망 반입 파일 크기를 대폭 절감할 수 있습니다.

### 3.9 UI 보조 라이브러리

- **Mermaid**: 시스템 산출물로 생성되는 다이어그램을 브라우저에서 실시간 렌더링합니다. NiceGUI에 내장된 라이브러리를 활용합니다. 다이어그램 문법 검사 및 자동 보정 규칙을 해당 내장 Mermaid 버전의 실제 파서 특성에 정확히 맞추어 튜닝했기 때문에, NiceGUI 의존성 범위를 `>=3.16,<4`로 엄격하게 관리하고 있습니다. NiceGUI의 메이저 버전이 올라가면 내장 Mermaid 버전도 함께 변경되므로 검사 로직의 재검증이 수반되어야 합니다.
- **Vue Flow**: 5번째 토론 전략인 '그래프 토론'의 오프라인 시각화 편집기 컴포넌트입니다. 외부 의존성을 모두 포함하여 156KB 크기의 단일 ES 모듈 파일로 번들링한 후 애플리케이션 내부에 탑재했습니다. NiceGUI가 이미 클라이언트에 제공하는 기본 Vue 런타임만을 공유하므로, 외부 CDN 연결이 차단된 폐쇄망 환경에서도 완벽하게 동작합니다. 라이선스 고지 및 재빌드 가이드 문서도 함께 동봉되어 있습니다.

### 3.10 테스트 프레임워크: pytest와 가짜 LLM

개발 초기에는 비즈니스 로직 내부에 포함되어 있던 시뮬레이터가 단위 테스트용 가짜 LLM 역할까지 겸임했습니다. 그러나 시뮬레이터를 프로덕션 코드에서 완전히 제거하면서([ADR-007](05-adr/ADR-007-no-simulated-answers.md)), 테스트 대역(Test Double) 역시 테스트 디렉터리 내부로 완전히 격리했습니다. 프로덕션 코드에는 일체의 가짜 로직이 존재하지 않으며, 오직 테스트 코드만이 모의 객체를 사용합니다. 이 경계가 흐려질 경우 "테스트는 통과하지만 프로덕션 런타임에서 가짜 응답이 섞여 들어가는" 위험한 상황이 재발할 수 있습니다.

한 가지 더 주목할 점은 데이터베이스 엔진의 싱글턴(Singleton) 문제입니다. 데이터베이스 엔진이 프로세스 전역 싱글턴으로 관리될 경우, 특정 테스트 케이스가 기본 설정 경로로 엔진을 먼저 초기화해 버리면 개발자의 로컬 개발 DB 파일에 테스트용 데이터가 누적되는 오염이 발생했습니다. 현재는 pytest의 테스트 픽스처가 시작될 때마다 인메모리 SQLite(`:memory:`) 엔진을 우선 생성하여 전역 객체를 선점하도록 격리했습니다. 싱글턴 패턴은 접근성이 편리하지만 "어떤 코드가 먼저 인스턴스를 생성했는가"에 따라 시스템 동작이 달라지는 암묵적 결합을 유발한다는 점을 유의해야 합니다.

## 4. 패키지 버전 고정 정책

MADO의 `requirements.txt` 파일에 정의된 대부분의 패키지는 최소 요구 버전(하한)만 명시되어 있습니다. 버전 상한을 엄격하게 제한한 패키지는 다음 두 가지뿐입니다.

| 패키지 | 지정 버전 범위 | 제한 근거 |
| :--- | :--- | :--- |
| `mcp` | `>=1.29.0,<2` | 2.x 버전에서 서버 라이브러리 명칭이 변경되어 번들된 도구 서버의 기동이 실패하는 문제 방지 |
| `nicegui` | `>=3.16,<4` | 내장된 Mermaid 버전과 연계된 다이어그램 문법 검사 및 자동 복구 정규식의 호환성 보장 |

버전 상한선은 구체적인 기술적 충돌 근거가 명확할 때에만 설정해야 합니다. 명확한 근거 없는 임의의 버전 상한은 보안 패치 적용을 가로막는 장애물이 되며, 근거가 있는 상한 설정의 경우 향후 유지보수 담당자가 안전하게 제약을 해제할 수 있도록 상세한 이유를 주석으로 명시해 두어야 합니다. 두 패키지 모두 `requirements.txt` 파일 내에 구체적인 제약 사유가 주석으로 기록되어 있습니다.

## 5. 아키텍처 선택의 종합 평가

| 기술적 선택 | 획득한 이점 | 감수한 비용 (트레이드오프) |
| :--- | :--- | :--- |
| **Python 단일 프로세스 (FastAPI + NiceGUI)** | 별도 프런트엔드 빌드 파이프라인 불필요, 폐쇄망 반입 단순화, 백엔드-프런트엔드 간 직렬화 계층 제거 | 화면 렌더링 연산이 서버 CPU를 소모하며, 활성 세션별 화면 상태가 서버 메모리에 상주함 |
| **LiteLLM 게이트웨이** | 설정 문자열 변경만으로 다양한 LLM 공급자 즉시 교체 가능 | 공급자별 세부 대화 컨텍스트 규칙 차이를 메인 앱에서 직접 흡수·정리해야 함 |

## 핵심 요약

- MADO의 기술 스택은 **Python 일원화**, **폐쇄망 반입 용이성**, **이종 LLM 공급자 연동**, **도구 확장성**, **최소 운영 리소스**라는 5대 제약 조건을 충족하도록 최적화되었습니다.
- 모든 엔지니어링 선택에는 반드시 그에 상응하는 비용(트레이드오프)이 따르며, MADO에서는 실제 운영 장애를 통해 이러한 비용을 식별하고 방어 설계를 적용했습니다.
- 범용 추상화 라이브러리를 도입하더라도, 계층 경계면에서 발생하는 공급자별 미세한 동작 차이를 완충하는 최종 책임은 애플리케이션 계층에 있습니다.
- 의존성 버전 상한은 명확한 장애 재현 근거가 존재할 때에만 제한적으로 설정하며, 그 이유를 코드베이스에 명확히 기록해 두어야 합니다.

## 학습 점검 과제

1. 시스템의 동시 접속 사용자가 50명 이상으로 증가한다고 가정할 때, 현재 기술 스택 중에서 가장 먼저 분리하거나 아키텍처를 전환해야 할 구성 요소는 무엇일까요? 그렇게 판단한 기술적 근거를 설명해 보십시오.
2. 만약 NiceGUI 대신 React 기반의 독립 SPA 아키텍처를 채택했다면, v0.7.2에서 마주했던 스트리밍 렌더링 병목 문제는 완전히 사라졌을까요? 아니면 다른 형태의 기술적 난제가 발생했을지 예측해 보십시오.
3. LiteLLM과 같은 통합 게이트웨이를 사용하지 않고 각 공급자별 공식 SDK(OpenAI, Anthropic 등)를 개별적으로 직접 연동했다면, 요청 구조 정리 계층(Sanitization Layer)의 필요성이 완전히 배제될 수 있었을지 논리적으로 분석해 보십시오.
