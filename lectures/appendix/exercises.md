# 부록 B. 실습과 토론 과제

> [강의 안내](../README.md) · [부록 A. 용어집](glossary.md)

강의 내용을 손으로 확인하는 실습, 결정을 직접 내려 보는 설계 과제, 그리고 이해를 점검하는 확인 문제로 구성했습니다.
실습은 MADO를 개발 PC에서 띄울 수 있다는 전제입니다. 설치 방법은 저장소의 사용 설명서(`docs/user_manual/`)를 참고하세요.

---

## 1. 실습

### 실습 1. 한 턴을 끝까지 따라가기 (관련: 3-2 동적 뷰)

1. 새 대화를 만들고 전문가 셋(아키텍트, 엔지니어, 리뷰어)으로 순차 토론, 최대 라운드 2로 설정합니다.
2. "간단한 할 일 관리 REST API를 설계하고 핵심 코드를 작업 공간에 써 주세요"라고 요청합니다.
3. 토론이 도는 동안 브라우저를 한 번 새로고침합니다.
4. 끝나면 다음을 확인합니다.
   - 새로고침 뒤에도 생성 중이던 발언이 이어서 흘렀는가?
   - 도구 실행 기록은 어느 발언에 붙어 있는가? 접이식 영역을 열어 인자와 결과를 봅니다.
   - 산출물 탭은 몇 개가 생겼고, 각 탭의 출처는 어디인가(합성 본문인가, 전문가 발언인가)?
   - 작업 공간 폴더에 실제로 파일이 생겼는가? git 기록은 어떤가?

### 실습 2. 전략 비교 (관련: 4-4 오케스트레이션)

같은 요청을 순차 토론, 디베이트, 병렬 지시로 각각 돌리고 표를 채워 보세요.

| | 순차 토론 | 디베이트 | 병렬 지시 |
| :--- | :--- | :--- | :--- |
| 턴 총 경과 시간 | | | |
| 발언 수 | | | |
| 전문가끼리 서로를 언급한 횟수 | | | |
| 결론에 남은 미해결 쟁점 수 | | | |

디베이트에서는 에이전트 카드의 메뉴로 진영을 바꿔 가며, 로스터의 발언 순서 미리보기가 어떻게 달라지는지도 봅니다.

### 실습 3. 실패를 일부러 일으키기 (관련: 4-7 실패 설계)

1. 에이전트 하나의 엔드포인트 주소를 존재하지 않는 주소로 바꾼 뒤 **새 대화**에서 토론을 돌립니다.
   - 그 에이전트의 발언은 어떻게 기록되는가? 다른 에이전트는 그 실패에 대해 말하는가?
   - 턴 끝의 합의 표시는 어떻게 되는가? 합성 보고서는 그 에이전트를 어떻게 다루는가?
2. 존재하지 않는 명령으로 MCP 서버를 하나 추가해 봅니다.
   - 상태 칩의 색과 툴팁에는 무엇이 보이는가? 앱은 계속 동작하는가?
3. 실험이 끝나면 설정을 원래대로 돌립니다.

### 실습 4. 구성 스냅샷 확인하기 (관련: ADR-011)

1. 대화 A를 시작해 한 턴을 돌립니다.
2. 전역 설정에서 대화 A에 참여한 에이전트 하나를 삭제합니다.
3. 대화 A에서 다음 턴을 돌립니다. 삭제한 에이전트는 발언하는가? 카드에는 어떤 표시가 붙는가?
4. 새 대화 B를 만듭니다. B의 로스터에는 그 에이전트가 있는가?
5. 대화 A에서 "설정 갱신"을 누르면 무엇이 바뀌고 무엇이 그대로인가?

### 실습 5. 대화 기억 관찰하기 (관련: 4-5 대화 기억)

1. 설정에서 한 전문가의 `max_context_window`를 8,000 정도로 작게 잡습니다(시험용).
2. 1턴에서 "데이터베이스는 SQLite만 쓰세요, 다른 DB는 제안하지 마세요"라고 조건을 줍니다.
3. 2턴에서 전혀 다른 기능을 요청하고 최대 라운드를 3으로 둡니다.
4. 로스터의 결정 장부 패널을 열어, 1턴의 조건이 어느 절에 들어가 있는지 확인합니다.
5. 2턴의 발언에서 1턴의 조건을 어기는 제안이 나오는가? 요약 진행 알림이 뜨는가?

### 실습 6. 그래프 토론 설계하기 (관련: ADR-021)

1. 그래프 편집기에서 `시작 → 설계 → (구현, 보안 검토) → 병합 → 게이트 → 끝`을 그리고, 게이트의 "아니오"를 구현으로 되돌립니다.
2. 검증 요약에 나오는 턴당 최악의 호출 수를 기록합니다.
3. 게이트를 거치지 않는 순환(예: 병합 → 구현)을 하나 더 그려 보고 검증 결과를 확인합니다.
4. 연결선의 "나르는 것"을 전문, 요지, 코드 참조로 바꿔 가며 같은 요청을 돌리고, 발언의 길이와 품질을 비교합니다.

## 2. 설계 과제

### 과제 1. ADR 써 보기

다음 중 하나를 골라 ADR을 쓰세요. 형식은 [5강 안내의 틀](../05-adr/README.md#새-adr-쓰기)을 따릅니다. 결과에는 좋아지는 것만큼
치르는 비용을 구체적으로 쓰세요.

1. **사용자별 계정 도입.** 원격 사용자가 20명으로 늘었고, 서로의 대화를 볼 수 없어야 한다는 요구가 생겼습니다.
   [ADR-019](../05-adr/ADR-019-owner-token-remote-access.md)와 어떻게 관계를 맺을지(대체인가, 확장인가)도 정하세요.
2. **PostgreSQL 이전.** 서버 PC 두 대로 부하를 나누려 합니다. [ADR-001](../05-adr/ADR-001-python-single-process.md)과
   [ADR-004](../05-adr/ADR-004-sqlite-persistence.md) 중 무엇이 먼저 걸림돌이 되는지 따져 보세요.
3. **지식베이스 L1 도입.** 재논의에서 "어느 문서인지 몰랐던 비율"이 45%로 나왔다고 가정하고,
   [ADR-022](../05-adr/ADR-022-knowledge-base-deferred.md)의 상태를 어떻게 바꿀지 쓰세요.

### 과제 2. 여러분 프로젝트의 C4 그리기

지금 맡고 있는 시스템 하나를 골라 C4 1단계(컨텍스트)와 2단계(컨테이너)를 그리세요. 그린 뒤 다음을 점검합니다.

- 컨테이너 사이의 화살표마다 "무엇을"과 "어떻게(프로토콜)"가 적혀 있는가?
- 도커 컨테이너가 아니라 C4 컨테이너(따로 실행되거나 따로 데이터를 담는 단위)로 나누었는가?
- 설정 파일처럼 "앱이 쓰기도 하는 저장소"를 빠뜨리지 않았는가?

### 과제 3. 격리 경계 표 만들기

여러분의 시스템에서 "여러 사용자(또는 테넌트, 대화)가 동시에 쓸 때 섞이면 안 되는 상태"를 모두 적고,
[3-1 정적 뷰의 격리 경계 표](../03-architecture/01-static-view.md#7-격리-경계)처럼 경계와 이유를 채워 보세요. 그 경계를 **누가**
정하고 있는지도 적습니다. 모델이나 클라이언트가 정하고 있는 경계가 있다면 위험 신호입니다.

## 3. 토론 주제

수업이나 스터디에서 20~30분씩 토론하기 좋은 주제입니다.

1. **정직성과 가용성.** ADR-009는 가용성을 포기하고 거절을 택했습니다. 여러분의 시스템에서 "조용히 틀리느니 거절한다"를 적용할
   곳과 적용하면 안 될 곳을 하나씩 들어 보세요.
2. **추상화가 새는 곳.** LiteLLM, MCP SDK, ORM처럼 "차이를 감춰 준다"는 라이브러리를 쓰면서 겪은 새는 추상화 사례를 나눠 보세요.
   누가 그 차이를 흡수해야 할까요?
3. **LLM에게 맡길 것과 맡기지 않을 것.** MADO는 대화 ID, 격리 경계, 다이어그램의 기계적 수정, 인수인계 노트의 사실 부분을 LLM에게
   맡기지 않았습니다. 반대로 결정 장부와 요약은 맡겼습니다. 기준이 무엇이었을까요?
4. **사후 ADR의 가치.** 이 강의의 ADR은 커밋 기록에서 복원한 것입니다. 결정 당시에 쓴 ADR과 무엇이 다를까요? 복원할 수 있었던
   이유는 무엇일까요? (힌트: 커밋 메시지의 모양)

## 4. 확인 문제

<details>
<summary>1. 오케스트레이터가 라운드 안에서 발언하지 않는다는 것은 무슨 뜻인가요?</summary>

오케스트레이터는 라운드 전에 계획하고 라운드 뒤에 합성합니다. 발언자 지명, 과업 분배, 게이트 판정, 결정 장부 갱신 같은 경로
결정도 하지만, 이는 도구 없는 사본으로 보내는 별도 호출이지 라운드의 발언이 아닙니다. 모든 전략은 발언자 목록에서
오케스트레이터를 뺍니다.
</details>

<details>
<summary>2. C4의 "컨테이너"로 MADO에서 꼽을 수 있는 것을 다섯 가지 이상 드세요.</summary>

웹 화면(브라우저), MADO 애플리케이션(파이썬 프로세스), 대화 DB(SQLite 파일), 설정(JSON과 .env), 앱 데이터 폴더, 작업 공간
폴더, 그리고 filesystem, memory, git, sandbox 각 도구 서버 프로세스.
</details>

<details>
<summary>3. 샌드박스 커널을 대화 단위가 아니라 "대화 × 발언자" 단위로 나눈 이유는?</summary>

도구 실행 기록은 다른 에이전트의 맥락에 들어가지 않습니다. 커널을 공유하면 리뷰어가 출처를 모르는 변수를 물려받아 낡은 값을
현재 값으로 믿고 검토하게 됩니다. 또 리뷰어가 샌드박스를 가진 목적은 엔지니어의 코드를 직접 실행하는 것인데, 엔지니어가 만든
객체를 들여다보는 것은 결과를 보는 것이지 코드를 검증하는 것이 아닙니다. 그래서 인계는 파일로 합니다.
</details>

<details>
<summary>4. 결정 장부를 시스템 프롬프트가 아니라 마지막 메시지 앞에 두는 이유는?</summary>

공급자의 프롬프트 캐시는 요청의 앞부분이 같을 때 적용됩니다. 장부는 라운드마다 바뀌므로 시스템 프롬프트에 두면 매번 요청 전체의
캐시가 깨집니다. 마지막 메시지 앞은 컨텍스트 자르기에서도 늘 보존되는 자리입니다.
</details>

<details>
<summary>5. `except Exception`과 `except BaseException`이 각각 어떤 사고를 냈나요?</summary>

`except Exception`은 anyio가 올리는 `BaseExceptionGroup`을 잡지 못해 토론 태스크가 죽었습니다. `except BaseException`은 취소
신호까지 삼켜 앱 종료가 멈췄습니다. 올바른 경계는 취소는 다시 올리고, 나머지는 예외 그룹까지 포함해 결과로 바꿉니다.
</details>

<details>
<summary>6. 소스 갱신 패키지에 운영 설정 파일(conf.json)을 넣지 않는 이유는?</summary>

배포된 쪽의 설정에는 그 망의 실제 엔드포인트와 설정이 들어 있습니다. 덮어쓰면 모든 에이전트가 엉뚱한 곳을 가리킵니다. 새 설정
항목은 예시 파일을 보고 사람이 옮깁니다.
</details>

<details>
<summary>7. ADR-009의 상태가 "대체됨"인데도 삭제하지 않고 남겨 둔 이유는?</summary>

ADR은 고치지 않고 쌓는 기록입니다. 대체된 결정도 "왜 예전에는 그렇게 했는가"에 답하고, 새 결정이 지켜야 할 원칙(남의 폴더를
조용히 건드리지 않는다)을 보여 줍니다.
</details>

<details>
<summary>8. 발언의 시작·종료 시각을 기존 생성 시각 컬럼으로 쓰지 않은 이유는?</summary>

그 컬럼은 이미 정렬 키였습니다. 행은 응답이 끝난 뒤 삽입되므로 대략 종료 시각이고, 병렬 라운드에서는 지시 순서를 박기 위해
덮어씁니다. 한 컬럼에 두 의미를 싣지 않으려고 새 컬럼을 더했고, 옛 행은 기본값으로 채우지 않았습니다.
</details>

<details>
<summary>9. 원격 접속 게이트가 X-Forwarded-For 헤더를 무시하는 이유와, 그 결과 생기는 제약은?</summary>

프록시 헤더를 믿으면 누구나 헤더를 꾸며 루프백인 척할 수 있습니다. 대신 리버스 프록시 뒤에 두면 모든 요청이 프록시, 즉
루프백에서 온 것으로 보여 인증 없이 통과하므로, 프록시 뒤에 두지 말라는 제약이 생깁니다.
</details>

<details>
<summary>10. 다이어그램 문법 검사기를 "일부러 불완전하게" 만든 이유는?</summary>

오류를 놓치면 치르는 비용은 예전과 같지만, 멀쩡한 다이어그램을 오류로 판정하면 LLM 호출을 낭비하고 고칠 것 없는 모델에게
잘 되던 다이어그램을 망칠 기회를 줍니다. 그래서 오탐이 없도록 규칙을 실제 파서로 하나씩 맞췄습니다.
</details>
