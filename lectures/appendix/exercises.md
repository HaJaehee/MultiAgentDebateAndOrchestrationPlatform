# 부록 B. 실습과 토론 과제

> [강의 안내](../README.md) · [부록 A. 용어집](glossary.md)

강의 내용을 직접 확인하는 실습, 아키텍처 결정을 직접 내려 보는 설계 과제, 그리고 이해도를 점검하는 확인 문제로 구성했습니다. 실습은 MADO 시스템을 로컬 개발 환경에서 기동할 수 있다는 전제로 진행됩니다. 설치 및 환경 구성 방법은 저장소의 사용자 매뉴얼(`docs/user_manual/`)을 참고하시기 바랍니다.

---

## 1. 실습

### 실습 1. 한 턴을 끝까지 따라가기 (관련: 3-2 동적 뷰)

1. 새 대화 세션을 생성하고 전문가 3인(아키텍트, 엔지니어, 리뷰어)을 배치한 후 순차 토론 전략, 최대 라운드 2로 설정합니다.
2. "간단한 할 일 관리 REST API를 설계하고 핵심 코드를 작업 공간에 작성해 주십시오"라고 요청합니다.
3. 토론이 백그라운드에서 진행되는 동안 브라우저를 한 번 새로고침합니다.
4. 토론이 완료되면 다음 사항들을 점검합니다.
   - 브라우저를 새로고침한 후에도 실시간 생성 중이던 발언이 끊김 없이 이어서 스트리밍되었는지 확인합니다.
   - 도구 실행 기록이 어느 발언 카드에 연결되어 있는지 확인합니다. 접이식(Accordion) 영역을 펼쳐 실행 인자와 관찰 결과를 검토합니다.
   - 산출물 탭이 몇 개 생성되었으며, 각 탭의 데이터 출처가 어디인지 파악합니다 (종합 오케스트레이터 본문인가, 전문가 발언인가?).
   - 지정된 작업 공간 디렉터리에 실제 소스 코드 파일이 생성되었는지 확인하고, Git 커밋 이력이 정상 기록되었는지 점검합니다.

### 실습 2. 전략 비교 (관련: 4-4 오케스트레이션)

동일한 요청 프롬프트를 순차 토론, 디베이트, 병렬 지시 전략으로 각각 실행해 보고 다음 비교 표를 완성해 보십시오.

| 평가 항목 | 순차 토론 | 디베이트 | 병렬 지시 |
| :--- | :--- | :--- | :--- |
| 턴 총 경과 시간 | | | |
| 생성된 발언 수 | | | |
| 전문가 에이전트 간 상호 호명 횟수 | | | |
| 최종 결론에 명시된 미해결 쟁점 수 | | | |

디베이트 전략에서는 에이전트 카드의 컨텍스트 메뉴를 통해 진영(제안/비판)을 변경해 보며, 로스터의 발언 순서 미리보기 화면이 어떻게 동적으로 갱신되는지 관찰해 보십시오.

### 실습 3. 실패를 일부러 일으키기 (관련: 4-7 실패 설계)

1. 에이전트 중 하나의 엔드포인트 URL을 존재하지 않는 임의의 주소로 수정한 뒤 **신규 대화 세션**에서 토론을 시작합니다.
   - 해당 에이전트의 발언이 시스템에 어떻게 기록되는지 관찰합니다. 타 에이전트들이 그 통신 실패 사실을 언급하는지 확인합니다.
   - 턴 종료 시 합의 도출 상태가 어떻게 표시되는지 확인하고, 최종 종합 보고서가 응답 누락(미응답) 에이전트를 어떻게 명시하는지 살펴봅니다.
2. 실행 명령어가 유효하지 않은 임의의 명령으로 신규 MCP 도구 서버를 등록해 봅니다.
   - UI 상태 칩의 색상 변화와 툴팁 진단 메시지를 확인합니다. 메인 애플리케이션이 크래시되지 않고 정상 동작을 지속하는지 점검합니다.
3. 실험을 마친 후 설정을 원래 상태로 복원합니다.

### 실습 4. 구성 스냅샷 확인하기 (관련: ADR-011)

1. 대화 A를 생성하여 첫 번째 턴을 실행합니다.
2. 시스템 전역 설정(`conf.json`)에서 대화 A에 참여했던 에이전트 중 하나를 삭제합니다.
3. 대화 A로 돌아와 두 번째 턴을 실행합니다. 삭제된 에이전트가 여전히 정상 발언하는지, UI 카드에 어떤 뱃지("이 대화 전용")가 부착되는지 확인합니다.
4. 새로운 대화 B를 생성합니다. 대화 B의 로스터 목록에 방금 전역 설정에서 삭제한 에이전트가 표시되는지 확인합니다.
5. 대화 A에서 '설정 갱신(Refresh Config)' 버튼을 클릭했을 때 어떤 정보가 변경되고 어떤 정보가 불변으로 유지되는지 비교합니다.

### 실습 5. 대화 기억 관찰하기 (관련: 4-5 대화 기억)

1. 설정에서 특정 전문가의 컨텍스트 윈도우 크기(`max_context_window`)를 8,000토큰 수준으로 작게 제한합니다 (테스트 목적).
2. 1턴에서 "데이터베이스는 SQLite만 사용해야 하며, 다른 외부 DBMS는 일절 제안하지 마십시오"라는 명시적 제약 조건을 부여합니다.
3. 2턴에서 1턴과 무관한 신규 기능 설계를 요청하고 최대 라운드를 3으로 설정합니다.
4. 로스터의 결정 장부 패널을 열어 1턴의 제약 조건이 5대 섹션 중 어느 영역에 구조화되어 저장되었는지 확인합니다.
5. 2턴의 후반부 발언에서 1턴의 조건을 위반하는 제안이 발생하는지, 혹은 긴 대화 요약 안내 메시지가 정상 출력되는지 관찰합니다.

### 실습 6. 그래프 토론 설계하기 (관련: ADR-021)

1. 그래프 편집기에서 `시작 → 설계 → (구현, 보안 검토) → 병합 → 게이트 → 끝` 파이프라인을 구성하고, 품질 게이트의 "아니오(False)" 분기를 구현 노드로 피드백 순환시킵니다.
2. 검증 요약 모달에 표시되는 턴당 최악의 LLM 호출 횟수 메트릭을 기록합니다.
3. 게이트를 경유하지 않는 무한 루프 순환(예: 병합 → 구현 직접 연결)을 고의로 추가해 보고, 그래프 사전 검증기가 이를 어떻게 감지 및 차단하는지 확인합니다.
4. 연결선의 컨텍스트 전달 모드를 전문 전달, 요지 전달, 코드 참조로 변경해 가며 동일한 요청을 실행하고, 에이전트 발언의 토큰 소비량과 응답 품질을 비교 분석합니다.

## 2. 설계 과제

### 과제 1. ADR 써 보기

다음 시나리오 중 하나를 선택하여 정식 아키텍처 결정 기록(ADR)을 작성해 보십시오. 문서 포맷은 [5강의 ADR 템플릿](../05-adr/README.md#새-adr-쓰기)을 준수해야 합니다. 결과(Consequences) 섹션에는 긍정적인 이점뿐만 아니라 시스템이 치러야 할 기회비용과 설계 트레이드오프를 솔직하고 구체적으로 기술하십시오.

1. **사용자별 개별 계정 체계 도입**: 원격 접속 협업 인원이 20명 이상으로 확대되었으며, 팀원 간에 상호 대화 세션을 열람할 수 없도록 엄격한 권한 격리가 요구되는 상황입니다. 기존의 [ADR-019](../05-adr/ADR-019-owner-token-remote-access.md)와 어떤 아키텍처 승계 관계(완전 대체인가, 확장 공존인가)를 수립할지 결정하십시오.
2. **PostgreSQL DBMS 이전**: 2대의 물리 서버 머신으로 서비스 부하를 분산하고자 합니다. 기존 [ADR-001](../05-adr/ADR-001-python-single-process.md)(단일 프로세스)과 [ADR-004](../05-adr/ADR-004-sqlite-persistence.md)(단일 SQLite 파일) 중 어떤 결정이 가장 먼저 핵심 걸림돌로 작용하는지 분석하고 마이그레이션 전략을 수립하십시오.
3. **지식 베이스(RAG) L1 단계 도입**: 사후 운영 데이터 분석 결과 "사용자가 필요한 대상 문서명을 사전에 인지하지 못했던 비율"이 45%로 집계되었다고 가정하고, [ADR-022](../05-adr/ADR-022-knowledge-base-deferred.md)의 상태를 '보류'에서 '채택됨'으로 전환하는 후속 ADR을 작성하십시오.

### 과제 2. 여러분 프로젝트의 C4 그리기

현재 담당하고 있는 소프트웨어 시스템 하나를 선정하여 C4 모델 1단계(시스템 컨텍스트)와 2단계(컨테이너) 다이어그램을 작성해 보십시오. 작성을 완료한 후 다음 관점을 점검하십시오.

- 컨테이너 간의 모든 상호작용 화살표에 "무슨 데이터/역할을 전달하는가"와 "어떤 통신 프로토콜/방식을 사용하는가"가 명확히 기술되어 있는지 확인합니다.
- 물리적 Docker 컨테이너가 아니라, C4 모델 고유의 컨테이너 개념(독립적으로 실행되거나 데이터를 별도로 영속화하는 논리적 실행 단위)으로 적절히 분할되었는지 검토합니다.
- 설정 파일, 환경변수 파일처럼 "애플리케이션이 런타임에 읽고 덮어쓰기도 하는 저장소"가 누락되지 않고 온전히 식별되었는지 점검합니다.

### 과제 3. 격리 경계 표 만들기

여러분의 프로젝트에서 "다중 사용자, 다중 테넌트, 혹은 복수의 작업 세션이 동시에 구동될 때 결코 뒤섞여서는 안 되는 상태 데이터"를 전수 식별하고, [3-1 정적 뷰의 격리 경계 표](../03-architecture/01-static-view.md#7-격리-경계)를 참조하여 격리 경계와 근거를 표로 정리해 보십시오. 특히 각 격리 경계를 **누가(어떤 소프트웨어 컴포넌트가)** 강제하고 있는지를 명시하십시오. 만약 클라이언트 브라우저나 LLM 모델의 자율적 판단에 의존하여 격리 경계를 유지하고 있다면, 이는 잠재적으로 매우 위험한 아키텍처 신호입니다.

## 3. 토론 주제

세미나나 스터디 그룹에서 20~30분씩 심도 있게 논의하기에 적합한 주제들입니다.

1. **데이터 정직성 대 시스템 가용성**: ADR-009는 교차 오염을 방지하기 위해 가용성을 희생하고 신규 세션 실행 거절을 선택했습니다. 여러분의 도메인 시스템에서 "조용히 잘못된 결과를 산출하느니 명시적으로 실행을 거절해야 하는 영역"과 "일부 오차가 발생하더라도 가용성을 최우선으로 보장해야 하는 영역"의 구체적 사례를 각각 하나씩 제시하고 그 기준을 논의해 보십시오.
2. **추상화 계층의 누수(Leaky Abstraction)**: LiteLLM, MCP SDK, ORM과 같이 "하위 구현체의 차이를 완벽히 은폐해 준다"고 주장하는 라이브러리를 도입하면서 경험했던 누수 사례를 공유해 보십시오. 이러한 추상화 누수를 흡수해야 하는 최종 책임은 아키텍처의 어느 계층에 위치해야 할까요?
3. **LLM 모델에게 위임할 영역과 배제할 영역의 경계**: MADO 아키텍처는 세션 ID 주입, 데이터 격리 경계 강제, 다이어그램 문법 검사 및 규칙 기반 복구, 세션 인계 노트의 객관적 사실 기록을 결코 LLM에게 위임하지 않았습니다. 반면 결정 장부 정리와 장기 대화 요약은 모델에게 적극 위임했습니다. 이러한 역할 분담의 근본적인 판단 기준은 무엇이었을까요?
4. **사후 복원된 ADR의 실무적 가치**: 본 강의에 수록된 ADR 문서들은 개발 완료 후 커밋 로그와 장애 보고서로부터 체계적으로 역추적 복원된 것입니다. 의사결정 당시에 실시간으로 작성된 ADR과 비교할 때 어떤 차별점과 통찰을 제공할까요? 또한 사후 복원이 성공할 수 있었던 기반 요건은 무엇이었을까요? (힌트: Git 커밋 메시지의 상세 구조와 이슈 트래킹 이력)

## 4. 확인 문제

<details>
<summary>1. 오케스트레이터가 라운드 안에서 발언하지 않는다는 것은 무슨 뜻인가요?</summary>

오케스트레이터는 라운드 시작 전에 계획을 수립하고 라운드 종료 후에 최종 종합 보고서를 작성합니다. 발언자 동적 지명, 태스크 분배, 품질 게이트 평가, 결정 장부 갱신과 같은 오케스트레이션 판단도 수행하지만, 이는 도구 권한이 배제된 경량 사본 모델을 호출하는 독립적 내부 절차일 뿐 라운드 내부의 정식 토론 발언이 아닙니다. 따라서 모든 토론 전략의 발언자 목록에서 오케스트레이터는 명시적으로 제외됩니다.
</details>

<details>
<summary>2. C4의 "컨테이너"로 MADO에서 꼽을 수 있는 것을 다섯 가지 이상 드세요.</summary>

웹 브라우저 클라이언트, MADO 애플리케이션(FastAPI+NiceGUI 단일 파이썬 프로세스), 대화 데이터베이스(SQLite 로컬 파일), 시스템 설정 저장소(conf.json 및 .env 파일), 시스템 데이터 디렉터리, 프로젝트 작업 공간 디렉터리, 그리고 외부 프로세스로 격리 구동되는 filesystem, memory, git, sandbox MCP 도구 서버 프로세스 풀을 꼽을 수 있습니다.
</details>

<details>
<summary>3. 샌드박스 커널을 대화 단위가 아니라 "대화 × 발언자" 단위로 나눈 이유는?</summary>

도구의 세부 실행 기록은 타 에이전트의 프롬프트 컨텍스트에 포함되지 않습니다. 샌드박스 커널을 세션 단위로 공유할 경우, 리뷰어 에이전트가 출처를 알 수 없는 전역 변수를 물려받아 과거의 낡은 상태를 현재 값으로 착각하고 잘못된 검토를 수행하게 됩니다. 또한 리뷰어에게 샌드박스를 제공하는 본래 목적은 엔지니어가 작성한 코드를 독립적으로 재실행하여 검증하는 것인데, 엔지니어가 메모리에 생성해 둔 객체를 단순히 조회하는 것은 결과를 엿보는 것일 뿐 코드 자체의 실행 가능성을 검증하는 것이 아닙니다. 따라서 에이전트 간의 데이터 인계는 파일 시스템을 통해서만 수행하도록 격리했습니다.
</details>

<details>
<summary>4. 결정 장부를 시스템 프롬프트가 아니라 마지막 메시지 앞에 두는 이유는?</summary>

상용 모델 공급자의 프롬프트 캐시는 요청 메시지 시퀀스의 앞부분(Prefix)이 이전 호출과 완벽히 일치할 때 적용됩니다. 결정 장부는 매 라운드마다 내용이 갱신되므로, 이를 시스템 프롬프트 영역에 배치하면 갱신 시마다 프롬프트 캐시 전체가 무효화됩니다. 반면 마지막 사용자 메시지의 서두 영역은 캐시 무효화의 영향을 최소화하면서도, 컨텍스트 축소 알고리즘이 적용될 때 항상 보존되는 최적의 위치입니다.
</details>

<details>
<summary>5. `except Exception`과 `except BaseException`이 각각 어떤 사고를 냈나요?</summary>

`except Exception`은 anyio가 하위 태스크 예외들을 취합하여 발생시키는 `BaseExceptionGroup`을 잡지 못해 백그라운드 토론 태스크를 비정상 종료시켰습니다. 반대로 `except BaseException`은 비동기 취소 신호(`asyncio.CancelledError`)까지 정상 오류로 삼켜버려 애플리케이션 정상 종료를 멈추게 만들었습니다. 올바른 시스템 경계 패턴은 취소 신호는 즉시 상위로 재전파(`raise`)하고, 복합 예외 그룹을 포함한 기타 모든 런타임 예외만을 안전하게 오류 관찰 결과로 변환하는 것입니다.
</details>

<details>
<summary>6. 소스 갱신 패키지에 운영 설정 파일(conf.json)을 넣지 않는 이유는?</summary>

실제 운영 환경에 배포된 설정 파일에는 해당 폐쇄망 내부의 실제 LLM 엔드포인트 URL, 인증 토큰, 네트워크 주소 등 민감하고 고유한 환경 정보가 포함되어 있습니다. 소스 패키지가 이를 덮어쓰게 되면 모든 에이전트가 무효한 주소를 가리키는 중대 장애가 발생합니다. 신규 버전에서 추가된 설정 필드는 관리자가 기본 설정 예시 파일을 대조하여 수작업으로 반영해야 합니다.
</details>

<details>
<summary>7. ADR-009의 상태가 "대체됨"인데도 삭제하지 않고 남겨 둔 이유는?</summary>

아키텍처 결정 기록(ADR)은 과거의 내용을 지우지 않고 불변으로 누적 보존하는 역사적 문서입니다. 비록 후속 결정에 의해 대체되었더라도 "과거에는 어떤 제약 조건 때문에 그런 방식을 선택했는가"를 설명해 주며, 신규 아키텍처가 결코 포기해서는 안 될 핵심 설계 불변식(타 세션의 파일을 조용히 침범하지 않는다)을 명확히 증명해 주기 때문입니다.
</details>

<details>
<summary>8. 발언의 시작·종료 시각을 기존 생성 시각 컬럼으로 쓰지 않은 이유는?</summary>

기존 생성 시각(`created_at`) 컬럼은 이미 데이터베이스 조회 시 발언 정렬을 위한 기본 키로 활용되고 있었습니다. 해당 레코드는 모델 응답 수신이 완전히 종료된 시점에 삽입되므로 실제로는 발언 종료 시각에 가까우며, 병렬 라운드 실행 시에는 시각적 정렬 순서를 강제하기 위해 임의로 덮어쓰이기도 했습니다. 단일 컬럼에 상충하는 복수의 도메인 의미를 부여하는 왜곡을 방지하기 위해 명시적인 시작·종료 타임스탬프 컬럼을 신설했으며, 과거 레코드의 공란을 임의의 허위 데이터로 채우지 않았습니다.
</details>

<details>
<summary>9. 원격 접속 게이트가 X-Forwarded-For 헤더를 무시하는 이유와, 그 결과 생기는 제약은?</summary>

프록시 헤더를 무조건 신뢰할 경우, 동일 네트워크 대역의 비인가 공격자가 `X-Forwarded-For: 127.0.0.1` 헤더를 위조하여 로컬 관리자인 것처럼 인증을 손쉽게 우회할 수 있습니다. 반면 프록시 헤더를 무시할 경우, 일반적인 리버스 프록시 뒷단에 MADO를 배치하면 모든 외부 인입 요청이 프록시 머신(루프백)에서 발송된 것으로 간주되어 인증 없이 통과되는 심각한 취약점이 발생합니다. 따라서 시스템을 리버스 프록시 뒷단에 직접 배치하지 말라는 엄격한 운영 제약이 발생합니다.
</details>

<details>
<summary>10. 다이어그램 문법 검사기를 "일부러 불완전하게" 만든 이유는?</summary>

문법 검사기가 실제 오류를 감지하지 못하고 놓치더라도 치러야 할 비용은 복구 시도 이전의 원래 렌더링 실패 상태와 동일합니다. 그러나 정상적으로 렌더링 가능한 유효한 다이어그램을 오류로 잘못 판정(오탐)할 경우, 불필요한 LLM 자동 복구 호출로 토큰을 낭비할 뿐만 아니라 멀쩡했던 다이어그램을 모델이 오히려 망가뜨리는 2차 장애를 유발합니다. 따라서 오탐률 0%를 목표로 실제 Mermaid 파서 사양에 엄격히 맞추어 검사 규칙을 보수적으로 구축했습니다.
</details>
